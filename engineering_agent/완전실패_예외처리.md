# 완전 실패(서버 책임) 예외 처리 — 구현 agent 요구사항

작성: 2026-09-29 · 대상: T-B1(프로토타입 HTML), T-B2(인포그래픽)

## 1. 왜 필요한가

웹에서 "실패"를 두 가지로 나눠 다룬다.

| | 완전 실패 | task별 재작성 |
|---|---|---|
| 원인 | 우리 서버 문제 — 에이전트 미작동, LLM 호출 실패로 결과물이 **안 만들어짐** | 사용자가 결과물 일부가 마음에 안 듦 |
| 판단 기준 | 결과물 생성 여부 (점수와 무관) | 사용자 선택 |
| 사용자에게 주는 것 | **처음부터 다시 생성** (재작성 횟수 차감 없음, 연속 2회 실패 시 "관리자에게 알렸어요" 안내로 전환) | 묶음마다 `rework_cap`(기본 1회) |

서버(`back/app/routers/projects.py`의 생성 워커)는 **에이전트가 예외를 올릴 때만** 완전 실패로 판정한다
(`project.status='failed'`, `failure_reason`, `last_error_kind` 기록). 에이전트가 예외를 삼키고
빈 결과나 대체 결과를 정상 반환하면 서버는 "성공"으로 보고 다음 단계(검증)로 넘긴다. 그러면 사용자에겐
실패 화면 대신 0점짜리 결과물이 보이고, 재작성 횟수까지 써야 하는 상황이 된다.

## 2. 규칙

### R1. `tools.llm` 예외는 잡지 않는다
`tools.llm`은 이미 내부에서 재시도하고(`retry_count`), 다 실패하면 `ToolCallExhausted(error, error_kind, tries)`를
올린다 (Orchestration `sbrain/orchestrator/tools.py`). 에이전트는 이걸 **그대로 위로 올린다.**

- `try/except Exception: return {...status: "failed"}` 금지
- 로그를 남기고 싶으면 잡은 뒤 반드시 `raise`
- 지금 `builder_html.build_prototype_html`, `builder_infographic.generate_infographic_content`는 잡지 않고 있음 → **유지**

### R2. "LLM이 응답은 했는데 쓸 수 없는 결과"는 `parse`로 재시도시킨다
빈 문자열, 코드블록 없음, JSON 파싱 불가처럼 **LLM 호출 자체가 사실상 실패한 경우**는 품질 문제가 아니다.
`tools.llm(..., parse=...)`에 검사 함수를 넘겨 `FormatError`를 올리면 tools가 재시도하고, 끝까지 안 되면
`ToolCallExhausted`로 완전 실패가 된다.

| 위치 | 지금 | 바꿀 것 |
|---|---|---|
| T-B1 `build_prototype_html` | 응답을 받은 뒤 `parse_code_blocks` → 진입 파일 없으면 `status="failed"`로 **정상 반환** (= 품질 실패로 취급) | `parse`에서 "코드블록 0개 / 응답 비어 있음"이면 `FormatError` |
| T-B2 `generate_infographic_content` | `schema=InfographicContent`로 검사 중 (tools가 `FormatError` 처리) | 유지 |

**구분 기준**
- 코드블록 자체가 없음, 응답이 비어 있음 → **R2** (`FormatError`)
- 코드는 있는데 게이트 위반(E-B1-ENTRY 파일명 틀림, E-B1-DEP 외부 CDN 사용) → 지금처럼 `CheckResult(passed=False)` 정상 반환. Supervisor 자동 재수행(`rerun_cap`)이 처리할 몫이다.

### R3. 에이전트 내부 오류도 예외로 올린다
파일 저장 실패(`OSError`), 템플릿 누락, 치환 안 된 플레이스홀더(`ValueError`) 같은 우리 코드 문제는 지금처럼 예외로 둔다.
`None`이나 빈 경로를 반환하는 방식으로 바꾸지 않는다.

### R4. 예외 메시지는 사람이 읽을 수 있게
`failure_reason`에 앞 2000자가 저장돼 관리자 화면에 그대로 뜬다. 키 값, 프롬프트 전문, 사용자 입력 원문은 넣지 않는다.

## 3. 오류 종류와 서버 동작

서버는 지금 예외 **메시지 키워드**로 종류를 나눈다(`back/app/pipeline_stages.py` `classify_error_kind`, 임시 방식).

| `last_error_kind` | 예 | 서버 동작 |
|---|---|---|
| 일시 | 타임아웃, 5xx, 연결 오류 | 백오프 후 자동 재개 최대 5회 (진행 지점부터 이어서) → 그래도 실패하면 `failed` |
| 운영 | API 키 만료, 크레딧 소진, 401 | 재개 없이 바로 `failed` + 관리자 알림 |
| 입력 | 입력 형식 오류 | 재개 없이 바로 `failed` |

`ToolCallExhausted`는 이미 `error_kind`(일시/입력/운영)를 갖고 있다.

**[2026-09-29 확인] 백엔드가 이미 그렇게 하고 있다.** `classify_error_kind`가
`getattr(exc, 'error_kind', None)`을 먼저 보고, 값이 없을 때만 메시지 키워드로 추측한다
(`back/app/pipeline_stages.py:105`). 키워드로도 못 맞추면 기본값 `'일시'`로 두어 재개
기회를 남긴다. **요청할 것 없음.** 위 표의 "임시 방식" 서술은 옛 상태다.

## 5. 참고: 웹/백엔드 쪽 처리 (구현 agent 범위 밖)

- 사용자 "처음부터 다시 생성" = 새 시도(attempt_no +1, 진행률 0부터). **이전 시도 기록(agent_executions 행, failure_reason, 시도별 산출물 경로)은 지우지 않는다.**
- 자동 재개(일시 오류)는 지금처럼 진행 지점부터 이어서 한다.
- 이 재생성은 `rework_cap` 카운트에 포함하지 않는다.
