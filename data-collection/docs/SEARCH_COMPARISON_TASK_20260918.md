# Claude 작업 지시서 — 임베딩 단독·하이브리드 공고 비교

작성: 2026-09-18 · Codex / 실행 담당: Claude / 후속 검토: Codex

사용자는 실제 공고 매칭 결과 비교를 Claude에게 맡기고, 지시와 결과를 파일로 남기도록 요청했다.
이 문서는 실행할 작업의 범위를 정한다. **현재는 지시서 작성 단계이며 비교 결과는 아직 없다.**

## 1. 목적과 완료 결과

같은 신청자 입력에서 임베딩 단독 검색(`dense`)과 하이브리드 검색(`hybrid`)이
어떤 공고를 추천하고, 순위와 구성은 어떻게 달라지는지 실제 데이터로 비교한다.

사용자가 결과를 보고 다음 세 가지를 판단할 수 있어야 한다.

1. 어떤 입력에서 하이브리드가 더 유용하거나 덜 유용해 보이는가?
2. 결과 차이는 검색 방식에서 발생했는가, 마감·지역·지원대상 처리에서 발생했는가?
3. 다음 개선 대상은 검색, 자격 조건, 재정렬 중 어디인가?

**이번 작업의 목표는 비교와 분석이다. 결과를 좋게 만들기 위한 서비스 코드 수정·가중치 튜닝·모델 학습은 포함하지 않는다.**

## 2. 시작 전에 읽을 것과 범위

- [AGENTS.md](../AGENTS.md), [STATUS.md](STATUS.md), [WORKLOG.md](WORKLOG.md)의 최신 항목.
- [FLOW.md](FLOW.md), [평가 안내](../eval/README.md), [최초 검토](MATCHING_REVIEW_20260918.md), [후속 검토](MATCHING_REVIEW_20260918_FOLLOWUP.md).
- 실제 구현: `search/app.py`, `search/hybrid.py`, `search/vecstore.py`, `shared/embed.py`, `search/gate.py`, `shared/region.py`.

작업 범위는 `data-collection/`이다. 필요한 비교 실행·결과 생성 도구는 `eval/`에 추가할 수 있다.
기존 도구를 재사용하고, 새 도구가 필요하면 서비스 함수를 호출하는 얇은 실행 도구로 만든다.
검색·규칙 구현을 별도로 복사하지 않는다. **Git 스테이징·커밋·push는 하지 않는다.**

공고와 색인은 읽기만 한다. 수집 배치, 공용 DB 변경, 색인 재생성, 임베딩 재생성, 기존 qrels 덮어쓰기는 포함하지 않는다.
새 유료 LLM 판정 호출도 이번 범위에 포함하지 않는다. 데이터·모델이 없어 실행할 수 없으면
확인 가능한 준비를 마치고 정확한 장애와 필요한 조치를 기록한다. 가짜 결과를 실제 검색 결과로 대체하지 않는다.

## 3. 비교 전 환경 확인

- 최신 로컬 코드와 테스트를 확인한다. 검색시간 표시 P3는 Claude의 수정 기록이 있으므로 관련 회귀 테스트도 확인한다.
- 사용할 DB 공고, Chroma 색인, BM25 문서 집합의 공고 ID와 내용 기준이 맞는지 확인한다.
  건수만 같다고 정합성이 맞는 것으로 간주하지 않는다. watermark 같은 관리용 ID는 공고에서 제외한다.
- BM25와 공고 메타데이터는 서버 시작 시 읽으므로 오래 실행된 서버의 데이터를 그대로 믿지 않는다.
  같은 실행에서 초기화한 코드·공고 상태로 두 검색을 수행한다. 다른 사람이 쓰는 서버를 임의로 종료하지 않는다.
- 실행 시각·기준 날짜, 모델/리비전/입력 버전, 공고·색인 건수와 식별 해시,
  Git 리비전 및 관련 로컬 수정 파일의 해시, 검색 설정을 실행 메타데이터로 남긴다. 비밀정보는 제외한다.
- 같은 신청자에 대해 두 방식의 최종 질의 문장이 같아야 한다. 업력 계산과 마감 판단의 기준 날짜도 같아야 한다.
  실행 중 날짜나 공고·색인이 바뀌면 해당 비교를 분리하거나 다시 실행한다.
  API가 지원하지 않는 날짜 인자를 보냈다는 이유만으로 날짜가 고정됐다고 기록하지 않는다.

## 4. 비교할 입력 10개 선정

기존 `eval/queries.jsonl`에서 **정상 질의 8개 + 무관 질의 2개**를 먼저 선정하고 입력 파일로 저장한다.
검색 결과를 본 뒤 유리한 사례로 교체하지 않는다. 선택 이유와 원래 qid를 남긴다.

- 정상 질의는 가능한 한 분야·신청자 유형을 나눈다: 제조/AI, 디지털 서비스, 소상공인, 콘텐츠, 수출 등.
- 지역·시군구·업력이 영향을 주는 사례를 포함한다. 기존 입력에 값이 없어서 보완하면
  가상 신청자 정보임을 명시하고 원본 질의 파일을 변경하지 않는다.
- 이름·사업자번호 등 실제 개인정보는 쓰지 않는다.
- 무관 질의도 그대로 검색해 결과를 확인한다. 자동으로 전부 부적합 판정을 부여하지 않는다.

첫 작업은 10개 사례의 상세 비교로 끝낸다. 전체 평가셋 재판정이나 모델별 대규모 실험으로 범위를 넓히지 않는다.

## 5. 실행 조건 — 두 단계, 각 단계에서 두 검색 비교

각 입력마다 아래 A·B를 수행하고, 각 단계에서 **`search`만 dense/hybrid로 바꿔** 비교한다.
첫 실행은 워밍업으로 분리하고, 결과는 실제 현재 `app.match()` 또는 최신 로컬 API를 사용한다.

| 설정 | A. 검색 방식 차이 확인 | B. 현재 서비스의 최종 결과 확인 |
|---|---|---|
| `top` | 5 | 5 |
| `hide_expired` | false | true |
| `demote_groups` | false | true |
| `demote_region` | false | true |
| `demote_district` | false | true |
| 신청자 정보 | 선정한 입력 그대로 | A와 동일 |
| `weights` | 기본값, mode=order | A와 동일 |
| 리랭커 | 사용하지 않음 | 사용하지 않음 |

기본 가중치는 현재 코드에서 확인해 명시적으로 저장한다(현재 기록: dense=1, bm25=1, rrf_k=60, mode=order).
지역이 비어 있으면 해당 규칙이 실질적으로 적용되지 않는다는 점도 표시한다.
총 기본 비교는 **10입력 × 2단계 × 2검색 = 40개 응답**이다.

검색 후보 수와 확장 반복은 현재 서비스 구현을 그대로 사용하고 `depth`, `search_rounds`를 함께 기록한다.
두 방식의 내부 후보 수가 다를 수 있으므로 이를 감추거나 '검색 방식 외 모든 내부 계산량이 동일'하다고 쓰지 않는다.
가중치 시험용 `score` 모드와 리랭커까지 섞지 않는다.

현재 `eval/evaluate.py`의 RRF 비교는 서비스의 마감 제외·지역 처리와 같지 않다.
그 출력만으로 B단계의 사용자 노출 결과를 검증했다고 보고하지 않는다.

## 6. 비교표와 해석

입력별로 두 방식의 상위 5개를 나란히 보여주고, A와 B를 구분한다.

필수 정보:

- 신청자 입력과 실제 생성된 질의 문장.
- 공고 ID, 제목, 원문 링크, 지역, 접수기간, 추천 순위.
- 코사인 유사도, 하이브리드의 dense/BM25 순위와 RRF 점수, 적용된 규칙.
- 공통 공고, 새로 포함된 공고, 빠진 공고, 공통 공고의 순위 이동.
- 반환 건수, 검색 깊이·라운드, 인코딩·검색 시간. 초기 모델 로딩 시간은 별도 표기.
- 추천 이유를 판단할 수 있는 공고 본문·지원대상 발췌. 비교 당시 내용을 원문 응답과 연결해 보관한다.

결과 해석 원칙:

- 코사인과 RRF 점수를 서로 비교하거나 정확도·확률·백분율 적합도로 변환하지 않는다.
- 한쪽 상위 5개 밖의 공고는 '미노출'로 표시한다. 실제 순위를 모르면 임의로 6위라고 두고 순위 이동을 계산하지 않는다.
- 'BM25에서도 상위라 RRF 순위가 높아짐'은 순위 정보로 확인할 수 있다.
  '이 단어 때문에 좋아졌다' 같은 원인 설명은 단어 기여를 실제로 분석했는지, 추정인지 구분한다.
- 내용 관련성과 신청 자격을 별도 항목으로 다룬다. 주제 평가 qrels를 자격 판정 정답으로 쓰지 않는다.
  자격 API가 통과라고 해도 unknown 항목이 있으면 자격을 보장한다고 표현하지 않는다.
- 기존 판정을 참조할 때 질의·공고 내용·label_version의 호환성을 확인하고 human/LLM/미판정을 구분한다.
  미판정은 부적합(0)이 아니다. 새 입력이나 내용이 바뀐 공고에 과거 라벨을 조용히 붙이지 않는다.
- 사용자 검토용 칸은 비워 둔다: '내용 관련성 / 신청 자격 / 선호 결과 / 이유'.
  Claude의 잠정 의견은 별도 칸에 적고 사람 판정처럼 저장하지 않는다.
- 10개 사례의 결과와 기존 잠정 판정만으로 전체 검색 품질의 우열·통계적 유의성을 확정하지 않는다.
  좋아진 사례뿐 아니라 나빠진 사례·차이 없는 사례·판단하기 어려운 사례도 보여준다.

## 7. 결과 파일

기존 실행 결과와 분리된 `reports/search_comparison_<실행시각>/`에 저장한다.
보고서 본문에 실제 생성한 파일의 경로와 재실행 명령을 적는다.

| 파일 | 내용 |
|---|---|
| `manifest.json` | 코드·데이터·모델·기준 날짜·설정·실행 환경 및 검증 결과 |
| `inputs.jsonl` | 사전에 선정한 10개 입력, 원래 qid와 선정 이유 |
| `responses.jsonl` | 40개 원본 응답, case_id·단계·검색 방식·시각으로 식별 |
| `notices.jsonl` | 비교에 등장한 공고의 당시 본문·조건·링크와 내용 해시 |
| `comparison.html` | 입력별 A/B·dense/hybrid 결과를 나란히 읽는 로컬 비교표 |
| `human_review.csv` | 내용 관련성·자격·선호·이유를 적는 빈 사용자 판정 양식 |
| `summary.md` | 주요 사례, 사실과 추정, 한계, 후속 개선 후보 및 재실행 방법 |

HTML은 저장된 결과를 보여주는 정적 문서로 만든다. 공고 텍스트를 HTML 이스케이프하고
외부 서비스 업로드나 별도 웹앱 구축은 하지 않는다. 사용자 검토 표시는 빈 양식이며 자동으로 qrels를 변경하지 않는다.
`reports/`가 Git 제외 대상이면 그 사실을 알리고, 추적되는 WORKLOG에 결과 위치를 남긴다. 강제 스테이징하지 않는다.

## 8. 완료 기준과 인계

- 10개 입력에 A/B × dense/hybrid 응답이 빠짐없이 있고, 데이터와 기준 날짜가 일치한다.
- 입력 쌍의 설정은 `search`만 다르며, 원본 응답과 비교표의 공고 ID·순위·점수가 일치한다.
- 5건 미만 결과가 나오면 실제 데이터 부족/필터 결과/실행 오류 중 원인을 구분한다.
- 비교표의 원문 링크와 한국어 표시, 미노출·미판정 표기를 직접 확인한다.
- 새 비교 도구의 데이터 결합·순위 이동 계산·누락 처리 등 중요한 부분을 검증하고 결과를 기록한다.
- 서비스 코드나 가중치를 임의로 변경하지 않았음을 확인한다. 새로 발견한 버그는 별도 보고한다.
- `STATUS.md`와 `WORKLOG.md`를 갱신하고, 사용자에게 비교표·요약·판정 양식 위치를 전달한다.
- Codex가 후속 리뷰할 수 있게 변경 파일, 실행 명령, 결과 경로, 미검증 사항을 정리한다.

완료 보고는 '하이브리드가 더 좋다'는 결론부터 쓰지 말고,
**실제로 비교한 조건·주요 차이·사용자가 판단할 사례·남은 한계**를 먼저 설명한다.
