# 아직 못 푼 문제

## 가산점 계산이 일부 공고에서 틀린 점수를 낸다

- 증상: Codex 재검수(2026-10-06)가 재현한 사례 — 다른 항목의 배점·연번이 근거로 승인됨, 같은 문장 안의 독립 가점(벤처·여성기업)이 한 묶음으로 합쳐져 4점이 사라짐(공고 123858), 공장 이전 항목에 현재 소재지만으로 5점(117751), 세부사업 최대값을 확정 점수처럼 냄, 개별 항목 최대값을 전체 합계 한도로 승인, 표·우대 구간 일부만 읽고 `none`(가점 없음)으로 확정.
- 영향: 순위 세기가 0이라 순서에는 영향이 없다. 다만 `bonus_score`를 조율 쪽이 그대로 보여 주면 신청자가 틀린 가산점을 믿는다.
- 지금 못 푸는 이유: 사용자가 처리 방식(보수적으로 줄이기 / 재추출 약 $2 / 모두 null)을 정하지 않았다(10/6 보류 결정). 조율 연결이 꺼져 있어 당장 사용자 영향은 없다.
- 가능한 방법: 보수적 축소는 저장된 AI 결과 재검사만으로 비용 거의 0. 어느 쪽이든 반영 뒤 표본 재추출과 전량 결과 재검수가 필요하다.

## 가점 하루 호출 기록이 손상되면 상한이 풀린다

- 증상: `data/bonus_daily_calls.json`을 읽지 못하면 그날 사용량을 0으로 보고 다시 300건까지 부른다.
- 영향: 같은 날 여러 번 돌면 OpenAI 비용이 상한을 넘는다(사용자 개인 결제).
- 지금 못 푸는 이유: 가산점 재검수 지적 묶음(위 문제)과 함께 처리하기로 보류됐다.
- 가능한 방법: 기록을 읽지 못하면 그날 호출을 보류하고, 쓰기를 임시 파일 → 교체로 원자적으로 한다.

## 결과서는 "벡터 DB 미사용"인데 코드는 Chroma를 쓴다

- 증상: 2026-10-06 제출한 벡터DB 결과서에는 공고 검색이 벡터 DB를 쓰지 않는다고 적었다. `search/app.py`는 여전히 Chroma를 열고 `_dense_within`으로 검색한다(머리말에도 "반드시 벡터 DB를 거친다"가 남아 있다).
- 영향: 심사·팀원이 코드를 보면 제출 문서와 다르다. PC·서버·팀 EC2의 색인 동기화 부담도 남는다.
- 지금 못 푸는 이유: 최소 작업 기간이라 사용자가 요청하면 바꾸기로 했다.
- 가능한 방법: 평가 도구의 `NumpyCollection` 방식으로 교체(ids 필터는 numpy). 10/6 실측상 상위 3 결과는 66개 중 64개가 같다.

## 배치 서버 코드가 저장소보다 오래됐다

- 증상: 서버 `~/sbrain/data-collection`은 10/2 복사본이라 14단계(가점)·추출기 v4·10/6 수정이 없다. 매일 새로 들어오거나 바뀐 공고의 가점은 추출되지 않는다.
- 영향: 가산점이 null인 공고가 날마다 늘어난다. 변경 SQL 007·008이 서버 쪽 경로에서 문제없는지도 확인되지 않았다(공용 DB에는 10/6 적용됨).
- 지금 못 푸는 이유: 서버 코드 복사는 사용자 결정 사항이고, 가산점 처리 방식이 먼저 정해져야 의미가 있다.
- 가능한 방법: 방식 결정 → 코드 복사(`experiments/`·서버가 읽는 `reports/` 결과 포함) → 다음 배치 `run.log`·`notice_bonus` 행 수 확인.

## 실행 안내 문서의 DB 초기화 명령이 실제 옵션과 다르다

- 증상: `README.md` "시작하기"는 `python -m shared.store_mysql --init-schema`라고 하지만, 실제 명령은 정규화 파일 경로를 받는 `python -m shared.store_mysql <파일> --init-db`다. 그대로 따라 하면 인자 오류로 끝난다.
- 영향: 새 환경에서 DB를 처음 만들 때 막힌다(팀 공용 DB에는 영향 없음).
- 지금 못 푸는 이유: 이번 정리는 새 문서 작성 범위였고 `README.md` 본문은 고치지 않았다.
- 가능한 방법: `README.md`의 해당 줄을 실제 명령으로 고친다.

## `.env.example`에 `OPENAI_API_KEY`가 없다

- 증상: 배치 10~14단계가 `OPENAI_API_KEY`를 읽는데 예시 파일에 이름이 없다. 키가 없으면 LLM 단계는 조용히 건너뛰고 종료 코드 4만 남는다.
- 영향: 새 환경(학원 계정 서버 등)에 옮길 때 판정표·가점이 갱신되지 않는 것을 늦게 알아챈다.
- 지금 못 푸는 이유: 코드·설정 파일 수정은 이번 범위 밖이었다.
- 가능한 방법: `.env.example`에 `OPENAI_API_KEY=`와 "개인 결제 계정, 배치 LLM 단계용" 설명을 더한다.

## `shared/config.py` 머리말의 `.env` 위치 설명이 코드와 다르다

- 증상: 머리말은 `poc/.env`·`finak_mok/.env`를 찾는다고 하지만, 코드는 `shared/.env` → `data-collection/.env` 순서로 찾는다.
- 영향: `.env`를 엉뚱한 곳에 두고 "환경변수가 없습니다"를 만난다.
- 지금 못 푸는 이유: 이번 범위는 문서였다.
- 가능한 방법: 머리말을 실제 두 경로로 고친다.

## data-collection 시험이 CI에서 돌지 않는다

- 증상: 저장소 CI(`.github/workflows/ci.yml`)는 PR 제목과 `web/backend`만 검사한다. data-collection의 758개 시험은 로컬에서만 돈다.
- 영향: 시험이 깨진 코드가 PR로 들어가도 막히지 않는다. 조율 쪽은 우리 브랜치를 머지해 쓴다.
- 지금 못 푸는 이유: CI 파일은 저장소 공용이라 팀 합의가 필요하다. 시험 일부는 `.venv`의 무거운 패키지(chromadb·sentence-transformers)를 필요로 할 수 있어 CI 시간·용량을 따져 봐야 한다.
- 가능한 방법: data-collection 시험만 도는 작업을 추가하되, 무거운 패키지가 필요한 시험은 건너뛰게 한다.
