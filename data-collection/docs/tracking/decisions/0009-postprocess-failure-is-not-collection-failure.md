# 0009. LLM 후처리 실패는 수집 실패로 보지 않는다

- 날짜: 2026-09-28 (Codex 통합 검수 반영)

## 배경
10~14단계(LLM 추출·판정 올리기·가점)가 실패하거나 일부 호출이 실패해도, 공고 자체는 1~4단계에서 이미 새것으로 저장돼 있다. 이 실패를 배치 `partial`로 기록하면 수집 상태가 '실패'가 되어 매칭이 멈춘다.

## 결정
배치 `status`는 그대로 두고 `stage_warnings`에 남기며 종료 코드 4로 알린다.

## 대안
- `partial`로 기록: 공고는 새것인데 LLM 쪽 일시 장애(키 없음·한도) 하나로 서비스가 멈춘다.
- 조용히 넘기기: 판정표가 며칠씩 낡아도 아무도 모른다.

## 결과
- 종료 코드 4(`run.log`의 `exit=4`)는 사람이 확인해야 한다. 자동 알림은 없다.
- 판정표·가점이 늦으면 해당 기능만 null·꺼짐으로 동작한다(지문 확인으로 옛 판정을 쓰지 않음).

## 넓힘 (2026-10-13)
- 계기: 10/12 시험 서버 배치에서 9단계(첨부 원본 올리기)가 표가 없어 실패했는데 `exit=0`이었다. 코드를 보니 5~9단계(첨부 받기·임베딩·벡터 올리기·첨부 원본 올리기) 전부가 `stage_warnings_of` 입력에 없었다. 6~8단계가 실패하면 새 공고가 의미 검색에서 빠지는데도 아무도 모른다.
- 결정(사용자 승인): 5~9단계 결과도 `stage_warnings_of`에 넣는다. 같은 원칙 — `status`는 그대로, 종료 코드 4. 이 단계들의 결과 맨 위에는 단계 실패(`error`)만 있고, 파일별 실패(`download_fail`·`parse_error`·`hash_mismatch`·`skipped_no_notice`)는 평소 일이라 경고로 올리지 않는다.
- 영향: 시험 서버(RDS에 `attachment_files` 표 없음)는 표를 옮길 때까지 매일 `exit=4`가 된다 — 실제 상태를 보여 주는 것이다. 수집 상태 판정·매칭은 그대로다.
