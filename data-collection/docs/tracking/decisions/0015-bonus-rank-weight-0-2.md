# 0015. 가산점을 순위에 세기 0.2로 반영한다 — Codex 재재검수 뒤 시행

- 날짜: 2026-10-08 · 결정: 사용자 · 상태: **결정 0017로 시행**(2026-10-08 — Codex 검수 통과 대신 "원문 대조를 마친 공고 목록에 있는 공고만" 순위에 얹는 조건으로 사용자가 켬)

> **10/8 재재검수 뒤 정정**: Codex 재재검수(`docs/notice_api/CODEX_BONUS_RECHECK2_20261007.md`)는 "추가 수정 후 재검수 필요, 0.2 활성화 보류"였다. 아래 ②의 "11건뿐·맞음 11·빠뜨림 확인 통과"는 결정 0016 전 값이고, "어떤 조합으로든 … 전부"는 과장이었다(800개 조합 탐색의 관측). 결정 0016 반영 뒤에는 **800개 조합 탐색에서 양수가 관측된 공고 10건, Claude 원문 대조 맞음 10·틀림 0**(`reports/bonus_boostable_20261008T034650Z/`)이다. 126819(표 밖 증빙 연도 조건)는 Claude 대조에서 "맞음, 참고"로 넘겼지만 Codex 지적대로 확인되지 않은 점수였다. 순위 비교 측정은 결정 0016 "결과" 참조. 켜는 조건은 Codex 3차 검수 결과를 보고 사용자가 정한다.

## 배경
멘토가 "가산점도 중요하다"고 했다(10/7). 지금 가산점(`bonus_score`, 확인된 가산점 부분합 — 결정 0012)은 결과에 실려 나가지만 순위에는 쓰이지 않는다(`Weights.bonus = 0`, 결정 0008). 사용자는 시험 화면(8000 `/` 결과 페이지의 "가산점 순위 반영 세기")에서 0·0.2·0.5·1.0을 직접 비교해 본 뒤 0.2로 정했다.

0008이 0을 고른 이유("평가 정답이 가산점을 몰라 좋은 순위인지 잴 수 없다, 가점 추출을 사람 정답으로 확인하지 않았다")는 지금도 그대로다. 그래서 이 결정의 근거는 지표 개선이 아니라 **멘토 의견 + 사용자 판단**이고, 안전장치는 아래 원문 대조와 "큰 규칙은 못 넘음"이다.

## 결정
- `Weights.bonus` 기본값을 0.2로 한다. 계산식은 지금 코드 그대로: 같은 재정렬 묶음 안에서만 `검색 점수 × (1 + 0.2 × min(가산점, 10) / 10)`. +5점이면 ×1.10, +10점 이상이면 ×1.20.
- 다른 시·도·다른 시·군·구·예비창업자 추정·대상 집단 규칙(재정렬 묶음)은 넘지 않는다. 가산점이 null(모름)·0인 공고는 그대로 둔다. 검색 후보(의미 검색·단어 검색 상위 50)에 없는 공고를 끌어오지 않는다.
- **켜는 시점**: Codex 재재검수(`docs/notice_api/CODEX_BONUS_RECHECK2_REQUEST_20261007.md`, 7번 항목에 이 결정 포함) 결과를 사용자가 보고 정한다. 통과 기준을 미리 정하지 않았다 — 지적이 나오면 그때 켤지 다시 정한다.
- 시행하면 이 결정이 0008의 "순위 반영 0"을 대신한다. 0008의 나머지("확실한 것만 남기기", K-Startup null)는 그대로다.
- 조율 담당에게는 켜고 확인한 **뒤에** 사용자가 알린다(알림 초안 `docs/notice_api/BONUS_NOTICE_DRAFT_20261007.md`에 문장 있음). 응답 키·모양은 그대로이고 순서만 조금 바뀐다.

## 알려진 쏠림
- K-Startup 공고는 가산점이 늘 null(첨부 자동 수집 금지)이라 올라가지 않는다. 가산점이 "모름"인 공고도 올라가지 않는다. 그래서 올라가는 것은 확인된 공고(결정 0016 뒤 탐색에서 관측된 기업마당 10건)뿐이다.
- 122309처럼 원문은 "또는 중소기업"이어도 우리는 중소기업 여부를 입력받지 않아, 확인되는 신청자(벤처기업)만 올라간다.
