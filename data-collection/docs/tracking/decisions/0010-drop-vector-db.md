# 0010. 공고 검색에 벡터 DB(Chroma)를 쓰지 않는다

- 날짜: 2026-10-06 결정(결과서 제출) · 2026-10-07 코드 반영 · 결정: 사용자

## 배경
9/14 "공고 검색은 반드시 Chroma를 거친다"를 원칙으로 세웠으나, 9/15 중간 평가에서 "굳이 벡터 DB가 필요한가"라는 질문을 받았다. 10/6 실측(같은 벡터 2,714건·질의 66): 메모리 계산 0.77ms vs Chroma 3.41ms, 상위 10 겹침 97.7%, 서비스 `match()` 전체 상위 3 동일 64/66(차이는 Chroma 근사 검색 탓), 요청 전체 59ms vs 75ms.

## 결정
공고 검색은 공용 DB의 벡터를 메모리에 올려 직접 계산하는 방식으로 간다. 이 내용으로 `docs/deliverables/[모델링 및 평가] 벡터DB_GraphDB 구축 결과서.docx`를 냈다(GraphDB는 처음부터 없음).

## 대안
- Chroma 유지: 2,700건 규모에서 속도·품질 이점이 없고, 색인 동기화(PC·배치 서버·팀 EC2)라는 운영 부담만 남는다.

## 결과
- 2026-10-07 반영: 공고 서버가 켤 때 공용 DB `notices.embedding`을 메모리에 올리고(`search/memvec.py`), 정형 필터 통과 공고 전부와 코사인을 계산한다. Chroma 인터페이스(count·query·get) 모양을 유지해 평가 도구가 그대로 돈다.
- 같은 공용 DB 벡터 2,825건으로 만든 임시 Chroma와 비교(질의 66개, `reports/vector_db_compare_20261007T005123Z/`): 의미 검색 상위 10 겹침 99.5%, 1위 같음 66/66, **서비스 추천 상위 3 같음 62/66(93.9%)**, 상위 10 같음 51/66. 다른 경우는 Chroma 근사 검색 탓이다. 시간은 의미 검색 6.6ms vs 7.6ms, 추천 전체 384ms vs 395ms(질의 인코딩이 대부분).
- 조율 쪽 실제 코드로 계약 시험 16개 통과, 모든 공고 2,825건 자격 판정 형식 오류 0(`reports/notice_api_contract_20261007T005326Z/`).
- 남은 정리(서비스 밖): 배치 7단계 로컬 Chroma 갱신, 팀 EC2 09:10 `ec2_vecstore` 예약, Chroma 정합성 검사 도구는 아직 그대로다. 공고 서버에는 필요 없다.
- 이제 불가능해진 것: 공고 서버가 공용 DB 없이 켜지는 일. 벡터도 DB에서 오므로 DB를 못 읽으면 의미 검색 없이 열린다(공고 정보도 DB라 사실상 서버가 멈춘다).
