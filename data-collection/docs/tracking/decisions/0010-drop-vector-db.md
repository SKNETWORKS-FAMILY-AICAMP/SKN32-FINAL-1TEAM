# 0010. 공고 검색에 벡터 DB(Chroma)를 쓰지 않기로 한다 — 코드 전환은 요청 시

- 날짜: 2026-10-06 · 결정: 사용자 (결과서 제출)

## 배경
9/14 "공고 검색은 반드시 Chroma를 거친다"를 원칙으로 세웠으나, 9/15 중간 평가에서 "굳이 벡터 DB가 필요한가"라는 질문을 받았다. 10/6 실측(같은 벡터 2,714건·질의 66): 메모리 계산 0.77ms vs Chroma 3.41ms, 상위 10 겹침 97.7%, 서비스 `match()` 전체 상위 3 동일 64/66(차이는 Chroma 근사 검색 탓), 요청 전체 59ms vs 75ms.

## 결정
공고 검색은 공용 DB의 벡터를 메모리에 올려 직접 계산하는 방식으로 간다. 이 내용으로 `docs/deliverables/[모델링 및 평가] 벡터DB_GraphDB 구축 결과서.docx`를 냈다(GraphDB는 처음부터 없음).

## 대안
- Chroma 유지: 2,700건 규모에서 속도·품질 이점이 없고, 색인 동기화(PC·배치 서버·팀 EC2)라는 운영 부담만 남는다.

## 결과
- **지금 코드는 아직 Chroma를 연다**(`search/app.py`의 `boot`·`_dense_within`, 머리말의 "반드시 벡터 DB를 거친다" 문구도 남아 있다). 결과서와 코드가 다르다.
- 전환 방법: 평가 도구의 `NumpyCollection` 방식(ids 필터는 numpy)으로 바꾼다. 사용자가 요청하면 한다.
- 전환 뒤에는 로컬 Chroma·`ec2_vecstore` 색인 갱신이 서비스에 필요 없어진다.
