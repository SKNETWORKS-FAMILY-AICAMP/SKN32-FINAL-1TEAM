# 업종 가중치 탐침·화면 리뷰

2026-09-22 · Codex · 코드·저장 결과·평가 데이터·화면 검토

대상:

- `eval/industry_weight_probe.py`

## 판정

**화면은 탐색용으로 사용할 수 있지만, 현재 평가 결과로 “업종 가중치를 적용할 근거가 없다”는 운영 결정을 확정하면 안 된다. F1 두 건을 수정하고 판정을 보강한 뒤 재실행해야 한다.**

이번 구현은 숫자 가중치를 조정한 실험이 아니다. 검색 문장에서 업종을 제거하거나, 같은 문구를 한 번 더 반복하거나,
문장 앞으로 옮긴 네 가지 문자열 휴리스틱을 비교했다. 실제 서비스 코드는 바꾸지 않았고, 화면도 별도 라우트로 분리했다.

## 필수 수정

### [F1] 기준 검색으로 만든 평가 풀만 사용해 변형별 최종 Top 3의 판정 범위가 다름

- 위치: `eval/build_pool.py:151-184`, `eval/industry_weight_probe.py:97-116`,
  `eval/query_ablation.py:201-209`.
- 새 후보 풀 170쌍은 `common.query_text(q)` 한 종류, 즉 현재 서비스의 기준 검색어로만
  `dense@20 + BM25@10`을 모아 만들었다. 업종 없음·반복·앞배치의 후보와 서비스 최종 규칙 재정렬 결과는
  풀 생성에 포함하지 않았다.
- 저장된 최종 Top 3를 현재 풀·qrels와 대조한 결과는 다음과 같다. 각 변형은 6질의 × 3칸 = 18칸이다.

| 검색 | 변형 | 풀 밖 Top 3 | 미판정 Top 3 |
|---|---|---:|---:|
| dense | 그대로 | 0 | 3 |
| dense | 업종 없음 | 0 | 4 |
| dense | 업종 반복 | 0 | 3 |
| dense | 업종 앞배치 | 0 | 2 |
| hybrid | 그대로 | 2 | 5 |
| hybrid | 업종 없음 | 3 | 5 |
| hybrid | 업종 반복 | 0 | 3 |
| hybrid | 업종 앞배치 | 2 | 6 |

- 풀 밖 예에는 `q056/bizinfo:PBLN_000000000125664`,
  `q057/bizinfo:PBLN_000000000121634`, `q053/kstartup:179112` 등이 있다.
- `metrics()`는 qrels에 없는 공고를 P@3과 nDCG에서 0점으로 계산한다. 변형마다 미판정 비율이 다른 상태에서
  P@3 차이 `0.000` 또는 `-0.056`을 비교하면 풀링 편향이 그대로 점수 차이에 들어간다.

수정 기준:

1. 네 변형 × dense/hybrid의 **최종 결과 합집합**을 평가 풀에 추가한다. 최소 Top 3 전부를 포함하고,
   가능하면 각 변형의 후보 Top 10~20까지 풀링한다.
2. 새 쌍을 같은 A/B 절차로 판정하고 불일치·미판정 수를 별도로 기록한 뒤 qrels를 다시 합친다.
3. 변형별 `풀 밖`, `미판정@3`, `판정칸만`, `바뀐 칸/질의`를 `summary.md` 표에 함께 표시한다.
4. 최종 Top 3의 풀 밖 쌍이 0인지 검사하는 회귀 테스트를 추가한다. 0이 아니면 운영 결론을 출력하지 않는다.

### [F1] 관련도 판정자에게 `main_industry`를 보여주지 않았고, 아이디어가 이미 업종을 정답처럼 드러냄

- 위치: `eval/common.py:127-139`, `eval/queries.jsonl:61-66`.
- `persona_text()`는 신청자 유형·설립일·아이디어·수익모델·팀 경력만 판정자에게 보여주며
  이번 실험의 독립 변수인 `main_industry`는 빠져 있다.
- 동시에 새 6개 아이디어는 “사출금형 공장”, “국밥 식당”, “SaaS”, “딸기 농장”, “리모델링 시공사”,
  “온라인 도매업체”처럼 업종을 이미 직접 드러낸다. 따라서 명시적인 주업종 필드가 아이디어에 없는 정보를
  더하는 상황이 아니라, 같은 의미를 중복한 상황만 시험한다.
- 판정 대상 신청자 정보와 실제 매칭 입력이 다르고 업종 필드의 추가 정보량도 거의 0이라,
  이 정답셋은 “명시 업종 필드의 가중치가 필요한가”를 분리해서 측정하지 못한다.

수정 기준:

1. 업종 실험용 판정 문구에는 `주업종: ...`을 명시해 검색 입력과 관련도 판정 입력을 맞춘다.
2. 현재처럼 아이디어와 업종이 일치하는 사례 외에, 아이디어는 동일하거나 모호하지만 업종만 다른 쌍을 만든다.
3. 업종 일치·불일치·복수 업종·상위/하위 업종 표현을 포함하고 업종별 한 건이 아니라 반복 사례를 둔다.
4. 변경된 신청자 설명으로 새 후보 쌍을 다시 판정한다. 기존 6질의 판정은 새 판정과 섞지 않는다.

## 보완 수정

### [F2] 작업 기록의 수량·순위 설명이 저장 결과와 다름

- 위치: `docs/WORKLOG.md`의 2026-09-22 업종 강조 탐침 항목,
  `reports/industry_weight_probe_20260922T020705Z/summary.json`.
- 실제 증분은 후보 170쌍, LLM 원시 호출 340행(A/B), qrels 채택 131쌍이다.
  A/B 일치 131쌍, 불일치 39쌍이다. `qrels +340쌍`과 `정답 340건`은 원시 호출과 채택 정답을 혼동했다.
- 하이브리드 `업종 반복`은 P@3만 같을 뿐 Top 3 두 칸·두 질의가 바뀌고 nDCG는 `0.510 → 0.500`이다.
  “그대로와 완전히 같은 순위”가 아니다.
- dense도 P@3만 네 변형이 `0.389`로 같을 뿐, 업종 없음 1칸·반복 1칸·앞배치 4칸이 바뀌었다.
  반복의 nDCG도 `0.451 → 0.422`라 “완전히 같은 결과”, “최근접 순위 자체가 안 바뀌었다”는 설명은 틀렸다.
- 업종 앞배치의 하이브리드 P@3 점 추정은 기준보다 `-0.056`이므로 “나빠지지 않았다”는 서술과도 맞지 않는다.

수정 기준:

1. `340호출 = 170쌍 × A/B`, `qrels 채택 131쌍`, `A/B 불일치 39쌍`으로 구분한다.
2. “P@3가 같다”와 “순위가 같다”를 구분하고 nDCG·바뀐 칸·미판정 수를 함께 적는다.
3. F1 재실행 전 현재 결론은 `평가 설계 보완 필요`로 표시한다.

### [F2] 결과에 실행 지문이 없어 같은 조건의 재실행인지 확인할 수 없음

- 위치: `eval/industry_weight_probe.py:120-149`.
- `summary.json`에는 실행 시각·질의 ID·집계표만 있다. queries/qrels/NPZ 해시, 모델 리비전,
  DB/BM25 스냅샷, 후보 깊이, RRF 가중치, 서비스 기본값, 기준일이 빠져 있다.
- `per_query.jsonl`에도 실행 ID가 없다. 데이터나 설정이 바뀐 뒤 다시 실행하면 두 결과가 같은 조건인지 판별할 수 없다.

수정 기준:

1. `query_ablation.py::manifest()` 수준의 실행 지문을 저장하되, DB 지문은 `notice_id|apply_end`만이 아니라
   BM25 입력과 최종 규칙이 읽는 모든 필드를 포함한다.
2. `summary.json`과 각 `per_query.jsonl` 행이 같은 실행 ID·지문을 참조하게 한다.
3. 평가 풀 해시와 변형별 풀 커버리지도 기록한다.

### [F2] 새 탐침 코드와 `/industry-probe`에 자동 회귀 테스트가 없음

- 위치: `eval/industry_weight_probe.py`, `experiments/sql_semantic/industry_probe.py`,
  `experiments/sql_semantic/viewer.py:633-661`, `web/industry_probe.html`.
- 전체 335개 테스트는 통과했지만 새 탐침이나 새 라우트를 직접 검증하는 테스트는 없다.
- 두 모듈은 `search.app.build_query` 전역 함수를 실행 중 바꾸므로, 예외가 발생해도 원복되는지와
  원본 payload가 규칙 처리에 남는지를 고정해야 한다. 화면은 API 오류·업종 없음·네 열 렌더링을 검증해야 한다.

수정 기준:

1. 네 변형의 정확한 검색 문장과 원본 요청 보존을 fixture로 검사한다.
2. `app.match()` 예외 시 `build_query`가 원복되는지 검사한다.
3. `/api/industry-probe`의 필수값·정상 응답·실패 응답과 화면의 업종 없음 경고·네 열 렌더링을 검사한다.
4. 평가 코드와 화면 코드에 중복된 변형 생성 로직을 한 구현으로 공유하거나, 두 구현의 동등성 테스트를 둔다.

## 확인한 정상 사항

- `search/app.py`와 실제 서비스 기본 동작은 변경하지 않았다.
- 평가 코드는 실제 `app.match()`를 호출해 마감 숨김과 규칙 재정렬을 포함한 최종 결과를 비교한다.
- 변형은 질의 문자열만 바꾸고 원본 `MatchRequest`는 유지하므로 업종 등 payload는 규칙 처리에 계속 전달된다.
- 화면 모듈은 별도 프로세스에서 읽기 전용으로 부팅하며, 락과 `finally`로 전역 함수 교체 범위를 제한한다.
- HTML은 결과 문자열을 escape하고 외부 링크를 HTTP(S)로 제한한다.
- 데이터 파일의 qid·pool 쌍·qrels 쌍 중복은 없다.
- 올바른 Python 3.12 환경에서 전체 테스트 **335개 통과, 13개 건너뜀**을 확인했다.

## Claude가 이어서 할 순서

1. F2의 사실관계 문구를 먼저 정정한다.
2. 판정자 persona에 주업종을 포함하고, 아이디어와 업종의 정보가 분리되는 질의를 보강한다.
3. 네 변형의 최종 후보 합집합을 풀링·판정한다.
4. 커버리지·미판정·변경 칸·실행 지문을 포함해 재실행한다.
5. 탐침과 화면 회귀 테스트를 추가한 뒤 전체 테스트를 다시 실행한다.

이번 리뷰에서는 실험·서비스·화면 구현과 평가 데이터를 수정하거나 재실행하지 않았다.
리뷰·상태 문서만 추가·갱신했으며 Git staging·commit·push는 하지 않았다.
