# Claude 작업 지시서 — 별도 로컬 DB 기반 정형 필터·임베딩 검색

작성: 2026-09-18 · Codex / 구현 담당: Claude / 후속 검토: Codex

## 1. 이번 요청과 완료 목표

사용자는 **기존 구현·DB·결과를 비교용으로 보존하고 새로운 검색 형식을 별도로 구현**하도록 요청했다.
이 문서가 이번 작업의 실행 범위다. 이전 Chroma 검증 지시서와 A–E 계획은 재개하지 않는다.

새 경로:

```text
기존 공고 읽기 → 별도 로컬 MySQL에 스냅샷·정형 조건 저장
             → 새 입력 형식으로 공고 임베딩 생성·로컬 DB 저장

신청자 입력 → 로컬 MySQL 정형 필터
           → 남은 후보의 저장 벡터와 신청자 임베딩 직접 비교
           → 설명 가능한 규칙 정렬 → Top N
```

실제 로컬 DB에서 실행 가능한 첫 실험을 만들고, 기존 결과와 나란히 볼 수 있는 결과물을 남긴다.
새 경로는 **VectorDB·BM25 없이** 시작한다. 이 설계는 `정형 필터 + 의미 검색`으로 부른다.
기존 dense+BM25 하이브리드가 불필요하거나 새 방식이 더 좋다고 미리 결론 내리지 않는다.
Elasticsearch/OpenSearch 전환, 모델 학습, 완성형 조건 추출 시스템은 이번 범위가 아니다.

## 3. 격리 범위 — 기존 경로를 그대로 남긴다

- 새 구현은 `data-collection/experiments/sql_semantic/` 아래에 둔다.
  설정 예시·스키마·준비/검색/비교 CLI·README를 기능에 맞게 최소한으로 구성한다.
  새 테스트도 이 실험 전용으로 추가한다. 과도한 모듈 분리나 별도 웹앱 구축은 필요 없다.
- **기존 `search/`, `shared/`, 배치, 공용 DB 스키마, 기존 환경설정은 수정하지 않는다.**
  부작용 없는 읽기/계산 함수는 재사용할 수 있다. 기존 서비스의 기본 라우트·실행 명령을 바꾸지 않는다.
- 소스 DB는 읽기 전용으로 접근한다. 쓰기는 별도 **로컬 MySQL 실험 DB**에만 수행한다.
  예시 이름은 `notice_match_sql_lab`이며, 기존에 사용 중인 DB라면 덮어쓰지 말고 새 이름을 정한다.
- 소스 연결과 대상 연결의 설정을 분리한다. 대상에는 `SQL_LAB_*`처럼 별도 접두사를 사용한다.
  설정 누락 시 소스 DB로 자동 대체하지 않는다. 로컬 호스트·대상 DB 이름·소스와의 분리를 쓰기 전에 검증한다.
  비밀번호·전체 접속 문자열은 로그나 결과물에 출력하지 않는다.
- 새 로컬 DB와 전용 테이블 생성·실험 데이터 저장은 이번 요청에 포함된다.
  기존 DB·Chroma·NPZ·과거 보고서·판정 파일에 대한 갱신/삭제/재생성은 포함하지 않는다.
  `DROP DATABASE`, 기존 데이터 초기화, 기존 환경의 서비스 종료·설정 변경은 하지 않는다.
- 로컬 MySQL이 없거나 연결 정보가 부족하면 가능한 코드·가상 테스트를 먼저 완료하고 필요한 환경 정보를 구체적으로 남긴다.
  임의로 다른 DB 엔진으로 바꿔 실제 MySQL 검증을 했다고 보고하지 않는다.
- **Git 스테이징·커밋·push는 사용자가 직접 한다.**

## 4. 원본과 정형 조건

기존 공고를 한 번 읽어 시각·공고 ID·내용 해시가 있는 실험 스냅샷으로 저장한다.
원문/기존 필드는 보존하고, 정형 조건과 임베딩용 텍스트를 구분한다.
테이블 분리는 구현자가 단순한 형태로 정하되 `notice_id`로 연결한다.

| 개념 | 첫 구현에서 필요한 의미 |
|---|---|
| region | 전국·지역 제한·복수 지역·미확인 구분. 서울 신청자가 전국 공고를 잃지 않도록 함 |
| industry | 지원 가능한 업종. 표준화한 값과 원문 근거를 함께 저장하고 미확인은 별도 처리 |
| company_size | 중소기업 등 기업 규모. 개인/법인 같은 사업자 형태와 혼동하지 않음 |
| business_age | 최소/최대, 포함/미포함 경계, 기준일 또는 기준일 미확인, 예비창업자 조건을 구분 |
| target | 스마트공장 도입 기업 등 대상 설명. 문자열이 다르다는 이유만으로 SQL에서 탈락시키지 않음 |
| support_amount | 기업당 최대 지원금·원화 기준인지 구분. 총예산·매출 기준을 넣지 않음 |
| support_type | 보조금·융자·보증 등. 신청자의 희망 지원 방식과 구분 |
| application_period | 시작일·마감일과 상시/예산 소진/날짜 미확인 등의 유형 |
| support_content / purpose / eligibility | 원문에 근거한 지원 내용·분야/목적·신청 자격 텍스트 |

각 조건에 원본 필드 또는 근거 문장, 변환/추출 버전, 상태(`known`, `unknown`, 명시적 제한 없음 등)를 남긴다.
값이 없는 것과 제한이 없다는 것을 같은 NULL 의미로 뭉개지 않는다.

첫 구현은 기존 구조화 필드·검증 가능한 규칙·원문 발췌를 우선한다. 불확실한 것은 unknown으로 둔다.
원문에 없는 지원 내용이나 자격을 생성하지 않는다. 새로운 유료 LLM 호출·ML 학습은 하지 않는다.
기존 `notice_conditions.age_years_*`는 참고용이므로 그대로 신뢰된 SQL 필터로 승격하지 않는다.
전수 추출 완성을 목표로 하지 말고 필드별 known/unknown 비율을 보고한다.

## 5. 정형 필터는 SQL에서, 모르는 조건은 탈락시키지 않는다

- 신규 신청자 입력에 지역·업종·기업 규모·설립일/예비창업 여부·사업 설명·선택적 선호를 정의한다.
  제공되지 않은 신청자 정보는 추정해서 채우지 않는다. 실험용 추가 정보는 가상 보완이라고 표시한다.
- 마감 및 검증된 자격 조건의 **확실한 불일치만 SQL에서 제외**한다.
  지원 내용·희망 금액·희망 지원 방식은 자격 조건과 구분해, 기본적으로 선호 처리한다.
- 조건은 `충족 / 불충족 / 확인 필요`로 다룬다.
  신청자 값 누락, 공고 값 미확인, 근거 불충분·복합 예외는 `확인 필요`로 후보에 남긴다.
  남겼다는 것은 신청 자격이 보장된다는 뜻이 아니다.
- 날짜를 고정할 수 있는 `as_of_date`를 신규 경로의 SQL 필터·업력 계산·표시 전체에 전달한다.
  '7년 미만/이내', 예비창업자, 전국/복수 지역, 상시 모집을 단순 문자열 비교로 처리하지 않는다.
- 실제 SQL에서 필터한 뒤 후보 ID와 임베딩을 가져온다. 전체 벡터 Top-K를 먼저 잘라 놓고 SQL 필터라고 부르지 않는다.
  값은 파라미터로 전달한다. 소스/실험 DB 선택을 사용자 입력 SQL 문자열로 조립하지 않는다.
- 후보 수와 조건별 제외/확인 필요 사유를 기록한다. 복수 사유는 중복될 수 있음을 표시한다.
  후보 0개면 원인과 0개 결과를 반환하며 조건을 몰래 완화하거나 기존 검색으로 전환하지 않는다.

## 6. 임베딩과 순위

- 새 임베딩 입력 계약을 **제목 → 지원 분야/목적 → 지원 내용 → 신청 자격** 순서로 정의한다.
  각 텍스트의 출처와 대체 규칙을 남긴다. 예: 별도 지원 내용이 없으면 원문 본문을 사용했다는 사실을 기록한다.
- 기존 `shared/embed.py`의 6필드 계약은 수정하지 않는다. 새 계약은 별도 버전과 입력 해시를 가진다.
- 로컬에 있는 기존 BGE-M3를 우선 사용한다. 모델 리비전·토큰 상한·차원·정규화·잘림 여부를 기록한다.
  새 계약의 공고 벡터 생성은 이번 실험 범위에 포함되며, 새 로컬 DB에만 저장한다.
  캐시된 모델이 없어 진행할 수 없다면 환경 장애를 보고한다. 기존 NPZ를 덮어쓰거나 다른 계약 벡터를 새 벡터처럼 재사용하지 않는다.
- DB에 벡터 바이트·dtype/차원·정규화·모델/입력 버전·입력 해시를 저장한다.
  기존 BLOB 저장 규약은 참고하되 새 로컬 테이블에 구현한다. 조회 시 길이·차원·유한 값·입력 해시를 검사한다.
- 신청자 설명을 같은 모델로 임베딩하고 SQL 통과 후보 **전체**와 코사인 유사도를 직접 계산한다.
  정규화 벡터라면 내적을 사용할 수 있다. 저장 벡터가 없거나 낡은 후보를 조용히 누락하지 말고 오류·누락 건수를 보고한다.
- 후처리는 확인 가능한 신청자 선호를 반영하는 단순하고 고정된 정렬 규칙으로 시작한다.
  규칙이 적용되지 않으면 유사도순, 동점은 공고 ID로 고정한다. 점수/순위 변화의 이유를 공고별로 보여준다.
  코사인과 자의적인 가중치를 섞어 '적합 확률'로 표시하지 않는다. 튜닝·별도 리랭커는 이번에 추가하지 않는다.
- 응답에는 제목·ID·원문 링크·순위·유사도·후보 수·필터/규칙 근거·확인 필요 조건·소요 시간을 담는다.
  후보가 N개 미만이면 실제 건수를 반환한다. 무관 입력에서도 Top N이 나올 수 있다는 기존 한계가 자동 해결됐다고 주장하지 않는다.

## 7. 작동 확인과 기존 방식 비교

1. 먼저 소규모 데이터로 DB 분리·저장/조회·필터·유사도 계산을 확인한다.
   통과하면 정한 스냅샷 범위에 한해 새 임베딩을 한 번 생성하고 10개 사례를 실행한다.
   전체 공고를 사용하지 못하면 선택 규칙·포함/제외 건수를 기록한다. 유리한 결과에 맞춰 표본을 고르지 않는다.
2. 기존 `054314Z/inputs.jsonl`의 10개를 기준으로 신규 결과를 만든다.
   새 신청자 조건이 필요하면 입력 파일을 새로 만들고 가상 보완을 명시한다. 기존 입력은 수정하지 않는다.
3. 기존 `054314Z/responses.jsonl`의 서비스 조건(B단계) dense/hybrid와 신규 Top-5를 정적 HTML로 나란히 보여준다.
   원본 결과는 불변으로 보관하고 새 결과 폴더에서 ID·공통/한쪽에만 노출·순위 이동을 계산한다.
4. **비교 가능 조건을 명시한다.** 과거 결과의 공고 집합/내용·신청자·기준일이 현재 스냅샷과 같다는 근거가 없으면
   과거 결과 열은 참고용으로 표시하고, 순위 차이를 새 구조의 개선량이라고 주장하지 않는다.
   과거 결과의 Chroma 내용 미검증 한계도 그대로 남긴다.
5. 같은 데이터·입력·모델·기준일로 분리된 효과를 볼 수 있도록, 신규 경로 안에서
   **정형 필터 켬/끔** 옵션을 제공해 비교한다. 후처리 조건과 임베딩 텍스트는 같게 유지한다.
   이는 새 임베딩 입력에서 사전 필터의 영향을 보는 대조이며, BM25 제거의 효과까지 입증하지 않는다.
6. BM25 추가 실험·다른 임베딩 계약의 추가 전수 생성·기존 서비스 재실행은 후속 과제로 남긴다.
   이번 첫 구현은 새 경로의 작동과 필터 효과를 확인하는 데서 끝낸다. 사람 판정 없이 우열을 확정하지 않는다.

## 8. 검증과 산출물

필수 테스트:

- 대상 연결 누락/비로컬/소스와 동일 DB이면 쓰기를 거부하고 소스에 DDL/DML을 보내지 않음.
- 전국·복수 지역·불일치·미확인, 업종/규모의 값 누락, 업력 경계와 잘못된 날짜·예비창업 조건.
- 마감일 경계·상시/날짜 미확인, 고정 기준일 전달, 후보 0개/N개 미만.
- SQL 필터 후 후보만 유사도 계산에 들어감. 모름을 탈락시키지 않음.
- 벡터 저장/조회 일치, 차원·NaN/누락·입력 해시 오류 검출, 직접 코사인 계산과 순위·동점 처리.
- 실험 실행이 기존 DB·색인·결과 파일에 쓰지 않고 새 로컬 DB에서 작동함.

새 `reports/sql_semantic_<실행시각>/`에 다음을 남긴다.

- `manifest.json`: 코드·스냅샷·모델/입력 버전·해시·기준일·필터/규칙 설정·환경·건수·비교 가능 여부.
- `inputs.jsonl`, `responses.jsonl`: 필터 켬/끔의 입력·원본 출력과 식별자.
- `data_quality.json`: 정형 필드별 확보율·미확인 사유, 필터 탈락/잔존, 벡터 생성/검사 결과.
- `comparison.html`: 과거 두 방식과 새 방식, 신규 필터 켬/끔 결과를 구분한 표.
- `summary.md`: 실행 명령·테스트/실데이터 검증 구분·주요 차이·추출/정합성/평가 한계.

새 README에는 DB 준비→스냅샷 적재→정형화→임베딩→검색→비교의 재현 명령을 적는다.
STATUS·WORKLOG에 실제 변경·실행 범위·실패와 미검증을 기록하고 Codex 리뷰 대상으로 인계한다.
기존 구현의 보존 여부는 시작/종료의 파일 상태·내용 해시 등으로 확인하되 기존 타인의 수정은 되돌리지 않는다.
로컬 DB 실행이 불가능하면 가상 테스트 결과와 분리해 정확한 장애를 보고한다.
