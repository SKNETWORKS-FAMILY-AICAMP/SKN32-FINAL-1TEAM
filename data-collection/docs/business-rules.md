# 판정 원칙과 도메인 규칙

신청자가 "지금 신청할 수 있고 내용도 맞는" 공고를 찾게 하는 것이 목적이다. 순서는 **아이템을 말한다 → 맞는 공고를 찾아준다 → 그 공고 기준으로 만든다**이며, 공고를 먼저 고르고 아이템을 맞추는 흐름은 쓰지 않는다. 이 규칙들은 기획서 v1.10·Agent 기능정의서 v1.9(`docs/specs/`, 팀 기준 문서)와 사용자 결정(2026-09-28 ~ 10-06)에서 왔다.

## 1. 용어

| 용어 | 뜻 | 헷갈리기 쉬운 것 |
|---|---|---|
| 공고 ID | `출처:원본ID` (예: `kstartup:179323`, `bizinfo:PBLN_…`). 출처는 `kstartup`·`bizinfo` 둘뿐 | 원본ID에 `/`가 들어갈 수 있다 |
| 신청자 유형 | `예비창업자`·`개인사업자`·`법인` 셋 | |
| 예비창업자 | 아직 설립하지 않은 사람. 업력 값은 "없음(미설립)" | **설립일을 모르는 사업자와 다르다.** 사업자인데 설립일이 비었거나 날짜가 아니면 "업력 모름"이다 |
| 업력 | 설립일부터 기준일까지 꽉 찬 개월 수(일자가 모자라면 1개월 뺀다, 0 미만은 0) | |
| 판정 값 | 참(충족) · 거짓(확실한 미달) · 없음(확인할 수 없음) | "없음"은 "조건 없음"이 아니다 |
| 정형 필터 | 검색 **전에** 후보에서 빼는 단계 | 순위 신호와 다르다 |
| 순위 신호 | 빼지 않고 **뒤로만** 보내는 규칙(지역·업종·대상 집단·예비창업자 불가 추정) | |
| 자격 판정 | 고른 공고 한 건 × 신청자 → 조건별 판정 | 화면용(4줄)과 조율용(2줄)이 다르다(5절) |
| 공고 가점 | 공고문에 적힌 가점·우대 항목(LLM 추출, 공고 단위) | |
| 가산점 | 공고 가점 × 신청자 정보 → 신청자 입력으로 확인된 점수의 부분합(받을 수 있는 전체 합계가 아님) | 9절, 결정 0012 |
| 내용 지문 | 공고 원문이 바뀔 때만 바뀌는 문자열(`content_version`) | 수집 시각과 무관하다 |

## 2. 기본 원칙 — 모르면 빼지 않는다

- **확실한 미달(거짓)만 뺀다.** 확인할 수 없는 조건(없음)은 통과로 두고 "확인 필요"로 표시한다.
- 확인할 수 없음을 미달로 바꾸면 안 된다: 기업마당 공고 대부분은 업력 칸이 없고 접수 마감일도 상당수 없어서, 그렇게 하면 거의 전부 빠진다.
- 확인할 수 없음을 "제한 없음"·"충족"으로 쓰면 안 된다: 신청자가 자격을 확인받은 것으로 읽는다. 통과는 "후보로 남긴다"는 뜻이지 "자격이 있다"는 뜻이 아니다.
- 입력이 빠진 경우도 같다. 설립일 없는 사업자의 업력은 "모름"으로 통과한다.
- 정형화(파싱·추출)에 실패한 값은 추정하지 않는다. 판정 불가로 둔다.

## 3. 정형 필터 (검색보다 먼저, 모든 공고에)

**순서가 규칙이다.** 정형 필터를 모든 공고에 먼저 걸고, 통과한 공고 안에서만 검색한다. 검색 상위 N건을 먼저 자르고 거르면 신청 가능한 공고가 하나도 안 남을 수 있어 결함으로 본다.

공고를 빼는 경우는 아래 넷뿐이다.

| 이유 | 조건 | 빼지 않는 경우 |
|---|---|---|
| 모집 마감 | 모집 상태가 `closed` | `unknown`은 남긴다 |
| 접수 마감 | 접수 종료일이 있고 오늘보다 앞 | 종료일 없음, 접수 **시작 전**인 공고는 남긴다 |
| 업력·신청자 유형 | 업력 칸 판정이 거짓 (예비창업자 전용 공고 ↔ 사업자, 업력 상한 초과, 사업자 전용 ↔ 예비창업자) | 업력 칸이 없거나 못 읽으면 남긴다. 업력 모름 사업자도 남긴다 |
| 예비창업자 불가(공고 본문) | 신청자가 예비창업자이고, 공고 본문 판정이 "강한 근거로 불가·세부사업 공통" | 본문 판정이 추정이면 빼지 않고 뒤로 보낸다(4절) |

- **지역·업종은 정형 필터에 넣지 않는다.** 순위 신호로만 쓴다(2026-09-28 결정, 기능정의서 R-2·R-3).
- 공고 본문에 "예비창업자 가능"이 명시되면 K-Startup API 업력 칸의 "예비창업자 불가"를 덮어 되살린다.
- 개인사업자·법인은 공고 본문으로 자동 판정하지 않는다. 근거만 보여 준다.
- 비교·평가용 스위치(`structured_filter`, `hide_expired`)를 끄는 것은 평가 도구만 한다. 서비스는 항상 켠다.

### 업력 칸 해석

API 업력 문자열을 쉼표로 나눠 `예비창업자` 토큰과 `N년미만` 토큰을 본다. 상한은 가장 큰 N × 12개월.

| 업력 칸 | 예비창업자 허용 | 상한 | 판정 예 |
|---|---|---|---|
| `7년미만` | 아니오 | 84개월 | 예비창업자 → 거짓, 업력 30개월 → 참, 90개월 → 거짓 |
| `예비창업자,1년미만` | 예 | 12개월 | 예비창업자 → 참, 업력 13개월 → 거짓 |
| `예비창업자` | 예 | 없음 | 사업자 → 거짓("예비창업자만") |
| 빈 값·못 읽는 값 | — | — | 누구든 없음(확인할 수 없음) |

업력 비교는 `업력 < 상한`이다(상한과 같으면 미달).

## 4. 검색과 순위

- 기본 검색은 하이브리드다: 의미 검색(BGE-M3 코사인) + 단어 검색(BM25)을 RRF(k=60, 두 검색 가중치 1:1)로 합친다. 각 검색에서 정형 필터 통과 공고 중 최대 50건을 가져온다.
- 공고 쪽 검색 입력은 제목·사업개요·지원대상·지원대상 분류·대분류·중분류 여섯 칸을 이은 것이고, 의미 검색과 BM25가 같은 입력을 쓴다.
- 대체 경로: 임베딩 쪽(질의 인코딩·공고 벡터) 실패 → `BM25단독`, BM25 실패 → `임베딩단독`, 둘 다 실패 → 필터 통과 공고를 마감 임박순(마감일 없는 공고 뒤, 같으면 공고 ID 순, `마감임박순`). 응답에 `fallback_used`·`fallback_mode`·`search_errors`를 남긴다. 조용히 넘어가지 않는다.
- 정형 필터 통과 0건이면 검색하지 않고 빈 결과를 준다.

### 재정렬 (빼지 않고 뒤로)

한 번의 정렬로 아래 우선순위를 동시에 적용한다(규칙을 하나씩 밀면 나중 규칙이 앞 규칙을 덮는다).

1. 다른 시·도 전용 공고 (신청자가 소재지를 골랐고, 공고 지역이 있고, 맞지 않음)
2. 같은 시·도의 다른 시·군·구 전용 (공고 제목에 시·군·구가 적혀 있고 신청자 시·군·구와 다름)
3. 예비창업자인데 공고 본문상 대상이 기존 사업자로 **추정**되는 공고
4. 업종 허용 목록 밖 — **기본 꺼짐**(`demote_industry=false`). 블라인드 판정에서 밀린 34건 중 11건이 부당했다
5. 대상 집단(장애인·여성기업·재창업·사회적기업 등)이 적힌 공고인데 신청자 입력에 그 집단 근거 단어가 없음
6. 같은 조건이면 검색 순서 그대로

- 지역·시·군·구·업종 정보가 없거나 신청자가 고르지 않았으면 그 공고는 **건드리지 않는다**(모른다고 벌주지 않는다). 지역 판정은 참·거짓·없음 3값이며 없음을 거짓으로 바꾸지 않는다.
- 업종 규칙은 공고 업종 판정이 확실한 공고(판정 `known`·목록 완전·잘림 없음·통합공고 아님·허용값 전부 KSIC 대분류)만, **허용 목록만** 쓴다. 제외 목록(유흥·사행 업종 등 세부 업종)은 대분류로 올리면 같은 대분류의 정상 신청자까지 걸리므로 순위에 쓰지 않는다. 신청자 업종을 대분류 하나로 정할 수 없으면 업종으로 순서를 바꾸지 않는다.
- 나이(청년·중장년)는 대상 집단 규칙에 넣지 않는다. 신청자 입력에 나이가 없고, 나이는 자격 조건이다.
- 가산점 반영(`Weights.bonus`)은 **기본 0.2**다(2026-10-08 결정 0017). 같은 재정렬 묶음 안에서만 `검색 점수 × (1 + 세기 × min(가산점,10)/10)`로 순서를 바꾸고, **원문 대조를 마친 공고 목록**(`search/bonus_reviewed.json`)에 있고 대조 당시와 공고 내용·가점 행 지문이 같으며 지금 결과 항목이 모두 승인 항목 안인 공고만 얹는다. 그 밖의 공고는 가산점이 보여도 순위에는 쓰지 않는다(결과 칸 `bonus_rank_applied` 거짓). 얹은 공고가 하나도 없으면 다시 정렬하지 않는다. 목록 파일이 깨지면 순위 반영 0건.
- 감점 방식(`weights.mode='score'`)은 가중치 시험용이다. 서비스 기본은 순서 방식(`order`)이고 기본 가중치에서 결과는 서비스와 같아야 한다.

### 후보 수와 표시

- 첫 조회 10건(상위 3건 카드 + 7건 리스트), 추가 조회 `offset=10`으로 다음 10건, 누적 최대 20건. HTTP 경로는 20건을 넘지 않게 자른다. 결과마다 `rank`(전체 기준 순위), `display_type`(1~3 `card`, 나머지 `list`), 응답에 `has_more`.
- `score`는 코사인 유사도 원값, `band`는 0.62 이상 "매우 적합", 0.55 이상 "적합", 그 밖 "참고". 단어 검색에서만 찾고 벡터를 못 꺼낸 공고는 둘 다 null.
- `fit_score` = 이번 요청이 쓴 검색 경로의 RRF 점수 ÷ 그 경로의 이론 최대값(하이브리드는 두 검색 모두 1위, 대체 경로는 쓴 검색 1위), 1을 넘지 않는다. 규칙으로 뒤로 밀려도 값은 그대로다. 마감임박순이면 null. 산식은 기능정의서에서도 잠정이다.
- **점수를 0~100점으로 바꾸거나 정확도·확률로 표현하지 않는다.** 무관한 질의도 유사도 0.43이 나오고 상위 3건이 0.49~0.67에 몰려 있어 100점 척도로 보이면 정확도로 읽힌다.

## 5. 자격 판정

판정 내용은 한 곳에서 정해지고, 추천의 정형 필터와 같은 결론을 내야 한다. 같은 공고·신청자에 대해 정형 필터가 뺀 공고를 자격 판정이 통과로 내거나 그 반대가 되면 결함이다.

조건 네 줄:

| 조건 | 판정 근거 | 화면용 `/api/eligibility` | 조율용 `/api/notices/{id}/eligibility` |
|---|---|---|---|
| 지원대상 유형 | 공고 본문 신청자 유형 판정. 예비창업자만 자동 판정(본문 강한 불가 → 거짓, 가능 → 참, 추정·모름 → 없음). 개인사업자·법인은 늘 없음(근거만) | 씀 | 씀 |
| 업력 | API 업력 칸(3절). 예비창업자인데 본문 판정이 "가능"이면 업력 줄도 참으로 바꾼다. 세부사업마다 예비창업자 허용이 갈리면 업력 줄은 없음 | 씀 | 씀 |
| 접수기간 | 종료일이 있으면 `시작일 ≤ 기준일 ≤ 종료일`, 종료일이 없고 예산 소진·상시·선착순이면 없음, 그 밖 없음 | 씀 | **안 씀** |
| 모집 상태 | `open` 참 · `closed` 거짓 · 그 밖 없음 | 씀 | **안 씀** |

- 결과 `passed` = 사용하는 조건에 거짓이 하나도 없음. 없음은 `unknown_conditions`로만 알린다(판정 불가 = 통과, 2026-09-29 결정).
- 조율용은 접수기간을 보지 않으므로 **접수 시작 전 공고도 고를 수 있다**. 화면용은 시작 전이면 접수기간이 거짓이다.
- 조율용 기준일은 요청의 `today`다. `business_age_months`는 사업자 업력(개월), 예비창업자·설립일 모르는 사업자는 null.

### 공고 상세의 허용 지원대상 유형

`예비창업자`는 위 두 조건(지원대상 유형·업력)에 거짓이 없을 때 포함한다. `개인사업자`·`법인`은 업력 칸이 "예비창업자"만일 때 빼고 그 밖에는 포함한다(업력 상한은 설립일에 달린 것이라 유형만으로 빼지 않는다). 조율 쪽은 이 값을 담아 두기만 하고 판정은 자격 판정 창구로 한다.

## 6. 수집

- 공고 데이터는 하루 한 번 배치로만 갱신한다. **사용자 요청 시점에 공고 API를 부르지 않는다**(API 장애일에도 전날 데이터로 동작).
- 범위: K-Startup 모집 중 공고 전량, 기업마당 **8개 분야 전부**(경영·기술·수출·금융·인력·내수·창업·기타). 기획서는 기업마당 창업·기술 분야만 쓴다고 적었으나 사용자가 전 분야 수집을 맞는 것으로 확인했다(2026-10-06). 대형 국가 R&D(IRIS·NTIS)는 공개 API로 접수기간·지원대상·규모를 얻을 수 없어 범위 밖이다.
- **출처별로 따로 검증하고 따로 실패한다.** 오늘 건수가 직전의 절반 미만이면 그 출처의 오늘 결과를 쓰지 않는다(`--force`로만 무시). 한 출처가 실패해도 다른 출처는 갱신하고, 실패한 출처는 직전 데이터를 유지한다. 합쳐서 세면 한 출처가 통째로 죽어도 검증을 통과하기 때문이다.
- 정규화 결과에 격리된 행이 하나라도 있으면 저장하지 않는다. `notice_id`는 반드시 `출처:원본ID`와 같아야 한다.
- 저장은 시간 순서를 지킨다: 이미 저장된 행보다 오래된 입력은 덮어쓰지 않는다(`snapshot_at` 기준).
- **K-Startup 모집 종료 처리**: K-Startup API는 모집 중 목록만 준다. 그날 K-Startup을 새로 받았고, 받은 행 수와 고유 공고 번호 수가 서버가 알린 건수와 같을 때만, 오늘 목록에 없는 K-Startup `open` 공고를 `closed`로 바꾼다. 행은 지우지 않는다. 이번 목록보다 최신인 행은 닫지 않는다. 목록에 다시 나타나면 `open`으로 돌아온다. 어제 파일을 재사용한 날·목록이 덜 온 날은 건너뛴다.
- 모집 상태는 API 값만 쓴다. 날짜로 `closed`를 추정하지 않는다(위 K-Startup 처리만 예외).
- 첨부 본문은 기업마당 공고문(`role='notice'`) 첨부만 받는다. **K-Startup 첨부 공고문은 자동으로 받지 않는다** — 경로 `/afile/`가 robots.txt에서 금지되고, 공공데이터포털 K-Startup API 4종에도 첨부 칸이 없다.

## 7. 수집 상태 (정상 · 지연 · 실패)

강한 것부터 판정한다.

| 상태 | 조건 |
|---|---|
| 실패 | 저장 기록(`import_runs`)이 없다 / 가장 최근 배치 로그가 `error`다 / 가장 최근 배치에서 출처 하나라도 실패했다(`partial`) / 마지막 저장에 쓰인 기업마당 스냅샷이 24시간 이상 오래됐다(재사용) |
| 지연 | 마지막 저장 성공이 24시간을 넘었다 |
| 정상 | 그 밖 |

- 배치 로그는 배치를 돌린 곳에만 있으므로, 로그가 없으면 DB만으로 판정한다. 배치 로그가 마지막 저장보다 10분 넘게 오래됐으면 그 로그는 판정에 쓰지 않는다.
- 공고 서버가 내보내는 상태는 위 판정에 "서버가 들고 있는 공고"를 얹는다: 서버가 올린 공고의 저장 시각이 24시간을 넘었거나 그 시각을 모르면 `정상`을 `지연`으로 내린다. `실패`는 그대로 둔다. DB를 읽지 못하면 상태를 지어내지 않고 오류(503)를 준다.
- **LLM 후처리(10~14단계) 실패는 수집 실패가 아니다.** 상태를 `partial`로 바꾸지 않는다. 공고 데이터는 새것이고 후처리만 늦은 것이라 매칭을 막을 일이 아니다. 종료 코드 4와 `stage_warnings`로만 알린다.
- 기준 문서는 "실패 또는 24시간 초과면 매칭하지 않는다"고 한다. **매칭을 멈출지는 조율 에이전트가 수집 상태 창구를 먼저 불러 정한다.** 추천 창구는 상태와 관계없이 결과를 준다(2026-10-06 사용자 확인).

## 8. 공고 내용 지문

- 넣는 것: 공고 원문 칸(제목·본문·지원대상·지원대상 분류·제외·업력 칸·지역·대분류·중분류·기관 3종·접수 시작·종료·접수기간 원본·기간 유형·모집 상태·링크 2종) + **지금 달린** 첨부의 파일 바이트 SHA-256(정렬, 빈 값 제외).
- 넣지 않는 것: 수집 시각·행 수정 시각·API 수정 시각, 정규화 경고, 원본 행 전체, LLM이 뽑은 값. 이런 값이 섞이면 내용이 그대로인 공고도 매일 "내용 바뀜"이 된다.
- 값 모양은 `cv2-` + SHA-256 앞 32자. 만드는 방식을 바꾸면 접두어를 올린다(모든 공고 값이 함께 바뀐다).
- 첨부가 빠지거나 바뀌면 지문도 바뀐다. 지문을 계산하지 못한 공고는 null.

## 9. 가산점 (화면에는 원문 대조된 공고만 — 2026-10-08 결정 0018)

- **`bonus_score`는 "확인된 가산점 부분합"이다**(2026-10-07 사용자 결정, 결정 0012). 신청자 입력으로 해당 여부와 배점을 확인한 묶음만 더한다. 받을 수 있는 전체 합계가 아니다 — 확인하지 못한 묶음은 더하지 않는다. 화면 문구 제안: "확인된 가산점(일부)" + "전체 가산점은 공고문 확인".
- 공고 단위:

| 공고 가점 상태 | 가산점 |
|---|---|
| 행 없음(첨부를 못 읽은 공고 — K-Startup 전부 포함) | null |
| 가점 없음(`none`)·가점 언급 없음(`no_mention`) | 0 |
| 찾았으나 근거 확인 실패(`unverified`) | null |
| 찾음(`found`) — 점수 있는 해당 항목 묶음이 있음 | 그 합(확인된 묶음만 더한 부분합). 단 합이 공고 합계 한도를 넘으면 null |
| 찾음 — 해당 묶음 없이 모두 "해당 아님" | 0 |
| 찾음 — 모름이 섞임·해당이지만 점수 없음 | null |
| 가점 없음(`none`)인데 AI가 불확실 사항을 남김 | null(없음을 확정하지 못함) |
| 찾음인데 AI가 불확실 사항을 **하나라도** 남김(한도·합산·읽기를 확정하지 못함) | null |
| 찾음인데 근거 원문을 읽지 못함(공고 서버가 켤 때 DB 오류) | null — `boot_errors.bonus_documents`에 이유 |

- 항목마다 신청자에게 참(해당)·거짓(해당 아님)·없음(모름)을 매긴다. 여성(여성기업 인증 또는 "대표" 문구면 성별), 장애인기업 인증, 우리 인증 목록 안의 인증, 지역(항목에 그 시·도·도내·관내가 적힌 것, 시·군·구가 있으면 시·군·구까지), 청년(생년월일과 "만 N세 이하·미만"), 재창업(첫 창업 여부 거짓 → 해당)만 판단한다. 고용·수출·특허·이전 실적·업종 등은 늘 모름.
- 항목에 추가 조건("최근 3년 이내", "개인사업자 제외" 등)이 있거나, 글에 앞으로 할 일(이전·이주·유치·예정·희망·신규 채용·신규 고용)이 적혀 있거나, **신청자 입력으로 확인할 수 없는 조건 말(모두·이내·최근·이상·이하·미만·초과·기준·한함·한정·경우·단서·회당·"단,")**이 있으면 해당이 나와도 모름으로 낮춘다. AI가 추가 조건 칸을 비워도 글을 본다. 청년 항목의 "만 N세 이하" 구절은 나이 판정에 쓰고 이 검사에서는 뺀다. 해당 아님은 그대로 둔다. ("공장을 도내로 이전하는 기업 5점", "본사와 생산공장 모두 전북"은 지금 그 지역에 있어도 모름)
- **예외(2026-10-08, 결정 0014): 증빙 서류·유효기간·"중소기업"처럼 뜻이 안 바뀌는 추가 조건은 모름으로 내리지 않는다.** 추가 조건을 `;`·`/`로 나눈 조각이 모두 증빙 서류(인증서 첨부·확인서 제출 …)·유효기간(유효기간 내 …)이거나 "중소기업" 단독이어야 하고, 위험 말(최근·협약·잔류·법인의 경우·개인사업자·추천·업종·이전·고용·"N년 이내" …)이 섞이면 예외가 아니다. 조건 말 검사도 위험 말이 없는 증빙·유효기간 구절은 빼고 한다("유효기간 내 인증서에 한함"). "최근 3년 이내 … 확인서 제출"은 그대로 모름.
- **근거 문장이 지금 공고 원문(본문·지원대상·지금 달린 첨부)에 공백만 다르고 그대로 이어져 있어야 한다.** AI가 떨어진 조각을 이어 붙인 근거("여성기업 가점 10점" ← 원문 "여성기업 가점 2점. 벤처기업 가점 10점.")는 그 항목을 모름으로 본다. 공고 서버가 켤 때 found 행만 확인한다(10/7 첨부 614개·약 525만 자, 조회 0.02초).
- **점수는 근거 문장에 "N점"으로 직접 적힌 것만 인정한다.** 표의 떨어진 배점 칸에서 가져온 점수, 숫자만 있는 경우(연번일 수 있음), **근거 문장에 서로 다른 "N점"이 둘 이상 섞인 경우**(어느 항목 점수인지 모름 — "벤처 각 1점, 여성기업 3점")는 점수 없음으로 본다. 같은 값이 되풀이되는 것은 괜찮다.
  - **예외(2026-10-08, 결정 0019) — 표 "배점" 칸**: 원문에서 근거 시작 앞 1,500자 안에 "배점"이 있고, 근거에 "N점"이 없고 단위 없는 숫자가 정확히 하나이며 그 값이 항목 점수면 점수로 본다("여성기업 및 / 장애인 기업 | 10"). 점수 주인은 숫자만 있는 줄 앞의 줄 전부를 행 이름으로 합쳐 보고, 행 이름에 대상 말이 있고 그 안의 자격 이름이 모두 같은 근거에서 뽑힌 짝의 자격이어야 한다. 나머지 규칙은 그대로.
  - **결정 0020(2026-10-08) — 완화와 조이기**: 같은 숫자가 되풀이되거나 "아니오(0)" 칸이 있어도 표 배점으로 인정, 한 문장에 점수가 여럿이면 쉼표 조각에서 주인이 분명할 때 인정, 다른 묶음의 "각 N점"은 더한다. 자격 자체만 말하는 "…인 경우"는 조건 말이 아니다. AI 불확실 메모가 특정 항목만 가리키면(①~⑳·따옴표·"‹낱말› 항목"·자격 이름, 전체를 흔드는 말 없음) 그 항목만 모름. 표 경로의 짝은 인증·종류 말로만, 행 이름은 숫자 줄 바로 앞 줄(+ 잇는 말로 끝나는 윗줄), "배점" 머리는 같은 표(조사 붙은 "배점"·숫자 없는 다른 글 사이·번호 숫자 제외).
- 한 점수를 여러 조건이 나눠 가지면(예: 벤처·이노비즈·메인비즈 중 하나 10점) 같은 묶음으로 보고 한 번만 센다(해당 항목 중 최대, 같은 점수면 이름순). 묶음은 추출한 묶음 표시(group)가 같을 때만이다 — 한 문장에 함께 적혔다는 이유만으로 묶지 않는다.
- **묶음 판단이 원문과 어긋날 수 있으면 null이다**: 점수로 고른 항목 가운데 묶음은 다른데 근거 문장·점수가 같은 것이 있다(선택 가점을 둘로 나눴을 수 있음 — 10점이 20점이 됨), 또는 한 묶음에 항목이 둘 이상인데 근거에 "각"이 있다(독립 가점을 하나로 묶었을 수 있음).
- 세부사업마다 가점이 다르면 세부사업별로 따로 계산해 **결과가 모두 같을 때만** 그 값을 쓴다. 0이면 0, 양수는 공통 항목만으로 같은 점수일 때 꼬리표 없이 낸다. 하나라도 다르거나, 같아도 세부사업 항목이 섞여야 그 점수면 null(신청자가 어느 세부사업에 내는지 모름).
- 합계 한도는 자르는 데 쓰지 않는다 — 그 한도가 공고 전체 한도인지 한 항목 한도인지 확인할 수 없어서, 합이 한도를 넘으면 null이다. 그래서 `bonus_items`의 점수는 원문 배점 그대로이고 합이 `bonus_score`와 같다.
- 신청자 인증 목록은 화면에서 고른 것이라 **빈 목록은 "확인된 없음"**으로 본다.
- 점수 없이 "가점 부여"라고만 적힌 항목은 합계에 넣지 않는다.
- 공고문이 바뀌었는데 아직 다시 뽑지 않은 가점(추출 당시 내용 지문이나 추출기 버전이 지금과 다름)은 쓰지 않는다 → null.
- **Codex 재재검수 처리(2026-10-08, 결정 0016)** — 해당이 나와도 모름으로 낮춘다:
  - ① 근거에 "둘 다"로도 읽히는 잇는 말(및·&·+·그리고)이 있고 같은 근거에서 뽑힌 짝 항목을 입력으로 확인할 수 없으면("가족친화인증 & 일·생활균형 우수기업", "일자리 으뜸기업 및 청년친화 강소기업"). 짝을 **안 가진 것이 확실하면 "둘 중 하나"로 보고 점수**("여성기업 및 장애인 기업(5점)"에서 여성기업만 가진 신청자는 5점). `&`·`+`인데 짝이 따로 안 뽑혔어도 모름. 또는·쉼표·"… 등" 나열은 그대로.
  - ② 공고 원문 한 줄에 증빙 말(인증서·확인서·증빙…) + 기간 말(최근·2024~2025·이내·N년간…) + 가점·인정이 함께 있으면, 그 공고의 인증으로 받는 항목(인증·여성·장애인). "가점·인정"이 없는 "필수 제출서류: 최근 3개년 재무제표" 같은 줄은 보지 않는다.
  - ③ 결정 0014 예외는 **그 항목 자신의 인증 증빙·유효기간일 때만**("벤처기업 인증서 및 대통령 표창장 제출"은 모름).
  - ④ 근거를 문장·항목 경계로 나눴을 때 그 "N점"이 있는 조각에 항목의 대상 말(이름·인증·종류·지역)이 없으면("여성기업 우대 안내. 벤처기업 가점 10점"의 여성기업).

## 10. 신청자 입력의 쓰임

| 갈래 | 칸 | 쓰는 곳 |
|---|---|---|
| 질의 문장 | 아이디어, 수익모델 항목, 유형·업력 문구, 팀 경력, 주 업종, 인증, 채용 계획 | 의미 검색·BM25 |
| 규칙 | 성별, 재창업 여부, 인증, 시·도, 시·군·구, 주 업종, 협력 기관 | 재정렬·가산점 |
| 받기만 함 | 이름, 생년월일, 사업자번호, 자기부담금, 희망 사업 규모, 장비 | 매칭에 안 씀. 생년월일은 가산점(청년)에만 씀 |

- 받기만 하는 칸은 쓸모없는 칸이 아니다. 사업계획서 작성 단계의 재료다(희망 사업 규모는 확정, 그 밖은 미확정). 지우자고 하지 않는다.
- 대표자 이력·팀 이력·수익모델·채용 계획은 **매칭에서 뺄 수 있는 후보**다. 빼도 된다·안 된다 어느 쪽도 평가로 확인되지 않았다(차이의 95% 구간이 0을 포함). 새 기능이 이 칸들에 기대게 만들지 않는다. 뺄지는 사용자가 정한다.
- 화면에 받는 칸이 매칭에 쓰이지 않으면 응답의 `stored_only`·`why_not_used`로 그 사실을 보여 준다.

## 11. LLM이 뽑은 값의 지위

- 자격요건·신청자 유형·업종·가점은 LLM 추출값이다. 근거 문장을 원문과 대조해 확인되지 않은 값은 버린다(지원 금액의 `amount_rejected`, 가점의 `unverified`).
- 업력 상한 추출값은 오답률이 높아 판정에 쓰지 않는다. 화면 설명의 근거로만 보여 준다. 판정은 API 업력 칸으로만 한다.
- Codex·LLM이 만든 판정 정답은 "AI 참고 정답"이다. 사람 정답으로 쓰지 않는다.
