## 1. 질문 답 (요청서 9절)

### 질문 1 — 언제 제공할 수 있나

- 새 API 3개(`GET /api/collection_status`, `GET /api/notices/{notice_id}`, `POST /api/notices/{notice_id}/eligibility`)와 추천 결과 키 3개(`content_version`·`bonus_score`·`bonus_items`)는 **만들고 확인까지 마쳤다**(2026-10-06). 코드는 `data-collection/search/`(`notice_api.py`·`app.py` 등)에 있다.
- **지금 Orchestrator 쪽이 접속할 수 있는 주소는 없다.** 공고 서버는 공고팀 PC(127.0.0.1)에서만 켜져 있다. 접속 주소는 배포 위치를 정한 뒤 알린다. 날짜는 아직 약속하지 못한다.

### 질문 2 — `fallback_mode` 값

요청서와 같다. `"BM25단독"` · `"임베딩단독"` · `"마감임박순"`, 대체 경로가 아니면 `null`이다.

### 질문 3 — `"지연"`과 `"실패"`를 나누는 기준

| 상태 | 조건 |
|---|---|
| `"실패"` | 저장 기록이 하나도 없다 / 가장 최근 배치가 저장 전에 실패했다 / 가장 최근 배치에서 출처(K-Startup·기업마당) 하나라도 실패해 전날 자료를 다시 썼다 / 기업마당 자료가 마지막 저장보다 24시간 넘게 오래된 것이다(다시 쓴 것) |
| `"지연"` | 마지막 저장이 24시간을 넘었다 / **공고 서버가 메모리에 올려 둔 공고가 24시간을 넘었거나, 그 시각을 모른다** |
| `"정상"` | 그 밖 |

- 공고 서버는 켤 때 공고를 메모리에 올려 그것으로 답한다. 그래서 DB가 새것이어도 서버를 다시 켜지 않았으면 `"지연"`이 된다. 실제로 추천에 쓰는 데이터를 기준으로 판단하기 위해서다.
- DB를 읽지 못하면 상태를 지어내지 않고 **HTTP 503**을 준다. 본문 최상위 `code`가 `"COLLECTION_STATUS_UNAVAILABLE"`이고, 참고용 `error` 키(오류 종류 한 줄)가 함께 온다. 본문 전체를 비교하지 말고 `code`만 보면 된다. 요청서 2.1의 재시도 규칙(HTTP 오류 코드)대로 다시 부르면 된다.
- 공고 데이터는 새것인데 AI 후처리(자격요건·신청자 유형·업종·가점 추출)만 실패한 날은 `"정상"`이다. 추천을 멈출 일이 아니라서다.
- 응답의 약속 키는 `status` 하나다. 나머지(`reasons`·`db_status`·`last_run_at`·`loaded_store_at`·`checked_at`)는 참고용이다.
- 매칭을 멈출지는 Orchestrator 쪽이 이 값으로 정한다(요청서 2.3·⑧대로). 공고 추천 API 자체는 상태와 관계없이 답한다.

**지금의 한계.** "최근 배치 실패"와 "출처 하나 실패"는 배치 일지로 판정한다. 그런데 매일 배치는 배치 서버에서 돌고, 공고 서버는 공고팀 PC에서 돌아서 그 일지를 볼 수 없다. 그래서 지금은 DB의 저장 기록만으로 판정하고, 결과는 이렇게 된다.

1. 배치가 저장 전에 실패하면 바로 `"실패"`가 되지 않고, 하루가 지나 `"지연"`으로 잡힌다.
2. K-Startup만 실패한 날은 `"정상"`으로 보인다. 기업마당이 전날 자료를 다시 쓴 경우는 DB 기록으로 알 수 있어서 `"실패"`로 잡힌다.

공고 서버를 배치와 같은 서버에 올리면 이 한계는 없어진다.

### 질문 4 — 내용 버전(`content_version`)에 넣는 칸 — 잠정

- 모양은 `"cv2-"` + 해시 32자다. 두 값이 같은지만 비교하면 된다(크기·순서에는 뜻이 없다).
- **넣는 것** (공고 원문에서 온 값만): 제목, 본문(사업 개요), 지원대상 글, 지원대상 분류, 제외 조건, 업력 칸, 지역, 대분류·중분류, 기관 3개, 접수 시작·마감, 접수기간 원본, 기간 유형, 모집 상태, 링크 2개, 그리고 **지금 공고에 달린 첨부 파일 자체의 해시**(글자를 뽑은 결과가 아니라 파일 바이트).
- **넣지 않는 것**: 가져온 시각, 행 수정 시각, 원천의 수정 시각, 정리 경고, AI가 뽑은 값(지원 금액·가점·자격요건·판정).
- 요청서 3.1의 "가점 조건·지원 금액": AI가 뽑은 값은 넣지 않는다. 대신 그 값을 뽑은 **원문(본문·첨부 파일)이 들어 있어서, 원문이 바뀌면 내용 버전도 바뀐다.** AI 추출을 다시 돌려도 원문이 그대로면 바뀌지 않는다.
- 첨부가 빠지거나 바뀌어도 바뀐다. 계산하지 못한 공고는 `null`이다.
- **잠정인 이유:** 10/7 배치 뒤부터 날마다 바뀌는 칸이 섞여 있는지 점검한다. 섞여 있으면 그 칸을 빼고 접두어를 `"cv3-"`로 올린다. 그날은 모든 공고의 값이 함께 바뀌어서 화면의 카드마다 "내용 바뀜"이 한 번씩 붙는다. 또 가점은 뽑을 때의 내용 버전이 지금과 같아야 쓰이므로, 다시 뽑기 전까지 모든 공고의 `bonus_score`가 `null`이 된다. **바꾸기 전에 미리 알린다.**

### 질문 5 — 가산점을 순위에 섞는 방식

- **지금은 순위에 섞지 않는다.** 가산점은 `rank`를 바꾸지 않는다(추천 순서는 가산점이 생기기 전과 같다).
- 섞을지, 섞는다면 어떻게 섞을지는 가산점을 정리한 뒤 정해서 알린다.
- 그래서 "아이템과 맞는 정도와 가산점을 함께 보고 골랐어요" 같은 문구는 지금 쓰지 말아 달라.

### 질문 6 — 가산점 계산에 쓰는 신청자 입력

| 입력 | 쓰는 가점 |
|---|---|
| `gender` | 여성 대표 가점(여성기업 인증을 요구하는 가점은 `certifications`로 본다) |
| `certifications` | 인증 가점(벤처·이노비즈·메인비즈·여성기업·장애인기업 등) |
| `region` · `district` | 지역 가점(시·도, 글에 시·군·구가 있으면 시·군·구까지) |
| `first_startup` | 재창업 가점 |
| 생년월일 | 청년 가점("만 N세 이하·미만") |

- **생년월일은 아직 보내지 말아 달라.** 쓰이는 곳이 청년 가점뿐이고, 가산점이 시험 단계라서다. 보내지 않으면 청년 항목은 "모름"으로 계산된다.
- `first_startup`이 늘 `null`이면 재창업 항목도 "모름"이다.
- 고용·수출·특허·이전 실적·업종 가점은 입력이 없어서 늘 "모름"이다.
- 항목이 "모름"이면 그 공고의 `bonus_score`는 `null`이 될 수 있다(0과 `null` 구분은 요청서 3.2대로다).

### 질문 7 — "공고 없음"이 생기는 경우

- 공고 행은 지우지 않는다. 모집이 끝나도 상태만 `closed`로 바꾼다.
- 공고 서버는 켤 때 공고 전체(마감된 것 포함)를 올린다. 그래서 **같은 서버가 추천한 공고가 그 서버에서 "공고 없음"이 되지는 않는다.**
- 생길 수 있는 경우는 서버가 다른 DB나 새로 만든 DB를 보게 된 때처럼, 데이터 자체가 바뀐 경우뿐이다. 같은 ID로 다시 들어오면 다시 찾을 수 있다.
- 지금 Orchestrator 쪽 처리(막지 않고, 다시 고르면 다시 묻기)는 그대로 좋다.

### 질문 8 — 동시 호출, 매일 갱신·재시작 중 응답, 응답 시간

**미정** — 배포 위치(요청서의 AWS 내부망), 동시 호출 안전성, 매일 재시작 방식은 배포 위치를 정할 때 답한다. 지금 아는 사실은 이렇다.

- 동시 호출 안전성은 아직 확인하지 않았다. 그 전까지는 요청서대로 워커 1대·한 번에 하나가 맞다.
- 매일 배치는 한국 시각 09:00에 돈다. **배치 뒤 공고 서버를 다시 켜야 새 공고가 반영된다.** 다시 켜지 않으면 하루가 지나 수집 상태가 `"지연"`이 되고, Orchestrator 쪽 추천이 멈춘다.
- 다시 켜는 동안 약 20~25초는 응답할 수 없다. 요청서의 "약 10초 안에 포기"보다 길다. 이 시간을 어떻게 다룰지는 운영 방식을 정할 때 함께 정한다.
- 지금 공고팀 PC의 시험 서버는 의미 검색 색인이 10/2 기준이다(매일 배치가 배치 서버로 옮겨 갔다). 그래서 그 뒤에 들어온 공고는 추천 결과에 나오지 않는다. 이때도 수집 상태는 `"정상"`일 수 있다. 배포할 때는 배치와 같은 데이터를 보게 해야 한다.
- 응답 시간 실측(10/6, 공고팀 PC): 공고 추천 약 0.5초(서버를 켠 뒤 첫 추천만 약 2.7초), 공고 상세 + 자격 판정 한 쌍 약 23ms. 30초 제한에 넉넉하다.
- 같은 서버 데이터·같은 날짜에서는 같은 요청에 같은 결과를 준다(다시 불러도 결과가 같다). 날짜가 바뀌면 접수 마감 판정이 달라질 수 있다.

### 질문 9 — 인증 방식, 요청 본문 기록

- 인증은 **지금 없다.** 방식은 배포 위치를 정할 때 정한다.
- 공고 서버는 **요청 본문(신청자 정보)을 파일·DB·로그에 남기지 않는다.** 접속 기록도 경고 수준만 남긴다.
- 신청자 정보를 서버 밖(외부 API 등)으로 보내지 않는다. 질의 임베딩도 서버 안에서 계산한다.

### 질문 10 — 신청서 양식·평가 항목 고도화

공고 데이터에는 공고별 양식·평가 항목 칸이 없다. **공고팀은 만들고 있지 않고, 계획도 없다.**

### 질문 11 — `fit_score`가 정확히 0이 될 수 있나

- 정상 결과의 `fit_score`는 0이 되지 않는다. 계산이 "이번 검색 점수 ÷ 그 검색 방식에서 나올 수 있는 최고 점수"라서, 하이브리드에서는 가장 낮아도 약 0.28이고, `"BM25단독"`·`"임베딩단독"`에서는 약 0.55다.
- `"마감임박순"`일 때만 늘 `null`이다.
- 참고: `band`(와 `score`)는 의미 검색 점수를 구하지 못한 공고에서 `null`일 수 있다. 대체 경로가 아니어도 그렇다. 요청서 ⑤의 "`band`가 `null`인 그 밖의 경우" 문장이 그대로 쓰인다.

## 2. 요청서 약속과 다르거나 덧붙일 점

여기 없는 키·값·오류 코드는 요청서 2·3절 약속대로다.

| 항목 | 내용 |
|---|---|
| 자격 판정 = 추천 필터 | 요청서 2.5대로다. 자격 판정의 신청자 유형·업력 규칙(공고 본문으로 신청자 유형을 판정하는 규칙 포함)은 추천의 정형 필터와 **같은 함수**를 쓴다. 정형 필터에서 접수기간·모집 상태만 뺐다. 실제 데이터로 13,825번 대조했을 때 결론이 모두 같았다(10/6). 그래서 "확실히 안 되는 경우만 불통과"가 지켜진다 |
| 가산점(`bonus_score`·`bonus_items`) | **시험 단계라 화면에 쓰지 말아 달라.** 일부 공고에서 점수가 틀릴 수 있다는 검수 지적이 남아 있다. 실제 연결 전에 정리 방법을 정해 다시 알린다. `bonus_items`의 `points`는 공고의 합계 한도를 적용한 **뒤** 실제로 더한 점수이고, 모두 더하면 `bonus_score`와 같다. **K-Startup 공고는 늘 `null`이다** — 공고문 첨부를 자동으로 받을 수 없어서다(사이트가 자동 수집을 막아 두었다) |
| 인증 목록 `certifications` | `[]`는(키가 없을 때도) "인증이 없음이 확인됨"으로 계산한다. 웹에서 인증을 고르지 않은 경우를 뜻한다면 지금 방식이 맞다 |
| 가점 조건 원문 `bonus_info` | 공고문에 적힌 글을 그대로 옮긴 것이라 **화면에 써도 된다.** 가점을 찾은 공고에만 있고, 그 밖과 K-Startup은 `null`이다 |
| 업력 상한 `eligibility.business_age_max_months` | 요청서는 `null`을 "제한 없음"으로 읽는다. 우리 쪽 `null`은 두 경우다. `parsed`가 `false`면 **업력 칸을 읽지 못한 것**(모름 — 제한이 없다는 뜻이 아니다)이고, `parsed`가 `true`면 예비창업자 전용 공고다(이때 `applicant_types`에 개인사업자·법인이 없다). 업력 칸을 읽은 공고는 약 19%(527건)뿐이고, 기업마당은 대부분 읽지 못한다 |
| 지원 금액 원문 `support_amount_text` | **늘 `null`이다.** 공고 원문의 금액 표기를 따로 저장하지 않는다. 금액 숫자 상한 `support_amount_max_won`은 약 31%(849건) 공고에만 있고, K-Startup은 없다. 참고용으로 근거 문장 `support_amount_evidence`가 함께 온다 |
| 사업자 신청자의 "확인 필요" | 개인사업자·법인은 공고 본문으로 자동 판정하지 않는다. 그래서 **사업자 신청자는 모든 공고에서 `unknown_conditions`에 `"지원대상 유형"`이 들어 있다.** 화면에는 늘 "공고문 직접 확인" 안내가 뜬다. 기업마당은 업력 칸이 없어서 `"업력"`도 대부분 함께 들어 있다 |
| 빈 값 표기 | 추천 결과의 `organizer`·`region`·`url`은 값이 없으면 `null`이 아니라 빈 문자열 `""`일 수 있다. `apply_end`도 마감일이 없으면 `""`다. 공고 상세의 날짜·기관은 없으면 `null`이다 |
| 옛 설명서 | 9/29의 직접 import 설명서(`data-collection/docs/guides/ORCHESTRATION_HANDOFF.md`)는 이 HTTP 방식으로 대체됐다 |

## 3. 공개 시험 서버와 계약 확인

- 요청서 5절이 말하는 "공개 주소의 시험 공고 서버"는 **없다.**
- 대신 공고팀이 **Orchestrator 쪽 실제 연결 코드**를 고치지 않고 그대로 써서 공고 서버를 불러 봤다. 쓴 코드는 `b8e7f50`(10/5)의 `agent-orchestration/sbrain/agents/notice`(요청 본문 만들기·HTTP 호출·응답 검사·`make_tc2`·`make_g01`)이고, 신청 정보는 가짜다.
  - 16개 확인 모두 통과했다: 추천 첫 조회·추가 조회, 시·도 바꾸기, 자격 판정, 공고 없음(404 + `NOTICE_NOT_FOUND`), 경로 없는 404와의 구분.
  - 모든 공고 2,765건에 자격 판정을 불렀을 때 형식 오류·공고 없음은 0건이었다.
  - 결과: `data-collection/reports/notice_api_contract_20261006T035438Z/`
- 그 뒤 브랜치에 새 커밋이 있었지만, 요청서와 `sbrain/agents/notice`는 바뀌지 않았다(10/6 확인).
- 함께 시험하는 방법은 배포 위치를 정할 때 정한다.
