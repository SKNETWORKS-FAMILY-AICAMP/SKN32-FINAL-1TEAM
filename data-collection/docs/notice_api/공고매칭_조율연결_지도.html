S-BRAIN · 공고 데이터 ↔ 조율 에이전트

공고 매칭은 조율과 이렇게 연결된다

조율 에이전트는 우리 코드를 직접 가져다 쓰지 않습니다. 공고 서버에 HTTP로 네 가지 질문을 보내고, 받은 답을 화면용 카드와 자격 결과로 바꿀 뿐입니다. 추천 순위와 자격 판정은 모두 우리 공고 서버가 정합니다.

먼저 비유로

도서관 사서와 상담 창구

상담 창구 직원 = 조율 워커손님(신청자)의 이야기를 듣고 정리합니다. 책을 직접 찾지는 않고, 사서에게 전화로 물어봅니다.agent-orchestration · agents/notice/
사서 = 공고 서버모든 책(공고)의 위치와 대출 규칙(자격)을 압니다. "이 손님에게 맞는 책 10권", "이 책을 빌릴 수 있나요?"에 답합니다.data-collection · search/app.py :8000
매일 아침 책 정리 = 매일 배치09:00에 새 공고를 서가(공용 DB)에 꽂고, 09:20에 사서가 서가를 다시 훑어 머릿속을 새로 고칩니다.배치 서버 sbrain-web → 공용 DB → 시험 서버 재시작

전화선은 딱 네 개(창구 4개)입니다. 창구 직원은 사서가 정한 순서를 바꾸지 않고 그대로 손님에게 보여 줍니다.

누가 누구를 부르나

조율 쪽은 공용 DB의 공고 표를 직접 읽지 않습니다. 공고 정보는 반드시 공고 서버를 거쳐 갑니다.

동그란 점은 공고 서버를 부르는 순간, 네모 점은 사용자가 화면에서 고르는 순간입니다.

조율 · T-C1

① 신청자 입력을 정리한다

  • 웹이 저장한 입력(유형·설립일·아이템·지역·인증·팀·수익모델…)을 조율 LLM이 읽기 좋게 정리합니다.
  • 아직 공고 서버는 부르지 않습니다.
공고 서버 · T-C2 첫 호출

② "지금 공고 데이터 괜찮아요?"

GET /api/collection_status
  • 답이 '정상'이 아니면('지연'·'실패') 조율 쪽은 추천을 아예 하지 않고 후보 0건으로 끝냅니다.
  • 그래서 배치가 하루 밀리거나 서버가 다시 안 켜져 공고가 24시간을 넘기면 추천이 멈춥니다.
공고 서버 · T-C2 둘째 호출

③ "이 신청자에게 맞는 공고 10건"

POST /api/match
  • 보내는 것: 신청자 유형, 설립일, 아이템 설명(이름·한 줄 요약·목표 고객·핵심 기능·키워드를 한 문장으로), 지역, 성별, 인증, 첫 창업 여부, 주 업종, 팀 경력, 수익모델, 채용 계획 유무, 협력사. top=10, offset=0
  • 보내지 않는 것: 대표자 이름, 생년월일, 사업자등록번호, 자기부담금, 희망 사업 규모, 보유 시설
  • 지역은 웹의 17개 시·도를 우리 16개 값으로 바꿔 보냅니다. 광주광역시와 전라남도는 둘 다 전남광주가 됩니다.
  • 우리 서버는 정형 필터 → 의미+단어 검색 → 규칙 재정렬을 거쳐 순위를 매겨 돌려줍니다.
웹 · 화면 3

④ 공고 카드를 보여 준다

  • 1~3위는 큰 카드, 나머지는 목록입니다. 조율 쪽은 순서를 다시 정렬하지 않습니다. 우리 순위가 그대로 화면 순위입니다.
  • 후보가 1건 이상이어야 실행 건이 만들어지고 이 화면으로 옵니다.
공고 서버 · 추가 조회 (선택, 1회)

⑤ "10건 더 보여 주세요"

GET /api/collection_statusPOST /api/match offset=10
  • 11~20위를 받습니다. 누적 20건이 상한입니다.
  • 첫 조회와 겹친 공고는 빼고, content_version(내용 지문)이 달라졌으면 카드에 "내용 바뀜"을 표시합니다.
웹 · 화면 3

⑥ 신청자가 공고 하나를 고른다

  • 이때는 고른 공고 ID만 저장합니다.
공고 서버 · G-01

⑦ "이 공고 자세히 + 이 사람 신청할 수 있어요?"

GET /api/notices/{id}POST /api/notices/{id}/eligibility
  • 먼저 공고 상세(기관·접수기간·모집 상태·지원금 상한·가점 원문·업력 상한)를 받습니다.
  • 사업자인데 설립일이 비었으면 판정 창구를 부르지 않고 "설립일 입력 필요"로 화면 3에 돌려보냅니다.
  • 그 밖에는 유형·설립일·오늘 날짜(한국)만 보내 판정을 받습니다. 확실한 미달이 없으면 통과, 모르는 조건은 통과로 봅니다.
웹 · 화면 5 또는 화면 3

⑧ 통과면 작성 시작, 불통과면 다시 고르기

  • 불통과 공고는 그 실행 건에서 막힙니다(ANNOUNCEMENT_BLOCKED). 추가 조회에서 내용이 바뀌면 풀립니다.
조율 · T-C3 이후

⑨ 우리 공고 정보가 사업계획서 지시문에 들어간다

  • ⑦에서 받은 공고 제목·접수기간·지원금 상한·가점 원문(bonus_info)이 작성 에이전트에게 주는 지시문의 참조 자료로 들어갑니다.
  • 여기서부터는 공고 서버를 더 부르지 않습니다.

가산점 책정 방법

비유하면 도장 찍힌 영수증만 경비로 인정하는 회계 담당자입니다. 공고문에 "여성기업 2점"이라고 또렷이 적혀 있고, 신청자 입력으로 여성기업임을 확인할 수 있을 때만 점수를 더합니다. 조금이라도 애매하면 0점이 아니라 "모름"(null)으로 둡니다. 틀린 점수를 내느니 모른다고 하는 쪽을 택했습니다.

1 · 매일 배치 14단계공고문에서 가점표를 뽑는다AI(LLM)가 가점·우대 문구가 있는 열린 공고의 본문과 첨부를 읽고, 항목·배점·근거 문장·묶음·합계 한도를 공용 DB notice_bonus에 저장합니다.K-Startup은 첨부 공고문을 못 읽어서(robots.txt 금지) 늘 null
2 · 공고 서버가 켤 때근거가 진짜 원문에 있는지 본다AI가 적은 근거 문장이 지금 공고 원문에 그대로 이어져 있어야 합니다. 공고문이 그 뒤 바뀌었으면 그 가점표는 쓰지 않습니다.내용 지문·추출기 버전이 다르면 null
3 · 추천할 때마다신청자 입력과 맞춰 본다항목마다 "해당·해당 아님·모름"을 매기고, 해당이면서 점수가 확인된 묶음만 더합니다. 이 값이 bonus_score입니다.순위에는 반영하지 않음(세기 0)

점수로 인정하는 조건

인정한다
  • 근거 문장에 "N점"이 직접 적혀 있다
  • 근거 문장이 원문에 공백만 다르고 그대로 이어져 있다
  • 여러 인증 중 하나면 되는 가점(예: 벤처·이노비즈·메인비즈 중 하나 10점)은 한 묶음으로 한 번만 센다
모름(null)으로 내린다
  • 근거에 서로 다른 점수가 섞여 있다 ("벤처 각 1점, 여성기업 3점")
  • 표의 떨어진 칸에서 가져온 점수, 숫자만 있는 경우
  • AI가 떨어진 문장 조각을 이어 붙인 근거
  • 입력으로 확인 못 하는 조건 말이 붙음 ("최근 3년 이내", "단,", "~인 경우" 등)
  • 앞으로 할 일이 조건 ("도내로 이전하는 기업", "신규 채용")
  • 묶음을 잘못 나눴거나 잘못 합쳤을 가능성이 있음
  • 세부사업마다 결과가 다름 (어느 세부사업에 낼지 모름)
  • 더한 값이 공고의 합계 한도를 넘음
  • AI가 불확실 메모를 하나라도 남김

숫자·0·null의 뜻

bonus_score뜻언제
숫자 (예: 3)확인된 가산점의 부분합. 받을 수 있는 전체 합계가 아님해당이면서 점수가 확인된 묶음이 있을 때. bonus_items에 항목별 원문 배점이 있고, 그 합과 같음
0해당하는 가점이 없음이 확인됨공고에 가점이 없거나, 모든 항목이 확실히 "해당 아님"
null확인된 것이 없음 · 계산 못 함공고문을 못 읽음(K-Startup 전부), 위 "모름" 조건에 걸림, 모름과 해당 아님만 남음

화면 문구 제안은 "확인된 가산점 +N점(일부)"과 "전체 가산점은 공고문 확인"입니다. 숫자가 실제로 받을 총점보다 작을 수 있기 때문입니다. 근거: docs/business-rules.md 9절, 결정 0012.

연결 뒤에 헷갈리기 쉬운 점

  • 새 공고는 09:20 이후에 보입니다공고 서버는 켤 때 한 번 DB를 메모리에 올립니다. 09:00 배치가 끝나고 09:20 재시작 뒤에야 새 공고가 추천에 나옵니다. 재시작하는 약 10초 동안은 응답이 없습니다.
  • 순위를 고치려면 우리 서버만 고치면 됩니다조율 쪽은 순서를 손대지 않으니, 추천 품질 개선은 전부 우리 쪽 일입니다. 반대로 키·값·오류 코드를 바꾸면 조율 쪽 형식 검사(convert.py)가 깨지므로 먼저 문서로 알려야 합니다.
  • 조율 쪽은 약속한 키만 봅니다우리가 참고용 키(score, rules, pipeline 등)를 더 실어도 괜찮습니다. 하지만 약속한 키가 하나라도 빠지면 형식 오류로 재시도합니다.
  • 판정은 두 군데가 같은 결론이어야 합니다추천의 정형 필터와 자격 판정 창구는 같은 규칙을 씁니다. 추천에 나온 공고가 판정에서 떨어지는 일이 없게 맞춰 두었습니다.
  • 조율 쪽 README는 10/6 오후 기준입니다거기엔 "공고팀이 API를 아직 주지 않음"이라고 적혀 있지만, 창구는 이미 다 열렸고 계약 시험도 통과했습니다.
