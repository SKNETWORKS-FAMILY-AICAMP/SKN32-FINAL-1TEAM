## 1. 판정

**완화 방향과 신규 목록 11건·19개 항목의 배점 대조는 적정하다. 괴산군 117554의 여성기업 10점도 정상 계산된다. 현재 원문 대조 목록 21건·50개 승인 항목에서 이번 탐색 결과와 승인 항목의 불일치를 발견하지 않았다.**

일반 계산 경로에는 **P2 2건**, 대조 문서에는 **P3 1건**이 남았다. P2 두 건은 구성 입력으로 재현한 다른 행 배점의 오인정과 다른 표·일반 문장의 “배점”을 표 머리로 인정하는 문제다. 현재 승인 목록에서 동일한 오배점을 발견했다는 뜻은 아니다. 목록 밖 재현에서는 `bonus_score=10`이어도 `bonus_verified=False`, `bonus_rank_applied=False`였다.

따라서 판정은 **현재 목록 대조 통과, 일반 판정 로직은 추가 보완 필요**다. 결정 0019의 숫자 배점 인정과 기존 기본 세기 0.2·목록에 한정한 화면 사용 결정을 취소할 근거로 해석하지 않는다. 코드·DB·운영 설정은 변경하지 않았다.

정상 가점이 여전히 모름으로 남는 경우도 별도로 기록했다. 기존의 보수적인 정책과 이번 표 경로의 새 결함을 구분했으며, 과잉 모름은 이후 완화 검토 대상으로 제시한다.

## 2. 검증 방법과 범위

### 2.1 직접 수행한 확인

### 2.2 해석 한계

- 단위 시험 16개 건너뜀은 확인하지 않은 범위다. `MYSQL_INTEGRATION_TEST=0`으로 DB 쓰기 통합 시험을 실행하지 않았다.
- 실제 DB 재추출·목록 갱신·배치·배포·서버 기동 및 종료를 하지 않았다.

- 800개는 항목별 최소 입력·둘씩·전체 합침 탐색이다. 모든 신청자 입력의 완전 탐색 또는 사람 정답에 따른 정확도·검색 품질 평가가 아니다.
- 새 11건은 저장된 추출 원문 텍스트와 대조했다. 원본 첨부의 표 좌표·시각적 레이아웃을 전부 다시 확인한 것은 아니다.
- 이번 검수는 실행 중인 조율 화면이나 서버 배포 상태의 확인 결과가 아니다. 화면 관련 확인은 소스·메모리 API 응답 기준이다.

## 4. 지적 사항

### R6-P2-1. 다른 행의 이름을 함께 추출하면 배점의 주인 검사도 통과한다

- 위치: `search/bonus.py:293`의 `table_mates()`, 같은 파일 512~523행의 `points_owned()`.
- 성격: 구성 입력으로 재현. 현재 승인 목록 21건에서 동일 오배점을 발견한 것은 아님.

원문:

```text
배점
여성기업 우대 안내
벤처기업
10
```

추출 근거는 `여성기업 우대 안내 벤처기업 10`이다. 두 항목을 같은 근거에서 추출한 상황을 사용했다.

| 추출 항목 | 종류·인증 | 배점 | group |
|---|---|---:|---|
| 여성기업 | 여성·여성기업 | 10 | g1 |
| 벤처기업 | 인증·벤처기업 | 10 | g2 |

신청자는 여성기업 인증만 보유한다. `verify()`는 두 항목 모두 유지하고, 원문 줄은 `["여성기업 우대 안내","벤처기업","10"]`으로 복구된다. `table_mates`에 두 대상이 모두 있으므로 숫자 앞의 모든 줄을 한 이름으로 합친 검사도 통과한다. 결과는 **여성기업 10점**이다. 그러나 원문에는 여성기업에 대한 10점 배점이 없다.

여성기업 항목만 추출하면 모름으로 막힌다. 반대로 여성기업 항목 하나의 AI 이름을 `여성기업 벤처기업`으로 바꿔도 통과한다. 인증 칸은 여성기업 하나인데, `table_mates()`가 AI 이름 낱말도 사용하는 `subject_words()`를 가져오기 때문에 벤처기업이 확인된 짝처럼 추가된다.

**같은 근거에서 추출됐다는 사실은 같은 표 행이라는 증거가 아니다.** 또한 항목 이름에 다른 자격이 적혔다는 사실만으로 신청자가 확인하는 짝 자격을 인정하면 안 된다.

권고는 표 배점 인정을 유지하면서 이 연결만 보완하는 것이다. 실제 같은 행에 감긴 이름과 다른 행·설명 줄을 구분하고, 짝 자격은 인증·종류 등 확인 가능한 정보와 연결해야 한다. 괴산군의 두 줄 이름·“또는” 설명과 대구 식품박람회의 공통 한 행은 정상 비교 사례로 유지한다.

목록 밖 실제 `match()` 재현은 `bonus_score=10`, `bonus_verified=False`, `bonus_rank_applied=False`였다. 현재 운영 경계에서 즉시 조율 화면·순위를 오염시킨 것으로 분류하지 않으며 P2로 기록한다.

### R6-P2-2. 앞 표나 일반 문장의 “배점”으로 등록번호도 가점이 된다

- 위치: `search/bonus.py:278`의 `score_header()`, 같은 파일 584~592행의 `_table_cell()`.
- 성격: 요청서가 확인을 요구한 1,500자 문맥 경계의 구성 재현.

원문:

```text
평가 항목 배점
사업계획 평가
표 끝
별도 안내
여성기업 등록번호 10
```

추출 항목은 여성기업·인증 여성기업·10점이며, 근거는 `여성기업 등록번호 10`이다. 신청자는 여성기업 인증만 보유한다.

현재 구현은 앞 1,500자 안에 “배점”이 있다는 이유로 `score_header=True`를 부여한다. 근거에는 단위 없는 숫자 하나가 있고 대상 말이 숫자 앞에 있으므로 최종 **여성기업 10점**이 된다. `배점에 관한 문의는 담당자에게 연락\n여성기업 등록번호 10`처럼 표가 전혀 없는 원문도 동일하다.

1,500자라는 길이 자체보다 **그 범위에 있는 “배점”과 현재 근거가 같은 표에 속하는지 확인하지 않는 점**이 원인이다. 숫자에 단위가 없다는 검사도 등록번호·참고 번호를 배점으로 구분하지 못한다.

권고는 모든 숫자 배점을 다시 차단하거나 거리를 일괄 축소하는 것이 아니다. 다른 표 종료·별도 안내·비배점 숫자 문맥을 구분하여 실제 표의 배점 연결만 유지해야 한다. 거리 조정만 하면 긴 정상 표의 뒤쪽 항목도 놓칠 수 있으므로, 정상 회수율도 함께 확인할 필요가 있다.

목록 밖 실제 `match()` 재현은 이 경우에도 `bonus_verified=False`, `bonus_rank_applied=False`였다. 현재 새 11건의 원문 대조에서는 이런 등록번호·다른 표 숫자의 오인정을 발견하지 않았다.

### R6-P3-1. 원문 대조 표의 계산 설명 일부가 실제 코드·DB와 다르다

- 위치: `reports/bonus_boostable_20261008T073942Z/README.md`의 119891·126506 행.
- 성격: 배점 승인 오류가 아니라 검증 기록의 정확성 문제.

1. **119891:** 문서는 “한 행이라 여럿이어도 10”에 이어 “계산은 둘 이상이면 모름”이라고 설명한다. 실제 DB의 세 항목은 모두 `g1`이다. 여성기업·장애인기업, 여성기업·사회적기업, 세 인증 모두 **10점**으로 계산된다. 실제 결과가 원문과 맞으며, 모름이라는 괄호 설명이 틀렸다.
2. **126506:** 문서는 둘 다면 한도 3 초과라 모름이라고 설명한다. 원문에는 최대 3점이 있으나 현재 DB의 `max_total_points`는 null이다. 실제 계산은 `strict=False`에서 4점, 엄격 계산에서는 `selection=True`와 두 묶음 적용으로 모름이다. 현재 반환값이 모름이라는 설명은 맞지만, 코드가 최대 3점 한도를 읽어 차단했다는 설명으로 사용하면 안 된다.

권고는 대조 문서에 원문 배점 판단과 현재 계산 결과·원인을 정확히 구분해서 남기는 것이다. 특히 126506은 이후 완화 때 최대 3점 근거의 저장 여부와 선택 조건의 범위를 확인할 수 있어야 한다. 기존 문서는 이번 검수에서 수정하지 않았다.

## 5. 정상 가점의 과잉 모름 및 알려진 한계

이 절은 이번 변경의 새 오배점 결함이나 결정 0019 위반 목록이 아니다. 정상 항목을 놓치지 않도록 다음 완화 범위를 판단할 자료다.

### 5.1 요청서에 적힌 두 한계

- **119727 부산 빅데이터:** 저장 원문상 부산 본사 5점은 “데이터 분석 고도화 컨설팅 지원” 표에만 있다. 기초 컨설팅·가치평가와 공통으로 인정할 근거는 없다. 현재 부산 입력으로 계산상 5점이 나오지만 목록 밖이며 `reviewed_ok=False`다. 이번 목록에서 제외한 판단은 적정하다. 향후 세부사업 범위를 복구하면 해당 유형의 정상 가점까지 활용할 수 있다.
- **126667 창원:** 원문은 “창원특례시 소재기업(본사, 연구소, 공장)”이다. 현재 경남·창원시 입력에 기업부설연구소 인증이 있어야 5점이 나온다. 본사가 창원이라는 입력으로도 충분할 수 있는데 연구소를 필수로 취급하는 제한은 과잉 모름 후보다. 이번 표 배점 인정에서 새로 만든 지역 규칙은 아니며, 요청서·결정 0019도 알고 있는 제한이다. 연구소 인증을 생략하도록 신청자 데이터를 임의로 고치지 않았다.

### 5.2 실제 DB의 “각 1점” 조합

목록에 있는 **122309**의 원문:

```text
❍ 여성, 장애인, 사회적, 녹색 기업 : 각 1점
```

현재 추출은 여성기업 `g2`, 장애인기업 `g3`, 사회적 기업 `g4`로 나뉜다. 여성기업만 또는 장애인기업만 입력하면 1점이다. **여성기업·장애인기업을 모두 입력하면 모름**, 세 인증을 입력해도 모름이다.

원인은 같은 근거·같은 배점이 다른 묶음에서 반복되면 선택 가점의 중복 추출일 수 있다고 보는 `search/bonus.py:689`의 기존 보호 규칙이다. `strict=False`도 이미 모름이므로 공통 보호 때문에 최종 계산 역시 모름이다.

원문의 “각”은 독립 가점이라는 직접 근거다. 이 사례는 자격이 더 많은 신청자가 확인된 1점조차 잃는 과잉 모름의 구체적인 후보다. **“각 N점”의 독립 항목은 유지하고, “또는·한 행”의 중복 가점은 한 번만 세는 구분**을 다음 완화 검토에 포함할 것을 권고한다. 이번 결정에서 중복 규칙을 변경하지 않았으므로 새 회귀나 운영 중단 사유로 분류하지 않는다.

### 5.3 구성 입력에서 남는 두 누락

| 정상 근거 구성 | 현재 결과 | 원인 |
|---|---|---|
| 표 머리 “배점”, `여성기업 및\n장애인기업 10점`, 같은 group의 두 항목, 여성기업만 입력 | 모름 | “N점”이 있어 새 표 경로를 사용하지 않음. 원문 줄 기준으로 여성기업 줄과 10점 줄이 갈림 |
| 같은 `여성기업 10`이 먼저 표 밖에 나오고 뒤에 실제 배점 표로 다시 등장 | 모름 | 첫 일치만 확인해 뒤쪽 정상 표의 머리를 보지 않음 |

첫 사례는 줄바꿈 배점 연결의 정상 비교 후보이며, 두 번째는 첫 일치를 택하는 설계의 한계다. 둘 다 이번 표 경로를 없애면 해결되지 않는다. 실제 원문과 연결되는 근거 선택을 개선하는 쪽이 목적에 맞다.

`docs/STATUS.md`에 추가된 불확실 메모의 항목별 적용 완화 후보는 이번 검수에서 독립 재현하지 않았다. 이를 완료된 검증이나 승인 목록으로 취급하지 않는다.

## 6. 최소 재현 방법

아래는 DB·코드 파일·결과 폴더를 쓰지 않는 메모리 재현이다. `data-collection`에서 실행한다. 가짜 연결은 기존 시험의 `LoadTests.conn()`을 사용한다.

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:MYSQL_INTEGRATION_TEST = '0'
@'
import json, sys
sys.path.insert(0, 'tests')
from search import bonus
from collect.extract_bonus import verify
from test_bonus import LoadTests, it, req

cases = [
    ('다른 행', '배점\n여성기업 우대 안내\n벤처기업\n10', [
        it('여성', 10, '여성기업', certs=['여성기업'],
           quote='여성기업 우대 안내 벤처기업 10', group='g1'),
        it('인증', 10, '벤처기업', certs=['벤처기업'],
           quote='여성기업 우대 안내 벤처기업 10', group='g2')]),
    ('앞 표 머리', '평가 항목 배점\n사업계획 평가\n표 끝\n별도 안내\n여성기업 등록번호 10', [
        it('여성', 10, '여성기업', certs=['여성기업'],
           quote='여성기업 등록번호 10')]),
    ('정상 표', '가점 항목 배점\n여성기업\n10', [
        it('여성', 10, '여성기업', certs=['여성기업'],
           quote='여성기업 10')]),
]
for label, raw, items in cases:
    data, problems = verify({
        'has_bonus': True, 'max_total_points': None,
        'uncertain': [], 'items': items,
    }, raw)
    connection = LoadTests().conn([
        ('n', 'found', None, data['bonus_info'],
         json.dumps(data['items'], ensure_ascii=False), 'cv', 'v4', '[]'),
    ], notices=[('n', raw, None)])
    entry = bonus.load(connection)['n']
    print(label, problems,
          bonus.score(entry, req(certifications=['여성기업'])))
'@ | ./.venv/Scripts/python.exe -B -X utf8 -
```

현재 결과는 세 경우 모두 여성기업 10점이다. 첫 두 경우는 여성기업의 10점 근거가 없고 마지막은 정상 배점이다. 따라서 동일한 양수 반환이라도 원문 연결의 정확성을 구분해야 한다.

## 7. 변경 보존 확인

검수 시작 때 관련 기존 파일 313개의 해시를 기록했다. 결과 작성 전 비교에서 코드·시험·목록·요청서·기준 문서는 같았으며, `docs/STATUS.md`만 검수 중 외부 변경이 관측됐다. 최신 내용에는 Claude가 추가한 다음 완화 후보가 있었다. 본 검수는 해당 파일을 수정하거나 되돌리지 않았다.

본 검수의 파일 쓰기는 이 결과 문서 하나뿐이다. 기존 수정·스테이징·미추적 파일은 보존했고, 커밋·push·배포를 하지 않았다.
