## 1. 한 일

비유하면 손님(조율 에이전트)이 후보 공고 하나를 고르면 **① 그 공고의 안내문을 내주는 창구**와 **② "이 손님이 이 공고에 신청할 수 있나요?"에 답하는 창구**를 열었습니다.

| 창구 | 하는 일 |
|---|---|
| `GET /api/notices/{notice_id}` | 공고 한 건의 상세. 제목·기관 3개·출처·링크·분류·접수 시작/마감·기간 유형·모집 상태·지원 금액·자격 조건 요약(`eligibility`) |
| `POST /api/notices/{notice_id}/eligibility` | 보내는 값 `{applicant_type, founded_at, today}` → `{passed, failed_conditions, unknown_conditions, business_age_months}` |
| 둘 다 | 공고가 없으면 **HTTP 404 + 본문 `{"code": "NOTICE_NOT_FOUND"}`**. 공고 ID는 퍼센트 인코딩(`kstartup%3A179323`)으로 와도, `/`가 들어 있어도 찾는다 |

### 판정 규칙을 한 곳으로 모았다

요청서가 가장 강조한 조건은 **"자격 판정은 추천의 정형 필터와 같은 규칙"**이다. 추천에 나온 공고를 골랐는데 판정에서 까닭 없이 떨어지면 사용자가 혼란스럽기 때문이다.

그래서 화면용 `/api/eligibility` 안에 있던 판정 코드를 **내용을 바꾸지 않고** `search/eligibility.py`로 옮겼다. 화면용 창구와 새 창구가 이 함수 하나를 함께 부른다. 이 함수는 추천 필터와 같은 부품(`gate._check_age`·`applicant_types.pre_founder`)을 쓴다.

새 창구는 그 결과에서 두 줄만 쓴다.

| 조건 | 판정 | 새 창구에서 |
|---|---|---|
| 지원대상 유형 | 예비창업자만 자동 판정(본문 '불가' 강한 근거 → 불통과, '가능' → 통과, 추정·모름 → 확인 필요). 개인사업자·법인은 늘 확인 필요 | 사용 |
| 업력 | API 업력 칸. **`today` 기준**으로 계산. 본문에 예비창업자 가능이 있으면 본문 우선 | 사용 |
| 접수기간 · 모집 상태 | — | **판정하지 않음**(요청서 2.5) |

- `passed`는 두 조건에 **확실한 미달**이 없으면 참이다. 확인할 수 없는 조건은 통과로 보고 `unknown_conditions`에 넣는다(9/29 결정 "판정 불가 = 통과"와 같다).
- `business_age_months`는 사업자의 업력(개월). 예비창업자, 설립일이 없는 사업자는 `null`.
- 신청자 유형 판정표가 꺼져 있으면(`active` 거짓) 본문 유형을 쓰지 않는다. 추천 필터도 그렇게 한다.
- 형식이 틀린 요청(유형이 세 값 밖, 날짜가 `YYYY-MM-DD`가 아님)은 422.
- 참고용 추가 키 `details`(조건마다 요구·설명)를 준다. 조율 쪽은 쓰지 않는다(표에 없는 키는 무시하는 약속).

### 공고 상세 값의 정의

| 키 | 값 |
|---|---|
| `organizer`·`supervising_org`·`executing_org`·`category`·`url`·`apply_url` | DB 값. 빈 문자열은 `null` |
| `apply_start`·`apply_end` | `YYYY-MM-DD` 또는 `null` |
| `recruitment_status` | `open`·`closed`·`unknown`. 그 밖의 값은 `unknown` |
| `support_amount_max_won` | 첨부 공고문에서 LLM이 뽑고 근거 문장과 대조한 금액(`notice_conditions.amount_max_won`, 버린 값 제외). 0은 쓰지 않고 `null` |
| `support_amount_text` | **`null`** — 공고 원문의 금액 표기를 따로 저장하지 않는다. 근거 문장은 참고용 추가 키 `support_amount_evidence`로 준다 |
| `bonus_info` | `null` — 03에서 채운다 |
| `eligibility.applicant_types` | 세 유형 중 **유형만으로 확실히 안 되는 것**을 뺀 목록. 예비창업자는 위 판정에서 불통과면 빼고, 사업자 둘은 업력 칸이 '예비창업자'만일 때 뺀다 |
| `eligibility.business_age_max_months` | API 업력 칸의 상한(개월). 칸을 읽지 못했으면 `null` |
| `eligibility.parsed` | API 업력 칸을 읽었는지. 거짓이면 상한 `null`은 "제한 없음"이 아니라 "모름" |

조율 쪽 실제 연결은 이 상세 값을 **선택 공고에 담아 두기만** 하고, 판정은 자격 판정 창구 결과를 쓴다(조율 코드 `agents/notice/g01.py` 확인).

## 4. 알아 둘 점 (05 답변서에 넣을 것)

- **사업자(개인사업자·법인)는 모든 공고에서 "지원대상 유형"이 확인 필요로 나온다.** 개인·법인 구분은 자동 판정하지 않기 때문이다(9/28 결정 — LLM 추출 신뢰도 문제). 그래서 조율 쪽 화면에는 사업자 신청자에게 늘 "자격요건 자동 확인이 어렵습니다" 안내가 뜬다. 바꾸려면 개인·법인 판정을 켜는 별도 결정이 필요하다.
- 업력 칸을 읽은 공고는 527건(19%)뿐이다. 기업마당은 업력 칸이 없어 대부분 "업력" 확인 필요다.
- `support_amount_text`는 `null`이다. 지원 금액이 있는 공고는 849건(31%)이고 K-Startup은 첨부가 없어 0건이다.
- 이 PC의 8000 서버는 옛 코드다. 새 창구를 쓰려면 다시 켜야 한다(사용자 확인 후).
