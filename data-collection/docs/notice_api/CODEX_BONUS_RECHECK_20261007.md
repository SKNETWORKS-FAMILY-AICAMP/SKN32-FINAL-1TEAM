## 1. 판정 근거

지정된 개선은 상당 부분 동작한다. 단위 시험은 실패 없이 통과했고, 모집 종료 공고를 제외한 1,741건에 대한 네 신청자 유형의 집계도 요청서와 일치했다. 그러나 양수 반환 건수의 감소는 남은 점수의 정확성을 보증하지 않는다.

다른 항목의 `N점`이 `quote` 안에 포함되거나, AI가 선택 조건을 다른 `group`으로 분리한 경우에 잘못된 양수 점수가 반환된다. 실제 DB에서도 상한 불확실성을 명시한 공고가 8점을 반환한다. 따라서 현재 결과를 “확실한 가산점 합계”로 화면에 표시하는 승인은 보류한다.

지적은 **P1 3건, P2 3건, P3 1건**이다. P1은 화면 표시 전에 해소할 점수 정확성 문제, P2는 조건 판단·계약·동시 실행 문제, P3는 현재 동작과 설명의 불일치다. 이 등급은 이번 검수의 분류이며 앞선 검수 건수와 합산하지 않는다.

| 식별자 | 등급 | 문제 | 근거 유형 |
|---|---|---|---|
| B-P1-1 | P1 | `N점`의 존재만 확인하여 다른 항목의 점수를 승인 | 추출기 검증부터 계산까지 재현 |
| B-P1-2 | P1 | 잘못 분리된 `group`을 신뢰하여 선택 가점을 중복 합산 | 이전·현재 계산 비교 재현, 실제 DB의 반대 방향 오분류 확인 |
| B-P1-3 | P1 | 상한 불확실성을 기록한 실제 공고에서도 양수 합계를 확정 | 실제 DB·첨부 추출 원문 대조 |
| B-P2-1 | P2 | 추가 조건이 비어 있으면 기간·복수 소재지 조건을 확인하지 않고 점수 부여 | 실제 DB 및 재현 |
| B-P2-2 | P2 | 확인된 부분합과 조율 계약의 신청자별 총합계를 구분하지 못함 | 조율 요청서·현재 코드·재현 |
| B-P2-3 | P2 | 호출 기록의 원자적 교체만으로 동시 실행의 하루 상한을 보장하지 못함 | 실제 기록 함수와 가짜 호출을 이용한 재현 |
| B-P3-1 | P3 | 현재 계산보다 넓게 설명하거나 이전 계산 설명이 남아 있음 | 코드 설명·요청서·답변서 대조 |

## 2. 검증 조건과 결과

### 2.1 단위 시험

`data-collection/`에서 실행했다.

```powershell
$env:MYSQL_INTEGRATION_TEST='0'
$env:PYTHONDONTWRITEBYTECODE='1'
.\.venv\Scripts\python.exe -B -X utf8 -m unittest discover -s tests
```

종료 코드 0. 전체 **778개 중 762개 통과, 16개 건너뜀, 실패 0, 오류 0**이다. 출력 집계는 같은 `unittest` 발견·실행 경로를 메모리 스트림으로 다시 실행하여 확인했다. 건너뛴 16개는 검증 완료로 계산하지 않는다. 실제 MySQL 통합 시험은 켜지 않았다.

추가 재현은 기존 시험 파일에 추가하지 않았다. `extract_bonus.verify()` 및 `bonus.score()`를 직접 호출한 메모리 입력과 임시 호출 기록만 사용했다. `ask()`·`_client()`·DB 저장은 실행하지 않았다.

### 2.2 실제 DB 비교

공용 DB에서 현재 내용 지문 2,825건을 읽었고, 지문 및 추출기 버전이 일치하는 가점 행 2,077건을 사용했다. 추출기 버전은 `extract_bonus/v4 gpt-5.6-luna medium`이다. 기준일은 `2026-10-07`로 고정했다.

비교 모집단은 `eval.bonus_conservative_compare.open_ids()`와 같은 조건, 즉 `recruitment_status <> 'closed'`이고 접수 마감일이 없거나 기준일 이후인 공고 1,741건이다. 이는 신청자별 모든 자격·지역 필터를 통과한 추천 후보 수를 의미하지 않는다.

이전 계산은 위 HEAD의 `search/bonus.py`를 별도 메모리 모듈로 읽었고, 현재 계산은 작업 폴더의 모듈을 사용했다. 같은 DB와 같은 지문·버전 필터에서 비교했다. 평가 도구의 결과 저장 함수 `run()`은 실행하지 않았다.

## 3. P1 지적

### B-P1-1. 점수가 해당 조건의 배점인지 확인하지 않음

**위치:** `search/bonus.py:190`~`196`; 관련 검증 경로 `collect/extract_bonus.py:336`~`370`, `392`~`437`.

`points_supported()`는 해당 수치의 `N점`이 `quote` 어디에든 있는지만 검사한다. 조건과 점수의 연결을 검사하지 않으므로 다음 입력이 추출기의 검증을 오류 없이 통과하고 여성기업에 10점을 반환한다.

| 원문 | 저장될 수 있는 항목 | 현재 결과 | 원문으로 확인되는 점수 |
|---|---|---|---|
| `여성기업 가점 2점. 벤처기업 가점 10점.` | 여성기업, points=10, quote=원문 전체, points_source=null | 여성기업 인증만으로 10점 | 여성기업 2점 |
| 같은 원문 | 여성기업, points=10, quote=`여성기업 가점 10점`, points_source=null | 여성기업 인증만으로 10점 | 여성기업 2점 |

두 번째 입력은 `locate_all()`의 순서 보존 재구성 경로로 승인된다. 중간의 `2점. 벤처기업`을 건너뛰어 근거 문장을 재구성할 수 있고, 검증은 매칭된 넓은 원문 구간의 숫자를 확인한다. 이후 계산은 재구성된 quote의 `10점`을 확인하므로 두 검사를 모두 통과한다. 두 재현의 `verify()` 문제 목록은 `[]`였다.

이는 이번에 추가한 “다른 배점은 points_source로 들어온다”는 시험만으로 잡히지 않는다. 실제 DB 발생 빈도를 주장하는 것이 아니라 현재 저장·소비 경로가 잘못된 양수를 허용한다는 재현이다.

**요구 사항:** 숫자의 존재와 해당 조건의 배점을 구분해야 한다. 원문 내 조건·배점의 연결 및 quote 재구성의 의미 보존을 확인할 수 없는 입력은 null로 내려야 한다. 재추출 없이 계산만 줄이려면 여러 배점이 섞인 근거나 재구성 여부를 확인할 수 없는 근거를 안전하게 채택할 범위를 제한해야 한다.

### B-P1-2. group 오분류가 선택 가점의 중복 합산으로 이어짐

**위치:** `search/bonus.py:234`~`258`, `261`~`281`.

원문 `벤처, 이노비즈, 메인비즈 기업 : 10점`을 벤처기업 `g1`, 이노비즈 `g2`로 잘못 추출하고 두 인증을 보유한 신청자를 넣었다. quote·points·points_source는 정상 형태이며 `verify()`는 문제를 보고하지 않았다.

| 계산 | 결과 |
|---|---|
| 이전 HEAD | 10점, 항목 1개 |
| 현재 | **20점**, 벤처기업 10점 + 이노비즈 10점 |
| 원문에서 인정되는 선택 가점 | 인증 여러 개를 보유해도 10점 |

같은 quote에 대한 일괄 병합을 제거하면서 독립 가점 사례는 개선됐지만, 선택 관계의 진위를 AI가 준 group에 계속 의존한다. `max_total_points=null`, `uncertain=[]`이면 현재 계산에는 이를 막는 장치가 없다.

반대 방향의 실제 오분류도 남아 있다. `123858`의 원문은 `벤처·이노비즈·메인비즈 각 1점, 여성기업 3점`인데 세 인증은 여전히 같은 `g1`이다. 네 인증을 모두 보유해도 현재 4점이며 원문의 항목 배점을 각각 더한 값은 6점이다. 실제 `122309`도 `여성, 장애인, 사회적, 녹색 기업 : 각 1점`을 같은 group으로 저장했다. 벤처·여성·장애인·사회적기업을 보유한 입력은 4점을 반환하며 해당 문장의 항목 배점 합은 6점이다. 이 두 사례는 과소 합산이며 20점 재현과 구분한다.

**요구 사항:** “또는·택1인 선택 조건”과 “각 N점인 독립 조건”을 구분하거나, group과 원문 관계를 확정할 수 없는 경우 null로 내려야 한다. 같은 quote를 모두 다시 병합하는 방식은 `123858`의 이번 개선을 되돌리므로 적절하지 않다.

### B-P1-3. 상한이 없다는 것과 상한을 확인하지 못했다는 것을 구분하지 않음

**위치:** `search/bonus.py:61`~`63`, `281`~`284`, `295`~`304`.

실제 공고 `bizinfo:PBLN_000000000117356`, **[전북] 2026년 중소기업육성자금 융자 지원계획 공고**에서 확인했다.

```text
status = found
max_total_points = null
uncertain = ["평가기준의 ‘가점(5점)’이 가점 합계 한도인지 여부가
              명시적으로 확인되지 않아 max_total_points를 null로 처리함"]

여성기업·벤처기업·경기 성남시 입력:
bonus_score = 8
bonus_items = 여성기업 5점 + 벤처기업 확인기업 3점
```

활성 첨부의 추출 원문에는 기존기업·창업기업 등의 평가표가 있고, 가점 영역은 반복해서 `가점(5점) … 가점대상 참조 5 총 점 105`로 표시된다. 여성기업 5점과 벤처기업 3점은 그 아래의 가점 대상에 속한다. 적어도 합계 상한을 확정하지 못했다고 기록한 상태에서 8점을 확정할 근거는 부족하다.

이 불확실 문장은 `GAP_WORDS` 및 `DUP_WORDS`에 걸리지 않는다. `cap is not None`일 때만 초과 검사를 하므로 상한 확인 실패가 사실상 상한 없음처럼 처리된다. 같은 유형의 수정 공고 `126642`는 저장 한도가 5여서 여성기업·벤처기업 입력에 null을 반환한다. 이번 검수는 이전 공고의 DB 한도를 5로 고치거나 점수를 5로 잘라야 한다고 요구하지 않는다. 현재 결정에 따른 안전한 반환은 null이다.

불확실 표현의 미탐도 별도 재현했다. `uncertain=["가점표를 파악하지 못했음"]`은 현재 GAP 정규식에 걸리지 않아 벤처기업 3점을 반환한다. 따라서 불확실성 처리는 현재 단어 목록만으로 완결되지 않는다.

**요구 사항:** 한도·합산 가능성·읽기 완전성을 확인하지 못했다는 기록이 있으면 양수 합계를 확정하지 않아야 한다. AI 자유 문장의 몇 단어가 없다는 사실을 확정 근거로 사용할 수 없다. 보수 축소 방침에서는 안전한 사유로 분류되지 않은 불확실 기록을 null로 처리하는 방법도 가능하다.

## 4. P2 지적

### B-P2-1. 미래 조건 외의 추가 요건은 여전히 빠질 수 있음

**위치:** `search/bonus.py:141`~`164`, `176`~`181`, `220`~`224`.

`extra_conditions`가 비어 있을 때 미래 조건 단어만 추가로 검사한다. 그러나 조건 누락은 미래 표현에 한정되지 않는다.

실제 `117356`에 다음 항목이 있다.

```text
quote = "전북특별자치도 안에 본사 및 사업장(생산공장)모두를 두는 기업(5점)"
kind = 지역, regions = [전북], extra_conditions = null
```

`region=전북`, `district=전주시`, 인증 없음이라는 입력만으로 5점을 반환한다. 입력에는 본사와 생산공장이 모두 전북에 있는지 확인할 정보가 없다. `regions`가 같다는 사실만으로 복수 소재지 요건을 충족했다고 단정한다. 여성기업·벤처기업까지 추가한 같은 지역 입력은 해당 5점까지 더하여 13점이다. 상한 문제는 B-P1-3, 이 추가 5점의 자격 확인 문제는 본 지적이다.

메모리 재현에서도 `최근 3년 이내 벤처기업 확인을 받은 기업은 가점 3점`을 `extra_conditions=null`로 추출하면 벤처기업 인증만으로 3점을 반환한다. 확인을 받은 시점은 신청자 입력에 없으므로 확정할 수 없다. 추출기 검증의 문제 목록도 `[]`였다.

**요구 사항:** 인증·지역 일치만으로 확인되지 않는 기간, 복수 소재지, 역할, 제외 대상 등의 조건이 원문에 있으면 null이어야 한다. `extra_conditions`가 비어 있다는 사실을 추가 요건이 없다는 근거로 사용하면 안 된다.

### B-P2-2. 부분합을 총합계로 해석할 수 있는 계약 상태

**위치:** `search/bonus.py:265`~`288`; 조율 요청서 3.2; `docs/business-rules.md:154`; `docs/contracts.md:56`~`57`; `docs/notice_api/05_reply/README.md:130`.

현재 구현은 점수가 확인되는 묶음이 하나라도 있으면, 다른 묶음이 unknown이어도 그 묶음의 합을 반환한다. 여성기업 2점과 직원 10명 이상 3점이 있는 공고에서 여성기업 인증만 확인된 입력은 2점과 여성기업 항목만 반환한다. 이는 현재 요청서의 부분합 정의와 일치한다.

그러나 조율 요청서 3.2는 `bonus_score`를 “이 신청자가 그 공고에서 받을 수 있는 가산점 합계”로 정의한다. 응답에는 누락·미확인 묶음이 있다는 표시가 없다. 받는 쪽은 같은 `2 / [{여성기업, 2}]`가 확정 총점인지 일부 확인값인지 구분할 수 없다. 항목의 합이 숫자와 맞는다는 형식 검증으로 이 차이는 발견되지 않는다.

**요구 사항:** 화면 표시 전에 아래 두 방식 중 계약을 정해야 한다. 재추출은 필요하지 않다.

1. 총합계 의미를 유지한다면, 총합에 영향을 줄 수 있는 unknown 묶음이 있는 공고는 null로 반환한다.
2. 부분합을 유지한다면, 조율 답변서·계약·화면 표기를 함께 “확인된 가산점 부분합”으로 명시한다. 미확인 항목은 제외되며 실제 총점이 다를 수 있다는 안내가 필요하다. 계약 의미 변경을 조율 담당에게 전달하고 확인해야 한다.

부분합을 유지할 경우의 전달 문안 초안은 다음과 같다. 이 문안은 본 검수에서 전송하지 않았다.

> `bonus_score`는 전체 가산점의 확정 총합이 아니라, 현재 신청자 입력으로 충족 여부와 배점을 확인한 항목의 부분합입니다. 미확인 항목은 합산하지 않습니다. 화면에는 “확인된 가산점(부분합)”으로 표시하고 전체 가산점은 공고문 확인이 필요하다고 안내해 주십시오. 순위 반영 기본값은 0입니다. 화면 사용 가능 여부는 점수 정확성 재검수 완료 후 별도로 알리겠습니다.

이 설명만으로 B-P1-1~3을 해결할 수는 없다. 잘못된 배점·중복·상한 초과가 섞이면 그 값은 안전한 부분합도 아니다.

### B-P2-3. 동시 실행에서는 잔여량 확인과 예약이 분리되어 있음

**위치:** `collect/extract_bonus.py:620`~`632`, `646`~`657`, `673`~`685`.

단일 실행에서 손상 기록을 차단하고 완성된 임시 파일을 교체하는 동작은 확인했다. 하지만 `_daily_used()`로 잔여량을 읽는 과정과 `_daily_add()`로 호출량을 기록하는 과정에 공통 잠금 및 잔여량 재검사가 없다.

운영체제 임시 폴더의 실제 기록 파일과 실제 `run_batch()`·`_daily_add()`를 사용하고, DB·LLM 작업인 `run_full()`만 가짜로 바꾸어 재현했다.

```text
시작 기록: 2026-10-07 = 250
하루 상한: 300
실행 A가 읽은 잔여량: 50
실행 B가 읽은 잔여량: 50
가짜 실행 A·B가 예약한 수: 각 50
최종 기록: 350
실제 API 호출: 0
```

재현에서는 기록 쓰기를 의도적으로 직렬화했다. 고정 `.tmp` 파일의 쓰기 충돌을 제외해도 오래된 잔여량을 그대로 예약하여 상한을 넘는다는 뜻이다. 쓰기 자체를 동시에 하면 같은 `path + '.tmp'`를 공유하는 추가 경합도 가능하다. 그 파일 경합은 정적 확인이며 이번 재현에서 파일 손상을 실제로 일으킨 것은 아니다.

**현재 운용 경로의 완화 요인:** `collect/daily_pipeline.py:216`의 `job_lock.acquire(LOCK)`은 같은 작업 폴더의 전체 배치 중복 실행을 막는다. 따라서 이 재현을 “현재 예약 배치에서 실제 상한 초과가 발생했다”는 주장으로 해석하면 안 된다. 외부 잠금을 반드시 거치는 단일 작업 폴더의 실행은 이 잠금의 보호를 받는다. 호출 기록 함수 및 `run_batch()` 자체가 동시 실행을 보호한다는 주장은 성립하지 않는다.

**요구 사항:** 잔여량 확인·호출량 확정·기록 반영을 같은 잠금 범위에서 처리하거나, 이 함수를 호출하는 모든 경로가 동일한 외부 잠금을 거친다는 계약을 강제해야 한다. 임시 파일 교체의 원자성은 중복 예약 방지를 대신하지 못한다.

## 5. P3 지적 및 판단 단어의 범위

### B-P3-1. 설명과 현재 동작을 일치시킬 필요

**위치:** `search/bonus.py:21`~`37`, `43`, `311`~`317`; 재검수 요청서 1절; `docs/notice_api/05_reply/README.md:130`.

## 6. 주요 메모리 재현 입력

아래는 실제로 실행한 점수 재현의 핵심 코드다. 저장소에 이 코드를 파일로 추가하지 않았다. `verify()`를 거친 결과를 사용하여 계산 함수에 임의로 검증 불가능한 항목을 직접 넣은 재현과 구분했다.

```python
from collect import extract_bonus as e
from search import bonus
from eval.bonus_conservative_compare import applicant

def it(kind, name, points, quote, certs, group='g1'):
    return dict(kind=kind, name=name, points=points, quote=quote,
                certs=certs, regions=[], detail=None, group=group,
                program=None, points_source=None, extra_conditions=None)

def run(doc, items, req, uncertain=None):
    raw = dict(has_bonus=True, max_total_points=None, bonus_info=None,
               items=items, uncertain=uncertain or [])
    verified, problems = e.verify(raw, doc)
    return problems, bonus.score(verified, req)

doc = '여성기업 가점 2점. 벤처기업 가점 10점.'
women = applicant(certifications=['여성기업'])
print(run(doc, [it('여성', '여성기업', 10, doc, ['여성기업'])], women))
print(run(doc, [it('여성', '여성기업', 10,
                   '여성기업 가점 10점', ['여성기업'])], women))
# 두 경우 모두 problems=[]; 현재 10점 반환

doc = '벤처, 이노비즈, 메인비즈 기업 : 10점'
print(run(doc, [it('인증', '벤처기업', 10, doc, ['벤처기업'], 'g1'),
                it('인증', '이노비즈', 10, doc, ['이노비즈'], 'g2')],
          applicant(certifications=['벤처기업', '이노비즈'])))
# problems=[]; 현재 20점 반환. 같은 입력의 이전 HEAD 계산은 10점

doc = '최근 3년 이내 벤처기업 확인을 받은 기업은 가점 3점'
print(run(doc, [it('인증', '벤처기업', 3, doc, ['벤처기업'])],
          applicant(certifications=['벤처기업'])))
# problems=[]; 확인 시점을 모르는데 현재 3점 반환

doc = '여성기업 가점 2점; 직원 10명 이상 기업 3점'
print(run(doc, [it('여성', '여성기업', 2, '여성기업 가점 2점', ['여성기업']),
                it('고용', '직원 10명 이상 기업', 3,
                   '직원 10명 이상 기업 3점', [], 'g2')], women))
# problems=[]; 직원 수는 unknown이지만 현재 여성기업 부분합 2점 반환
```

동시 호출 기록 재현의 핵심 코드는 다음과 같다. `run_full`은 호출량 예약 콜백만 실행하는 가짜 함수다.

```python
import json, os, tempfile, threading
from concurrent.futures import ThreadPoolExecutor
from unittest.mock import patch
from collect import extract_bonus as e

with tempfile.TemporaryDirectory(prefix='codex_bonus_review_') as td:
    path = os.path.join(td, 'calls.json')
    day = '2026-10-07'
    with open(path, 'w', encoding='utf8') as f:
        json.dump({day: 250}, f)
    barrier, write_lock = threading.Barrier(2), threading.Lock()

    def fake_full(limit=None, say=None, report=None, on_calls=None):
        barrier.wait(timeout=5)  # 양쪽 실행이 잔여량을 읽은 뒤 예약
        with write_lock:
            on_calls(limit)
        return dict(called=limit, no_mention=0, saved=0, failures=[],
                    cost_usd=0, left=0)

    with patch.object(e.config, 'get', return_value='mock-key'), \
         patch.object(e, '_today_kst', return_value=day), \
         patch.object(e, 'run_full', side_effect=fake_full):
        with ThreadPoolExecutor(max_workers=2) as ex:
            results = list(ex.map(
                lambda _: e.run_batch(limit=300, say=lambda *_: None,
                                       daily_file=path), range(2)))
    print([r['called'] for r in results], e._daily_used(day, path))
    # [50, 50] 350 — 실제 DB 작업·API 호출 없음
```

## 7. 승인 조건 및 미실행 범위

재추출이나 DB 변경 없이 계산을 더 보수적으로 제한하는 방향으로 개선할 수 있다. 이번 검수는 재추출을 요구하거나 허가하지 않는다.

화면 표시를 승인하려면 다음을 확인해야 한다.

1. B-P1-1~3의 재현이 확정 양수 대신 null로 처리되거나, 원문과 입력으로 정당한 배점임이 검증된다.
2. B-P2-1의 추가 요건을 확인하지 못한 항목은 채택되지 않는다.
3. `bonus_score`의 총합계·부분합 의미와 화면 문구를 조율 계약에 명시한다.
4. 일일 호출 상한의 잠금 보장 범위를 정하고, 해당 동시 실행 경로를 검증한다.
5. 현재 배점 의미와 세부사업 반환 조건을 문서에 반영하고 관련 시험을 다시 실행한다.

이번에 하지 않은 작업은 다음과 같다.

| 작업 | 사유 |
|---|---|
| 가점 재추출·유료 API 호출·DB 쓰기 | 검수 범위 밖이며 사용자 요청에서 제외 |
| 운영·시험 서버 재시작, 배포, AWS 변경 | 검수 범위 밖 |
| 현재 서버에 대한 전체 HTTP 계약 시험 재실행 | 이번 검수는 계산 정확성과 호출 기록 보호를 검증함. 요청서의 16/16·2,825건 형식 오류 0은 Claude의 기존 실행 보고이며 이번 독립 실행 결과로 계산하지 않음 |
| MySQL 통합 시험 16개 | `MYSQL_INTEGRATION_TEST=0`; 실제 DB 점수 대조는 별도의 SELECT 검수로 수행 |
| 벡터 저장소 변경·검색 품질 평가 | 현재 요청의 대상이 아님. 전체 단위 시험에 포함된 시험 통과가 별도 기능 승인까지 의미하지 않음 |
| 조율 담당에게 메시지 전송 | 본 문서에 전달 문안만 작성 |
| STATUS·WORKLOG·문서 지도·미해결 목록 갱신 | “결과 파일만 작성”이라는 사용자 요청을 우선하여 이 문서에만 기록 |

검수 시작 시 기록한 관련 `.py`·`.md`·`.sql` 239개 파일의 SHA-256 대조에서 기존 파일 변경이 없음을 확인했다. 기존 미커밋·미추적 변경은 보존했다. 결과 문서 외의 저장소 파일 추가·수정, Git 스테이징·커밋·push는 수행하지 않았다.
