## 1. 판정

**3차 지적 4건의 기존 재현 경로는 수정된 것을 확인했다. 현재 원문 대조 목록 10건·31개 항목에서는 배점 오류를 발견하지 않았다. 추가 확인에서 P2 3건·P3 1건이 남았다.**

목록 밖 공고, 공고 내용 지문 불일치, 가점 행 지문 불일치, 승인 밖 항목은 순위 반영을 차단하는 구조다. 현재 DB에서 시험한 800개 입력 조합 중 양수가 나온 100개 조합은 모두 목록의 10건 안에 있었고, 각각의 결과 항목도 승인 항목 안이었다.

다만 다음 세 가지는 추가 보완이 필요하다.

- 점수가 없는 `*` 설명 줄을 앞줄에 붙이면, 설명에 등장한 다른 대상이 앞줄 점수의 주인으로 인정된다.
- 목록의 `points` 자료형이 잘못돼도 읽기를 통과한다. 해당 공고가 검색 후보에 들어오면 순위 기능만 꺼지는 대신 HTTP 500이 발생한다.
- 첨부 파일 바이트가 같고 추출 텍스트만 바뀐 경우, 대조 목록이 사용했던 증거의 변경을 지문 두 개로 감지하지 못한다. 구성 시험에서는 추가 자격 조건이 새로 보이는 텍스트로 바뀐 뒤에도 점수·순위 반영이 유지됐다.

화면은 순위 미반영 이유를 목록 밖으로 단정하는 문제가 별도로 있다.

**검수 판정은 추가 보완 필요다.** 결정 0017에 기록된 기본 세기 0.2 운영 결정을 취소하거나 설정을 변경하지 않았다. 현재 목록에서 즉시 잘못된 배점을 반환한다고 결론 낼 근거도 발견하지 않았다. 표시 정확성 전체와 “증거가 바뀌어도 미확인 점수가 순위를 올릴 수 없다”는 일반 보장은 통과 판정을 내리지 않는다.

## 3. 지적 사항

### R4-P2-1. 점수가 없는 별표 설명을 붙이면 다른 대상에 앞줄 점수를 인정한다

- 위치: [search/bonus.py:234](../../search/bonus.py#L234), `quote_lines()`의 줄 합치기.
- 관련 위치: `points_owned()` 434~446행.
- 성격: 구성 입력으로 재현. 현재 목록 10건에서 동일 오류를 발견한 것은 아니다.

원문:

```text
벤처기업 가점 10점
* 여성기업 우대 안내
```

추출 항목은 이름 `여성기업`, 종류 `여성`, 인증 `여성기업`, 배점 10이고 근거는 두 줄 전체다. 신청자는 여성기업 인증만 보유한다.

`verify()`는 원문에 있는 두 줄을 한 줄 근거로 저장한다. `quote_lines()`는 두 번째 줄에 점수가 없다는 이유로 첫 줄과 합친다. 합친 조각이 하나가 되면 반환값이 None이므로 `quote_lines` 칸도 붙지 않는다. `points_owned()`는 평탄화된 근거에서 “10점”과 “여성기업”이 함께 있는 것으로 보고 통과한다.

| 확인 | 결과 |
|---|---|
| 추출 검증의 버린 이유 | 없음 |
| `in_document` | True |
| `quote_lines` | 없음 |
| `bonus_score` | 10.0 |
| `bonus_items` | 여성기업 10.0 |
| 목록 밖으로 실제 match 실행 | 표시 10.0, 순위는 그대로, `bonus_rank_applied=False` |

“배점이 있는 별표 줄”을 분리한 기존 수정은 작동한다. 그러나 “배점이 없는 별표 줄”도 앞줄의 인증을 설명한다는 보장이 없으므로, 점수 존재 여부만으로 무조건 합치면 다른 대상을 앞줄 배점의 주인으로 만들 수 있다.

**권고:** 별표 설명의 대상이 앞줄 항목의 정의·별칭임을 확인할 수 있는 경우로 연결 범위를 제한하거나, 연결을 확인하지 못하면 점수를 모름으로 남길 필요가 있다. `127009`의 “혁신형 중소기업 / 1점 / * 이노비즈, 메인비즈, 벤처기업”은 정상 연결 사례로 유지하면서, 위 다른 대상 사례를 구분하는 검증이 필요하다.

목록이 비어 있는 재현에서는 순위 영향이 차단됐다. 따라서 이번 지적은 기존 3차의 P1과 동일하게 분류하지 않고, 현재 운영 경계 아래에서 남은 표시·대상 연결 결함인 P2로 분류한다.

### R4-P2-2. 잘못된 목록 배점이 읽기를 통과하고 검색 요청을 HTTP 500으로 만든다

- 위치: `search/bonus.py` 680~682행, `load_reviewed()`의 승인 항목 검증.
- 관련 위치: 같은 파일 694행, `reviewed_ok()`의 `float(i['points'])`; `search/app.py` 498~499행.
- 성격: 잘못된 설정 파일을 가정한 장애 경로. 현재 저장소 목록의 배점 자료형은 정상이다.

목록 항목의 필수 키 존재만 검사하므로 다음 값 모두 읽기에 성공한다.

```json
{"name": "여성기업", "points": "오점"}
```

`points: null`과 `points: {}`도 같은 문제가 발생한다. 내용 지문·행 지문이 현재 값과 맞고 해당 공고에서 양수가 계산되면, 승인 집합을 만들 때 ValueError 또는 TypeError가 발생한다. `boot()`의 목록 읽기 예외 처리 이후에 발생하는 오류이므로 `boot_errors.bonus_reviewed`를 남기고 기능을 끄는 경로를 타지 않는다.

| 입력 배점 | 목록 읽기 | 실제 match 결과 |
|---|---|---|
| `"오점"` | 성공 | ValueError |
| `null` | 성공 | TypeError |
| `{}` | 성공 | TypeError |
| `"오점"` + FastAPI 요청 | 성공 | HTTP 500, Internal Server Error |

결정 0017의 “파일이 없거나 깨지면 목록 전체 미사용, 순위 반영 0건”은 JSON 문법 오류와 일부 구조 오류에서는 확인됐지만, 배점 자료형 오류까지 충족하지 못한다.

**권고:** 읽는 시점에 이름·배점의 자료형과 유한한 양수 여부를 검증해 잘못된 목록을 전체 거부하고, 요청 중에도 목록 값 때문에 전체 검색이 실패하지 않도록 처리할 필요가 있다. 기존 정상 검색·가산점 표시가 계속되는지도 확인해야 한다.

### R4-P2-3. 첨부 추출 텍스트가 바뀌어도 대조 당시 증거와 같다고 판단한다

- 위치: `search/bonus.py` 143~152행, `row_fingerprint()`; 686~696행, `reviewed_ok()`.
- 관련 위치: `search/content_version.py` 48~56·70~85행, `search/bonus.py` 159~178행.
- 성격: 첨부 재파싱·추출 개선 시의 증거 변경을 구성 입력으로 재현. 현재 10건의 첨부가 실제로 변경됐다는 뜻은 아니다.

내용 지문은 공고 본문과 **첨부 파일 바이트 SHA-256**을 사용한다. 첨부의 `extracted_text`는 포함하지 않는다. 가점 행 지문은 상태·한도·items·uncertain만 포함한다. 반면 점수 계산과 원문 대조에는 `extracted_text`를 사용한다.

같은 파일을 재파싱하거나 추출기를 개선하여 글자가 더 읽히거나 줄 구조가 달라져도, 파일 바이트와 저장된 가점 행이 같으면 두 지문이 유지된다. `collect/attachment_store.py` 152~160행도 성공 재추출 시 텍스트·추출기 버전·파일 지문을 저장하며, 파일 바이트 지문이 같다는 이유로 텍스트 갱신을 막지 않는다.

가짜 DB의 공고 본문·첨부 SHA-256·가점 행을 고정하고, 첨부 추출 텍스트만 다음과 같이 바꿨다.

대조 당시 텍스트:

```text
여성기업 가점 5점
```

재추출 후 새로 보이는 텍스트:

```text
여성기업 가점 5점
※ 해당 가점은 대통령 표창장 보유 기업에만 적용
```

대조 목록에는 처음 텍스트에서 확인한 여성기업 5점을 기록했다. 신청자는 여성기업 인증만 보유한다. 실제 `content_version.load()` → `bonus.load()` → `match()` 실행 결과:

| 확인 | 결과 |
|---|---|
| 전후 내용 지문 | 같음 |
| 전후 가점 행 지문 | 같음 |
| 기존 근거 원문 포함 | True |
| 재추출 후 점수 | 5.0 |
| `reviewed_ok` | True |
| 가짜 검색 후보 순서 | a → n |
| 가산점 반영 후 | n → a |
| n의 `bonus_rank_applied` | True |

새로 읽힌 조건은 근거 문장 밖에 있고 현 기간 각주 검사 대상도 아니므로 점수 계산만으로 차단되지 않았다. 이 사례는 계산 규칙의 근거 밖 조건 누락과 **대조 목록의 증거 변경 미감지**가 결합한 경로다. 모든 추출 텍스트 변경이 잘못된 점수를 만든다는 뜻은 아니지만, 새 증거를 기존 대조와 동일하게 취급하는 경계 누락은 존재한다.

**권고:** 공개 `content_version`의 기존 의미를 바꾸기보다, 순위용 대조 목록에 별도 증거 지문을 두고 현재 계산에 사용한 본문·지원대상·활성 성공 첨부 텍스트와 대조 당시 텍스트가 같은지 확인할 필요가 있다. 줄 경계를 판단에 사용하므로, 공백을 모두 제거한 지문만으로 충분하다고 보기는 어렵다. 증거를 읽지 못하거나 지문이 다르면 재대조 대상으로 남겨야 한다.

### R4-P3-1. 목록 안 공고도 순위 방식 때문에 미반영되면 “목록 밖”으로 표시한다

- 위치: `web/app.html` 635~639행.
- 관련 위치: `search/app.py` 710~713·779행.
- 성격: API 재현과 HTML 분기 검토. 실제 브라우저 화면 미검증.

`bonus_rank_applied=False`는 목록 밖 외에 score 방식, 마감임박순 대체 경로, 세기 0 등의 경우에도 정상적으로 반환된다. API는 이를 올바르게 구분해 False로 냈다.

그러나 화면은 세기가 0이 아니면서 False이면 언제나 “원문 대조 목록 밖이라 순위 미반영”으로 표시한다. 목록 안 여성기업 5점 공고에 대해 검색을 둘 다 실패시키면 마감임박순·False가 반환됐는데, 이 응답은 목록 밖이 아니다.

**권고:** 별도 이유 정보가 없다면 “이번 검색에서는 순위 미반영”처럼 확인된 사실만 표시하거나, 실제 검색 경로·미반영 이유에 따라 안내를 구분할 필요가 있다.

## 5. 목록 조건 및 점수 검사 범위

### 5.1 차단되는 경로

직접 재현 및 전체 시험에서 목록 밖, 내용 지문 변경, 가점 행 지문 변경, 승인 밖 이름·배점, 빈 결과 항목의 거부를 확인했다. 목록 밖의 잘못된 양수 표시 사례도 실제 match에서 순위를 올리지 않았다.

`row_fingerprint`는 items의 name·kind·certs·regions·quote·detail·points·points_source·group·program·extra_conditions 등 DB 항목 필드를 포함한다. 따라서 저장된 점수·그룹·근거·추가 조건이 바뀌면 지문이 바뀐다. 원문 검사에서 붙이는 `in_document`·`period_condition`·`quote_lines`는 제외하는 구조이며, 해당 제외 자체를 DB 행 지문 오류로 판단하지 않았다.

`bonus_info`는 행 지문에서 빠지지만 현재 점수·순위 계산에 사용하지 않는다. 그 누락만으로 순위 우회라고 지적하지 않았다. 다만 설명 표시의 대조 범위까지 같다고 주장해서는 안 된다.

목록의 `extractor_version`은 기록용이고 `reviewed_ok()`는 직접 비교하지 않는다. 서비스의 `bonus.load()`가 현재 추출기 버전으로 가점 행을 먼저 걸러내므로, 현재 요청서의 “지문 두 개 + 승인 항목” 조건과 일치한다.

### 5.2 알려진 제한을 다시 확인한 결과

| 구성 입력 | 점수 | 해석 |
|---|---|---|
| 여성기업 안내, 벤처기업 10점 — 쉼표만 구분 | 10.0 | 요청서에 명시된 표시 한계 재현 |
| 여성기업 안내 다음 줄 `10점` | 10.0 | 배점 칸을 앞줄에 붙이는 명시된 구분 한계 재현 |
| 여성기업 안내 다음 줄 `(가점 10점)` | 10.0 | 같은 배점 칸 한계 |
| `※` 없는 두 줄 기간 조건 | 5.0 | 새 구현의 각주 머리 기호·연속 줄 범위 밖 |

앞의 세 사례를 “이번에 새로 발견한 실제 공고 오류”로 중복 집계하지 않았다. `※` 없는 두 줄 기간 조건은 좁은 각주 처리의 범위 한계로 기록하며, 기존 R3-P2-1의 동일 입력이 여전히 실패한다고 표현하지 않는다.

목록은 계산 결과의 이름·배점이 대조 목록 안인지 확인한다. 모든 신청자·추가 조건·그룹 해석을 사람 정답으로 검증한 장치가 아니므로, 목록 추가 시에는 배점 숫자뿐 아니라 대상 조건·합산·한도도 함께 대조해야 한다.

## 7. 순위 반영 값과 검색 영향

가짜 검색 색인과 실제 match 경로로 확인한 결과:

| 조건 | 순서 | 대상 공고의 `bonus_rank_applied` |
|---|---|---|
| 정상 목록, 여성기업 5점, order, 세기 0.2 | a→n에서 n→a | True |
| 같은 양수, 목록 없음 | a→n 유지 | False |
| 같은 목록, 세기 0 | a→n 유지 | False |
| 같은 목록, score 방식 | a→n 유지 | False |
| 같은 목록, 검색 둘 다 실패·마감임박순 | 마감 기준 정렬 | False |

“실제로 순위에 쓰였다”는 값은 정렬 점수에 보너스를 얹었다는 뜻이다. 결과 순번이 반드시 달라졌다는 뜻은 아니다. 다른 지역 등 상위 규칙을 넘지 못해 제자리를 유지한 공고도 정렬 계산에 사용했다면 True인 것이 구현·결정과 일치한다.

기존 30건 순위 보고는 제목 입력 10건 모두 1→1, 일반 분야 입력 10건 모두 20위 밖, 제목 핵심어 입력 중 120238·125997 두 건만 2→1이다. 이 보고는 특정 입력의 순위 변화 근거이며, 추천 품질 향상이나 편향 해소의 증명은 아니다.

현재 세기 0.2는 점수 1점이면 검색 점수 2%, 5점이면 10%, 10점 이상이면 최대 20%를 올린다. 정렬에서 앞선 지역·업종·대상 집단 규칙은 그대로 우선한다. 목록을 둔다고 “모름” 공고와 “확인된 양수” 공고 사이의 쏠림이 없어지지는 않는다. K-Startup 등 읽은 가점이 부족한 출처는 계속 불리할 수 있으며, 이 부분은 결정 0017의 명시된 운영 한계로 구분했다.
