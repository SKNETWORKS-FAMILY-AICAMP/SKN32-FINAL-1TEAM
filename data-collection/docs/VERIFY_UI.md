# 검증 화면 — 사람이 눈으로 확인하는 절차

작성: 2026-09-21 · Claude · 지시서 [CLAUDE_UI_VERIFICATION_TASK_20260921.md](CLAUDE_UI_VERIFICATION_TASK_20260921.md)

터미널 로그와 JSON 파일로만 보던 실험 결과를 브라우저에서 직접 보기 위한 화면이다.
**읽기 전용이다.** 저장된 결과 폴더와 fixture 만 읽는다. DB 에 쓰지 않는다.
`/compare` 화면만 사용자가 입력할 때 검색을 돌린다(저장하지 않음, 아래 3-1).

기존 서비스 화면(`search/app.py`, 8000 포트)과 **다른 앱·다른 포트**다. 운영 검색 결과와 섞이지 않는다.

## 1. 실행

`data-collection` 폴더에서 한 줄이다.

```
.\.venv\Scripts\python.exe -X utf8 -m experiments.sql_semantic.viewer
```

접속 주소: **http://127.0.0.1:8010**  (포트를 바꾸려면 `--port 8011`)

DB·임베딩 모델이 없어도 화면은 뜬다. 근거 문장을 실험 DB 에서 읽을 때만 `.env` 의 `SQL_LAB_*` 가 필요하고,
없으면 "읽지 못했다"는 이유를 화면에 적는다.

## 2. 화면 구성

| 구역 | 보는 것 |
|---|---|
| 맨 위 | 알려진 문제와 상태 (F1·F2·F3·Chroma 미검증·사람 판정 없음)와 테스트 명령 |
| A | 실행 식별자·기준일·공고/벡터 수·모델·리비전·계약·차원·결과 폴더와 파일 해시·조건 확보율 |
| B | 조건 판정 반례 6건 (가짜 공고를 실제 추출기에 넣은 결과) |
| C | 사례별 정형 필터 켬/끔 비교 — 공고 ID·제목·원문 링크·순위·순위 이동·유사도·조건 판정·근거 |
| D | 벡터 검증 — 입력 해시·계약/모델·차원/dtype 검사와 벡터 없음/손상/낡음 건수와 개별 사유 |

맨 위 드롭다운에서 볼 실행을 고른다.

- `저장된 실행 · 2026-09-21… · 추출기 sql_lab_v2` — F1 수정 후 조건으로 다시 돌린 결과(기본 선택)
- `저장된 실행 · 2026-09-18… · 추출기 sql_lab_v1` — F1 수정 전 결과(보존). 공고·벡터·입력·기준일은 같다
- `FIXTURE (가짜 데이터)` — 가짜 입력. 화면 위에 노란 띠로 **DEMO/FIXTURE — 실제 검색 결과 아님**이 붙는다

## 3. 사람이 따라 하는 확인 절차

아래 순서대로 보면 지시서 5절이 요구한 항목을 모두 눈으로 확인할 수 있다.

1. **서버를 켜고** http://127.0.0.1:8010 을 연다.
2. **맨 위 목록**에서 각 문제의 현재 상태를 본다 (2026-09-21 기준).
   F1·F2·F3 `해결 · Codex 승인`, Chroma `통과 · 검사 도구 Codex 승인`, 사람 판정 `없음`.
   Codex 승인 전에는 `해결`로 적지 않는다 — 테스트가 이것을 확인한다.
3. **A 구역**에서 실행 식별자·기준일·공고 수 1,852·벡터 수 1,852·벡터 없는 공고 0·모델 리비전을 확인한다.
   `결과 파일과 해시`를 펼치면 어떤 파일을 읽었는지와 sha256 이 나온다.
   업종 확보율 **0%** 는 오류가 아니라 실제 측정값이다(지원 분야 분류를 업종 자격으로 세지 않는다).
4. **B 구역**에서 여섯 가지 반례를 본다. F1 수정(2026-09-21, Codex 승인) 뒤에는 **모두 `기대대로`** 여야 한다.
   - `제한 없다는 문구를 규모 제한으로 읽지 않는가` → `제한 없음`
   - `제외 문구를 허용 목록으로 뒤집지 않는가` → `정보 없음`
   - `지역 제한 없음이 업종 제한 없음으로 새지 않는가` → `정보 없음`
   - `업종 제한 없음이 규모 제한을 지우지 않는가` → `확인됨(중소기업)`
   - 지원 분야 오인·업력 없음 → `정보 없음`
   한 건이라도 `문제 재현됨`으로 빨개지면 같은 오해석이 다시 들어온 것이다.
   `원문 보기`를 펼쳐 실제 문구와 판정 근거를 대조한다.
5. **C 구역**에서 사례를 하나씩 바꿔 가며 본다.
   - 위 표에서 `공통 / 필터 켬 전용 / 필터 끔 전용`과 순위 이동(▲▼)을 본다.
   - 아래 두 칸이 필터 **켬**과 **끔**이다. 어디서 몇 건이 빠졌는지 단계별로 나눠 보여 준다.

     ```
     전체 후보 (필터 끔 기준)   1852
     − SQL 단계 제외            1033      ← 마감 지남·다른 지역 전용
     = SQL 통과                  819
     − 조건 제외 (지역·업력 등)    25      ← 파이썬에서 3값 판정
     = 조건 통과                  794
     − 벡터 없음·손상·낡음          0
     = 유사도 비교                794
     → 반환                         5
     ```

     SQL 단계 제외는 같은 사례의 **필터 끔** 후보 수에서 뺀 값이다. 기준이 없거나 더 작은
     비정상 입력에서는 숫자 대신 `계산 안 함`과 이유가 나온다. 모두 사례 단위 줄 수이며
     고유 공고 수가 아니다.
   - 공고마다 조건별 `충족 / 불충족 / 확인 필요`와 사유가 붙는다. `근거 문장`을 펼친다.
     저장된 실행에는 근거가 들어 있지 않아 `근거 불러오기` 버튼으로 실험 DB 에서 읽는다.
   - 공고 제목 옆 `원문` 링크로 실제 공고를 연다.
6. **FIXTURE 로 바꾼다.** 여기서만 볼 수 있는 화면이 있다.
   - `fx-case01` — 지역 불충족·업력 불충족으로 빠지는 공고, 벡터 없음·손상·낡음이 한 번에 나온다.
     벡터가 한 건 깨져도 나머지 결과는 계속 나온다.
   - `fx-case02` — 신청자 소재지·설립일을 비운 경우. 후보를 떨어뜨리지 않고 전부 `확인 필요`로 남는다.
   - `fx-case03` — 후보 0건. 빈 화면이 깨지지 않고 "조건에 맞는 공고가 없거나 모두 제외됐다"가 나온다.
7. **D 구역**에서 `모델 리비전이 같은가` 줄이 `검사함`으로 나오는지 본다(F2 해결).
   FIXTURE 의 `fx-case01` 에서 `fx-007` 이 `다른 모델 리비전` 사유로 빠지는지 확인한다.
   `개별 사유`를 펼치면 어떤 공고가 왜 빠졌는지 공고 ID 와 함께 나온다.
8. **새로고침**해서 같은 값이 다시 나오는지 확인한다. fixture 는 기준일과 벡터를 고정해 두어 항상 같다.

## 3-1. 직접 검색해서 비교하기 (/compare)

**http://127.0.0.1:8010/compare** — 입력을 한 번 하면 세 방식의 결과를 나란히 보여 준다.

| 열 | 무엇 |
|---|---|
| 기존 · 하이브리드 | 기존 서비스(8000) `/api/match` 기본값 — 의미 검색 + 단어 검색(BM25) |
| 기존 · 의미 검색만 | 같은 서비스에 `search='dense'` |
| 새 방식 | 정형 필터(SQL) → 임베딩 직접 비교 (`experiments/sql_semantic/search.run`) |

- **기존 서비스(8000)가 켜져 있어야 한다.** `python -m search.app`. 꺼져 있으면 그 열에 이유가 나온다.
- 서비스 코드는 고치지 않았다. HTTP 로 부르기만 한다. 새 방식은 실험 DB 를 SELECT 로만 읽는다. 아무것도 저장하지 않는다.
- 세 방식 Top N 목록에 모두 나온 공고는 초록색. **겹침은 화면에 보인 Top N 안에서만 센 것이다** —
  `이 방식 Top 5에만` 은 다른 방식이 그 공고를 못 찾았다는 뜻이 아니라 5위 밖이라는 뜻이다(Top 10 으로 늘리면 겹칠 수 있다).
- 기존 결과 중 새 방식 데이터(9/18 스냅샷)에 아예 없는 공고는 `새 방식 데이터에 없는 공고` 로 표시한다. 이 목록은 요청마다 새로 읽는다.
- 처음 한 번은 새 방식 모델을 올리느라 20초~1분 걸린다.
- 비교 한계(화면 맨 위에도 적었다): 보는 공고가 다르다(운영 DB 전체 / 9/18 접수 중 1,852건),
  검색어가 다르다(기존은 아이디어에 업종·인증 등을 붙임), 사람 판정이 없다.

## 3-2. /compare 입력 계약 (2026-09-21 확장)

지시서 [COMPARE_INPUT_EXPANSION_TASK_20260921.md](COMPARE_INPUT_EXPANSION_TASK_20260921.md) ·
코드 `experiments/sql_semantic/compare_input.py`. 사용자 결정: **설립일은 개인사업자·법인만 필수**, **성별은 여성/남성/응답 안 함 중 필수**.

| 구분 | 칸 |
|---|---|
| 필수 | 신청자 유형 · 이름 · 생년월일(미래 불가) · 성별 · 시·도 · 주 업종 · 대표자 이력 · 수익모델(항목+단가 1개 이상) · 아이디어 |
| 사업자만 필수 | 사업자등록번호(숫자 10자리) · 설립일(미래 불가) |
| 선택 | 시·군·구 · 보유 인증·확인서 · 희망 사업 규모(예비창업자만) · 자기부담금·가능액(사업자만) · 팀 구성원 · 채용 계획 · 장비 · 협력기관 |

- 검증은 브라우저와 서버(`compare_input.validate`) 양쪽에서 한다. 서버는 실패하면 **검색·모델·DB 를 부르기 전에** 400 과 칸별 오류를 돌려준다. 오류에 입력값을 넣지 않는다.
- 신청자 유형을 바꾸면 맞지 않는 칸을 숨기고 값을 지운다. 서버도 유형에 맞지 않는 칸을 지우고 그 **칸 이름만** `dropped_for_type` 으로 알린다.
- 기존 서비스(hybrid·dense)에는 같은 요청을 보낸다. 대표자 이력은 서비스에 칸이 없어 **팀 첫 행(역할 '대표', 이름 비움)** 으로 넣고, 같은 이력의 팀원 행은 한 번만 넣는다. 성별 '응답 안 함' 은 빈 값으로 보낸다(서비스 규칙은 '여성' 일 때만 쓴다).
- 새 방식에는 실제로 읽는 칸만 넘긴다 — 아이디어·시·도·설립일·예비창업 여부·업종. 업종은 새 방식 어휘(제조업·서비스업 …)로 바꾸고, 못 바꾸면 넘기지 않는다(글자가 달라 잘못 '불충족' 이 나는 것을 막는다).
- 결과 아래 **"입력한 칸이 방식별로 어떻게 쓰였나"** 표에 칸마다 `검색어 / 규칙 / 조건 판정 / 입력만 받음 / 미사용` 을 적는다.
- 개인정보: 이름·생년월일·사업자번호는 응답(`input_summary`)·브라우저 저장소·주소창·서버 로그에 남기지 않는다. 가짜 예시는 `테스트대표`·`0000000000` 이다.

## 3-3. 비교 화면 자체 시험 (/compare/selftest)

**http://127.0.0.1:8010/compare/selftest** — 실제 /compare 화면을 안에 띄워 **브라우저 동작**을 자동으로 확인한다.
`/api/compare` 요청만 가짜 응답으로 바꾸고(검색·DB·모델 호출 없음) 선택지는 진짜를 쓴다. 결과는 표와 `window.__selftest` 에 남는다.

확인하는 것 (2026-09-21 Codex 입력 확장 리뷰): 예시 버튼이 이전 선택(인증·장비·자기부담·팀 행)을 남기지 않는지,
예시 전환 순서와 무관하게 같은 요청이 나오는지, 입력·예시·내용 있는 행이 바뀌면 이전 결과와 사용 여부 표가 지워지는지,
검색 중 입력이 바뀌면 늦게 온 응답을 버리는지, 수익모델·팀이 20행에서 막히는지, 수익모델 묶음·입력의 필수·오류 연결과
오류 칸 초점, 서버 오류 행 번호를 화면 행으로 옮기는지, 브라우저 저장소·주소창을 쓰지 않는지. **14개.**

## 5. 이 화면으로 확인되지 않는 것

- **F1·F2·F3 는 모두 2026-09-21 Codex 승인.** 다른 PC 에서 돌릴 때는 모델 리비전이 잡히는지 먼저 본다
  (로컬 Hugging Face 캐시 `refs/main` 을 읽는다. 못 찾으면 모든 벡터가 낡은 벡터로 빠진다). 화면은 그 상태를 그대로 보여 준다.
- 저장 실행 두 개(v1·v2)는 결과가 같다. 10개 사례에 신청자 기업 규모·업종 입력이 없어 F1 로 고친 판정이
  쓰이지 않기 때문이다. F1 효과를 결과로 보려면 규모·업종을 적은 사례가 필요하다.
  수정의 영향은 `reports/verify_ui/f1_impact_20260921.json` 에 따로 재어 두었다(1,852건 중 54건 변경, 2차 수정 기준).
- 조건 추출은 여전히 **단어 목록**에 기대고 있다. 목록에 없는 표현은 읽지 못한다.
- Chroma 는 2026-09-21 읽기 전용 검사로 이 PC 의 색인을 확인했다(179193 한 건 재동기화 뒤 통과).
  EC2 쪽 벡터는 확인하지 않았다. 새 방식은 Chroma 를 쓰지 않는다.
- 어느 결과가 더 쓸모 있는지에 대한 **사람 판정이 없다.** 순위·유사도는 품질 우위의 근거가 아니다.
- fixture 숫자는 어떤 실제 데이터도 나타내지 않는다.
- 단계별 제외 수는 사례 단위 합계다. 고유 공고 수가 아니다.
- SQL 조건별(마감·지역) 제외 사유는 저장돼 있지 않아 총건수만 나온다. 조건별 사유는 파이썬 단계의
  저장된 예시(최대 10건) 기준이며 전체 집계가 아니다.
