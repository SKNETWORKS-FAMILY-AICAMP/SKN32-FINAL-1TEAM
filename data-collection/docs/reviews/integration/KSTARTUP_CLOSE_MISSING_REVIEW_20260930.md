# K-Startup 모집 종료 처리 검수 (2026-09-30)

검수: Codex. 대상은 [Claude 검수 요청](KSTARTUP_CLOSE_MISSING_REVIEW_REQUEST_20260930.md)의 미커밋 변경이다. 서비스·배치 코드, DB, Git 스테이징은 수정하지 않았다.

## 결론

**보류 — P1 1건·P2 2건.** 완전하지 않은 수집 목록으로 닫지 않는 가드와 같은 트랜잭션에서 처리하는 구조는 확인했다. 그러나 모집 종료 변경이 기존의 `snapshot_at` 시간 순서 보호를 우회한다. 오래된 파일의 재적재·서로 다른 수집 시점의 저장 순서가 뒤바뀌는 경우 실제 상태가 잘못 바뀐다. ID 정규화와 안내 SQL의 날짜 기준에도 경계 오류가 있다. 수정 후 재검수를 권한다.

## P1-1. 종료 처리에도 수집 시각을 적용하고 갱신해야 한다

위치: [store_mysql.py:201-207](../../../shared/store_mysql.py#L201), [234-241행](../../../shared/store_mysql.py#L234), [256-259행](../../../shared/store_mysql.py#L256).

현재 `close_missing()`은 모든 `open` 행을 읽어 `recruitment_status`만 바꾼다. 이번 `stamp`·`run_id`를 받지 않고, `snapshot_at` 조건도 없으며 닫은 행의 `snapshot_at`·`last_import_id`도 갱신하지 않는다. 기존 upsert의 `old.snapshot_at > stamp` 가드는 이 변경을 보호하지 못한다.

실제 `store_payload()`를 SQL 동작을 해석하는 메모리 연결 대역에 넣어 두 경로를 재현했다. 공용 DB 쓰기나 SQL 서버 생성은 하지 않았다.

| 재현 | 현재 결과 | 필요한 결과 |
|---|---|---|
| t1(00:10 UTC)에 100·101을 `open`으로 저장 → t2(00:20)에 목록 `{100}`으로 101 종료 → t1의 100·101 파일 재적재(`listed` 없음, 기존 저장 CLI와 같은 호출) | 101의 `snapshot_at`은 t1 그대로여서 오래된 행이 건너뛰어지지 않고 **101이 다시 `open`**이 됨. `processed=1`, `skipped_older=1`(100만 건너뜀). | t2 종료 상태 유지. 오래된 101 입력도 건너뛰어야 함. |
| t3(00:30)에 100·101이 최신 `open`으로 저장돼 있음 → 늦게 도착한 t2의 목록 `{100}` 저장 | 100 upsert는 `skipped_older=1`로 보호되지만, 입력에 없는 최신 101은 **`closed`로 바뀜**(`closed_missing=1`). | 이번 목록보다 최신 상태인 101은 종료 처리 대상에서 제외. |

첫 경로는 기존 `python -m shared.store_mysql <지난 정규화 파일>` 재적재에서 발생할 수 있다. 두 번째는 다른 수집 PC·프로세스의 정규화와 저장 순서가 뒤바뀌는 경우다. `GET_LOCK`은 동시 저장을 막지만 과거 스냅샷이 나중에 저장되는 것은 막지 않는다.

**수정 방향:** 종료 처리에도 해당 목록의 기준 시각과 현재 `run_id`를 전달한다. 더 최신인 행은 닫지 않고, 닫힌 행에는 종료 판정의 시각과 실행 ID를 반영해 이후 과거 upsert가 되살리지 못하게 해야 한다. `last_import_id`가 실제 상태를 바꾼 실행을 가리키도록 함께 맞추는 것이 적절하다. 위 두 경로를 회귀 시험에 포함한다.

## P2-1. 원본 목록 ID와 DB ID의 정규화 방식이 다르다

위치: [daily_job.py:110-111](../../../collect/daily_job.py#L110), [daily_pipeline.py:168-171](../../../collect/daily_pipeline.py#L168), [normalize.py:130](../../../collect/normalize.py#L130).

완전성 검사와 `listed`는 원본 `pbanc_sn`을 단순히 `str()`로 바꾼다. DB에 저장하는 `source_id`는 `normalize.text()`를 거쳐 앞뒤 공백 등을 정리한다. 따라서 정규화가 정상적으로 받아들이는 입력이 목록 비교에서는 다른 ID가 된다.

**재현:** `pbanc_sn=' 100 '`인 정상 제목·기간·`rcrt_prgs_yn='Y'` 행 1개, 서버 건수 1. `is_complete()`는 True, `kstartup_listed()`는 `{' 100 '}`을 반환한다. 정규화·저장 ID는 `'100'`이므로 같은 `store_payload()` 호출에서 방금 넣은 모집 중 공고가 목록에 없다고 판단돼 **즉시 `closed`**가 된다.

오늘 원본 242건에서 실제 ID 변환 차이는 0건이었다. 현재 자료에서 발생했다는 지적이 아니라 허용 입력의 경계 반례다. 숫자 ID의 `str()` 변환 자체는 현재 DB 형식과 맞는다.

**수정 방향:** 원본 목록의 ID를 DB 저장과 같은 방식으로 정규화하고, 그 기준으로 고유 ID 수를 검사한다. 목록은 계속 원본 전체에서 만들되 ID 변환 규칙을 공유한다. 정규화 거부 행을 임의로 목록에서 빼는 수정은 피한다.

## P2-2. 새 목록 SQL의 `CURDATE()`가 한국 날짜와 다르다

위치: [TEAM_DATA.md:200-203](../../guides/TEAM_DATA.md#L200), [store_mysql.py:151](../../../shared/store_mysql.py#L151).

안내서 첫 접속 예시는 `store_mysql.connect()`를 사용한다. 이 함수는 MySQL 세션 시간대를 `+00:00`으로 설정하므로 새 SQL의 `CURDATE()`도 UTC 날짜다. 서비스의 날짜 비교는 `date.today()`이며, 이 PC·사용자 기준은 한국 시간이다. 한국 시간 00:00~08:59에는 목록 SQL이 전날 마감 공고를 남긴다.

**날짜 계산 재현(실제 SQL 실행은 하지 않음):** 한국 시간 `2026-10-01 00:30`, `apply_end=2026-09-30`이면 UTC 세션 날짜는 `2026-09-30`이다. 새 SQL의 `apply_end >= CURDATE()`는 참이지만, 한국 날짜를 쓰는 서비스의 접수 마감 비교에서는 제외된다. 특히 모집 상태가 `unknown`인 기업마당 공고에서 그대로 노출된다.

**수정 방향:** 목록 쿼리에 서비스가 정한 기준 날짜를 파라미터로 넘기거나, SQL에서 한국 날짜를 명시적으로 구한다. `unknown`을 남기고 `closed`만 제외하는 나머지 조건은 서비스 원칙과 맞다.

## 요청 항목별 확인

| 항목 | 확인 결과 |
|---|---|
| 수집 실패·검증 거부·어제 파일 재사용 | `ks.status != 'ok'`이면 `kstartup_listed()`가 None이다. 완전성 False·파일의 complete 누락·파일 읽기 실패도 닫기 목록을 넘기지 않는다. |
| dry-run·skip-store | 저장 단계 자체를 건너뛰므로 종료 UPDATE도 실행되지 않는다. 관련 기존 회귀 시험 통과. |
| `matchCount`와 `totalCount` | 양수 `matchCount`를 우선 사용한다. 대역에서 `matchCount=2,totalCount=9,2행`은 완전, 0건·조기 빈 페이지의 부분 수집은 불완전으로 확인했다. 0건은 기존 `validate()`도 거부한다. |
| 정규화 거부 | 목록은 원본에서 만들지만, 현재 `validate_payload()`는 `rejected`가 하나라도 있으면 **저장 전체를 거부**한다. 따라서 거부된 행 때문에 공고를 잘못 닫는 경로는 없고, 일부 유효 행만 저장하는 동작도 아니다. |
| `skipped_older` | 목록에 포함된 해당 행은 닫히지 않는다. 하지만 목록 밖의 더 최신 행과 종료 후 과거 재적재는 P1-1대로 보호되지 않는다. |
| 트랜잭션·잠금 | named lock 획득 → begin → upsert·닫기·import 보고서 → commit 순서다. 스키마는 InnoDB이고, 종료 UPDATE 실패를 주입한 메모리 대역에서 rollback 호출과 이전 상태 복원을 확인했다. 실제 MySQL 잠금·rollback은 이번에 실행하지 않았다. |
| 정상적인 재개·API `N` | 더 최신 입력의 `Y`는 기존 upsert로 `open`이 되고, `N`은 정규화에서 `closed`가 된다. 문제는 더 오래된 입력까지 되살릴 수 있다는 P1-1이다. |
| 첫날 235건·추가 비율 가드 | 235건은 Claude의 조회 결과이며 이번에 공용 DB로 재집계하지 않았다. 첫날 누적 정리라는 이유만으로 고정 비율 상한을 필수로 보지는 않는다. 다만 건수 일치는 시간 순서·ID 일치를 보장하지 않으므로 P1-1·P2-1을 먼저 고쳐야 한다. |
| 문서 의미 변경 | 이번 diff의 FLOW·QUERIES·FIELD_MAP·TEAM_DATA·스키마 주석에서 목록 제외에 따른 종료 처리를 설명했다. SQL 날짜 경계는 P2-2. 과거 검수 기록의 당시 설명은 변경 대상으로 보지 않았다. |

건수와 고유 ID 수 일치는 부분 응답·중복 페이지를 막는 데 유효하지만, 페이지를 받는 사이 API 목록 자체가 변하는 상황에서 하나의 일관된 스냅샷을 증명하지는 않는다. 이번 검수는 그 실제 발생 빈도나 API의 페이지 일관성 보장을 확인하지 않았다. 이 한계를 근거 없이 ‘전량 수집이 항상 증명된다’로 확대하지 않는다.
