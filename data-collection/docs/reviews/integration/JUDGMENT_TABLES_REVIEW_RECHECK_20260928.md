# 판정 테이블 검수 응답 재검수 (2026-09-28)

검수: Codex · 대상: [Claude 응답](JUDGMENT_TABLES_REVIEW_RESPONSE_20260928.md) 및 [직전 검수](JUDGMENT_TABLES_REVIEW_20260928.md). **P1 보호는 아직 승인하기 어렵다.** 현재 공용 DB와 파일은 일치하지만, 파일을 무조건 더 최신이라고 판단하는 경로와 파일 손상 시 서버 시작 예외를 가짜 DB로 재현했다. 공용 DB에는 SELECT만 실행했고 코드·DB·Git 스테이징·커밋은 건드리지 않았다.

## 재검수 요청에 대한 답

### 1. P1 보호와 파일 없는 EC2: 95%만으로는 부족하다

`search/applicant_types.py::load_auto()`의 95% 검사와 공고별 파일 해시 비교는 **일부 업로드·DB보다 새 파일**에는 도움이 된다. 그러나 다음 두 경우가 남는다.

- **파일이 없는 호스트**: `expected=100`, DB 한 행만 있는 가짜 연결에서도 그 행의 `blocked`를 그대로 썼다. 코드의 주석은 “DB에 없는 공고는 모름이라 빼지 않는다”지만 **남아 있는 오래된 행**은 여전히 제외에 쓴다. DB가 100%여도 기존 행의 문서가 바뀌었는지는 행 수로 알 수 없다. 95%는 완전성의 근거가 아니다.
- **파일이 있는 호스트**: DB 문서 해시와 파일 해시가 다르면 파일 값을 무조건 덮는다. 가짜 DB에 새 `allowed`(`new-db`), 파일에 옛 `blocked`(`old-file`)를 두자 `refreshed_from_file=1`이고 결론은 `blocked`가 됐다. 해시 불일치는 **방향**을 알려 주지 않는다. 파일이 11단계 실패·복구·경로 변경으로 오래됐으면 원래 P1인 잘못된 제외가 재발한다. 반대로 11단계가 새 공고를 300건 상한으로 미뤘거나 3회 실패해 파일도 옛 값이면 DB·파일 해시가 같아 옛 `blocked`를 계속 쓴다.

**권고**: DB의 `blocked`를 정형 필터에 쓰려면 현재 공고문과 판정 행이 같은 입력 세대라는 근거가 필요하다. 제안된 `judgment_uploads` 같은 완료 표를 만들되, 업로드 건수만 기록해서는 부족하다. 공고 스냅샷/문서 해시, 11단계 완료 범위, 규칙 버전, 13단계 완료를 묶어 **완료된 세대**만 게시·사용해야 한다. 파일이 없는 곳에서는 이 증거가 없는 행을 `모름`으로 처리하는 것이 안전하다. DDL·DB 쓰기는 사용자 결정이 필요하므로 이번에는 제안만 한다. 업종은 기본 `file` 유지가 맞다.

### 2. 13단계 90% 기준: 손상 신호로는 유용하지만 정상 축소를 막고 누락도 놓친다

`collect/upload_judgments.py::run()`은 `len(rows) < 0.9 * len(current)`만 본다. 가짜 DB 2행에서 결과 파일이 정상적인 대상 1행으로 좁아지면 오류가 나 **남은 1행의 갱신도 막는다**. 다만 공고 자체가 `notices`에서 삭제됐다면 FK `ON DELETE CASCADE`로 비교 대상 DB 행도 줄기 때문에 이 예시는 “공고 삭제”가 아니라 **추출 대상/수집 범위만 축소하고 notices는 남는 상황**에 해당한다.

반대로 파일을 같은 공고 2행으로 중복시켜 고유 ID는 1개만 남겨도 `rows=2`, `error=None`으로 통과했다. `no_notice` 행도 길이에는 들어간다. 현재 방식은 파일 급감의 한 형태만 막고, DB에서 누락 행을 삭제하지 않으므로 10% 이내 누락은 옛 행으로 남는다. **고유 ID·현재 notices와 교집합·직전 정상 세대**를 함께 검사하고, 의도한 범위 변경은 별도 절차로 승인/표시하는 것이 좋다. 90% 자체는 임시 경보 기준으로 유지할 수 있지만 성공 판정이나 정합성 보증으로 사용하면 안 된다.

### 3. 9/29 배치 뒤 확인: 아직 실행 전이므로 확인 항목과 현재 기준선만 남긴다

검수 시각은 **2026-09-28 17시대 KST**다. 현재 `data/collect_log.jsonl`의 마지막 행은 **9/28 09:02**로 `stage_warnings`·`judgments_upload` 필드가 없는 옛 형식이다. 9/29 결과는 아직 검증할 수 없다. 현재 공용 DB SELECT 기준 `notices`·두 판정표가 각각 **2,476행**이고, 로컬 두 결과 파일도 각 2,476행/고유 ID 2,476개다. DB와 파일의 전체 비교는 각 표 **같음 2,476, 신규·변경·공고 없음 0**이었다.

9/29 실행 뒤에는 같은 입력 시점에서 다음을 확인한다.

1. 배치 로그의 `run_at`, `status`, `stage_warnings`, 종료 코드, `applicant_types`·`industries`의 `extracted`/`failed`/`deferred`/`gave_up`, `judgments_upload`의 **두 표 각각** `rows`/`uploaded`/`error`를 본다. `stage_warnings`가 비어도 `deferred`·`gave_up`만 있으면 경고가 안 뜬다(`stage_warnings_of()` 재현 결과 `[]`).
2. 공용 DB SELECT로 `notices`와 두 표의 행 수·고유 ID, 파일의 고유 ID·문서 해시·판정 열 대조를 한다. 90% 가드를 넘겼는지뿐 아니라 새/변경 공고가 실제로 업로드됐는지 확인한다. 13단계 오류 또는 중단이면 테이블별 일부 커밋 여부도 확인한다.
3. 배치 완료 뒤 서비스를 재시작해 신청자 유형 `source`와 `refreshed_from_file`을 확인한다. **0이 정상의 충분조건은 아니다**(11단계가 미완료이면 DB·파일 모두 옛 값일 수 있다). 현재 `/api/health`와 `/api/match` 응답에는 이 숫자가 노출되지 않는다. `boot()`의 로그도 값이 0이면 출력하지 않으므로 실행 중 상태를 별도로 점검하거나 진단 로그가 필요하다. 업종은 기본 `file`인지 확인한다.

## 검증 방법과 한계

- 공용 DB는 프로젝트 가상환경의 PyMySQL 패키지를 시스템 Python 경로에 더해 **직접 연결**했다. `shared.store_mysql.connect()`의 세션 `SET`도 실행하지 않고 SELECT만 사용했다. 코드·DB·실제 결과 파일은 수정하지 않았다.
- 가짜 DB·임시 파일로 **옛 파일이 새 DB를 `blocked`로 덮음**, **손상 파일의 `JSONDecodeError`**, **파일 없는 부분 DB에서 `blocked` 사용**, **90% 가드의 범위 축소 차단/중복 통과**, **업력 빈 DB**를 재현했다. 표적 테스트 **156개 통과**. Claude의 전체 619개 통과와 8000 재시작 결과는 기록으로 참고했으며 이번 환경에서는 Python/가상환경 확장 모듈 불일치로 독립 재실행하지 않았다.
- 9/29 실배치, EC2 파일 없는 서버, 사람 기준 업종 정확도는 이번에 실행/검증하지 않았다.
