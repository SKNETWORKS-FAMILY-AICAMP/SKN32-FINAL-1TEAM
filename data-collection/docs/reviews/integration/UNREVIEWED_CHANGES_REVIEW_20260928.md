# 2026-09-28 오후 변경 통합 검수 — Codex

대상: [Claude 검수 요청](UNREVIEWED_CHANGES_REVIEW_REQUEST_20260928.md). `data-collection/`만 읽고 검증했다. 아래 판정은 현재 작업 파일 기준이며 코드·DB·Git 스테이징·커밋은 바꾸지 않았다. 신청자 유형 블라인드 판정은 [AI 참고 결과](../applicant_type/APPLICANT_TYPE_INDUSTRY_LABEL_RESULT_20260928.md)이지 사람 정답이 아니다.

## 수정할 문제 (우선순위순)

### P1 · 서버 시작 중 임베딩·Chroma 장애는 BM25 대체 경로에 도달하지 못함

실제 실행 진입점 `search/app.py:1024-1030`은 서버를 열기 전에 `boot()`를 호출한다. `boot()`는 Chroma 연결·`count()`·전체 ID `get()`(`search/app.py:108-113`)을 먼저 수행하고 마지막에 임베딩 워밍업 `_encode()`(`search/app.py:147-150`)도 예외 처리 없이 수행한다. 이 단계의 장애는 BM25 색인이 있더라도 서버 시작 자체를 막는다. `tests/test_match_deh.py`는 이미 만들어진 `STATE`에서 `match()`만 직접 호출해 이 경로를 확인하지 않는다. E의 대체 검색이 서버 재시작 시에도 동작하려면 BM25 초기화와 Chroma/임베딩 상태를 분리하고 초기 장애를 기록한 채 서비스를 시작할 수 있어야 한다.

### P1 · 하이브리드 검색에서 보조 벡터 조회가 실패하면 대체 검색 없이 500

`search/app.py:388-390`의 `_fill_distances()`는 Chroma `query()`가 성공하고 BM25에서만 찾은 공고가 있을 때 호출된다. `search/app.py:669`의 `col.get()`은 예외를 던질 수 있지만 이 경로는 `search/app.py:367-370`의 검색 오류 처리 범위 밖이다. 따라서 Chroma 조회 중 일부만 실패해도 BM25 결과가 있는데 `/api/match`가 예외로 끝난다. E의 “임베딩 장애 시 BM25 단독” 보장을 만족하지 못한다. `query()` 성공, BM25에만 있는 ID 하나, `get()` 실패를 구성하면 재현된다. 보조 조회 오류도 `search_errors`에 기록하고 BM25 단독 또는 거리 없이 표시할 수 있는 안전한 결과로 내려가야 한다.

### P2 · “하루 300건”은 실제로 실행당 300건

`collect/applicant_type_daily.py:55-61,103`은 남은 공고를 매 실행마다 `limit`만큼 고른다. 실행 날짜와 그날 이미 시도한 호출 수를 저장하거나 확인하지 않는다. 가짜 공고 5건, `limit=2`로 같은 날 `run_batch()`를 연속 두 번 호출하니 첫 실행 2건, 두 번째 실행 2건으로 총 4번 호출됐다. 배치 재실행이나 장애 복구 때 문서의 하루 비용 상한을 넘을 수 있다. 성공뿐 아니라 유료 호출 시도와 체크포인트 복구분을 포함한 날짜별 한도를 유지해야 한다. 실패 공고도 다음 실행에 다시 선택되므로 호출 실패의 재시도 정책을 명시하는 편이 안전하다.

### P2 · 신청자 유형 추출이 실패해도 전체 배치는 정상 종료로 기록

`collect/daily_pipeline.py:348-357`은 11단계 예외를 `applicant_types_result.error`로 저장한다. API 키가 없으면 `collect/applicant_type_daily.py:107-112`도 오류 객체를 반환한다. 그러나 `collect/daily_pipeline.py:365-385`의 `status`는 출처별 `degraded`와 저장 여부만 보며 11단계 결과를 반영하지 않는다. CLI도 `status=ok`면 0으로 끝난다(`daily_pipeline.py:465-481`). 즉 유형이 갱신되지 않았는데 배치 성공으로 보인다. 수집 출처 실패와 구분되는 11단계 실패 표시, 종료 상태 또는 별도 경보가 필요하다. 이 실패가 매칭 자체를 막아야 하는지는 별도 운영 결정이다.

### P2 · 등록 사업자 추정 규칙이 신청 자격이 아닌 문장을 읽을 수 있음

`search/applicant_types.py:33-46,91-98`은 저장된 세 유형의 `evidence` 어디서든 “등록증 보유”, “신고서 제출 완료” 등을 찾으면 예비창업자 공고를 뒤로 보낸다. `registered_only('제출서류: 사업자등록증 보유 확인 서류')`도 `사업자등록증 보유`를 반환한다. 원래 [판정 지시서](../applicant_type/APPLICANT_TYPE_INDUSTRY_LABEL_TASK_20260928.md) 3절은 제출서류로 신청 자격을 판단하지 않도록 했다. 반대로 “예비창업자 제외. 사업자등록증 보유 업체만 가능”은 `예비`가 문장에 있다는 이유로 `None`이 된다. 실제 67건의 자동 상향은 원문 문맥에 대한 독립 검증 없이 수치만 확인된 상태다. 현재는 제외가 아니라 순위 이동이지만, 신청 가능한 공고의 노출 순서를 바꿀 수 있다. 자격·제외 문장만 판별하고 부정/예외를 해당 표현 주변에서 해석해야 한다.

### P2 · 공개 매칭 API에서 `top`만 크게 주면 최대 20건을 넘김

`search/app.py:328-335`는 `offset`이 있을 때만 `MAX_CANDIDATES=20`을 적용한다. `offset=0, top=100`은 20건 넘게 반환한다(`search/app.py:507-512`). `tests/test_match_deh.py:64-66`도 25건 반환을 의도적으로 고정했다. 평가 도구의 전량 조회 요구는 이해하지만, 기능정의서의 사용자 조회 최대 20건과 같은 `/api/match`를 공유하여 API 경계가 없다. 평가용 전량 조회를 별도 내부 함수/경로로 두거나 공개 요청의 `top`을 제한해야 한다.

### P3 · 일일 결과 파일이 Git 무시 대상이 아님

`.gitignore`에는 `data/*.jsonl`만 있고 `data/applicant_types/`는 없다. 실제 `results.jsonl` 4,783,190바이트와 `meta.json`이 미추적 파일로 보인다. 산출물을 버전 관리할 의도가 없다면 하위 디렉터리를 무시하고, EC2 전달 방법을 별도로 정해야 한다. 현재 파일을 삭제하거나 이동하지 않았다.

### P3 · 화면의 “적합도 N%”는 상대 RRF 값을 확률처럼 보이게 함

`search/app.py:533-535`의 `fit_score`는 해당 검색 경로에서 가능한 RRF 최대값으로 나눈 상대 점수다. 두 검색에서 모두 1위이면 관련성 검증과 무관하게 1.0이 된다. `web/app.html:521-555`는 이를 “적합도 100%”로 표시한다. 같은 `search/app.py:25-27`의 유사도 표시 원칙과도 어긋난다. 화면에 계산 기준과 비확률 성격을 드러내거나 퍼센트 표현을 피해야 한다.

## 확인한 부분과 검증 범위

- 업종 순위 기본값은 `demote_industry=False`이고, 이 값이면 `industry_section=None`이므로 업종 순위 신호가 적용되지 않는다. `industry.active`는 결과 파일 로드 여부이므로, 응답에서 “규칙 사용 중”으로 해석하면 안 된다.
- 앞선 업종 허용 갈래 P1 수정의 저장 결과를 현재 `industry_rank.load()`로 다시 읽으면 1,852행 중 순위 적용 가능 174건이다. 지적된 7개 ID(`...123299`, `...120474`, `...125920`, `...122368`, `...125664`, `...123769`, `...121389`)는 적용 목록에서 빠졌고, `...120877`은 `C`만 남는다. 새 DB·서비스 검색 평가를 실행한 것은 아니므로 348쌍 재평가 수치는 Claude의 기존 기록으로만 취급한다.
- 본문 `allowed`가 API의 `업력·신청자 유형` 사유만 제거하는 코드는 다른 제외 사유를 유지한다(`search/app.py:311-325`). `blocked`도 해당 사유가 이미 있는 공고를 중복 집계하지 않는다. 결과 파일에 없는 ID의 `pre_founder()`는 `None`이다.
- 실험 경로 `evaluate()`의 4값 반환은 저장소 내 `run()` 호출부와 테스트에서 맞춰 쓴다. 지역·업종·규모 `NO`는 `demote`로 분리되고, 업력·접수기간 `NO`만 제외한다. 실제 DB 실험은 다시 실행하지 않았다.
- 수집 상태 판정은 로그의 `partial`, 오래된 저장/기업마당 스냅샷을 별도로 다룬다. 11단계 실패를 `partial`로 바꾸면 이 판정이 매칭을 차단할 수 있으므로 위 수정 시 함께 결정해야 한다.
- 시스템 Python으로 `tests.test_applicant_type_daily`, `test_sql_semantic`, `test_applicant_type_llm`, `test_industry_groups`, `test_label_score` **121개 통과**. 임시 파일과 가짜 API로 일일 상한 초과를 재현했다. 저장소 `.venv`는 삭제된 Python 3.12 실행 경로를 가리켜 전체 테스트를 시작하지 못했고, 시스템 Python에는 FastAPI가 없어 `test_match_deh`, `test_applicant_types` 등의 통합 테스트를 실행하지 못했다. Claude의 기존 561개 통과 기록을 이번 실행 결과로 취급하지 않는다.

우선 P1과 비용 상한·실패 상태(P2)를 고친 뒤, 같은 가짜 의존성 테스트와 서비스 매칭 테스트를 다시 실행하는 것이 좋다.
