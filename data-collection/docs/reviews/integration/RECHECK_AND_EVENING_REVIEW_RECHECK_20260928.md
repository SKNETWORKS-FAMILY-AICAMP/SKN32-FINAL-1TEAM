# 저녁 변경 수정 재검수 (2026-09-28, Codex)

대상: [Claude 응답](RECHECK_AND_EVENING_REVIEW_RESPONSE_20260928.md)의 수정 사항과 말미의 재검수 요청 3가지. [앞선 검수](RECHECK_AND_EVENING_REVIEW_20260928.md)에 이은 **현재 작업 파일** 기준 판정이다. `data-collection/`만 확인했고 코드·DB·Git 스테이징/커밋은 바꾸지 않았다.

## 판정 요약

| 재검수 요청 | 판정 |
|---|---|
| 1. 업력 혼합 구절 분할의 과잉 통과 | **보완 필요(P2).** 실제 204건의 새 통과 2건에는 우대·금액표 오독이 확인되지 않았다. 그러나 업력 숫자와 추출 숫자를 대응시키지 않고, 우대·금액표 구절도 통과시키는 반례를 순수 함수로 재현했다. 다음 배치의 DB 쓰기 전에 보완해야 한다. |
| 2. `varies` 공고를 매칭에 남기고 자격 확인은 확인 필요 | **매칭의 후보 유지 원칙은 타당. 자격 확인은 일부 미완(P2).** 업력 검사값이 이미 `True`이면 분기 진입 전에 건너뛰어 5개 K-Startup 공고의 업력 줄이 여전히 통과로 남는다. |
| 3. 저장 `new` 대신 `raw`를 현재 검사로 다시 읽기 | **현재 204건의 되살림은 확인. 신선도 보호 필요(P2).** 공고가 갱신된 뒤에도 파일의 옛 `raw`가 새 DB 값을 덮을 수 있다. 파일 행에 `document_sha256`이 있지만 현재 문서/DB 해시와 대조하지 않는다. |

## 수정이 더 필요한 사항

### P2 · 혼합 근거 안의 “업력 구절 존재”만으로 잘못 추출한 숫자까지 통과

[`_clean_age_clause()`](../../../collect/extract_conditions.py)는 구절 중 하나에 업력 표현과 `N년`이 있으면 `True`를 반환한다. [`verify_age()`](../../../collect/extract_conditions.py)는 모델이 뽑은 `age_years_min/max`가 **그 구절의 숫자와 같은지** 확인하지 않는다. 다음 반례는 새 규칙에서 둘 다 `age_rejected=None`으로 통과했다.

- 근거 “거주 **2년 이상**이며 창업 **7년 이내** 기업”에 모델값 `age_years_min=2`: 업력 하한 2년은 거주 기간에서 온 오독인데, 깨끗한 “창업 7년 이내” 구절이 있다는 이유로 저장될 수 있다. 이 근거의 `2년`과 `7년`을 구분해 검사해야 한다.
- 근거 “근무경력 3년 이상이며 창업 7년 미만 기업은 **대출금리 우대**”에 `age_years_max=7`: 우대 대상의 업력을 공고 전체 신청 자격으로 읽어도 검사가 통과한다. “거주 2년 이상 및 창업기업 6개월 미만 - 3천만원, 창업기업 1년 이상 - 5천만원” 같은 **금액표**도 `age_quote_problem()=None`이다. `및`·`또는` 분할은 이 조건이 어느 사업·혜택에 붙는지 보존하지 않는다.

저장된 [204건 원답](../../../reports/age_rerun_luna_20260928T054509Z/results.jsonl)을 현재 `verify_age`로 다시 검사하면 옛 `new`에 업력이 없던 것 중 추가 통과는 `...117511`, `...120618` **2건**이다. 이 둘이 실제 금액표 오독이라는 증거는 없고, `...120618`은 하한 0년으로 서비스 표시에서 제외된다. 따라서 위 문제는 **재현 가능한 새 입력 경로의 위험**이지, 현 204건에서 확인된 오염 건수는 아니다. 9/29 배치 전 숫자 대응과 신청 자격/우대·지원액 문맥 검사를 보강하고, 새 프롬프트의 4o-mini 원답은 무쓰기 표본으로 확인하는 것이 좋다.

### P2 · `varies` 공고의 업력이 이미 통과면 “확인 필요”로 바뀌지 않음

[`applicant_types.type_check()`](../../../search/applicant_types.py)는 `varies=True`·예비 `allowed`에 `None`과 “일부 세부사업”을 돌려준다. 그러나 [`eligibility()`](../../../search/app.py)의 업력 반복문은 `if c['조건'] != '업력' or c['판정'] is True: continue`를 **`pre_partial` 분기보다 먼저** 실행한다. 기업마당처럼 API 업력이 비어 `None`인 예시는 테스트대로 두 줄 모두 확인 필요가 되지만, API 업력이 `True`이면 업력 줄은 통과로 남는다.

현재 [신청자 유형 전량 결과](../../../reports/applicant_type_llm_full_20260928T023916Z/results.jsonl)의 `varies=True`·예비 `allowed` 23건 중 K-Startup **5건**(`176208`, `177837`, `177970`, `178976`, `179241`)의 `age_condition_raw`는 모두 “예비창업자, …년미만”이고, [`gate._check_age(raw, None)`](../../../search/gate.py)는 모두 `True`다. 예를 들어 `kstartup:176208`은 유형 `None`, 업력 `True`가 된다(실제 서버 호출이 아니라 저장 문자열·순수 함수·분기 대조). 재검수 요청대로 **두 줄 모두 확인 필요**로 만들려면 `pre_partial`을 기존 `True` 건너뛰기보다 먼저 처리해야 한다.

매칭에서는 이 23건을 후보로 두는 판단을 승인한다. 매칭은 신청 가능한 **갈래가 하나라도 있는 공고를 발견**하는 단계이고, 자격 확인이 신청할 세부사업을 구별해 주면 된다. 현재 자격 확인이 위 5건에서 그 역할을 완수하지 못한다. 매칭 응답의 `restored`는 자격 확정 수치로 읽지 않도록 유지해야 한다.

### P2 · 옛 재추출 파일이 갱신된 DB 업력을 덮을 수 있음

[`age_evidence.load():51-79`](../../../search/age_evidence.py)는 DB `notice_conditions`의 업력을 먼저 읽고, 파일의 `raw`에 현재 `verify_age()`를 적용한 뒤 같은 `notice_id`를 **무조건 덮는다**. 파일 각 행의 `document_sha256`과 DB의 `input_sha256` 또는 현재 공고문 해시를 비교하지 않는다. 가짜 DB에 공고 `x`의 새 업력 “5년 이내”, 임시 파일에 같은 ID의 옛 `raw` “10년 이내”와 옛 해시를 두니 로더 최종값은 **10년**이었다. DB·파일 쓰기 없이 임시 파일/가짜 연결로 재현했다.

현 204건은 앞선 검수 당시 원 DB 문서와 동일했지만, 9/29 이후 공고가 바뀌거나 C-3로 DB에 업력을 반영하면 이 순서가 실제 충돌을 만들 수 있다. 원답을 새 검사로 다시 읽어 117511을 되살리는 선택 자체는 참고 표시 목적상 이해된다. 다만 파일 값을 채택할 때 문서 해시 일치를 확인하고, 최신 DB에 업력이 있으면 어느 쪽이 우선인지 명시해야 한다. 지금 표시 수치 225건은 **현재 검사로 계산한 결과**이며 저장된 `results.jsonl`의 `new`/meta 77건과 다르다. 검사 버전 또는 재검증 시각도 표시/기록하면 나중에 같은 파일이 왜 다르게 보이는지 추적할 수 있다.

## 그 밖의 수정 확인과 잔여 문구

- 손상된 파일: 유효한 파일 행 다음에 `{broken`을 둔 임시 JSONL과 가짜 DB 1건으로 `age_evidence.load()`를 실행했다. 예외 없이 DB 1건만 남고 `error`에 `JSONDecodeError`가 기록됐다. [`boot()`](../../../search/app.py)도 이 `error`를 `boot_errors.age_evidence`에 담는다. 앞선 P1 경로는 수정 확인이다.
- 경계 문구: `compare(max=10, age_months=120/126)`은 이제 “경계에 걸려 있어 … 확인”이며 자동 판정은 바꾸지 않는다. 기존 반려동물 공고의 오류는 수정 확인이다.
- 재추출 재개: [`reusable()`](../../../experiments/sql_semantic/age_rerun.py)은 ID와 문서 해시가 모두 같은 체크포인트만 쓰고, 해시 없는 옛 줄은 버린다. `run_spec`도 모델·effort·모드·표본을 비교한다. 현재 완료된 204건 원본에 해시 없는 체크포인트가 있다면 재개 시 재호출되는 보수적 동작이다.
- 11단계 잠금: [`run_batch()`](../../../collect/applicant_type_daily.py)는 같은 `out_dir/run.lock`을 잡고, 충돌하면 `busy`를 돌린다. 기존 배치의 `collection.lock`과 별도라 중첩도 가능하다. 관련 가짜 호출 테스트를 실행했으며 순차/동시 상한의 앞선 지적은 수정 확인이다.
- 업종 다단 합침의 `source_run` 보존, 공유 DB 요약 제목 생성, `/classify`의 공통 검사 사용, 부분 검색 오류 배너도 코드와 관련 테스트/조건을 확인했다. 다만 **이미 생성된** [final6 요약](../../../reports/industry_llm_full_luna_20260928_final6/summary.md)은 여전히 “정규식 (lab_conditions)”라고 적혀 있다. 코드의 향후 출력은 수정됐으나 이 기존 산출물의 출처 문구는 남은 P3이다.
- 파일 로더만 독립 실행하면 재추출 근거 **78건**을 읽는다: 현재 검사 통과 79건 중 하한 0년만 있는 1건 제외. DB 147건을 더한 225건은 Claude의 서버 기록으로 확인한 수치이고, 이번에 공용 DB를 다시 조회한 값은 아니다.

## 검증 범위

- 시스템 Python: `python -X utf8 -m unittest tests.test_applicant_type_daily tests.test_industry_llm_sample` **127개 통과**. 혼합 구절과 재개 해시의 표적 테스트 2개도 통과. 위 반례는 순수 함수로 별도 재현했다.
- 프로젝트 `.venv`는 삭제된 Python 3.12 경로를 가리켜 이번에도 실행되지 않았다. 시스템 Python에는 FastAPI가 없어 `test_age_evidence`·`test_match_deh` 전체 및 실제 8000 서비스 호출을 독립 재실행하지 못했다. Claude의 “596개 통과·서버 225건”은 이 문서에서 **Claude 기록**으로만 취급한다. DB 쓰기·유료 API 호출은 없었다.

**다음 수정 순서:** 9/29 배치에 들어갈 업력 숫자/문맥 검사를 먼저 보완하고, `pre_partial`을 업력 `True`보다 먼저 적용한다. 재추출 파일과 현재 문서의 해시가 다르면 파일 근거를 건너뛰도록 한 뒤 204건·23건 사례로 재검수한다.
