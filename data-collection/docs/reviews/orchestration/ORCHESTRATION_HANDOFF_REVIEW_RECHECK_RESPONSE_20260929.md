## 2. 공고팀 내부 교차 검토 (Codex 제출 전)

Claude 보조 에이전트 16개로 돌렸다. 구성은 검토자 3명(우리 코드 대조, 조율 계약 대조, 스크립트·문서 일관성)과, 지적마다 반박을 시도하는 검증자다. 모두 읽기 전용이었다.
지적 13건 중 **8건이 반박을 견뎠다.** 같은 지적이 겹쳐 실제로는 6건이다.

| # | 확인된 지적 | 조치 |
|---|---|---|
| C1 | 4.5 "접수 예정" 판단식 `apply_start > 오늘`이 시작일 없는 985건에서 `TypeError` (세 검토자가 각자 발견) | `start is not None and start > 오늘`으로 바꿨다. 시작일 없는 공고는 접수 예정이 아니라 `apply_period_type`으로 표시한다. G-01 안에서는 `inp.today`를 쓴다 |
| C2 | 확인 필요 이유로 쓰라는 `설명` 칸이 업력 줄 대부분과 모집 상태 줄 전부에 없음(`KeyError`) | `c.get('설명') or c['요구']`로 쓰도록 했다. 모집 상태 줄은 `요구`를 쓴다. 4.5에 목록 예시 코드를 추가했다 |
| C3 | **더 보기(offset 10)에서 "지연" 빈 카드를 주면** 조율 흐름이 E-C2-STALE 없이 0건을 보여 주고 `more_used`만 소진된다. 조율 흐름은 더 보기 뒤 수집 상태를 보지 않는다(`sbrain_flow.py:196`, `service.py:117-121`) | `tc2()`의 분기를 `inp.offset == 0`일 때만 적용했다. 스크립트 A에 "지연 + offset 10이면 카드가 그대로 나온다" 검사를 추가했다. ⑧에 흐름의 한계와 대안(MORE 구간 끝에서 상태 확인)을 적었다 |
| C5 | 스크립트 D의 0건 검사가 실제 상태가 "정상"이 아니면 건너뛰고 통과 | 조건을 없애고, 수집 상태도 대역으로 "정상"을 준 뒤 0건 경로를 늘 시험한다 |
| C6 | 확인하는 법이 삭제된 `origin/feature/SB-86-orchestration-flow`를 가리킴 | 설명서 7절과 스크립트 설명을 저장소 루트 `..\agent-orchestration`(main 머지본, `deb5c81`과 같음) 기준으로 바꿨다 |
| C8 | 절 번호 참조 오류(⚠ ⑤, 스크립트 주석 "8절 ③") | "①② 2절, ⑤ 6절", "2절 ③"으로 고쳤다 |

**기각된 5건** (반박 검증에서 문서에 이미 있거나 과장으로 판정):
- ⑦이 마감 정보 없음을 안내하지 않는다 → ①의 `apply_period_type` 표시가 다룬다.
- D 거짓 통과(code 관점) → C5와 같은 지적이다. probe 관점의 지적은 확인돼 반영했다.
- 재시작을 놓치면 옛 공고로 추천 → 3.3에 이미 있다.
- ⑩ "공고 공급이 단순해진다" 과장 → 제안 문장일 뿐이고, 5절 조립 예시는 두 칸을 계속 채운다.
- ⑦ 나 방식 기각 이유가 부정확하다 → 공급 단계에는 신청자 정보가 없다는 설명이 맞다.

## 3. 검증

```powershell
.\.venv\Scripts\python.exe -X utf8 -m experiments.orchestration_probe --sbrain ..\agent-orchestration
```

- 결과: **D·A·B·C 모두 통과**, 종료 코드 0.
  - D: 정상 10건, "지연"이면 `('지연', [])`, 0건이면 `('정상', [])`.
  - A: offset 0·10 각 10건. 수집 지연이면 첫 조회 0건(지연), 더 보기 10건.
  - B: 2,525건 × 5가지 경우, 다름 0.
  - C: 계획서작성까지 진행(공고 공급은 스텁 값).
- 4.5 예시 코드를 설명서에서 꺼내 실행했다. 결과는 `[('모집 상태', '모집 상태 정보 없음')]`로 문서와 같다. 공고 2,525건 × 설립일 없는 개인사업자로 확인 필요 목록과 접수 예정 판단식을 돌렸고 오류는 0이었다.
- 전체 unittest는 서비스 코드를 바꾸지 않아 돌리지 않았다.
