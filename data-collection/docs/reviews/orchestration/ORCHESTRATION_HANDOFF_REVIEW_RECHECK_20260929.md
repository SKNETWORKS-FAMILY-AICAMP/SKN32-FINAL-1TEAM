## 추가로 보완할 사항

### P2-1. ⑦의 확인 필요 목록을 어디서 만들지 정해야 한다

2절 ⑦은 `GateResult.unknown_conditions=['업력', '모집 상태']`를 제안한다. 현재 조율 `G01In`에는 `company_info`, `eligibility`, `eligibility_parsed`, `today`만 있고 공고 ID·모집 상태·접수 형태가 없다(`sbrain/contracts/tasks.py:99-103`). `EligibilityRule`에도 이 필드가 없다. 5절 `g01()`만 수정해서는 “모집 상태”나 마감 정보가 모르는지 알 수 없다. **공고 ID 또는 필요한 상태·기간을 G-01에 전달할지**, 공고 공급 단계에서 확인 필요 목록을 미리 계산할지까지 ⑦ 합의에 포함해야 한다. 현재 `GateResult`는 `extra="forbid"`라 추가 필드를 합의 전 전달할 수 없다.

### P2-2. 빠른 시작 코드는 수집 상태와 빈 결과를 처리하지 않는다

1절 23~29행은 `status`가 `지연`·`실패`여도 `app.match()`를 호출하고 `out['results'][0]`을 바로 읽는다. 문서 4.2절은 필터 통과 0건이면 빈 목록이라고 설명하고, 조율 `service.py:103-105`는 수집 상태가 정상이 아니거나 후보가 비면 중단한다. 현재 데이터에서 D가 통과한 것은 `status='정상'`·결과 있음인 사례다. `experiments/orchestration_probe.py:67`도 세 상태 모두를 통과로 취급한다. 빠른 시작에 상태 분기·빈 목록 처리를 넣고 D에서 그 경로를 확인하면 “이것만 보면 된다”는 안내와 실제 조율 흐름이 맞는다.

### P2-3. 화면용 `app.eligibility()` 근거를 G-01 안내에 재사용할 때 접수기간을 구분한다

4.5절은 `checks[].설명`을 계획서 화면의 확인 필요 문장으로 참고할 수 있다고 한다. 이 함수는 접수 시작 전 공고를 `접수기간 X`로 판정한다. 사용자는 그 공고를 고를 수 있게 결정했고 5절 G-01은 접수기간을 보지 않는다. 설명만 가져오더라도 접수기간의 X를 G-01 불합격 또는 확인 필요 사유처럼 표시하면 사용자에게 모순된다. **유형·업력의 근거만 선별**하고, 접수기간은 별도의 “접수 예정” 표시로 다루는 범위를 적어 달라.

### P2-4. 기간 계약 변경 대상과 운영 메모리를 더 구체화한다

2절 ①의 `date | None` 제안은 `Announcement.apply_end`뿐 아니라 `AnnouncementCard.apply_end`에도 적용 대상임을 명시할 필요가 있다(`sbrain/models/domain.py:162,178`). 조율 화면과 `service.py:259`의 비교도 같이 수정해야 한다. 또한 3.3절은 약 2GB 프로세스를 EC2 4GB에서 **새 프로세스로 먼저 띄운 뒤 교체**하라고 권한다. 두 프로세스만 약 4GB이고 OS·DB·다른 서비스 메모리가 추가되므로 동시 구동 가능 여부는 측정 전 보장할 수 없다. 권고에 메모리 여유 확인 또는 일시 중단을 조건으로 붙인다.

## 독립 실행 결과와 한계

- 번들 Python 3.12와 기존 `.venv` 패키지로 개정된 `orchestration_probe`를 다시 실행했다. `app.boot()` 17.2초, 공고 2,525건·신청자 유형 DB 2,525건을 읽었고 **D·A·B·C 모두 종료 코드 0**이었다. A는 offset 0/10 각 10건, B는 공고 2,525건×5입력 차이 0, C는 스텁 공고로 계획서작성 진입이었다. D는 수집 정상·필터 통과 1,594건·1위 `bizinfo:PBLN_000000000126505`였다.
- D는 현재 공고팀 PC의 정상 상태만 시험한다. 스크립트가 미리 `data-collection`을 `sys.path`에 넣으므로 빠른 시작의 상대 import 경로 자체는 독립적으로 검증하지 않는다. 문서가 “저장소 루트 기준”이라고 한 경로는 그 조건에서 맞다.
- 개정 설명서의 `git diff --check`는 통과했다. 서비스 코드·DB·Git 스테이징·커밋·유료 API 호출은 하지 않았다. 공용 DB 접근은 probe의 읽기 전용 조회뿐이다.
- **미검증**: Linux(EC2), 실제 `Announcement` 공급, `unknown_conditions` 표시, 동시 요청·프로세스 교체, 비정상 수집 상태·빈 결과, 사람 기준 신청 가능 여부. 신청자 유형 판정표의 별도 P1 수정은 사용자 지시대로 멈춘 상태다.
