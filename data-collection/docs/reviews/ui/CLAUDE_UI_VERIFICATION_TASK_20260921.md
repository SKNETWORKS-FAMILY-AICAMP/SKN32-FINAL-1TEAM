# Claude 작업 지시서 — 사람이 눈으로 확인하는 검증 UI 추가

작성: 2026-09-21 · 실행 담당: Claude · 후속 검토: Codex

## 1. 목적

`data-collection`의 테스트·검색 실험·자격 조건 판정 결과를 코드 실행 로그만으로 확인하지 않고,
사람이 로컬 브라우저에서 직접 확인할 수 있도록 UI를 추가한다.

이번 작업은 Claude에게 직접 메시지를 보내는 대신 이 문서를 전달해 실행한다.

작업 범위는 `data-collection/` 안으로 제한한다. Git 스테이징·커밋·push는 하지 않는다.
기존 서비스 코드·공용 DB·Chroma 색인·기존 평가 결과를 임의로 삭제하거나 덮어쓰지 않는다.

## 2. 먼저 읽을 문서

작업 전에 아래 문서를 최신 상태와 실제 코드에 대조한다.

- `../AGENTS.md`
- `STATUS.md`
- `WORKLOG.md`
- `SQL_SEMANTIC_EXPERIMENT_TASK_20260918.md`
- `SQL_SEMANTIC_REVIEW_20260918.md`
- `SEARCH_COMPARISON_REVIEW_20260918.md`
- `../experiments/sql_semantic/README.md`

문서의 과거 수치를 현재 실행 결과처럼 표현하지 않는다. 실제 실행값·저장된 산출물·테스트용 fixture를
화면에서 명확히 구분한다.

## 3. UI에 포함할 검증 대상

가능하면 기존 `search/app.py`의 화면 구조와 `web/` 자산을 재사용하되, 새 실험 UI가 기존 서비스 검색
결과나 운영 배치와 섞이지 않도록 별도 화면·라우트·모듈로 분리한다.

최소한 다음 내용을 사람이 한 화면에서 확인할 수 있어야 한다.

### A. 실행·데이터 상태

- 실행 식별자와 기준일
- 실제 데이터인지 fixture인지, 필터 켬/끔인지에 대한 명확한 표시
- 공고 수·벡터 수·누락·손상·낡은 벡터 수
- 모델명·모델 리비전·임베딩 차원·dtype·입력 계약
- 테스트 실행 결과와 실행 명령
- 결과 산출물의 경로와 스냅샷 식별 해시

### B. 정형 조건 판정

신청자 입력과 공고별 조건을 나란히 보여준다.

- 지역
- 업력
- 접수기간
- 예비창업 여부
- 사업자 형태
- 기업 규모
- 업종
- 지원금액·지원방식 등 선호 항목

각 항목은 `충족`, `불충족`, `확인 필요`, `제한 없음`, `정보 없음`을 구분한다.
근거 문장(`source_quote`)과 판정 사유를 함께 보여주며, 근거 없는 값을 확정값처럼 표시하지 않는다.

특히 다음 반례를 UI에서 확인할 수 있는 fixture 또는 회귀 화면으로 제공한다.

- 제한 없는 문구가 특정 규모 제한으로 잘못 해석되지 않는 사례
- 부정·예외 문구가 허용 목록으로 잘못 바뀌지 않는 사례
- 단순 지원 분야 분류가 업종 자격으로 오인되지 않는 사례
- 신청자 정보 누락 시 후보를 탈락시키지 않고 `확인 필요`로 남기는 사례

### C. 검색 결과·비교

최신 SQL 의미 검색 결과가 있으면 필터 켬/끔을 나란히 표시한다.

- 공고 ID
- 제목
- 원문 링크
- 순위
- 코사인 유사도
- 공통 결과·필터 켬 전용·필터 끔 전용
- 순위 이동
- SQL 단계에서 제외된 수와 Python 조건에서 제외된 수를 분리
- 최종 조건별 상태와 탈락·확인 필요 사유

기존 dense/hybrid 결과를 함께 보여줄 경우 `참고용`, `Chroma 내용 미검증`, `사람 판정 없음`을 화면에
명시한다. 코사인 점수를 정확도·확률·적합도 백분율로 바꾸지 않는다.

### D. 벡터 검증

- 현재 공고 입력 해시와 저장 벡터 입력 해시
- 모델 리비전 일치 여부
- 차원·dtype·유한값 검사 결과
- `missing_vector`, `broken_vector`, `stale_vector` 건수와 개별 사유
- 벡터가 한 건 손상되어도 정상 후보가 계속 표시되는지 확인할 수 있는 테스트 사례

## 4. 실행 방식과 UI 품질 기준

- 로컬에서 한 줄 명령으로 실행할 수 있게 한다.
- 기본 포트와 접속 URL을 README 또는 새 UI 문서에 적는다.
- 브라우저 새로고침으로 동일 결과를 다시 볼 수 있도록 입력과 결과를 결정적으로 만든다.
- 실제 DB·모델이 없어도 UI 구조를 확인할 수 있는 명시적 fixture 모드를 제공할 수 있다.
  단, fixture 결과에는 `DEMO/FIXTURE — 실제 검색 결과 아님`을 눈에 띄게 표시한다.
- 빈 결과, 후보 0건, 5건 미만, 오류, 확인 필요 상태도 깨지지 않고 표시한다.
- 긴 원문은 접기/펼치기로 보여주고, 표는 가로 스크롤·고정 헤더 등으로 읽을 수 있게 한다.
- 색상만으로 상태를 구분하지 않는다. 상태 글자와 아이콘·텍스트를 함께 제공한다.
- UI가 외부로 데이터를 전송하지 않으며, 비밀정보·개인정보를 화면이나 로그에 노출하지 않는다.

## 5. 테스트 및 눈으로 확인하는 절차

코드 테스트만 추가하지 말고 다음을 모두 남긴다.

1. 정형 조건·벡터 검증·결과 결합에 대한 단위/회귀 테스트
2. UI 라우트가 정상 응답하는 API 또는 HTML 스모크 테스트
3. fixture 모드에서 주요 화면 요소와 상태 문구를 확인하는 테스트
4. 사람이 따라 할 수 있는 수동 검증 절차
5. 가능하면 주요 화면 캡처 또는 브라우저에서 확인한 화면 목록

수동 절차에는 최소한 다음을 포함한다.

- 서버 실행 명령
- 접속 URL
- fixture 화면 확인
- 실제 저장 결과 화면 확인 방법
- 필터 켬/끔 전환
- 공고 상세의 근거 문장과 원문 링크 확인
- `확인 필요`, `불충족`, 손상 벡터, 후보 0건 화면 확인

브라우저 자동화가 환경상 불가능하면 그 사실을 기록하고, HTML 스모크 테스트와 수동 브라우저 절차로
대체한다. 화면을 확인하지 않았는데 확인했다고 기록하지 않는다.

## 6. 기존 리뷰 사항과의 관계

이 UI 작업은 다음 문제를 숨기거나 자동으로 해결된 것으로 표시하면 안 된다.

- F1: 자격 제한이 아닌 문구의 오해석 가능성
- F2: 검색 시 모델 리비전 불일치 검사 누락
- F3: 재생성 UPSERT의 메타데이터 갱신 누락
- Chroma 실제 벡터 내용 미검증
- 사람 관련성 판정 없음

F1~F3를 함께 수정한다면 수정 이유·회귀 테스트·UI에서 확인되는 반례를 각각 기록한다.
이번 UI가 단순 표시 기능이라 해당 문제를 수정하지 않았다면 `미해결`로 표시한다.

## 7. 완료 산출물

- UI 코드 및 필요한 정적 자산
- UI/라우트 스모크 테스트와 기존 관련 테스트 결과
- 사람이 따라 할 수 있는 실행·확인 문서
- 실제 결과와 fixture 결과를 구분한 화면
- 캡처 또는 브라우저 확인 기록(가능한 경우)
- 변경 파일·실행 명령·검증 결과·미검증 사항을 `STATUS.md`와 `WORKLOG.md`에 기록

완료 보고에는 UI를 만들었다는 사실만 쓰지 말고, 어떤 상태를 사람이 실제로 확인할 수 있게 되었는지,
실제 DB/모델을 사용했는지, fixture만 검증했는지, 아직 확인하지 못한 항목이 무엇인지 구분해 적는다.
