# 공고 매칭 코드 검토 — 2026-09-18

검토자: Codex. 요청: Claude가 구현한 정형 조건과 하이브리드 검색 확인.
서비스·테스트 코드는 수정하지 않았다. 이 문서는 읽기 검토와 가상 데이터 재현 결과다.

## 현재 구현

시험용 화면 `web/app.html`은 `POST /api/match`를 호출한다.
`search/app.py`의 실제 경로는 다음과 같다.

```text
신청자 입력
  → build_query(): 아이디어·수익모델·업력·팀경력·일부 추가 정보로 질의 생성
  → BGE-M3 질의 벡터 → Chroma 의미 검색
  → BM25 단어 검색 (hybrid 모드)
  → 두 목록 상위 50개씩 RRF 결합 (기본 dense:bm25=1:1, k=60)
  → 마감일이 지난 후보 제외 (기본 hide_expired=True)
  → 지원대상 집단·시도·시군구 순으로 후순위 이동 (기본 order 모드)
    또는 규칙 감점 후 점수 정렬 (시험용 score 모드)
  → 상위 top개 반환

사용자가 공고의 자격 확인을 요청
  → POST /api/eligibility
  → gate.judge(): 업력·접수기간·모집상태 판정
```

하이브리드 검색은 구현돼 있다. 다만 현재 매칭 API는 **정형 조건으로 먼저 대상 공고를 줄이고 검색하는 구조가 아니다.**
검색 뒤 마감일로 제외하고 지역·집단 규칙으로 재정렬한다.
지역·집단 불일치는 기본 모드에서 제외하지 않으며, 업력 판정도 매칭 후보를 제거하는 데 사용하지 않는다.
`search/vecstore.py`에는 `allow_ids` 기반 검색이 있지만 이 API의 `col.query()`에는 허용 ID/where 조건이 전달되지 않는다.
이는 구현 범위 설명이며 업력 사전 필터를 이번 검토에서 새로 요구하거나 구현하는 것은 아니다.

## 재현한 문제

아래 네 건의 우선순위는 P2(수정이 필요한 동작 오류)다.
실제 운영 데이터에서 발생 빈도를 측정한 결과는 아니다. 줄 번호는 검토 당시 코드 기준이다.

### 1. 시군구 규칙이 시도 우선순위를 뒤집는다

- 위치: `search/app.py:385-391`, 시도 처리 `375-377`.
- 조건: 신청자는 경기 수원시. 검색 후보 순서는 경기 성남시 공고 → 서울 공고 → 경기 수원시 공고.
- 실제: 최종 순서는 **수원 → 서울 → 성남**이다.
- 원인: 시도 불일치인 서울 공고는 `district_matches()`에서 None을 받는다. 마지막 시군구 분할에서
  None은 keep으로, 성남의 False는 moved로 들어가 앞서 적용한 시도 우선순위를 덮어쓴다.
- 영향: '시도 규칙을 더 강하게 적용한다'는 코드 의도와 달리 다른 시도 공고가 같은 시도 공고보다 앞선다.
- 수정 방향: 시도 적합성 묶음을 보존한 상태에서 그 내부에 시군구 규칙을 적용하거나,
  시도 → 시군구 → 집단 우선순위를 명시한 복합 정렬을 사용한다.

### 2. score 모드에서 RRF와 코사인 유사도를 섞어 정렬한다

- 위치: `search/app.py:353-357`, 후보 꼬리 추가 `300-303`.
- 조건: 정상 공고 60개, top=3, 기본 마감 숨김, 모든 규칙 감점=0.
  Dense/BM25 상위 50개가 동일한 순서다. Dense는 실제로 51개를 가져온다.
- 실제: order 모드는 `n001, n002, n003`, score 모드는 **`n051, n001, n002`**를 반환한다.
  `n051`의 weighted_score는 코사인 유사도 `0.55`, `n001`은 RRF `0.03279`였다.
- 원인: RRF 후보 밖의 꼬리 후보는 `rrf_score`가 없어 `1-dist`로 대체된다.
  두 점수는 척도가 다르므로 규칙 감점을 하나도 주지 않아도 결과가 크게 바뀐다.
- 영향: 가중치 비교 화면에서 규칙·가중치의 효과와 점수 혼용 오류를 구분할 수 없다.
  기본 order 검색에는 해당하지 않는다.
- 수정 방향: hybrid 모드에서는 모든 재정렬 후보에 같은 RRF 점수 체계를 적용하거나,
  보충 후보를 RRF 후보 뒤의 별도 묶음으로 유지한다. Dense 점수로의 fallback은 dense 모드에만 둔다.

### 3. 마감 후보를 제거한 후 부족한 결과를 보충하지 않는다

- 위치: `search/app.py:271-278`, `314-317`.
- 조건: 공고 60개 중 검색 상위 51개만 마감됐다. 52~60위 9개는 접수 중이다.
  Dense/BM25 후보 순서가 동일하며 기본 hybrid·top=3·hide_expired=True다.
- 실제: 유효 공고가 9개 있는데도 **count=0**이 나온다.
- 원인: 고정 수의 후보를 먼저 가져온 뒤 마감 공고를 버리고 검색 범위를 더 늘리지 않는다.
- 영향: '검색 결과 없음'이 실제로는 '첫 후보 묶음에 접수 중 공고가 없음'일 수 있다.
- 수정 방향: 두 검색에 같은 접수 조건을 먼저 적용하거나, 후처리 후 부족하면 후보 깊이를 늘려 다시 검색한다.
  정형 필터를 적용한다면 기간 미상 등의 후보 유지 정책은 별도로 보존한다.

### 4. 설립일 미입력 사업자를 예비창업자로 판정한다

- 위치: `search/app.py:527-529`, `search/gate.py:124-139`.
- 조건: `/api/eligibility`에 `applicant_type='법인사업자'`, `founded_at=''`,
  공고 업력 조건 `7년미만`을 전달한다. API 모델상 유효한 요청이다.
- 실제: 내 값이 **'예비창업자 (미설립)'**, 판정은 **False**, 요구는 '예비창업자 신청 불가'가 된다.
- 원인: 설립일 누락의 None과 예비창업자의 None을 같은 의미로 처리한다.
- 영향: 기존 사업자의 업력을 알 수 없는 상태를 신청 불가로 잘못 판정한다.
  현재 기본 화면은 사업자의 설립일을 필수로 받아 범위가 제한되지만 직접 API 호출·다른 화면 연결 시 발생한다.
- 수정 방향: 사업자의 설립일을 API에서도 필수 검증하거나, '미설립'과 '설립일 미상'을 분리해 후자는 판단 불가로 처리한다.

## 검증 방법과 한계

- 기존 테스트: `test_applicant.py` **15개 통과**, `test_gate.py` **18개 통과**. 총 33개, 건너뜀 없음.
- `.venv/Scripts/python.exe`는 원본 Python 실행 접근 제한으로 시작하지 못했다.
  대체로 번들 Python 3.12.14에 프로젝트 `.venv/Lib/site-packages`를 연결했다. 패키지 설치·환경 파일 변경은 하지 않았다.
- 테스트 명령(작업 디렉터리 `data-collection`, 아래 실행기의 `python`은 번들 Python 3.12.14):

```powershell
$env:PYTHONPATH = Join-Path (Get-Location) '.venv/Lib/site-packages'
python -B -X utf8 -m unittest discover -s tests -p test_applicant.py -v
python -B -X utf8 -m unittest discover -s tests -p test_gate.py -v
```

실제 실행기 경로:
`C:\Users\playdata2\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`.
위 명령의 `python`을 해당 실행기로 치환해 실행했다. PATH의 Anaconda Python에는 FastAPI가 없어 사용하지 않았다.

네 가지 재현은 Python 표준입력 스크립트에서 실제 `app.match()`/`app.eligibility()`를 호출해 검증했다.
`unittest.mock.patch`로 `STATE`와 `_encode`를 호출 중에만 대체했다.

- 질의: '창업 지원', 법인사업자, 설립일 `2025-01-01`(4번은 빈 값).
- 가상 Chroma: ID `n001`부터 순서대로 반환하고 0부터 시작하는 순번 i의 거리를 `0.20 + i*0.005`로 반환.
- BM25: 실제 `hybrid.BM25` 구현에 모든 문서 텍스트를 '창업 지원'으로 넣어 같은 ID 순서의 결과를 구성.
- 공통 공고: 지원대상 '중소기업', 업력 '7년미만', 접수 시작 `2000-01-01`, 마감 `2099-12-31`, 모집 상태 open.
- 1번만 지역·제목을 각 사례에 맞춰 변경. 2·3번 공고는 전국 대상.
- 3번만 앞 51개의 마감일을 `2000-12-31`로 변경.
- 결과는 assert로 네 건 모두 확인했다. HTTP 서버·실제 DB·실제 모델·외부 API는 호출하지 않았다.

기존 테스트는 개별 규칙을 확인하지만, 이번에 재현한 후보 검색·다중 규칙 결합·API 입력 누락 상황을 막지 못한다.
수정할 때 이 네 가지 상황을 회귀 테스트로 추가하는 것이 적절하다.
실제 공고에 대한 검색 품질 비교, 전체 테스트, 배포 검증은 이번 범위에 포함하지 않았다.
