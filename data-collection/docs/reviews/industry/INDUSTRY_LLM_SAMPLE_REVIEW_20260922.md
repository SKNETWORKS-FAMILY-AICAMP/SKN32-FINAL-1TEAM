# 업종 LLM 추출 v1·v2 리뷰

2026-09-22 · Codex · 코드·저장 결과·실행 계약 검토

대상:

- `experiments/sql_semantic/industry_llm_sample.py`
- `reports/industry_llm_sample_20260922T022756Z/` (v1)
- `reports/industry_llm_sample_20260922T023053Z/` (v2)
- `docs/STATUS.md`, `docs/WORKLOG.md`의 업종 LLM 표본 기록

## 판정

**30건 탐색 결과와 “업종을 탈락 필터로 쓰지 말고 참고/확인 필요로만 사용한다”는 결론은 승인한다. 현재 v2 추출값 자체는 운영 필터·전량 적재용으로 승인하지 않는다.**

같은 ID 30건에서 v1 `known 20`이 v2 `known 8`로 줄었고 저장 집계는 코드 결과와 일치한다.
그러나 사람 정답이 없고, 남은 8건도 최소 1건 오판과 4건 이상의 불완전 목록이 확인된다.
따라서 이 결과는 보수적 설계가 필요하다는 탐색 근거이지 정확도 개선의 증거가 아니다.

## 필수 수정

### [F1] v2 후처리가 근거 문자열의 존재만 보고 판정 의미는 검증하지 못함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:95-101`, `:128-155`.
- `verify()`는 quote가 문서에 포함되는지와 일부 표면어만 검사한다. quote가 실제 신청 업종 제한,
  제한 없음 또는 제외 업종 판정을 지지하는지는 확인하지 않는다.
- 독립 반례에서 다음 동작을 재현했다.
  - `status=no_limit`, quote=`제조업 지원사업`은 제한 없음 표현이 없는데도 `no_limit`으로 통과한다.
  - quote=`도내 농가 대상`은 정확한 업종명 `농업`이 없어도 넓은 별칭 때문에 `known/농업`으로 통과한다.
    실제 v2 결과 `bizinfo:PBLN_000000000117568`의 오판과 같은 유형이다.
  - quote=`제조업을 영위하는 상시근로자 10인 이상 기업만 신청`은 실제 업종 제한인데
    `상시근로자`가 있다는 이유만으로 `unknown`으로 내려간다.
  - `excluded_industries`는 quote나 문서에 실제 표현이 있는지 검증하지 않는다.
- 현재 후처리는 v1의 일부 환각을 줄이는 보조장치일 뿐 “엄격 검증”이나 DB 적재 전 안전장치가 아니다.

수정 기준:

1. `no_limit`은 `업종 제한 없음/전 업종/업종 무관` 같은 명시 표현이 quote에 있을 때만 허용한다.
2. 허용·기타·제외 업종 각각에 원문 근거 span을 받고 모든 값을 원문과 대조한다.
3. `농가→농업`, `농식품→농업` 같은 의미 확장 별칭은 정확한 업종명 검사의 통과 조건에서 분리한다.
4. `상시근로자` 한 단어로 전체를 내리지 말고 업종별 규모 정의와 실제 복합 신청 조건을 구분한다.
5. 후처리가 통과시킨 값도 사람이 판정한 정답셋에서 false-positive와 목록 완전성을 측정하기 전에는 필터에 쓰지 않는다.

## 보완 수정

### [F2] v2 수동 판독의 “불완전 목록 3건”은 최소 4건으로 정정해야 함

- 위치: `docs/WORKLOG.md`와 `docs/STATUS.md`의 v2 결과 기록,
  `reports/industry_llm_sample_20260922T023053Z/results.jsonl`.
- 기록한 3건 외에 태백시 공고 `bizinfo:PBLN_000000000117600`도 불완전하다.
  근거에는 `②지식·정보 관련업`이 명시돼 있지만 최종 허용 목록에는 없고, LLM의 `정보통신업`은
  표면어 검사에서 빠진 뒤 원문 표현을 `other_industries`로 보존하지 않았다.
- 따라서 8건은 현재 판독 기준으로도 `그럴듯/완전 최대 3`, `불완전 최소 4`, `오판 1`로 보는 편이 맞다.
- 사람 정답이 없으므로 “과잉 추론이 크게 줄었다” 대신 “known 출력이 20→8로 줄었다”로만 표현해야 한다.

### [F2] v1↔v2가 같은 입력 문서를 사용했는지 증명할 실행 지문이 없음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:292-304`, `:336-342`.
- `--previous`는 같은 notice ID가 있는지만 확인한다. 제목·본문·지원대상·첨부 발췌가 바뀌어도 비교를 계속한다.
- 두 저장 결과의 `doc_chars`와 첨부 개수는 모두 같지만, 같은 길이는 같은 내용이라는 증거가 아니다.
- meta에는 document/prompt/schema/code 해시와 API가 반환한 실제 모델 ID도 없다.

수정 기준:

1. 각 결과에 `document_sha256`와 첨부 원본 지문을 저장한다.
2. meta에 system prompt·JSON schema·코드 파일 해시와 응답의 실제 모델명을 기록한다.
3. 이전 실행과 ID뿐 아니라 document hash가 같아야 정식 전후 비교로 표시한다.
4. 기존 두 실행은 `ID·문자 수·첨부 수 동일, 본문 해시 미기록`으로 한계를 명시한다.

### [F2] 옵션 없는 실제 호출의 기본값이 실패가 확인된 v1임

- 이후 문서대로 실행하면 개선 실험이 아니라 오독이 확인된 v1에 다시 비용을 쓴다.
- 기본값을 v2로 바꾸거나 `--prompt`를 필수로 하고, v1 재실행은 별도의 명시적 확인이 있을 때만 허용한다.

### [F2] 부분 실패 체크포인트와 새 모듈 회귀 테스트가 없음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:324-345`, `tests/`.
- `pool.map()` 중 한 호출이 실패하면 이미 성공해 비용이 발생한 결과도 보고서로 저장되지 않는다.
  재실행은 전부 다시 호출할 수 있어 전량 확장 전에 성공·실패 체크포인트와 재개 키가 필요하다.
- `tests/`에는 `industry_llm_sample`을 참조하는 테스트가 없다. 전체 335개 테스트가 통과해도
  v2 기본값·검증 경계·문서 지문·부분 실패는 보호되지 않는다.
- 재개 키는 `(notice_id, document_sha256, prompt_sha256, model)`로 두고, 위 F1 반례와 재개 동작을 테스트한다.

### [F3] `$0.0116`·`$0.0133`은 실제 청구액이 아니라 토큰 기반 계산값임

- 위치: `experiments/sql_semantic/industry_llm_sample.py:46-48`, `:333-340`, 관련 WORKLOG.
- API usage 토큰에 코드의 고정 단가를 곱한 추정치이며 청구 내역을 조회한 실제 비용은 아니다.
- `보고된 토큰 × 기록 단가 기준 약 $...`으로 표현하고 단가 기준일을 meta에 남긴다.

## 확인한 정상 사항

- v1·v2 모두 실험 DB와 출처 DB에서 SELECT만 했고 DB 적재는 하지 않았다.
- 두 결과의 ID 30개, `doc_chars`, 첨부 개수가 서로 같고 집계도 보고서와 일치한다.
- v2 결과는 `known 8`, `unknown 22`, 코드 후처리 하향 16건이며 토큰·비용 계산도 meta와 맞는다.
- 정답 없음과 정확도 평가가 아니라는 한계를 보고서에 명시했다.
- 허용 목록 누락이 정상 신청자를 탈락시킬 수 있음을 인식하고 참고/확인 필요 용도로 제한한 결론은 안전하다.
- 전량 실행과 조건 테이블 적재를 하지 않았다.
- Python compile 통과, 전체 테스트 **335개 통과·13개 건너뜀**을 확인했다.

2. 30건에 `status`, 전체 허용 업종, 제외 업종, 목록 완전성, 근거 span의 사람 정답을 만든다.
3. F1 검증 반례·실행 지문·부분 실패 재개·테스트를 수정한다.
4. 같은 문서에서 정규식·v1·v2 confusion matrix와 목록 완전성을 비교한 뒤 전량 실행 여부를 다시 결정한다.

이번 리뷰에서는 LLM을 추가 호출하거나 DB·실험 코드를 수정하지 않았다. 읽기 전용 plan과 로컬 테스트만 실행했고,
리뷰·상태 문서만 추가·갱신했다. Git staging·commit·push는 하지 않았다.

## 후속 재검토 — v3 코드 반영 (2026-09-22)

### 판정

**이전 F1·F2·F3의 대부분은 해결됐다. 다만 값별 근거 연결 F1 한 건이 남아 있어 실제 v3 LLM 호출은 수정 후 진행한다.**

### 해결 확인

- `--prompt`가 필수이고 v1·v2는 `--allow-legacy` 없이는 실행되지 않는다.
- v3는 원문 업종 표현을 보존하고 어휘 라벨을 `exact/alias`로 분리한다.
- 명시적인 업종 제한 없음 표현만 `no_limit`으로 인정하며, 규모 정의와 실제 복합 조건을 구분한다.
- `list_complete`와 `filter_ready=False`를 별도로 기록해 사람 정답 전에는 탈락 필터로 사용할 수 없게 했다.
- 결과에 문서·첨부 지문을, meta에 프롬프트·스키마·코드 해시와 응답 모델을 기록한다.
- 성공 호출을 즉시 체크포인트에 저장하고 실패 건만 재개하는 경로가 추가됐다.
- 비용을 API 보고 토큰 × 기록 단가의 추정값이며 청구액이 아니라고 정정했다.
- 신규 테스트 29개가 ResourceWarning을 오류로 처리한 조건에서도 통과했고 전체 **364개 통과·13개 건너뜀**이다.
- 실제 DB 읽기 전용 plan은 30건·첨부 23건·예상 약 `$0.0151`, 이전 v2 비교 등급 `limited`로 정상 종료했다.

### [F1] 허용·제외 업종이 근거 문장이 아닌 문서의 다른 위치에 있어도 판정을 통과함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:210-230`, `:318-388`.
- v3 schema의 각 `allowed` 항목은 `text`, `label`, 각 `excluded` 항목은 `text`만 가진다.
  이전 리뷰에서 요구한 **값별 근거 span**이 없다.
- `verify_v3()`는 업종 표현이 전체 `document` 어딘가에 있는지만 검사하고, `quote` 안에 있는지는
  `in_quote`로 기록만 한다. `in_quote=False`여도 `status=known`, `list_complete=True`가 그대로 유지된다.
- 재현 입력:
  - 지원 내용: `제조업 디지털 전환 및 유흥업 관리`
  - 신청 자격/quote: `신청대상은 도내 중소기업`
  - LLM 출력: 허용 `제조업`, 제외 `유흥업`, status `known`
  - 실제 결과: 두 값이 모두 남고 `known`, `list_complete=True`, 허용 값의 `in_quote=False`.
- 따라서 지원 주제나 다른 조항에서 본 업종을 신청 제한으로 옮기는 v1 유형의 오독이 v3에서도 후처리를 통과할 수 있다.
  `filter_ready=False`라 운영 탈락은 막지만, v3 정확도 실험 자체를 오염시킨다.

수정 기준:

1. `allowed[]`와 `excluded[]` 각각에 원문 `evidence` span을 필수로 받는다.
2. 각 evidence가 document에 있고 해당 값 text가 그 evidence 안에 있을 때만 값을 남긴다.
3. 허용 값의 evidence가 신청 가능 조건을 설명하는지 확인할 공통 eligibility quote 또는 관계를 명시한다.
4. 현재 구조를 유지한다면 최소한 `known`의 허용 값은 `in_quote=True`인 것만 남기고,
   하나라도 quote 밖이면 `list_complete=False` 또는 `unknown`으로 내려야 한다.
5. 위 지원 내용/신청 자격 분리 반례와 제외 업종 반례를 회귀 테스트에 추가한다.

### [F2] 안내된 `--resume` 명령은 원래의 이전 실행 비교 정보를 잃음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:4-7`, `:672-686`, `:739-752`.
- 문서의 재개 예시는 `--resume <폴더>`만 사용한다. 그러나 `previous`는 현재 CLI의 `--previous`가 있을 때만 다시 로드한다.
- 재개 폴더 meta에 기존 `previous`·`previous_prompt`·`previous_grade`가 있어도 읽어 복원하지 않고,
  완료 시 `previous=None`으로 meta와 보고서를 덮어쓴다. 따라서 v2↔v3 비교 열과 비교 등급이 재개 후 사라진다.

수정 기준:

1. `--resume`이면 기존 meta의 previous 경로·비교 등급을 기본으로 복원한다.
2. CLI로 다른 `--previous`를 주면 기존 meta와 불일치한다고 중단한다.
3. 재개 키에 schema hash도 포함하거나 기존 checkpoint의 schema hash를 검증한다.
4. 기존 checkpoint와 새 호출의 실제 응답 모델이 다르면 혼합 실행임을 명시하고 비교 결과를 확정하지 않는다.
5. `main()` 수준에서 최초 일부 실패 → 문서의 재개 명령 → 이전 비교 열·등급 보존을 테스트한다.

### 후속 결론

v3의 구조적 안전장치와 재현성은 크게 개선됐다. F1 값별 근거 연결을 고친 뒤 같은 30건을 실행하는 것은 가능하다.
그 결과 역시 사람 정답과 목록 완전성 검토 전에는 참고/확인 필요용이며 전량 실행·DB 적재·탈락 필터 사용 근거가 아니다.
이번 후속 재검토에서는 LLM을 호출하거나 구현을 수정하지 않았다.

## 2차 후속 재검토 — 값별 evidence·재개 provenance 반영 (2026-09-22)

### 판정

**재개 provenance F2는 해결됐다. 값별 evidence 필드는 추가됐지만 판정 의미를 값에 연결하는 F1은 아직 불완전하다.**
현재 코드로 v3 30건을 호출하면 운영 필터에는 쓰이지 않더라도 정확도 실험의 `known`·제외 업종 집계가 다시 오염될 수 있으므로,
아래 두 반례를 먼저 막고 실행한다.

### 해결 확인 — 재개 provenance

- `--resume`은 기존 meta의 `previous`, `previous_prompt`, `previous_grade`를 복원한다.
- 다른 `--previous`, 바뀐 prompt/schema hash, 바뀐 이전 비교 등급을 거부한다.
- 재개 키에 schema hash가 포함되고 실제 응답 모델이 섞이면 `mixed_models=True`와 보고서 경고가 남는다.
- 최초 실행 일부 실패 → 안내된 `--resume` → 이전 비교 열·등급 보존 회귀 테스트가 통과했다.

### [F1] `대상` 같은 단어가 지원내용에 있어도 신청 자격 quote로 통과함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:167`, `:406`.
- `known`의 신청 자격 검사는 `ELIGIBILITY_CUES` 중 한 문자열이 quote 어디에든 있는지만 본다.
  목록에 `대상`, `가능`, `참여`, `모집`, `업종`처럼 지원내용에도 흔한 단어가 있어 문장의 역할을 구분하지 못한다.
- 독립 반례:
  - 문서·quote·evidence: `지원내용: 제조업을 대상으로 디지털 전환 비용 지원`
  - allowed: `제조업`, status: `known`, list_complete: `true`
  - 실제 결과: `known`, `allowed=[제조업]`, `list_complete=True`로 통과.
- 이는 프롬프트가 명시한 “지원 내용·사업 목적 문장은 quote가 될 수 없다”와 반대이며,
  직전 리뷰가 막으라고 한 지원 주제→신청 업종 오독을 그대로 재현한다.

수정 기준:

1. `대상` 등의 단일 부분 문자열 존재를 신청 자격 증명으로 사용하지 않는다.
2. `지원대상/신청대상/신청자격/지원자격` 같은 자격 필드·헤더 문맥 또는
   신청 주체와 제한 서술어가 함께 있는 패턴으로 quote의 역할을 검증한다.
3. `지원내용/사업내용/사업목적/지원 분야` 문맥은 명시적으로 자격 근거에서 제외한다.
4. 위 문장을 회귀 테스트에 추가하고 `unknown` 또는 허용 값 제거를 기대한다.

### [F2] 제외 표현이 같은 evidence의 다른 업종에 붙어도 제외 값으로 인정함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:384-385`.
- 현재 검사는 excluded text와 제외 cue가 같은 evidence 문자열 안에 각각 존재하는지만 본다.
  제외 cue가 어떤 업종을 수식하는지는 확인하지 않는다.
- 독립 반례:
  - 문서: `지원대상: 도내 중소기업. 유흥업 교육 포함, 제조업은 지원 제외`
  - excluded: `유흥업`, evidence: `유흥업 교육 포함, 제조업은 지원 제외`
  - 실제 결과: `유흥업`이 제외 업종으로 남는다. 실제 제외 대상은 제조업이다.
- 운영 탈락 필터는 `filter_ready=False`로 막혀 있지만 제외 업종 보고와 v3 품질 판독은 틀어진다.

수정 기준:

1. evidence 전체의 cue 존재가 아니라 excluded text와 제외 서술어가 같은 절에서 연결되는지 확인한다.
2. 가능하면 LLM 출력에 값별 최소 span을 요구하고, 후처리는 쉼표·마침표·접속 표현을 고려한 동일 절 근접 검사를 한다.
3. 위 반례와 `유흥업은 지원 제외, 제조업 교육 포함` 순서 반례를 모두 회귀 테스트에 추가한다.

### 검증 기록

- `tests.test_industry_llm_sample` 41개 통과.
- 위 두 미등록 반례는 각각 잘못된 `known`과 잘못된 제외 값 보존으로 재현됐다.
- 전체 테스트는 이번 세션에서 독립 완료하지 못했다. 저장된 `.venv`가 삭제된 Python 3.12 실행기를 가리키고,
  사용 가능한 Python 3.13/번들 Python에는 프로젝트의 FastAPI·NumPy 네이티브 의존성이 맞지 않아 수집 단계에서 중단됐다.
  따라서 Claude가 기록한 전체 376개 통과는 이번 재검토의 독립 확인값으로 쓰지 않는다.
- LLM 호출·DB 쓰기·구현 수정·Git staging/commit/push는 하지 않았다. 리뷰·상태 문서만 갱신했다.

### 2차 후속 결론

재개 기능은 승인한다. v3의 값별 evidence 스키마도 방향은 맞지만, evidence 안의 단어 공존만으로 관계를 증명할 수는 없다.
신청 자격 문맥과 제외 관계를 위 반례 수준에서 고친 뒤 30건 실제 호출 여부를 다시 판단한다.

## 3차 후속 재검토 — quote 역할·제외 관계 휴리스틱 반영 (2026-09-22)

### 판정

**2차 리뷰의 정확한 두 반례는 해결됐고 전체 393개 테스트도 독립 재현했다. 다만 새 휴리스틱에 `known`과 제외 값을 잘못 남기는 경계 반례가 있어 최종 승인은 보류한다.**
`filter_ready=False`와 원시 체크포인트 저장 덕분에 운영 탈락으로 바로 이어지지는 않지만, 수정 전 보고서의 v3 품질 집계는 신뢰할 수 없다.

### 해결 확인

- `지원내용: 제조업을 대상으로 디지털 전환 비용 지원`은 `support`로 판정돼 `unknown`으로 내려간다.
- `유흥업 교육 포함, 제조업은 지원 제외`에서 유흥업은 빠지고 제조업만 제외 값으로 남는다.
- 자격/지원 머리말, 기업마당의 첫째·둘째 `☞`, 제한 서술어와 콜론형 제외 목록에 대한 테스트가 추가됐다.
- 전용 58개 및 전체 **393개 통과·13개 건너뜀**을 프로젝트 Python 3.12 환경에서 독립 확인했다.
  전체 실행 중 업종 코드와 무관한 `search_comparison.py`의 닫히지 않은 파일 ResourceWarning은 출력됐지만 테스트 종료는 성공이었다.

### [F1] 미등록 구역 머리말과 반복 quote가 이전 자격 머리말을 상속함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:363-390`.
- `quote_role()`은 공백을 없앤 전체 문서에서 `doc.find(q)`로 **첫 번째** quote 위치만 고르고,
  앞 80자 안의 등록된 자격/지원 머리말 중 마지막 것만 본다. 다른 구역 머리말은 문맥을 끊지 않는다.
- 독립 반례 1:
  - 문서: `지원대상: 도내 중소기업. 기타 안내: 제조업 기업 우대 프로그램`
  - quote/evidence: `제조업 기업 우대 프로그램`, allowed: `제조업`
  - 실제 결과: `quote_role=eligibility`, `status=known`. `기타 안내` 구역인데 앞의 `지원대상`을 상속했다.
- 독립 반례 2:
  - 문서: `지원대상: 제조업 기업. 지원내용: 제조업 기업 디지털 전환 비용 지원`
  - quote: `제조업 기업`
  - 실제 결과: 첫 등장만 보므로 항상 `eligibility`. LLM이 둘째 지원내용의 동일 문자열을 반환했는지는 구분할 수 없다.

수정 기준:

1. quote의 모든 정확 일치 위치를 검사하고 역할이 서로 다르면 `unclear`로 내린다.
2. 고정 80자만 보지 말고 줄바꿈·문장 경계와 일반적인 `...내용/안내/절차/기준:` 머리말에서 이전 구역 문맥을 끊는다.
3. 가장 안전한 방법은 LLM에 짧은 부분 문자열이 아니라 머리말을 포함한 자격 문장 전체 또는 시작·끝 span을 요구하는 것이다.
4. 위 두 반례를 회귀 테스트로 추가한다.

### [F1] 쉼표 앞의 일반 문구를 제외 목록 항목으로 간주함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:439-452`.
- excluded 값 뒤 같은 절에 제외 표현이 없으면, 뒤의 짧은 쉼표 절에서 제외 cue를 찾는 순간 앞 값을 목록의 일부로 인정한다.
  앞 절이 실제 업종 목록인지 확인하지 않는다.
- 독립 반례:
  - evidence: `유흥업 교육, 제조업은 지원 제외`
  - excluded text: `유흥업`
  - 실제 결과: `(True, '목록 끝의 제외 표현')`. 실제 제외 대상은 제조업뿐이다.
- 기존 테스트의 `유흥업 교육 포함, ...`은 `포함`이 positive marker라 막히지만, 같은 문장에서 `포함`만 빠지면 다시 잘못 통과한다.

수정 기준:

1. 후속 절로 제외 의미를 전파하려면 앞 절들이 업종명·열거 접속어만으로 구성된 목록임을 확인한다.
2. `은/는/이/가` 같은 새 주어가 후속 절에 나오면 앞 항목까지 제외하는 목록으로 보지 않는다.
3. 위 반례와 `유흥업 관련 사업, 제조업은 지원 제외`를 회귀 테스트에 추가한다.

### [F2] 업종명 내부의 `·/ㆍ`를 절 구분자로 잘라 정상 제외 값을 잃음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:392-397`, `:399-455`.
- `_clauses()`가 evidence를 `·`, `ㆍ`로 먼저 나눈 다음 각 조각에서 전체 excluded text를 찾는다.
  따라서 값 자체에 그 문자가 포함되면 어떤 조각에도 전체 값이 존재하지 않는다.
- 독립 반례: `excluded_linked('금융ㆍ보험업', '금융ㆍ보험업은 지원 제외')`가
  `(False, '근거에서 값을 찾지 못함')`을 반환한다. v3 프롬프트의 제외 예시도 바로 `금융ㆍ보험업`이다.

수정 기준:

1. text span을 evidence에서 먼저 찾은 뒤 그 span 밖의 구분자만 절 분리에 사용하거나, 값을 임시 토큰으로 보호한 뒤 분리한다.
2. `금융ㆍ보험업`, `숙박·음식점업`의 직접 제외와 콜론형 제외 목록을 테스트한다.

이전 두 차례보다 안전해졌고 재개·원시 결과 보존 계약도 승인 상태다. 그러나 위 F1 두 건은 같은 종류의 false-positive를 다시 만들므로
작은 코드 수정과 회귀 테스트 후 v3 30건을 실행하는 편이 낫다. 이번 재검토에서도 LLM 호출·DB 쓰기·구현 수정·Git 작업은 하지 않았다.

## 4차 후속 재검토 — 구역 경계·제외 목록·복합 업종 반영 (2026-09-22)

### 판정

**3차 리뷰의 세 반례는 모두 해결됐고 전체 403개 테스트도 독립 재현했다. 그러나 제외 머리말을 자격 머리말로 분류하는 F1 한 건이 남아 v3 호출은 한 번 더 보류한다.**
이 문제를 고친 뒤에는 휴리스틱에 반례를 계속 덧대기보다 v3 30건을 실행하고 사람 정답으로 오판율·목록 완전성을 측정한다.

### 해결 확인

- 미등록 콜론 머리말과 새 구역 글머리가 앞 자격 문맥을 끊고, 역할이 다른 구역에 반복된 quote는 `unclear`가 된다.
- `유흥업 교육, 제조업은 지원 제외`와 `유흥업 관련 사업, ...`의 유흥업은 제외 값으로 남지 않는다.
- `금융ㆍ보험업`, `숙박·음식점업`처럼 값 내부에 `ㆍ/·`가 있는 직접 제외와 콜론 목록을 보존한다.
- 전용 68개 및 전체 **403개 통과·13개 건너뜀**을 프로젝트 Python 3.12 환경에서 독립 확인했다.
  업종 코드와 무관한 기존 `search_comparison.py` ResourceWarning은 이전과 같이 출력됐지만 종료코드는 0이었다.

### [F1] `제외업종:`을 `업종`이 들어간 자격 머리말로 분류함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:398-404`.
- 일반 콜론 머리말은 지원 머리말이 아니면서 이름에 `대상/자격/요건/업종` 중 하나가 있으면 `E`(eligibility)가 된다.
  이미 정의된 `EXCLUSION_HEADERS`를 이 분기에서 확인하지 않아 부정·제외 머리말까지 자격 머리말로 승격한다.
- 독립 반례:
  - `제외업종: 유흥업`, quote/evidence/allowed=`유흥업` → `quote_role=eligibility`, `status=known`.
  - `지원제외 업종: 금융ㆍ보험업` → `금융ㆍ보험업`이 allowed로 남고 `known`.
  - `비대상 업종: 도박업` → `도박업`이 allowed로 남고 `known`.
- 이는 LLM이 제외 목록을 allowed로 잘못 출력했을 때 후처리가 막아야 하는 직접적인 방향 반전이다.

수정 기준:

1. 일반 eligibility label 판정보다 `EXCLUSION_HEADERS`와 `제외/불가/비대상/금지/제한` 같은 부정 머리말을 먼저 판정한다.
2. 제외 머리말은 `eligibility`가 아닌 별도 역할 또는 `unclear`로 두어 `known`을 통과시키지 않는다.
3. 위 세 반례를 `quote_role()`과 `verify_v3()` 수준 회귀 테스트로 추가한다.
4. 수정 후 같은 30건 v3를 실행하되 결과를 운영 필터나 DB에 쓰지 않고 사람 정답 30건 평가로 바로 넘어간다.

### 4차 후속 결론

재개·지문·원시 evidence·보수적 `filter_ready=False` 계약과 직전 세 수정은 승인한다. 남은 F1은 작은 우선순위 분기 누락이지만
허용/제외 의미를 뒤집으므로 실행 전 고친다. 그 다음 단계의 품질 판단은 추가 정규식이 아니라 사람 정답으로 한다.
이번 재검토에서는 LLM 호출·DB 쓰기·구현 수정·Git staging/commit/push를 하지 않았다.
