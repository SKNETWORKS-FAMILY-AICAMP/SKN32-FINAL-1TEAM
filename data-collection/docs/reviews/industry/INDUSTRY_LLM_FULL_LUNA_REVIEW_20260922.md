## 판정

**1,852건 실행과 결과 저장은 정상 완료됐지만, 이 결과를 정형 업종 필터나 DB 조건 데이터로 사용하는 것은 승인하지 않는다.**

이번 실행은 `lab_notices` 스냅샷 1,852건을 대상으로 했으며 현재 전체 공고 2,390건을 처리한 것은 아니다.
API 실패는 0건이고, 결과·체크포인트 모두 1,852건이며 ID 중복·누락과 문서 해시 누락은 없었다.
기록된 사용량은 입력 4,973,114토큰, 출력 1,192,922토큰(추론 553,181 포함), 기록 단가 기준 약 `$2.4261`이다.

그러나 최종 품질은 개선됐다고 보기 어렵다. 30건 중 기존 Codex 판정과 일치한 건수는 최초 Luna 표본의 24건에서
전수 재호출 후 23건으로 줄었다. 이 Codex 판정도 사람 정답셋이 아니므로 정확도 증거가 될 수 없다.

## 필수 수정

### [F1] 최종 `unknown` 결과 111건에 `allowed` 값이 남아 있음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:625-638`, `:652-693`.
- 검증기는 먼저 `allowed`를 채운 뒤, 근거·문장 역할 검사에 실패하면 `status`만 `unknown`으로 내린다.
- 전수 결과에서 최종 `unknown`인데 `allowed`가 비어 있지 않은 행은 111건이다.
  - raw `known`에서 내려간 행 98건
  - raw 상태부터 `unknown`인데 허용값을 함께 반환한 행 13건
- 현재 모든 행이 `filter_ready=false`라 즉시 탈락 필터에 쓰이지는 않지만, 후속 소비자가 상태 확인 없이
  `allowed`를 읽으면 검증에서 폐기한 업종이 다시 사용될 수 있다.

수정 기준:

1. 최종 `status != known`이면 `allowed=[]`를 강제한다.
2. 최종 `status != no_limit`이면 `no_limit_text=''`를 강제한다.
3. 감사용 후보는 `dropped` 또는 별도 `raw_allowed` 필드에만 보존한다.
4. raw `unknown`+비어 있지 않은 allowed와 `known→unknown` 하향 사례를 회귀 테스트에 추가한다.

### [F1] `known`의 67.8%가 공통 업종 라벨로 정규화되지 않음

- 최종 `known`은 538건이지만 정확한 정규화 라벨을 하나 이상 가진 행은 173건뿐이다.

수정 기준:

  base 1,755행과 18,000자 재독 97행으로 구성된다. `filter_ready=true`는 0건이다.

### [F1] 제외 업종을 발견하고도 `not_mentioned`로 바뀌는 행이 244건 있음

  - `bizinfo:PBLN_000000000116998`: 이유에 금융·보험업 등 보증제한업종이 명시됐다고 적었지만

### [F1] 통합공고와 조건부 분기의 업종 범위를 합쳐 공고 전체 조건으로 만듦

- 위치: `experiments/sql_semantic/industry_llm_sample.py:142-169`, `:282-307`.
- 현재 스키마는 공고당 `allowed[]` 하나만 있어 값이 어느 세부사업·신청자 분기에 적용되는지 저장할 수 없다.
- 실제 반례:
  - `bizinfo:PBLN_000000000116741` 중소기업 수출지원사업 **통합공고**는 한 세부사업의
    `K-수출전략품목 분야 제조 중소기업`만 보고 공고 전체를 `known/제조`로 표시한다.
  - `bizinfo:PBLN_000000000116943` 기술개발 **통합공고**도 한 세부사업의 제조 수요기업 조건을
    공고 전체 `known/제조`로 표시한다.
  - 6개 공고는 일반기업용 구체 업종과 `중점 육성기업이면 전 업종` 같은 조건부 분기를 한 allowed 목록에 합친다.
    이후 `ALL`을 단순 합집합으로 사용하면 중점기업 여부와 관계없이 전 업종이 통과한다.
- 이 문제는 업종명 정규화로 해결되지 않는다. 조건의 적용 범위를 잃은 데이터 모델 문제다.

수정 기준:

1. 통합공고는 세부사업 단위로 분리하거나 `scope/subprogram/when`을 가진 조건 그룹으로 저장한다.
2. 분기 구조를 저장할 수 없으면 통합공고·조건부 ALL은 `unknown/conditional`로 내려 전역 필터에 사용하지 않는다.
3. 신청자 인증·기업유형 같은 다른 조건을 만족할 때만 해당 업종 분기를 적용하도록 조건식을 보존한다.

### [F1] KSIC 묶음 규칙이 실제 값들을 잘못된 대분류로 표시함

- 위치: `experiments/sql_semantic/industry_groups.py:36-43`, `:47-90`, `:106-143`.
- 괄호 속 두 자리 숫자를 문맥 없이 KSIC 중분류로 신뢰하고, 부분 문자열 규칙과 선착순 EXCLUSIVE 규칙을 사용한다.
- 현재 코드에서 독립 재현한 반례:
  - `정보서비스업(72)` → `M 전문·과학·기술 서비스` (원문 업태 코드 72를 KSIC로 오해; 표현상 J 정보통신)
  - `컴퓨터 프로그래밍, 시스템 통합 및 관리업(72)` → `M` (동일)
  - `양식장`, `패류 양식 어가` → `I 숙박·음식점` (수산 양식을 서양식 음식으로 오해)
  - `음식료품 도매업` → `C 제조 + G 도소매 + I 음식점`
  - `건설업 및 제조업` → `F`만 남음(EXCLUSIVE가 제조업을 잃음)
- 위 값들은 최종 결과 파일에 실제로 존재하거나 같은 규칙 경계의 실제 표현이다.
- 따라서 “91% 묶임”, “표준 대분류 87%”는 정확도가 아니라 규칙이 무엇인가를 반환한 coverage일 뿐이다.

수정 기준:

1. 숫자는 `KSIC`, `한국표준산업분류`, 대분류 문자 등 분류 체계가 명시된 경우에만 우선한다.
2. 숫자와 업종명 키워드가 충돌하면 한쪽을 선택하지 말고 `ambiguous`로 보낸다.
3. 수산 양식/서양식, 식품 제조/음식점, 업종 복합 표현을 토큰·문맥 단위로 분리한다.
4. 현재 최종 결과에서 층화 표본을 사람이 검수해 대분류 값 단위 precision을 측정하기 전에는
   신청자 업종에도 같은 함수를 적용하지 않는다.

### [F2] 6,000자 상한에 닿은 공고 중 104건은 긴 원문으로 다시 읽지 않음

- `rough_split`에서 6,000자 상한에 닿은 행은 총 201건이다.
- 이 중 `industry_status=unknown`의 일부 97건만 18,000자로 재호출했다.

  `known` 70건, `excluded_only` 12건, `unknown` 22건.
- 상한 도달 `known` 70건 중 39건은 `list_complete=true`다. 하지만 뒤쪽 원문에 다른 허용·제외 분기가
  더 있는지 읽지 않았으므로 완전하다고 증명할 수 없다.
- 원인은 `industry_status()`가 상한 검사를 하기 전에 `known/no_limit`과 `excluded_only`를 반환하는 순서다.

수정 기준:

1. 정형 조건 후보로 사용할 목적이면 상태와 관계없이 상한에 닿은 모든 행을 긴 원문으로 다시 확인한다.
2. 재독 전에는 상한 도달 행의 `list_complete`를 false로 강제하고 별도 `truncated=true`를 저장한다.
3. 비용을 줄이려면 최소한 `known/list_complete=true`, `no_limit`, `excluded_only`부터 다시 읽는다.

### [F2] 합친 최종 meta의 토큰 합계가 원답 비용과 대응하지 않음

- 위치: `experiments/sql_semantic/industry_llm_sample.py:1307-1319`.

  `tokens_in/out`은 기준 실행의 4,973,114/1,192,922만 복사한다.
- 재독 663,662/92,821토큰을 포함한 출처 합계는 5,636,776/1,285,743이어야 한다.
- 토큰과 비용을 함께 표시·감사할 때 내부적으로 맞지 않는다. merge 시 토큰도 합산하고 모델·profile·prompt/schema가
  호환되는지 검증한 뒤 `mixed_models`를 계산해야 한다.

### 결론과 다음 순서

1. `not_mentioned` 1,065건은 매칭 통과값으로 사용하지 않는다. 먼저 dropped 제외값을 반영해 재분류한다.
2. 통합공고·조건부 분기를 표현할 데이터 모델을 정하거나, 해당 공고를 전부 확인 필요로 내린다.
3. KSIC 묶음은 화면 탐색 참고로만 유지하고 신청자 업종 비교에는 아직 연결하지 않는다.
4. 위 수정은 대부분 저장 결과의 오프라인 재처리로 가능하다. 다만 통합공고 분리와 남은 104건 긴 원문 확인은
   추가 추출/재독 설계가 필요하다.

이번 후속 리뷰에서는 LLM·DB를 호출하거나 구현을 수정하지 않았다. 실제 화면과 저장 결과를 읽고 전용 테스트를 실행했으며,
리뷰 문서만 갱신했다. Git staging·commit·push는 하지 않았다.

## 2차 후속 재검토 — 제외 머리말·남은 104건 재독·final4 (2026-09-22)

### 판정

**직전 리뷰의 `not_mentioned` 오분류, 104건 재독 누락, 대표 KSIC 반례, 합치기 메타데이터는 수정됐다.**
그러나 통합공고 일부가 여전히 전역 `not_mentioned/excluded_only`로 표시되고, 실제 제외 업종 대신 “붙임의 제외 업종”이라는
참조문만 가진 25건도 `excluded_only`가 된다. 따라서 `final4`는 탐색·검수 화면으로는 사용할 수 있지만 신청자 업종 정형 필터에는
아직 연결하지 않는다.

### 해결 확인

- `final4`는 1,852행·고유 ID 1,852개이며 실패 0건이다.
- 두 차례 합치기 출처는 base 1,651건 + long97 97건 + long104 104건으로 정확히 나뉜다.
- final3와 final4를 의미 필드 기준으로 비교하면 long104의 104건만 바뀌고 나머지 1,748건은 동일하다.
- 최종 토큰 6,394,949/1,472,128, 원답 비용 약 $3.0455는 base+long97+long104 합계와 맞는다.
- `not_mentioned` 817건 중 dropped 후보 또는 `raw_allowed`가 남은 행은 0건이다. 직전 리뷰의 244건 문제는 해결됐다.
- 18,000자에서도 상한에 닿은 행은 최종 결과 전체에서 12건이며 모두 `truncated=true`, `list_complete=false`다.
- 직전 KSIC 반례 다섯 개는 모두 기대대로 바뀌었다:
  `정보서비스업(72)→J`, `양식장→A`, `패류 양식 어가→A`, `음식료품 도매업→G`,
  `건설업 및 제조업→F,C`.
- `filter_ready=true`는 여전히 0건이라 현재 결과가 자동 탈락 필터에 직접 쓰이지는 않는다.

- Chrome에서 `/industry-results`를 직접 확인했다. `final4` 기본 선택, 1,852건 집계, 필터와 표 렌더링은 정상이다.

### [F1] 통합공고 보호가 `known`에만 적용되어 8건은 여전히 전역 판정처럼 보임

- 위치: `experiments/sql_semantic/industry_llm_sample.py:712-733`.
- 제목의 `통합 공고` 검사는 `out['status'] == 'known'` 블록 안에서만 실행된다. 따라서 같은 통합공고라도 LLM 상태가
  `unknown`이고 quote가 있으면 아래쪽에서 `not_mentioned` 또는 `excluded_only`로 빠진다.
- 최종 결과에서 제목이 `통합\s*공고`인 25건은 `conditional` 10, `unknown` 7, `not_mentioned` 7,
  `excluded_only` 1건이다.
- `not_mentioned` 반례에는 `2026년 스마트 제조혁신 지원사업 통합 공고`, `2026년 지식재산 보호강화 사업 통합 공고`,
  `2026년 중앙부처 및 지자체 창업지원사업 통합공고`가 있다. 세부사업을 모두 보존하지 못한 상태에서 이들을
  “업종 제한 없음(언급 없음·추정)”으로 전역 해석하면 안 된다.
- `넷제로 챌린지X 통합 공고`는 구체 업종표 없이 “창업에서 제외되는 업종” 참조문만 남았는데 `excluded_only`다.

수정 기준:

1. 통합공고 guard를 `known` 분기 밖에서 먼저 적용한다.
2. 세부사업 범위를 저장하지 못한 통합공고의 `not_mentioned/excluded_only`는 최소 `unknown`, 가능하면
   `conditional`과 함께 `scope_unresolved=true`로 둔다.
3. `known`뿐 아니라 raw unknown + quote, 제외값만 있는 통합공고 회귀 테스트를 추가한다.

### [F1] 구체 제외 업종이 없는 참조문 25건을 `excluded_only`로 확정함

- 위치: `experiments/sql_semantic/industry_llm_sample.py:789-812`, `:722-723`.
- 제외 검사는 text가 실제 업종인지 확인하지 않는다. evidence가 제외 문맥과 연결되기만 하면
  `소상공인 정책자금 융자제외 대상 업종`, `지원제외 업종`, `창업에서 제외되는 업종` 같은 목록 제목·참조문도
  그대로 `excluded`에 넣고, 값이 하나라도 있으면 `excluded_only`로 확정한다.
- final4에서 `excluded_only`이면서 제외값 전부가 이런 일반 참조문뿐인 행을 보수적으로 세면 **25건**이다.
  예: `bizinfo:PBLN_000000000119739`, `...120031`, `...124560`, `...126566`.
- 이 25건은 “어떤 업종을 빼야 하는지”를 데이터가 갖고 있지 않다. 화면 설명의
  “그 업종만 빼면 누구나”처럼 사용하거나 주업종 불일치 게이트에 넣으면 제외표에 실제로 해당하는 신청자를 통과시킬 수 있다.

수정 기준:

1. `제외 업종`, `제외 대상 업종`, 법령/붙임 참조만 있는 값을 실제 업종값과 구분한다.
2. 참조 대상 표를 추출하지 못했으면 `unknown` 또는 `excluded_reference_only`로 둔다.
3. `excluded_only`는 최소 하나의 구체 업종명/KSIC 코드가 검증되고, 참조된 목록의 완전성을 확인한 경우에만 매칭에 쓴다.

3. 화면에는 공고 단위 coverage와 함께 전체 허용값 수/미분류 값 수를 같이 보여 준다.
