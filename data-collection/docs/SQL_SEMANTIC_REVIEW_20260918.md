## 판단

별도 DB 설정, 후보 전체 코사인 비교, 조건 미확인 유지, 기존 결과의 참고용 표시는 구현되어 있다.
다만 아래 5건을 수정하기 전에는 요청한 자격 필터와 벡터 검증이 완료됐다고 보기 어렵다.
검색 품질의 우열은 이번 리뷰로 판단하지 않는다.

사용자가 전달한 최신 Claude 보고는 로컬 스냅샷 1,852건·50건 시험 임베딩·실제 검색 성공,
전량 임베딩 진행 중이다. 기존 WORKLOG의 ‘실제 실행 대기’는 이전 시점 기록이다.
이번 리뷰는 DB 접속·모델 실행·생성 프로세스 확인 없이 수행했으므로, 위 실행 수치와 완료 상태를 독립 검증한 것은 아니다.

## 수정 필요

### 1. [P2] 지원 분야를 업종으로 저장하고, 업종·기업 규모 자격을 판정하지 않음

- 위치: `conditions.py:119–126`, `search.py:47–48`, `search.py:138–148`, 검색 CLI와 `compare.applicant_from`.
- `industry_condition()`은 지원사업 분류인 `category/subcategory`를 업종 `known`으로 저장한다.
  원본 스키마도 category를 ‘출처별 지원사업 대분류’로 정의한다. 이는 제조업·서비스업 등의 신청 가능 업종과 다르다.
- 가상 공고 `category='기술', target_text='제조업을 영위하는 중소기업만 신청 가능'`이
  `industry={status: known, value_text: 기술}`로 변환됐다. 따라서 보고된 **industry 100%는 업종 자격 확보율로 사용할 수 없다.**
- 검색은 업종 입력/판정이 없고, 조회한 기업 규모도 판정하지 않는다.
  가상 신청자 `company_size='대기업'`과 공고 `size_status='known', size_value='중소기업'`을 전달해도 결과가 반환되며,
  두 조건 모두 `conditions`와 `needs_check`에서 빠진다.
- 지시서 5절에서 선호로 구분한 것은 지원 내용·희망 금액·희망 지원 방식이다.
  기존 WORKLOG의 ‘업종·규모도 선호이므로 제외하지 않음’은 지시서 해석 오류다.
- 수정: 지원 분야는 목적 필드로 유지하고, 업종 근거가 없으면 unknown으로 둔다.
  업종·규모 입력과 3값 판정을 연결한다. 신뢰 가능한 명시적 자격 불일치만 제외하고,
  단순 단어 출현이나 지원 분야 차이를 불일치로 승격하지 않는다. 미입력·미확인은 확인 필요로 표시한다.
- 검증: 지원 분야와 업종 구분, 명시적 규모 불일치, 신청자 누락, 복합/불확실한 자격의 후보 유지.
  수정 후 확보율도 다시 산출한다. 전수 업종 추출이나 ML/LLM 추가는 필요하지 않다.

### 2. [P2] 현재 공고와 저장 벡터의 입력 해시를 대조하지 않음

- 위치: `search.py:67`, `search.py:219–228`; 재사용 판단은 `prepare.py:159–164`.
- 검색은 `v.input_sha256`을 읽지만 사용하지 않으며, 현재 공고로 임베딩 입력을 재구성할 필드도 조회하지 않는다.
  스냅샷 본문을 갱신하고 임베딩 재생성이 끝나지 않은 상태에서 이전 본문 벡터로 새 공고를 추천할 수 있다.
- 가상 행에 `input_sha256='obsolete-input-hash'`를 넣어도 반환 1건·손상 0건으로 처리됐다.
  실제 DB에서 낡은 벡터를 발견했다는 뜻이 아니라, 검사 부재를 재현한 것이다.
- 생성 재개도 입력 해시만 같으면 건너뛰므로 모델 리비전·토큰 상한 등의 변경을 구분하지 못한다.
- 수정: 현재 입력의 기대 해시와 저장 해시를 대조하고, 모델·리비전·입력 계약 등 호환 조건을 검증한다.
  불일치는 결과에서 제외하고 stale 등 명시적 건수/이유로 남긴다. 생성 시 재사용 조건도 동일하게 맞춘다.
- 검증: 본문 변경 후 이전 벡터 유지, 같은 본문/다른 모델 메타데이터, 정상 일치 사례.

### 3. [P2] 차원이 다른 벡터 한 건으로 전체 검색이 실패함

- 위치: `search.py:221–228`, `embedding.py:71–79`.
- unpack은 바이트 길이와 행에 저장된 dim만 비교한다. 실제 질의/모델의 차원과는 비교하지 않는다.
  바이트와 dim이 서로 일치해도 현재 검색에 사용할 수 없는 벡터가 통과한다.
- 가상 질의 2차원에 문서 2차원·3차원 벡터를 섞으면 `np.vstack`의 `ValueError`로 요청 전체가 중단됐다.
  실제 모델에서도 같은 구조로 1024차원과 다른 차원이 섞일 때 발생한다.
- 수정: 각 후보를 추가하기 전에 모델/질의 기대 차원과 dtype·유한값 등 규약을 검증하고,
  실패한 공고만 `broken_vector`에 기록한다. 손상 벡터가 섞여도 정상 후보의 결과는 반환한다.
- 검증: 현재의 ‘바이트 길이와 dim 불일치’ 테스트에 더해, 바이트와 dim은 일치하지만 모델 차원과 다른 경우를 추가한다.

### 4. [P2] 접수 시작 전 공고도 접수기간 ‘충족’으로 판정함

- 위치: `search.py:126–135`; 스냅샷 선택도 `prepare.py:36`에서 종료일만 확인한다.
- apply_start를 조회하지만 SQL 조건과 기간 판정에서 사용하지 않는다.
  기준일 2026-09-18에 접수기간 2026-10-01~2026-10-31인 가상 공고가 반환되며,
  application_period는 `ok / 마감 2026-10-31`로 표시됐다.
- 수정: 접수 전 상태와 접수 중 상태를 구분한다. 접수 중 검색이면 확정된 미래 시작일은 제외하고,
  예정 공고도 보여줄 정책이면 별도 표시한다. 어느 정책이든 현재 신청 가능하다는 `ok`로 표시하지 않는다.
  시작일 없는 상시·날짜 미상 공고는 기존 3값 정책을 유지한다.
- 검증: 시작 전/당일, 마감 당일/다음 날, 시작일 미상. 스냅샷 범위 이름도 실제 선택 조건과 일치시킨다.

### 5. [P2] 모든 임베딩을 ‘잘리지 않음’으로 저장함

- 위치: `prepare.py:188–189`, `embedding.py:24`, `embedding.py:101–102`.
- 모델 입력 상한은 512토큰인데 벡터 저장 시 `truncated=0, token_count=None`을 상수로 넣는다.
  긴 본문이 잘려도 DB에는 잘리지 않았다고 기록된다. 본문 뒤에 붙인 신청 자격이 실제 임베딩에 포함됐는지도 알 수 없다.
- 이는 정적 코드로 확인한 메타데이터 오류다. 이번 리뷰에서 실제 1,852건의 토큰 길이나 잘림 비율을 측정한 것은 아니다.
- 수정: 실제 tokenizer 기준으로 잘림 전 토큰 수와 상한 초과 여부를 기록한다.
  같은 해시로 건너뛰는 기존 행도 메타데이터를 보정할 경로가 필요하다.
  단순 메타데이터 보정 때문에 전량을 다시 임베딩하지 않는다. 입력 배분/계약을 바꿀 경우에만 별도 버전으로 생성한다.
- 검증: 짧은 입력/상한 초과 입력/기존 행의 메타데이터 보정. 비교 보고서에 잘림 건수를 포함한다.

### 남은 수정 사항

**F1 [P2] 자격 제한이 아닌 문구와 제외 문구를 허용 목록으로 사용함**

- 위치: `conditions.py:110–116`, `conditions.py:141–153`, 연결되는 `search.py:151–168`.
- 규모 추출은 여전히 제목·분류 등에서 단어를 발견하면 known이다. 이제 이 값을 강제 제외에 연결해 잘못된 탈락이 발생한다.
  가상 제목 `대기업과 함께하는 기술교류`, 대상 `기업 규모 제한 없이 모든 기업 신청 가능`, target_category 빈 값에서
  규모가 `known/대기업`이 되고 **중소기업 신청자는 반환 0건**이다. 근거 문자열도 빈 값이다.
- 업종도 제한 힌트와 업종 단어의 동시 출현만 본다.
  `제조업을 영위하는 기업은 제외하며 그 외 업종은 모두 신청 가능`을 `known/제조업`으로 저장해,
  **제조업 신청자는 통과하고 서비스업 신청자는 탈락**하는 반대 결과를 재현했다.
- 수정: 지원대상의 명시적 긍정 자격만 허용 목록으로 만든다. 부정·예외·협력사 언급·복합 문구를 안전하게 해석하지 못하면 unknown으로 유지한다.
  제한 없음이 명시된 경우와 업종/규모 분류의 겹침도 단순 문자열 불일치로 탈락시키지 않는다.
  전수 추출 고도화는 필요 없으며 위 최소 반례를 회귀 테스트로 추가한다.
- 현재 저장 비교는 업종·규모 신청자 값이 없고 업종 조건도 전부 unknown이다. 위 오류가 이번 저장 결과에서 실제 발생했다고 주장하는 것은 아니다.

**F2 [P2] 검색에서 모델 리비전 불일치를 허용함**

- 위치: `search.py:268–272`. model_revision을 조회하고 현재 meta도 얻지만 비교하는 것은 contract/model뿐이다.
- 같은 모델명·입력 해시·차원에 `model_revision='obsolete-revision'`인 가상 벡터가
  **반환 1건, stale_vector 0건**으로 통과했다. 생성 중 일부만 새 리비전이거나 모델 캐시 리비전이 바뀌면
  서로 다른 벡터 공간을 비교하고도 정상으로 보고할 수 있다.
- 수정: 실제 질의 인코더의 리비전과 저장 리비전의 일치 여부를 검색에서도 검사한다.
  알 수 없는 리비전의 정책도 명시하고, 불일치는 stale로 제외한다. 입력 해시가 같다는 것만으로 호환된다고 판단하지 않는다.
- 현재 보고서에 실제 리비전 혼합이 있었다는 증거는 없다. 이번 확인은 검증 누락 재현이다.

**F3 [P2] 모델·차원 불일치로 재생성해도 기존 메타데이터가 남음**

- 위치: `prepare.py:165–169`, `prepare.py:191–194`.
- 재사용 판정은 model/model_revision/dim을 비교해 재생성하지만, 기존 키의 UPDATE에는
  `model`, `dim`, `dtype`, `normalized`가 빠져 있다. 예를 들어 dim이 잘못된 기존 행을 다시 만들면
  새 벡터 바이트 옆에 이전 dim이 남아 검색에서 계속 손상으로 제외되고 다음 생성도 반복된다.
- 가짜 연결/인코더로 재생성을 실행해 created=1과 실제 발행 UPDATE 절을 확인했다.
  갱신 항목은 vector/input_sha256/created_at/model_revision/truncated/token_count뿐이다.
  실제 DB에 쓰거나 재임베딩하지 않았다.
- 수정: 새 벡터의 모든 관련 메타데이터를 같은 UPSERT에서 갱신한다.
  기존 모델·차원 불일치 행을 재생성 → 검색 통과 → 다음 생성은 skipped가 되는 회귀 사례를 추가한다.
