## 1. [P2] 비교표의 기준일이 실제 검색 기준일과 다르다

- 위치: `eval/search_comparison.py:275–279`.
- 10개 입력의 `as_of_date`와 HTML의 기준일은 모두 **2026-09-15**다.
  하지만 manifest의 `as_of_today`는 **2026-09-18**이며, 원본 40개 응답은
  `2026-09-18T05:16:06+00:00`부터 `05:16:22+00:00` 사이에 생성됐다.
- `run_case()`는 원래 질의의 날짜를 서비스에 적용하지 않는다.
  `app.match()`의 마감 판단과 업력 계산은 실행일의 `date.today()`를 사용한다.
- 따라서 표를 보고 9월 15일 기준의 마감·업력 결과라고 판단하면 잘못된 해석이다.
  이번 쌍들이 서로 다른 날 실행됐다는 증거는 없으며, 문제는 실제 실행 조건과 표시의 불일치다.
- 수정: 실제 적용한 날짜를 비교표에 표시하고, 원래 질의의 날짜는 `원본 질의 기준일`로 별도 표기한다.
  재실행 시에는 시작·종료의 로컬 날짜를 확인해 날짜가 바뀌면 비교를 분리하거나 중단한다.
  과거 날짜로 실행한 것처럼 기록하지 않는다.

## 2. [P2] 규칙 적용 후보의 예시 건수를 최종 상위 5건의 통계로 해석했다

- 서비스는 **전체 검색 후보 중 규칙에 걸린 공고를 배열별 최대 5개씩** 이 필드에 넣는다.
  최종 `results`에 남은 공고 목록도 아니고, 전체 후보 중 규칙에 걸린 총건수도 아니다.
  전후 순위가 반드시 실제로 내려갔다는 의미도 아니다.
- 원본 B 단계 `results[*].rules`를 재계산하면 다음과 같다.

| 최종 상위 5에 남은 규칙 플래그 | dense 10사례·50칸 | hybrid 10사례·50칸 |
|---|---:|---:|
| 다른 시도 | 0 | 0 |
| 다른 시군구 | 0 | 0 |
| 집단 근거 없음 | 0 | 0 |

- 수정: 기존 수치는 `규칙에 걸린 후보 예시의 누적 건수(응답·규칙별 최대 5개)`로 고친다.
  최종 노출 잔존 건수는 위 표처럼 별도로 계산한다. 전체 영향 건수나 실제 순위 하락 건수를
  분석하려면 후보 전체와 재정렬 전후 순위가 필요하므로, 현재 응답만으로 추정하지 않는다.
  플래그가 0이라는 것은 **신청 자격이 모두 충족됐다는 뜻은 아니다.**

## 3. [P2] ID가 같고 내용이 낡은 색인을 정합성 검사에서 통과시킨다

- 위치: `eval/search_comparison.py:114–120`, `main()`의 `checks = data_check()` 이후.
- `corpus()`가 반환하는 공고별 입력 해시 `_shas`를 사용하지 않고,
  Chroma는 `get(include=[])`로 ID만 읽는다. BM25도 ID 집합만 비교한다.
- 공고 ID는 유지된 채 본문·지원대상이 변경되고 벡터만 이전 내용이면,
  현재 검사 결과는 모두 true여도 dense와 BM25가 다른 내용 기준으로 검색할 수 있다.
  또한 ID 집합 불일치가 false로 나와도 출력 후 실험을 계속한다.
- **이번 색인이 실제로 낡았다고 확인한 것은 아니다.** 저장된 산출물로는 지시서가 요구한
  내용 기준 일치를 입증할 수 없다는 검증 결함이다. DB의 `corpus_sha256` 하나로는
  그 DB 내용과 실제 검색 색인이 일치하는지 알 수 없다.
- 수정: 공고별 입력 해시와 저장 벡터의 입력 해시를 비교하고, 실제 Chroma 색인까지
  연결되는 검증 근거를 남긴다. BM25도 같은 입력 스냅샷으로 구성됐는지 확인한다.
  ID·내용 불일치 시 비교를 중단하고 별도 오류 기록을 남긴다. 색인을 자동 재생성하지 않는다.
  기존 `eval/build_pool.py`의 입력 해시 검사와 `shared/embed.py`의 메타데이터 처리를 참고할 수 있다.
- 재현 정보도 보완한다: 모델 리비전, 관련 로컬 코드 해시, 색인 식별 해시가 manifest에 없다.
  WORKLOG의 실행 Git 리비전 `0a72706`은 manifest의 `ab38ddf`와 다르므로 근거를 확인해 정정한다.
  `git_info()`의 전체 출력 `.strip()`은 첫 상태 행의 선행 공백을 제거해
  실제 manifest에서 `docs/STATUS.md`를 `ocs/STATUS.md`로 기록했다. 행의 선행 공백을 보존해야 한다.
  지금 구한 해시를 당시 실행에서 확보한 해시처럼 소급해 쓰지 않는다.

### 남은 기존 사항 — 실제 Chroma 벡터는 검증하지 않는다

`data_check()`는 DB와 NPZ 벡터 파일의 입력 해시를 비교하지만,
검색에 사용하는 Chroma는 여전히 `get(include=[])`로 ID만 읽는다.
입력 해시가 맞는 NPZ와 낡은 Chroma가 공존해도 `integrity_failures()`는 빈 목록을 반환한다.
가상 데이터에서 이 경로를 확인했다. 실제 저장 색인이 낡았다는 뜻은 아니다.

Claude가 `chroma_content_verified: false`를 manifest와 요약에 명시한 점은 올바르다.
따라서 이 결과는 **Chroma 내용 미검증이라는 한계를 가진 사례 비교**로 읽어야 하며,
전체 내용 정합성 검증이 완료됐다고 처리하면 안 된다.

추가 개선 시 색인 재생성부터 할 필요는 없다. Chroma의 `get(include=['embeddings'])`로
실제 벡터를 읽어 NPZ와 공고 ID별로 비교하고 컬렉션의 임베딩 메타데이터를 대조하는
읽기 전용 검사도 가능하다. 기존 `search/app.py::_fill_distances()`도 이 벡터 조회 기능을 사용한다.
입력 해시 메타데이터 추가만이 유일한 방법은 아니다.

### 이번 검증 근거

- 새 실행의 10입력·40응답·20비교를 독립적으로 재계산했다. 요청 쌍은 `search`만 다르고
