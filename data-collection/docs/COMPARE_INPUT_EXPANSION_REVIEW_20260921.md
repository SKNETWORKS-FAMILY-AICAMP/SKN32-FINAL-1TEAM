# `/compare` 신청자 입력 확장 리뷰

2026-09-21 · Codex · 구현 변경 없이 코드·API·테스트·실제 브라우저 동작 검토

대상:

- `experiments/sql_semantic/compare_input.py`
- `experiments/sql_semantic/viewer.py`
- `web/compare.html`
- `tests/test_verify_ui.py::CompareInputTests`
- `docs/VERIFY_UI.md`

## 판정

**입력 목록·조건부 필수·서버 선검증·방식별 변환·개인정보 응답 차단의 큰 구조는 맞다. 그러나 실제 비교 입력과 결과가 서로 다른 상태가 되는 P1 한 건과 데이터가 조용히 바뀌는 P2를 수정한 뒤 재검토가 필요하다.**

전용 테스트 30개와 전체 테스트 322개는 통과했다. 실제 8010 화면에서도 필수 항목, 사업자 유형별 조건부 필드,
세 열 결과와 사용 여부 표가 표시된다. 다만 현재 정적 문자열 위주의 UI 테스트는 아래 상태 전이 문제를 잡지 못한다.

## 수정 필요

### [P1] 예시 버튼이 폼 전체를 초기화하지 않아 이전 선택값이 다음 비교에 섞임

- 위치: `web/compare.html:390-416`.
- 예시 적용 코드는 유형·대표자 기본값·지역·업종·이력·아이디어·수익모델·팀만 덮어쓴다.
  `certifications`, `hiring_plan`, `equipment`, `partners`, `self_funding`, `self_funding_budget`는 초기화하지 않는다.
- 실제 브라우저에서 `예비창업자` 예시를 적용한 화면에 이전 선택인 `기업부설연구소`가 계속 체크된 상태를 확인했다.
  이후 `제조 법인` 예시로 바꿔도 같은 인증이 남았다. 다음 검색에서는 예시 정의에 없는 인증이 검색어·규칙에 들어가므로,
  같은 이름의 예시가 이전 조작에 따라 다른 결과를 낸다.

수정 기준:

1. 예시 적용 전에 모든 입력·체크박스·반복 행·조건부 값을 한 번 초기화한 뒤 예시 값을 채운다.
2. 임의 선택값을 만든 뒤 각 예시 버튼을 눌러 `collect()` 결과가 예시 정의와 정확히 같은지 브라우저 동작 테스트를 추가한다.
3. 예시 전환 순서와 무관하게 같은 payload가 나오는지도 확인한다.

### [P2] 입력을 바꿔도 이전 검색 결과와 사용 여부 표가 그대로 남음

- 위치: `web/compare.html:252-287`, `web/compare.html:358`, `web/compare.html:406-416`, `web/compare.html:470-489`.
- 검색 완료 뒤 예시 버튼이나 일반 입력을 바꿔도 `#out`과 완료 상태가 갱신되거나 오래된 결과로 표시되지 않는다.
- 실제 브라우저에서 현재 폼은 `법인 / 남성 / 제조업`인데 결과 아래 성별 사용 여부는 이전 실행의
  `규칙 (여성 대상 공고 유지)`로 남아 있었다. 결과 목록도 이전 입력의 결과가 그대로 보였다.
- 이 화면은 입력별 검색 방식 비교를 검증하는 도구이므로, 현재 폼과 결과가 섞이면 사람이 잘못된 결론을 내릴 수 있다.

수정 기준:

1. 검색 성공 시 제출한 입력의 지문 또는 복사본을 페이지 메모리에만 둔다.
2. 이후 입력·선택·반복 행·예시가 바뀌면 결과를 지우거나 `입력이 바뀌었습니다. 다시 검색하세요`로 명확히 잠근다.
3. 검색 중 입력 변경도 처리하고, 이전 요청이 늦게 끝나 새 입력 화면에 결과를 덮어쓰지 않게 요청 세대 번호나 취소 처리를 둔다.
4. 입력 변경 후 이전 사용 여부 표가 유효한 것처럼 남지 않는 브라우저 회귀 테스트를 추가한다.

### [P2] 서버 날짜 검증이 뒤 문자열을 잘라 내고 유효한 날짜로 승인함

- 위치: `experiments/sql_semantic/compare_input.py:105-109`.
- `_date()`가 `str(text).strip()[:10]`만 파싱한다. 따라서 `birth_date="1980-01-01garbage"`와
  `founded_at="2021-04-01garbage"`가 모두 오류 없이 승인되는 것을 독립 재현했다.
- 문서와 오류 문구는 정확한 `YYYY-MM-DD` 형식을 계약으로 말하므로 API 검증이 그 계약과 다르다.

수정 기준:

1. 공백 제거한 전체 문자열을 `date.fromisoformat()`으로 파싱하고 뒤 문자를 허용하지 않는다.
2. 정상 윤년·잘못된 월/일·날짜 뒤 문자열을 포함한 서버 테스트를 추가한다.

### [P2] 21번째 이후 수익모델·팀 행을 오류 없이 버림

- 위치: `experiments/sql_semantic/compare_input.py:256-279`, `experiments/sql_semantic/compare_input.py:319-331`.
- 두 반복 필드는 검증 전에 `raw.revenue[:MAX_LIST]`, `raw.team[:MAX_LIST]`로 자른다.
- 21개 완성 행을 API 계약에 넣었을 때 200 상당으로 승인되고 정리 결과는 20개만 남는 것을 재현했다.
  화면에는 행 추가 제한도 없어 사용자가 입력한 내용이 조용히 사라질 수 있다.

수정 기준:

1. 자르기 전에 길이가 `MAX_LIST`를 넘는지 검사해 4xx 필드 오류를 반환한다.
2. UI에서도 최대 행 수에서 추가 버튼을 비활성화하고 이유를 글자로 알린다.
3. 20개 승인·21개 거부를 API와 UI 양쪽 테스트로 고정한다.

### [P2] 필수 수익모델 반복 입력에 필수·오류 관계가 접근성 트리에 없음

- 위치: `web/compare.html:162-166`, `web/compare.html:229-250`, `web/compare.html:338-355`.
- 수익모델은 필수지만 반복 행 컨테이너나 생성된 입력에 `aria-required`가 없고, 각 입력이 `e-revenue`와
  `aria-describedby`로 연결되지 않는다. 실제 접근성 트리에서는 두 입력이 placeholder 설명만 가진 일반 텍스트 필드로 보였다.
- 오류 시 첫 입력으로 초점은 가지만 동적 입력에는 `aria-invalid`가 설정되지 않는다.

수정 기준:

1. 수익모델 묶음을 접근 가능한 이름을 가진 `group`으로 만들고 필수 상태와 `e-revenue`를 연결한다.
2. 오류가 난 행의 입력에 `aria-invalid`와 오류 설명 연결을 적용한다.
3. 정적 HTML 문자열 개수 테스트 대신 실제 접근성 트리에서 필수·오류·초점 이동을 확인한다.

## 낮은 우선순위

### [P3] 새 방식에서 쓰지 않는 `district`를 adapter가 전달함

- 위치: `experiments/sql_semantic/compare_input.py:377-388`.
- `field_usage()`는 시·군·구를 새 방식 `미사용`으로 정확히 표시하지만 `lab_applicant()`는 `district`를 넘긴다.
- 동작 오류는 아니지만 “새 방식이 실제로 읽는 칸만 넘긴다”는 함수 설명과 지시서의 adapter 원칙에 어긋난다.
  판정에서 지원하기 전에는 payload에서도 빼거나, 향후 사용을 위한 전달이라면 설명과 계약을 명시한다.

## 확인한 정상 동작

- 사용자 목록의 필수·선택·조건부 필드가 화면에 있고 개인사업자·법인에서 사업자번호·설립일이 필수다.
- 예비창업자 payload에서 사업자번호·설립일·자기부담금이 서버에서도 제거된다.
- 검증 실패는 세 검색을 호출하기 전에 400과 필드별 오류를 반환하며 오류 응답에 이름·생년월일·사업자번호 값을 넣지 않는다.
- hybrid·dense는 동일 payload를 받고 검색 모드만 다르며, 새 방식에는 업종이 adapter를 거쳐 전달된다.
- 응답 `input_summary`와 결과에는 이름·생년월일·사업자번호가 포함되지 않는다.
- `/compare` 코드에는 `localStorage`, `sessionStorage`, query string 저장이 없다.
- 실제 화면의 데스크톱 배치는 읽을 수 있고 조건부 필드가 시각적으로 구분된다.

## 후속 재검토 — Claude 수정 반영 결과 (2026-09-21)

### 판정

**기존 P1·P2 네 건과 P3는 해결됐다. `/compare` 입력 확장은 승인한다.**

예시 적용 전 전체 초기화, 입력 변경 시 결과 무효화와 늦은 응답 폐기, 정확한 날짜 형식 검사,
20행 승인·21행 거부, 반복 입력의 접근성 연결, 새 방식의 `district` 미전달을 코드·테스트·실제 브라우저에서 확인했다.
아래 P3 한 건은 검색이나 payload를 잘못 만들지 않는 상태 안내 문제라 승인을 막지 않는다.

### 해결 확인

- `resetForm()`이 `top`을 제외한 입력·체크박스·반복 행을 지운 뒤 예시를 채운다. 실제 브라우저에서
  `기업부설연구소`를 체크한 법인 화면에서 `예비창업자` 예시로 전환했을 때 인증 선택이 비고 사업자 필드가 숨겨졌다.
- 성공 결과가 있는 상태에서 payload가 바뀌면 결과와 사용 여부 표를 지우고 재검색을 안내한다.
  검색 중 변경에는 세대 번호를 사용해 늦은 응답을 버린다.
- `birth_date="1980-01-01garbage"`, `founded_at="2021-04-01garbage"`를 독립 호출에서 모두 거부했다.
- 수익모델·팀은 각각 20행을 승인하고 21행을 서버에서 400으로 거부한다. 화면도 20행에서 추가를 막고 이유를 표시한다.
- 수익모델 묶음은 접근 가능한 이름·오류 설명을 가지며 오류 입력에 `aria-invalid`와 초점이 연결된다.
- 새 방식 adapter의 실제 키에 `district`가 없고 사용 여부 표도 `미사용`과 일치한다.
- `/compare/selftest`: **14개 통과, 0개 실패**. 일반 `/compare` 탭의 콘솔 경고·오류는 없었다.

### [P3] 검증 오류 뒤 예시를 적용해도 상태줄의 이전 오류가 남음

- 위치: `web/compare.html:368-375`, `web/compare.html:492-503`.
- `showErrors()`가 `shown=false`, `inFlight=false` 상태에서 `입력을 확인하세요`를 표시한다. 이후 예시 버튼은
  모든 값을 정상값으로 채우고 필드 오류를 지우지만, 마지막 `invalidate()`가 `if(!shown && !inFlight) return`에서 끝나
  상태줄은 계속 `입력을 확인하세요 (1개 칸).`으로 남는다.
- 실제 `/compare/selftest` 안의 비교 화면에서 이름을 비우고 제출한 뒤 `제조 법인` 예시를 적용해 재현했다.
  이름은 `테스트대표`로 복구되고 필드 오류는 사라졌지만 상태줄만 이전 오류를 유지했다.
- 예시 적용이나 오류 필드 수정으로 현재 로컬 검증 오류가 해소됐을 때 상태를 비우거나
  `입력이 채워졌습니다. 검색하세요.`로 바꾸고, 이 전이를 자체 시험에 추가하면 된다.

- 전체 테스트: **335개 통과, 13개 건너뜀**
- 기존 비차단 `ResourceWarning`은 `eval/search_comparison.py`, `tests/test_search_comparison.py`에서 동일하게 남는다.
- 구현·테스트는 수정하지 않았고 리뷰·상태 문서만 갱신했다. Git staging·commit·push는 하지 않았다.
