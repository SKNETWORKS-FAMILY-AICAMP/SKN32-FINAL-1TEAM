## 2. 결정 — 업종은 순위 신호로 쓴다 (2026-09-28)

**사용자 결정: 기획서대로 신청자의 주 업종은 매칭 순위에만 반영하고, 정형 필터와 자격 게이트에는 쓰지 않는다.**

근거 문서:

- 기획서 4-2·5-3: 희망 지역·주 업종은 정형 필터와 자격 판정에 쓰지 않고 매칭 순위에만 반영한다.
- 기능정의서 R-2: 게이트 대조 항목은 지원대상 유형·업력·접수기간 세 가지다. 생년월일·희망 지역·주 업종·첫 창업 여부는 대조하지 않는다(담당자 협의 2026-09-22).
- 기능정의서 R-3: `preference: {region, industryCode}`는 순위 반영용이며 필터에 쓰지 않는다. **반영 방식은 구현 시 확정한다.**
- 기능정의서 `EligibilityRule.industryCodes`: 업종 조건. 쓰임은 `regionCodes`와 같다(희망 지역과 대조해 순위 반영, 게이트 대조 아님).

이 결정으로 바뀌는 것:

| 항목 | 이전(2026-09-22 인계) | 지금 |
|---|---|---|
| 업종 추출의 목적 | 신청자 주업종과 비교하는 **정형 게이트**. "확실한 불일치만 제외" | 공고의 `industryCodes`를 만들어 R-3의 **순위 신호**로 쓴다. 공고를 후보에서 빼지 않는다 |
| `filter_ready` | 사람 검증 후 게이트 사용 여부 | 게이트 용도는 폐기. 순위 신호 사용 가능 여부의 표시로 다시 정의할지 설계 때 정한다 |
| 오류의 비용 | 잘못 빼면 신청 가능한 공고가 사라짐(치명) | 잘못 반영하면 순서가 밀림(비치명). 그래도 틀린 신호는 순위를 해치므로 정확도는 계속 중요 |
| [인계서](archive/NEXT_SESSION_HANDOFF_20260922.md)의 "신청자 주업종 정형 게이트 승인 전 금지" | 유효 | 게이트 연결 자체를 하지 않으므로 대상 없음. DB 적재와 순위 연결은 설계 확정과 검증 뒤에 한다 |

### 순위 반영 방식 — 확정 (2026-09-28 사용자 승인, 구현 전)

기능정의서가 "구현 시 확정"으로 남겨 두었다. 지역의 현행 방식(`search/app.py`: 다른 지역 전용 공고는 뒤로 보내고 빼지 않음, 지역 정보가 없는 공고는 건드리지 않음)과 같은 원칙이다. 사용자가 아래 표대로 하기로 했다.

| 공고의 업종 판정 | 신청자 주 업종과의 관계 | 제안 반영 |
|---|---|---|
| `known` + 목록 완전 | 신청자 업종이 허용 목록 밖 | 뒤로 보낸다(감점) |
| `known` | 신청자 업종이 허용 목록 안 | 그대로 또는 가산(가산 여부는 평가로 정함) |
| `excluded_only` | 신청자 업종이 구체 제외 목록 안 | ~~뒤로 보낸다~~ → **건드리지 않는다**(2026-09-28 사용자 결정, 아래 참고) |
| `not_mentioned`·`no_limit`·`conditional`·`unknown`, 목록 불완전·잘림, 제외표 참조문만 있음 | — | **건드리지 않는다**(모른다고 벌주지 않는다) |

**제외 목록은 순위에 쓰지 않는다 (2026-09-28 사용자 결정, A안).** F2에서 확인해 보니 제외값은 "일반유흥주점업·갬블링·담배 중개업·모피제품 도매업"처럼
세부 업종이었다. 대부분 소상공인 정책자금 제외 업종 목록을 옮겨 적은 것이다(final5 기준: 제외 목록이 있는 공고 370건 가운데 사행·도박 174건, 유흥·주점 125건).
이 값을 KSIC 대분류로 올리면 같은 대분류의 신청자(일반 음식점 I, 편의점 G)까지 "제외 목록 안"이 된다.
신청자에게 세부 업종 코드를 받는 방식(C안)은 예비창업자에게 코드가 없어 맞지 않고, 대분류 이름 그대로인 제외만 쓰는 방식(B안)은 "금융업"처럼 범위가 애매한 경우가 많다.
따라서 업종 순위에는 **허용 목록만** 쓴다(`industry_groups.allowed_sections`). 필요하면 평가 뒤에 B안을 덧붙인다.

감점 크기 같은 값은 [가중치 평가](../eval/weight_eval.py) 방식처럼 평가 질의로 효과를 재서 정한다. 원칙은 확정했지만 아직 구현하지 않았다. 신청자·공고 업종을 같은 코드로 맞추는 F2가 먼저 필요하다.

### 업종 작업 우선순위에 주는 영향 — 제안

- **F2 KSIC 대분류 매핑**의 중요도가 올라간다. 순위 비교는 신청자 주 업종과 공고 업종을 같은 코드 체계로 맞춰야 성립한다(기능정의서 `industryCode`·`industryCodes`).
- **F1-2 제외표 참조문**은 여전히 필요하다. 참조문만 있는 `excluded_only`를 "구체 제외 목록"으로 읽으면 신청자를 잘못 뒤로 보낼 수 있다. 다만 게이트가 아니므로 치명도는 낮아졌다.
- 제안 순서: 순위 반영 방식 확정 → F2 KSIC 매핑 → F1-2 → 평가 질의로 효과 측정. 사용자가 순서를 정한다.

### 담당이 불분명하거나 미확정

- **가산점 정보(`bonusInfo`)**: 공고 본문에서 가져온다(R-1). 코드가 없다. LLM 채점 방식·저장 구조·사용자 정보 대조 여부가 미확정이고, 확정되면 규칙 모듈 밖의 LLM 처리로 정의한다고 적혀 있다.
- **출처 고지 문구**(6-1): 카드·상세 요약에 표시한다. 화면은 프론트 파트, 출처 필드 제공은 데이터 파트.
- **기능정의서 미확정 목록(v1.9)**: 지역·업종의 순위 반영 방식과 지역 한정 공고 보완 방안, 폴백 중 BM25 오류·둘 다 실패의 처리, `fitScore` 산식, RRF 상수 k.

### 기획서에 없는 이 폴더의 작업

- 리랭커·업력 분류기(`ml/`): ML 제출물용. 서비스 미연결이며 기획서와 충돌하지 않는다.
