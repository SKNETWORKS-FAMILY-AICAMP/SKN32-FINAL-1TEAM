# 직접 검색 비교 화면 `/compare` 리뷰

2026-09-21 · Codex · 구현 변경 없이 코드·API·테스트·실제 브라우저 동작 검토

대상:

- `experiments/sql_semantic/viewer.py`
- `web/compare.html`
- `tests/test_verify_ui.py::CompareTests`
- `docs/VERIFY_UI.md`

## 판정

**세 검색을 실제로 실행하고 나란히 보여 주는 기본 동작은 정상이다. 다만 비교 결과를 잘못 해석하게 할 수 있는 P2 두 건을 수정한 뒤 재검토가 필요하다.**

8010 `/compare`에서 제조 예시를 실제 실행해 기존 hybrid·dense와 새 SQL→임베딩 결과가 각각 5건씩 표시되고,
조건 판정·검색어·겹침 배지·새 방식 후보 수가 렌더링되는 것을 확인했다. 데스크톱 3열 배치는 읽을 수 있었고
브라우저 콘솔 오류는 없었다. 기존 서비스 8000과 검증 화면 8010 모두 정상 응답했다.

## 수정 필요

### [P2] `이 방식에만`은 전체 검색 결과가 아니라 선택한 Top N에만 해당함

- 위치: `web/compare.html:148-151`, `web/compare.html:170`, 연결되는
  `experiments/sql_semantic/viewer.py:491-492`, `experiments/sql_semantic/viewer.py:545`.
- `mark_overlap()`은 세 방식이 돌려준 **Top N 목록만** 비교한다. 목록에 없다는 것은 N위 밖이라는 뜻이지,
  그 방식에서 찾지 못했거나 그 방식에만 존재한다는 뜻이 아니다.
- 화면은 이를 `이 방식에만`, `세 방식 모두에 나온 공고`라고 표시해 전체 검색 공간에 대한 배타성·공통성처럼 읽힌다.
- 실제 제조 예시에서 Top 5일 때 `이 방식에만`으로 표시된 `kstartup:178831`, `kstartup:175817`은
  같은 입력의 Top 10 비교에서는 다른 방식 목록에도 나타났다. 따라서 현재 문구는 실데이터에서도 바로 반례가 나온다.

수정 기준:

1. `이 방식 Top N에만`, `다른 방식 Top N에도`, `세 방식 Top N 공통`처럼 범위를 문구에 명시한다.
2. 현재 선택값을 반영해 `Top 5`, `Top 10`처럼 표시하면 더 명확하다.
3. Top 5에서는 단독이지만 Top 10에서는 겹치는 fixture를 추가해, UI/API 문구가 전체 독점으로 표현되지 않게 고정한다.

### [P2] 실험 DB 공고 ID 영구 캐시가 재적재 뒤 존재 배지와 건수를 낡게 만듦

- 위치: `experiments/sql_semantic/viewer.py:437`, `experiments/sql_semantic/viewer.py:467-478`.
- `_LAB_IDS`는 첫 `/api/compare` 요청에서 한 번 읽은 뒤 프로세스가 끝날 때까지 갱신되지 않는다.
- 반면 `run_lab()`은 매 요청마다 현재 실험 DB를 조회한다. 서버가 켜진 상태에서 `prepare`로 실험 DB를 재적재하면
  새 방식 결과는 새 DB를 쓰지만 `in_lab_data`, `lab_notice_count`, `새 방식 데이터에 없는 공고` 배지는 이전 ID 집합을 쓴다.
- 특히 이 화면은 F1 수정 뒤 `sql_lab_v1 → sql_lab_v2` 재적재를 실제 작업 흐름으로 갖고 있어 단순 이론적 경우가 아니다.

수정 기준:

1. 비교 요청마다 ID를 다시 SELECT하거나, 데이터셋 버전/갱신 지문과 함께 캐시해 변경 시 무효화한다.
2. 같은 프로세스에서 첫 조회 뒤 DB ID 집합을 바꾼 두 번째 요청이 새 건수·존재 여부를 반환하는 회귀 테스트를 추가한다.
3. ID 조회 실패 시 현재처럼 비교 자체는 계속하되, 배지를 숨긴 이유를 화면에 명시하면 진단하기 쉽다.

## 낮은 우선순위

### [P3] 잘못된 `top` 값이 400이 아니라 500이 됨

- 위치: `experiments/sql_semantic/viewer.py:499`.
- `top: "abc"`를 보내면 `int()`의 `ValueError`가 처리되지 않아 실제 API가 500을 반환했다.
- 화면의 `<select>`로는 발생하지 않지만 API 경계에서는 유효성 오류다. Pydantic 요청 모델 또는 안전한 변환으로
  1~10 범위를 검증하고 4xx를 반환하는 편이 좋다. `1.5`는 현재 정수 1로 조용히 잘린다.

### [P3] 결과 링크는 HTML 이스케이프만 하고 URL 스킴을 제한하지 않음

- 위치: `web/compare.html:145`.
- `esc()`는 따옴표 삽입은 막지만 `javascript:`·`data:` 같은 URL 스킴은 막지 않는다.
  공고 URL은 수집 데이터이므로 `http:`·`https:`만 링크로 만들고 나머지는 텍스트로 표시하는 편이 안전하다.

### [P3] 검색 상태 변경이 보조기기에 공지되지 않음

- 위치: `web/compare.html:94`, `web/compare.html:164-173`.
- `검색 중`, 오류, 완료 건수를 글자로 보여 주는 것은 좋지만 상태 영역에 `aria-live` 또는 `role="status"`가 없어
  키보드·화면 읽기 사용자에게 비동기 완료가 전달되지 않는다.

## 확인한 정상 동작

- 8000 서비스 코드를 수정하지 않고 `/api/match`를 hybrid·dense로 각각 호출한다.
- 새 방식은 실험 DB를 SELECT로 읽고 결과를 저장하지 않는다.
- 한 열이 실패해도 다른 열 결과를 반환하며, 실패 사유를 해당 열에 표시한다.
- 아이디어 필수 입력, Top N 상한 10, 예비창업자 전달, 세 열 공통 ID 계산의 기본 테스트가 있다.
- 제목·ID·조건 문구 등 HTML 본문 값은 이스케이프하며 외부 링크에 `noopener`·`noreferrer`를 둔다.
- 서로 다른 공고 집합·서로 다른 검색어·사람 판정 부재를 화면 상단에 명시해 방식 우위를 주장하지 않는다.
- 결과의 코사인 유사도를 정확도나 확률로 부르지 않는다.
- 1,500px급 데스크톱 화면에서 폼과 3열 결과가 겹치거나 잘리지 않았고, 콘솔 warning/error가 없었다.

## 후속 재검토 — P2·P3 반영 결과 (2026-09-21)

### 판정

**이전 리뷰의 P2 두 건과 P3 세 건이 모두 해결됐으며 `/compare`를 승인한다.**

새 차단 결함은 발견하지 못했다. 기존 한계인 서로 다른 공고 집합·서로 다른 검색어·사람 관련성 판정 부재는
화면에 그대로 공개돼 있으며, 따라서 이 화면만으로 검색 방식의 품질 우위를 주장하지 않는 조건도 유지된다.

### 이전 지적 해결 확인

1. **Top N 범위 명시**
   - API가 `top`, `overlap_scope`를 반환한다.
   - 상단 안내, 완료 상태, 결과 배지가 각각 `Top N 목록 안에서만`, `세 방식 Top 5 목록`,
     `이 방식 Top 5에만`처럼 범위를 명시한다.
   - Top 5에서는 단독이지만 Top 10에서는 다른 방식에도 나타나는 회귀 사례가 추가됐다.
2. **실험 DB ID 캐시 제거**
   - `lab_notice_ids()`가 요청마다 새 연결로 현재 `lab_notices` ID를 SELECT하고 연결을 닫는다.
   - 같은 프로세스의 연속 두 조회에서 변경된 두 번째 ID 집합을 반환하는 테스트가 통과했다.
   - ID 목록 조회만 실패하면 세 검색 결과는 유지하고, 존재 배지를 생략한 이유를 `lab_ids_error`와 화면 상태에 표시한다.
3. **`top` 입력 검증**
   - `parse_top()`이 불리언·비정수 실수·해석 불가 문자열을 거부하고 검색 호출 전 HTTP 400을 반환한다.
   - 실제 실행 중인 8010 API에서도 `top="abc"`가 400으로 재현됐다.
4. **외부 링크 제한**
   - `safeUrl()`이 `http:`·`https:` 링크만 만들고 나머지는 제목 텍스트로 표시한다.
5. **비동기 상태 접근성**
   - 상태 영역에 `role="status"`, `aria-live="polite"`가 추가됐다.

### 독립 재검증

- `/compare` 전용 테스트: **13개 통과**
- 전체 테스트: **305개 통과, 13개 건너뜀**
- 실행 중인 8010 API: 잘못된 `top` → HTTP **400**
- 실제 `/compare` 화면: Top 5 범위 안내·상태·각 결과 배지가 일관되게 표시됨
- 실제 외식 예시: 세 방식 Top 5 공통 2건, 새 방식 데이터 1,852건, 세 열 결과 정상
- 브라우저 콘솔: warning/error 없음
