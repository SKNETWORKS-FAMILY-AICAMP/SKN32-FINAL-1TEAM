# Claude 작업 지시서 — `/compare` 신청자 입력 확장

작성: 2026-09-21 · Codex / 구현 담당: Claude / 후속 검토: Codex

## 목적

현재 `/compare`는 아이디어·신청자 유형·지역·시군구·설립일·Top N 정도만 받는다.
사용자가 지정한 신청자 정보를 빠짐없이 받도록 확장하고, 같은 입력을 기존 hybrid·dense와
새 SQL→임베딩 방식에 전달한다.

단순히 입력칸만 추가하지 않는다. 아래 네 가지를 함께 맞춘다.

1. 필수·선택·조건부 필수 규칙
2. 브라우저와 API 양쪽 검증
3. 각 검색 방식에 전달되는 값과 실제 사용 여부의 투명한 표시
4. 이름·생년월일·사업자등록번호 등 개인정보를 저장·로그·보고서에 남기지 않는 처리

메인 화면 `web/app.html`에는 이미 대부분의 입력 UI와 요청 필드가 있다. 같은 의미의 필드명·선택지·설명을
새로 발명하지 말고 최대한 재사용한다. 다만 `/compare`의 목적과 검증 계약은 별도로 명확히 둔다.

## 범위

이번 1차 범위는 **`/compare` 입력 폼과 `POST /api/compare` 요청 계약 확장**이다.

- 기존 서비스 8000의 검색 알고리즘·랭킹·가중치를 바꾸지 않는다.
- SQL 실험의 조건 추출·벡터·DB 스키마를 다시 만들지 않는다.
- 입력받았다는 이유만으로 모든 필드가 매칭에 쓰인다고 표현하지 않는다.
- 사람 관련성 판정, 모델 재학습, 재임베딩, Chroma 변경은 범위 밖이다.
- Git staging·commit·push는 하지 않는다.

## 입력 계약

### 필수 항목

| 화면 이름 | 권장 요청 필드 | 조건·검증 | 현재 처리와 연결 |
|---|---|---|---|
| 신청자 유형 | `applicant_type` | `예비창업자 / 개인사업자 / 법인` 중 하나 | 기존 서비스·새 방식 모두 |
| 이름 | `owner_name`, 필요 시 기존 `name`에도 동일 값 | 공백 제거 후 필수 | 현재 서비스에서는 저장 정보이며 검색어에 넣지 않음 |
| 생년월일 | `birth_date` | 유효한 날짜, 미래 날짜 금지 | 현재는 보관만 함. 검색에 쓴다고 표시하지 않음 |
| 성별 | `gender` | 명시된 선택지 중 하나 | 현재 서비스 규칙은 `여성`일 때만 여성 대상 공고에 사용 |
| 지역 | `region` | 시·도 필수. 시·군·구는 별도 선택 항목으로 유지 가능 | 두 방식 모두 지역 판정에 사용 |
| 주 업종 | `main_industry`; 새 방식 adapter에서는 `industry` | 공백 제거 후 필수 | 기존 서비스는 질의·규칙, 새 방식은 업종 조건 판정 |
| 사업자등록번호 | `business_no` | **개인사업자·법인만 조건부 필수**, 숫자 10자리 | 현재 서비스는 보관만 함. 예비창업자 전환 시 값 제거 |
| 대표자 이력 | `owner_career` 신규 권장 | 공백 제거 후 필수 | 선택 팀원과 분리. 기존 검색에 연결할 때 대표 경력 1건으로 명시적으로 adapter 처리 |
| 수익모델 단가 | `revenue: [{item, price}]` | 완성된 항목 최소 1개. 항목명·단가 모두 필수 | 기존 서비스 질의에 수익 항목을 사용. 단가는 현재 보관 성격임을 표시 |
| 아이디어 설명 | `idea` | 공백 제거 후 필수 | 세 방식 모두 검색 입력 |

### 선택 항목

| 화면 이름 | 기존/권장 필드 | 조건 |
|---|---|---|
| 보유 인증·가입/확인서 | `certifications: list[str]` | 기존 `/api/form` 선택지 재사용. 특정 “가입 확인서”가 별도 종류라면 의미를 확인하기 전 새 판정 로직을 만들지 않음 |
| 예비창업자 희망 사업 규모 | `budget_scale` | 예비창업자일 때만 표시·전달, 0 이상 금액 |
| 자기부담금 가능 여부 | `self_funding`, `self_funding_budget` | 개인사업자·법인일 때만 표시. 가능액은 선택 |
| 팀 구성원 | `team: [{name, role, career}]` | 대표자 이력과 별도. 불완전한 빈 행은 전송하지 않음 |
| 채용 계획 | `hiring_plan` | 불리언 |
| 장비 보유 | `equipment: list[str]` | 쉼표 목록 또는 반복 행. 현재는 보관만 함 |
| 협력기관 보유 | `partners: list[str]` | 현재 서비스 규칙에 사용. 장비와 한 필드로 합치지 않음 |

## 설립일 처리 — 구현 전에 명시할 결정

사용자 새 목록에는 `설립일`이 없지만 현재 두 검색 방식은 업력 판정에 `founded_at`을 사용한다.
**권장 기본안은 개인사업자·법인의 조건부 필수로 유지하는 것**이다. 빼면 업력 조건이 대부분 `확인 필요`가 되어
새 방식 비교의 의미가 약해진다.

Claude는 구현 이력에 이 판단을 명시한다. 사용자가 설립일을 받지 않겠다고 확정하면 임의로 가짜 날짜를 넣지 말고,
빈 값으로 전달해 업력 `확인 필요`를 그대로 보여 준다.

## 요청 모델과 adapter

### 1. `/api/compare` 전용 입력 모델

지금처럼 `body: dict`에서 값을 하나씩 꺼내지 말고 Pydantic 모델을 둔다. 필수·조건부 필수 검증은 서버에서도 한다.
기존 `search.app.MatchRequest`의 기본값을 한꺼번에 필수로 바꾸면 다른 UI·테스트·CLI를 깨뜨릴 수 있으므로,
이번에는 compare 전용 모델에서 검증한 뒤 각 검색 방식 payload로 변환한다.

검증 실패는 검색·모델·DB를 호출하기 전에 HTTP 4xx와 필드별 오류로 반환한다. 원본 개인정보 값은 오류 메시지에 넣지 않는다.

### 2. 기존 hybrid·dense

두 호출에 **완전히 같은 전체 payload**를 보낸다. `search` 값만 각각 `hybrid`, `dense`로 달라야 한다.

- 이름·생년월일·사업자번호는 검색어에 넣지 않는다.
- 대표자 이력과 선택 팀원 이력은 중복 삽입하지 않는다.
- 기존 `MatchRequest`에 `owner_career`가 없으면 명시적인 adapter로 대표 `TeamMember` 한 건을 만들거나
  별도 필드를 추가한다. 어떤 방식을 택했는지 테스트와 문서에 남긴다.
- 수익모델은 기존 `RevenueItem` 구조를 재사용한다.

### 3. 새 SQL→임베딩 방식

현재 실제 사용하는 필드만 `run_lab()` applicant에 명시적으로 전달한다.

- `idea`
- `region`, `district`
- `founded_at`, `prestartup`
- `industry` ← `main_industry`
- 그 밖에 새 검색이 실제 지원하는 필드

지원하지 않는 이름·생년월일·성별·사업자번호·단가·장비 등을 사용한 것처럼 꾸미지 않는다.
응답 `meta` 또는 화면 설명에서 방식별로 `검색에 사용 / 규칙에 사용 / 입력만 받음·미사용`을 구분해 보여 준다.

## 화면 구성

한 줄에 모든 필드를 몰아넣지 않는다. 다음 순서로 묶는다.

1. 신청자 유형
2. 대표자 기본 정보: 이름·생년월일·성별
3. 사업 정보: 지역·시군구·주 업종·조건부 사업자번호·조건부 설립일
4. 대표자 이력
5. 아이디어와 수익모델 단가
6. 선택 정보: 인증/확인서·희망 사업 규모·자기부담금·팀·채용·장비·협력기관
7. Top N과 비교 실행

필수 표시를 텍스트와 `required`/`aria-required`로 제공한다. 제출 시 첫 오류로 초점을 옮기고 항목 가까이에
구체적인 오류를 표시한다. 색만으로 필수·오류·조건부 상태를 구분하지 않는다.

신청자 유형 전환 시:

- 예비창업자: 사업자번호·설립일·자기부담금 영역을 숨기고 전송 값도 제거한다.
- 개인사업자·법인: 희망 사업 규모 영역을 숨기고 전송 값도 제거한다.
- 숨긴 필드의 이전 값이 payload에 남지 않게 한다.

예시는 실제 개인정보처럼 보이지 않는 명백한 테스트 값만 사용한다.

## 개인정보·저장 제한

이름·생년월일·사업자등록번호는 개인정보 또는 민감한 식별 정보로 취급한다.

- `/compare`는 현재 원칙대로 결과와 입력을 파일·DB에 저장하지 않는다.
- localStorage/sessionStorage/URL query string에 전체 입력을 저장하지 않는다.
- 서버 로그, 오류 메시지, 테스트 결과, WORKLOG, 스크린샷에 원본 이름·생년월일·사업자번호를 남기지 않는다.
- 화면 재표시가 필요하면 현재 페이지 메모리 안에서만 유지한다.
- 테스트에는 `테스트대표`, `0000000000`처럼 명백한 가짜 값을 사용한다.
- 응답에 입력을 되돌려줄 필요가 있으면 사업자번호는 제외하거나 마스킹한다.

메인 화면 `web/app.html`은 현재 직전 입력을 localStorage에 저장하므로, 이번 작업이 그 화면까지 공통화된다면
민감 필드를 그대로 저장하는 기존 동작도 함께 점검하고 별도 판단 없이 복사하지 않는다.

## 필수 테스트

외부 DB·모델·8000 서비스를 가짜로 바꾼 테스트로 확인한다.

1. 모든 필수값이 있으면 hybrid·dense·lab이 각각 한 번 호출된다.
2. 각 필수값을 하나씩 빼면 4xx이고 세 검색은 한 번도 호출되지 않는다.
3. 개인사업자·법인은 사업자번호와 설립일이 없으면 실패한다(설립일 권장안을 채택한 경우).
4. 예비창업자는 사업자번호·설립일 없이 통과하고, 숨겨졌던 이전 값이 payload에서 제거된다.
5. 사업자번호 형식, 미래 생년월일, 불완전한 수익모델 행, 잘못된 금액을 거부한다.
6. 대표자 이력과 선택 팀원이 기존 서비스 payload에서 중복되지 않는다.
7. hybrid·dense payload는 `search` 외에는 동일하다.
8. `main_industry`가 새 방식의 `industry`로 전달되어 조건 판정에 실제 반영된다.
9. 새 방식이 지원하지 않는 필드는 “미사용”으로 표시되며 검색에 쓴 것처럼 표시되지 않는다.
10. 신청자 유형을 바꿀 때 조건부 필드가 화면과 payload에서 함께 제거된다.
11. 실제 개인정보가 localStorage·URL·응답·로그·저장 보고서에 남지 않는다.
12. 필드별 오류, 키보드 이동, 상태 공지가 접근성 트리에 나타난다.
13. 기존 Top N 범위·안전 URL·실험 DB ID 재조회 회귀 테스트가 계속 통과한다.

## 완료 기준

- 사용자 목록의 필수·선택·조건부 입력이 `/compare`에 모두 보인다.
- compare 전용 서버 검증과 필드별 UI 검증이 일치한다.
- 세 방식에 전달된 값과 실제 사용 여부가 문서·응답·화면에서 구분된다.
- 기존 `/compare` P2·P3 수정과 전체 테스트가 유지된다.
- 실제 8000·8010에서 가짜 예시 한 건을 실행해 세 열이 표시되고 콘솔 오류가 없다.
- `docs/VERIFY_UI.md`, `STATUS.md`, `WORKLOG.md`에 입력 계약·검증 결과·남은 미사용 필드를 기록한다.
- Codex 재검토 전 Git staging·commit·push를 하지 않는다.
