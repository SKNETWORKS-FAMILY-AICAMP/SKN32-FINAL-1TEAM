# 검색어 구성 ablation 리뷰

2026-09-21 · Codex · 코드·저장 결과·평가 계약 검토

대상:

- `eval/query_ablation.py`
- `reports/query_ablation_20260921T081116Z/`
- `docs/STATUS.md`, `docs/WORKLOG.md`의 검색어 구성 비교 기록

## 판정

**원시 검색 단계의 탐색 결과로는 유용하지만, 현재 결과만으로 이력·수익모델·채용 계획을 운영 매칭 검색어에서 빼거나 유지하는 결정을 내리면 안 된다. 수정 후 재실행이 필요하다.**

저장 결과의 표와 요약 수치는 코드 계산과 일치하며 “95% 구간이 0을 포함하므로 차이를 말할 수 없다”,
“채용 계획은 실제 입력자가 없어 품질 비교가 아니다”, “대부분 LLM 잠정 판정”이라는 문구 자체는 신중하다.
문제는 이 순위가 사용자가 보는 최종 서비스 순위가 아니라는 점이다.

## 수정 필요

### [P1] `Runner`가 서비스의 마감 필터와 규칙 재정렬을 건너뛰어 최종 매칭 Top 3을 평가하지 않음

- 위치: `eval/query_ablation.py:47-67`, 비교 대상 `search/app.py:263-448`.
- ablation의 `Runner.run()`은 numpy dense와 BM25 RRF 결과를 그대로 반환한다.
- 실제 `/api/match`는 후보 검색 뒤 마감 공고를 제외하고, 신청자 집단·시도·시군구 규칙으로 후보를 다시 정렬한 뒤 Top N을 만든다.
- 특히 팀 이력은 `search/app.py:341-347`의 집단 판정용 신청자 텍스트에도 쓰인다. 운영에서 검색어에서만 이력을 빼고
  규칙에는 유지하려면 원래 payload의 팀 정보는 보존한 채 **질의 문자열만** 바꿔 최종 파이프라인을 통과시켜야 한다.
- 현재 보고서의 P@3과 “상위 3 바뀐 칸”은 최종 노출 결과의 변화량이 아니므로 서비스 수정 판단 근거로 직접 쓸 수 없다.

수정 기준:

1. 공통 함수로 후보 검색 이후의 마감 필터·규칙 재정렬을 서비스와 공유하거나, 같은 스냅샷에서 `match()`와 동등한 경로를 사용한다.
2. 변형은 payload를 삭제하지 말고 검색어 생성 옵션만 바꿔, 팀 이력·성별·인증 등이 규칙에 쓰이는 동작은 유지한다.
3. `원시 검색 Top 3`과 `서비스 최종 Top 3`을 분리해 저장하고, 운영 결정은 후자를 기준으로 다시 계산한다.
4. 실제 서비스 기본값인 후보 깊이·마감 숨김·규칙 모드·RRF 가중치를 회귀 테스트로 고정한다.

### [P2] 새 `대표자 이력` 필드 자체를 평가한 데이터가 아님

- 위치: `eval/query_ablation.py:22-30`, 저장 결과 `summary.json`.
- 평가 질의는 입력 확장 전 `payload.team`만 갖고 있으며 정상 52개 중 35개에 팀 경력이 있다.
  `owner_career`를 독립 필드로 갖는 질의나 대표 이력과 팀원 이력이 구분된 정답셋은 없다.
- `/compare` adapter가 대표자 이력을 팀 첫 행으로 보내므로 실행 경로는 이어지지만, 현재 `-이력` 결과는
  대표자 이력만 뺀 효과와 선택 팀원 이력만 뺀 효과를 분리하지 못한다.

수정 기준:

1. 보고서 표현을 “기존 평가셋의 팀 경력 전체 제거(35/52질의)”로 정확히 제한한다.
2. 대표자 이력과 팀원 이력을 따로 결정하려면 두 필드를 구분한 평가 입력을 만들고 각각 ablation한다.

### [P2] 실행 재현에 필요한 데이터·검색 설정 지문이 결과에 없음

- 위치: `eval/query_ablation.py:139-193`, `reports/query_ablation_20260921T081116Z/summary.json`.
- 결과에는 실행 시각·판정자별 쌍 수·질의 수·`numpy (data/embeddings_v1.npz)`만 있다.
- 질의/qrels 파일 해시, NPZ 해시·모델 리비전, MySQL/BM25 공고 스냅샷, 후보 깊이, RRF 설정,
  마감·규칙 처리 여부가 없어 데이터가 바뀐 뒤 같은 결과인지 판단하기 어렵다.
- 공통 규칙상 검색 비교는 데이터 기준·모델/색인 상태·기준 날짜·후보 수/Top-K·검색 방식·가중치·후처리를 기록해야 한다.

수정 기준:

1. manifest에 입력 파일과 벡터 파일 해시, 모델 리비전, DB 공고 수·지문, BM25 문서 수,
   후보 깊이·Top-K·RRF 설정·기준일·마감/규칙 적용 여부를 저장한다.
2. `per_query.jsonl`과 `summary.json`이 같은 실행 지문을 참조하도록 한다.
3. 최소 fixture로 변형별 질의 문자열, 원본 payload 보존, 최종 순위 후처리를 테스트한다.

## 해석상 유지할 한계

- 저장 실행의 정상 질의는 52개이고 사람 판정만으로는 하이브리드 각 변형 Top 3의 156칸 중 **23칸만** 판정돼 있다.
  사람 판정만으로 변형 우열을 말할 수 없는 수준이다.
- 전체 판정은 human 143쌍, llm 473쌍, llm_old 870쌍이며 LLM 잠정 판정 비중이 크다.
- 변형에서 미판정 Top 3 비율이 달라지므로 미판정을 0점으로 둔 차이는 풀링 편향의 영향을 받는다.
- `+채용계획`은 실제 채용 계획이 있는 평가 질의가 0개라 제거/유지 결정 실험이 아니다.

## 확인한 정상 사항

- 서비스 코드를 수정하거나 Chroma를 쓰지 않고 저장된 NPZ와 읽기 전용 DB/BM25로 실행한다.
- `build_query()`를 공용 함수로 호출해 질의 문자열 형식을 중복 구현하지 않는다.
- 정상 52개와 무관 8개를 구분하고 주요 지표는 정상 질의만 집계한다.
- 짝지은 부트스트랩 구간과 미판정 비율을 함께 기록하며, 통계적으로 확인되지 않은 차이를 개선으로 주장하지 않는다.
- 저장 `summary.json`, `summary.md`, `per_query.jsonl`의 수치·건수는 서로 맞는다.

## 다음 단계

먼저 실제 서비스의 최종 후보 처리까지 재현하도록 실험을 수정한다. 그 결과와 사람 판정 범위를 본 뒤에야
`search/app.py::build_query()`에서 이력·수익모델·채용 계획을 빼는 운영 변경을 결정한다.
이번 리뷰에서는 실험 코드·결과·서비스 코드를 수정하거나 재실행하지 않았다. Git staging·commit·push도 하지 않았다.

## 후속 재검토 — 서비스 최종 순위 재실행 (2026-09-21)

### 판정

**기존 P1은 해결됐고 새 실행의 해석도 타당하다. `083240Z`를 최신 결과로 사용할 수 있지만,
DB 지문이 실제 검색 입력 전체를 대표하지 못하는 재현성 P2 한 건은 남아 있다.**

운영 판단은 `reports/query_ablation_20260921T083240Z/`의 `final` 단계만 사용한다.
이 실행만으로 팀 경력·수익모델·채용 계획을 검색어에서 빼거나 유지하는 결정을 내릴 수 없다는 결론은 맞다.
첫 실행 `081116Z`의 원시 순위 수치는 운영 결정 근거로 사용하지 않는다.

### 해결 확인

- `Pipeline.final()`이 실제 `search.app.match()`를 호출한다. 변형 시 원본 `MatchRequest`는 보존하고
  `build_query()`만 바꿔 검색 문자열을 변화시키므로 팀 경력은 대상 집단 규칙에 계속 쓰인다.
- 마감 숨김·집단/지역 규칙·서비스 기본값을 거친 `final`과 검색 직후 `raw` 결과를 분리해 저장했다.
- 기준일을 질의의 `as_of_date`인 `2026-09-15`로 고정했다.
- 결과 문구가 `-팀경력`을 “기존 평가셋의 팀 경력 전체 제거”로 제한하고 대표자 이력과 팀원 이력을
  분리해 평가하지 못했다는 한계를 명시한다. 채용 계획 보유 질의가 0개라는 한계도 유지했다.
- 질의·qrels·NPZ 해시, 모델 리비전, 공고/BM25 수, 후보 깊이, Top-K, RRF 설정, 서비스 기본값,
  기준일, 평가셋 구성이 `summary.json.manifest`에 기록됐다. 저장 해시 3개가 현재 파일과 일치함을 확인했다.
- `per_query.jsonl`은 60질의 × 5변형 × 2검색 방식 × 2단계인 **1,200행**이며 실행 시각을 공유한다.

### [P2] DB `rows_sha256`가 ID와 마감일만 해시해 검색 결과를 바꾸는 데이터 변경을 놓침

- 위치: `eval/query_ablation.py:264-280`.
- 현재 지문은 각 행의 `notice_id|apply_end`만 이어 해시한다. 제목·본문·대상·지역·분류 등이 바뀌어도
  ID와 마감일이 같으면 `rows_sha256`가 그대로다.
- BM25는 `shared/embed.py::FIELDS`의 `title`, `body`, `target_text`, `target_category`, `category`,
  `subcategory`로 문서를 만들고, 최종 규칙은 `search.app.FIELDS`의 대상·지역 등에도 의존한다.
  따라서 manifest가 같아도 실제 원시 후보와 최종 순위가 달라질 수 있다.

수정 기준:

1. BM25 입력 문서와 최종 규칙이 읽는 모든 DB 필드를 안정적인 순서·직렬화로 해시한다.
   한 방법은 `notice_id + embed.build_input(row) + 규칙용 app.FIELDS`의 정규화된 값을 공고 ID 순으로 해시하는 것이다.
2. 해당 필드 중 하나만 바꾸고 ID·마감일은 유지했을 때 DB 지문이 달라지는 회귀 테스트를 추가한다.
3. 수정 뒤 결과를 다시 만들고 새 지문을 `summary.json.manifest`에 남긴다.

### 최신 결과 해석 확인

- 하이브리드 최종 P@3(2): 전체 0.564, `-팀경력` −0.013, `-수익모델` −0.026,
  `-팀경력-수익모델` −0.032, `+채용계획` −0.019. 네 95% 구간은 모두 0을 포함한다.
- 변형은 Top 3을 실제로 바꿨지만 미판정 비율도 0.212에서 0.244~0.282로 늘었다.
  점 추정만 보고 검색어를 빼거나 유지하면 안 된다는 보고서 결론이 맞다.
- 사람 판정 칸은 하이브리드 최종 Top 3의 156칸 중 변형별 16~19칸뿐이다.
  다음 운영 결정 전에는 대표/팀 이력을 구분한 입력과 사람 판정 범위를 먼저 보강해야 한다.
