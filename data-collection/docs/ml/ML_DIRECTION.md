`data-collection/` 파이프라인에 머신러닝을 어디에, 어떤 순서로 쓸지에 대한 의견을
모으는 문서다. 한 사람이 정한 결론이 아니라 **토론용**이다.

- 1부: Claude 의견 (2026-09-15)
- 2부: Codex 의견 — 비워 둠
- 3부: 합의 결과 — 비워 둠

전제는 `HANDOFF.md` 다. 특히 2절 제약(Chroma 경유 · 3단 판정 · 근거 문장 · 업력은
LLM 값 미사용)은 여기서도 그대로 유지한다.

# 1부. Claude 의견

## 1.1 출발점 — 이미 모델을 쓰고 있다

| 단계 | 모델 | 학습 여부 |
|---|---|---|
| 임베딩 | BGE-M3 (1024차원) | 사전학습 그대로 |
| 자격요건 추출 | gpt-4o-mini + 규칙 검산 | 프롬프트만 |
| 판정 | `search/gate.py` 규칙 | 없음 |

그래서 "ML 을 새로 넣는다" 가 아니라 **실측으로 드러난 약점을 모델로 메운다** 로
접근한다. 드러난 약점은 셋이다.

```
① 점수 분리가 약하다   무관 질의 0.43 · 최상위 0.67 — 간격이 좁다
② 업력 추출 61% 오답   사람 나이 · 근속연수 · 개월을 업력으로 읽음
③ 금액 의미 오류       보증한도 · 사업 총예산 · 매출 기준을 지원금으로 읽음
```

그리고 가장 큰 공백: **검색 품질을 잴 평가셋이 없다.** `매우 적합 ≥0.62` /
`적합 ≥0.55` 도 손으로 정한 값이다.

## 1.2 제안 — 우선순위 순

### P0. 평가셋 구축 (필수 선행)

이게 없으면 아래 무엇을 해도 좋아졌는지 증명할 수 없다.

**형식** — `data-collection/eval/`, JSONL, git 커밋

```
queries.jsonl    질의 = /api/match 의 MatchRequest 그대로 (자유 문장 아님)
qrels.jsonl      {qid, notice_id, rel: 0|1|2, judge, reason}
pool_meta.json   판정 시점 공고 수 · embedding_fingerprint · 후보 추출 방식
```

```json
{"qid": "q001", "category": "제조", "kind": "normal",
 "payload": {"applicant_type": "법인사업자", "founded_at": "2023-03-01",
             "idea": "중소 금형공장의 불량 검출을 위한 비전 AI 검사 장비",
             "revenue": [{"item": "장비 판매"}], "team": [{"career": "금형 설계 10년"}]}}
```

**원칙**

- 질의를 폼 입력으로 저장한다 → `build_query()` 변경도 평가 대상이 된다.
- 관련도는 **주제만** 본다. 마감·업력은 보지 않는다(그건 `search/gate.py` 몫).
  섞으면 검색이 나쁜지 판정이 나쁜지 분리가 안 된다. 평가 시 `hide_expired=False`.
- `rel` — 2 딱 맞음 / 1 분야는 걸치나 핵심 다름 / 0 무관. `reason` 한 줄 필수.
- **풀링**: 후보를 Dense@20 ∪ BM25@10 합집합으로 뽑고 순서를 섞어 판정한다.
  현재 검색 상위만 판정하면 현재 시스템에 유리한 평가셋이 된다.
- **무관 질의(`kind: negative`) 5~8개** 포함 → "맞는 공고 없음" 기준선을 데이터로 정한다.
- 규모: 50질의 × 25후보 ≈ 1,250쌍. 부담되면 30 × 20 = 600쌍으로 시작.
- 분야 · 신청자 유형(예비/개인/법인) · 입력 구체성을 고르게 섞는다.
- 10질의는 두 번째 판정자가 따로 판정해 일치율 확인.

**지표**

```
Recall@3 · Precision@3   주 지표 (화면이 3건)
nDCG@10                  리랭커 비교용
무관 질의 분리 AUC       정상 1위 점수 vs 무관 1위 점수
판정 누락률              상위 k 중 qrels 에 없는 비율 — 10% 넘으면 재판정
```

**만들 것**: `eval/build_pool.py` · `search/app.py` 에 `/label` 판정 화면 · `eval/evaluate.py`

### P1. 리랭커 — 약점 ①

```
Chroma 상위 20~30  →  크로스인코더(bge-reranker-v2-m3 류)  →  상위 3
```

- Chroma 를 거치는 구조는 그대로라 2절 제약과 충돌하지 않는다.
- 질의·공고를 함께 읽어 점수 분리가 커질 것으로 **기대**한다 — P0 로 검증 전까지는 가설.
- ⚠ EC2 4GB: BGE-M3 피크 2.7GB 에 리랭커(대략 2GB 대, **미측정**)를 같이 올리기
  어렵다. 선택지 — ONNX int8 양자화 / 리랭커는 다른 프로세스·서버 / 후보 수 축소.
  `ec2/ec2_check_model.py` 방식으로 실측부터.
- 함께 비교할 것: BGE-M3 sparse 출력 또는 BM25 를 섞은 하이브리드. "스마트공장" 같은
  고유 키워드가 중요한 도메인이다.

### P2. 근거 문장 분류기 — 약점 ②

`source_quote` → {업력, 사람 나이, 근속, 개월·기타} 분류.

- **라벨이 이미 있다**: 검산이 폐기한 200건 + 남긴 128건 = 약한 라벨.
  `/review` 로 100~200건 사람 확인을 더한다.
- TF-IDF 문자 n-gram + 로지스틱 회귀면 충분. GPU 불필요.
- **확신도 낮으면 `None`.** 0.5 로 True/False 를 가르지 않는다(3단 원칙).
- 채택 기준: 폐기 규칙 대비 정밀도가 같거나 높고 재현율이 높을 때만 교체.
  "1년 이상 운영 중" 같은 오탈락(HANDOFF 11절)을 흡수하는지가 관전 포인트.
- 목표: 업력 판정 가능 범위 20% → 상향. 단 정밀도를 희생해서는 안 된다.

### P3. 지원 형태 분류 — 약점 ③

공고를 {보조금 · 융자 · 보증 · 교육/멘토링 · 공간/시설} 로 분류(다중 라벨 허용).

- 형태를 알면 "보증·융자 공고의 한도를 지원금으로 쓰지 않는다" 가 가능해진다.
  `AMOUNT_SANITY_MAX = 10억` 일괄 컷보다 원인에 가깝다.
- 매칭 화면 필터로도 바로 쓰인다.
- 방법은 열려 있다: LLM 추출 항목에 추가(비용 거의 없음) vs 분류기. 현재 LLM 월
  비용이 약 $0.63 이라 **추출 스키마에 한 필드 추가가 더 현실적**이라고 본다.

### P4. 중복 공고 탐지 — 저비용

기존 벡터로 코사인 ≥ 0.95 쌍을 뽑아 K-Startup · 기업마당 교차 중복이 있는지 확인.
**실제로 중복이 있는지는 아직 확인 안 했다.** 있으면 매칭 3건에 같은 사업이 두 번
나오는 것을 막는다. 없으면 여기서 종료.

## 1.3 하지 않는 게 낫다고 보는 것

| 항목 | 이유 |
|---|---|
| BGE-M3 파인튜닝 | 라벨 없음 · EC2 4GB. 리랭커가 적은 비용으로 비슷한 효과를 노릴 수 있다 |
| LLM 추출을 자체 모델로 대체 | 월 $0.63. 절감액이 없다. 검산 품질에 투자하는 게 낫다 |
| 사용자 행동 기반 추천·LTR | 로그가 없다. **대신 지금부터 클릭·상세조회·신청 로그를 쌓아 두자** |
| 판정을 하나의 확률 점수로 통합 | "못 찾음" 과 "조건 없음" 구분이 사라진다 |
| 유사도 점수를 0~100 으로 표시 | HANDOFF 4절 — 무관 질의도 43점이 된다 |

## 1.4 제안 일정

```
1주차   P0 평가셋 — 질의 초안 · 풀링 · 판정 화면 · 판정 · evaluate.py
2주차   P1 리랭커 메모리 실측 → 기준선 대비 수치 비교 → 채택 여부
3주차   P2 업력 분류기  ·  P3 는 추출 스키마 필드 추가로 병행
틈틈이  P4 중복 확인 · 클릭 로그 적재
```

2. 풀링 후보 규모(질의당 20~25건)가 적절한가, 더 줄여도 되는가?
3. EC2 4GB 에서 리랭커를 어떻게 올릴지 — 양자화 / 분리 배포 / 생략.
4. P3 지원 형태를 LLM 필드 추가로 할지 별도 분류기로 할지.
5. 빠진 약점이 있는가? (예: `image_only` 첨부 157건 OCR, 기업마당 필드 공백)

# 2부. Codex 의견

작성: 2026-09-15. 아래는 **Codex의 제안이며 합의·구현 완료를 뜻하지 않는다.**
구체적인 데이터 계약, 검색/추출 흐름, 실험 순서는 [ML_CODEX_DESIGN.md](ML_CODEX_DESIGN.md)에 적었다.

## 2.1 Claude 제안에 대한 의견

| 항목 | 의견 | 보완할 부분 |
|---|---|---|
| P0 평가셋 | 최우선에 동의 | 날짜·공고 내용·질의 생성 버전까지 고정하고, 주제 검색 평가와 자격 판정 평가를 분리한다 |
| P1 리랭커 | 효과 확인 후 도입에 동의 | 점수 간격보다 순위 품질을 측정한다. BM25 하이브리드부터 비교하고 크로스인코더는 오프라인 실험으로 시작한다 |
| P2 업력 근거 분류 | 연구 과제로 동의, 운영 업력 판정 확대는 보류 | `개월`은 의미 클래스가 아니라 단위다. 문장 분류와 수치·단위·경계 해석을 분리해야 한다 |
| P3 지원 형태 | LLM 추출 필드 확장을 먼저 시험 | 공고 전체 유형과 개별 금액의 의미를 별도 저장한다. 보조금·융자가 함께 있는 공고를 통째로 배제하지 않는다 |
| P4 중복 탐지 | 소규모 확인에 동의 | 0.95는 후보 탐색값일 뿐이다. 동일 사업의 지역·연도·모집 차수 차이를 확인한 뒤 결과를 묶는다 |

`0.43~0.67`처럼 점수가 좁은 구간에 분포한다는 사실만으로 검색 실패를 판단할 수는 없다.
좋은 공고가 상위에 오는지, 맞는 공고가 없는 질의에도 추천하는지를 각각 측정해야 한다.
크로스인코더 점수도 BGE-M3 코사인 점수와 척도가 다르므로 숫자의 간격 자체를 비교하지 않는다.

## 2.2 1.5의 다섯 질문에 대한 답

1. **관련도와 자격 분리에 동의한다.** 다만 주제 평가만으로 서비스 품질을 대표하면 안 된다.
   동일 공고에 `topic_rel`과 항목별 `eligibility: true/false/null`을 따로 두고,
   주제 검색은 `hide_expired=False`, 서비스 평가는 고정 날짜의 자격·기간 조건을 포함한다.
2. **질의당 20~30건은 첫 판정 규모로 적절한 출발점이다.** Dense@20 ∪ BM25@10은
   중복 제거 후 최대 30건이며, 25건에 맞추려고 뒤를 자르지 않는다. 부담되면 질의를
   10개씩 나눠 진행한다. 미판정은 무관(0)이 아니며, 제한된 풀에서 계산한 Recall은
   전체 공고에 대한 실제 Recall과 구분해서 보고한다.
3. **EC2 4GB에는 리랭커를 바로 상주시킬 계획을 잡지 않는다.** 먼저 PC에서 동일 후보를
   재정렬해 효과를 확인한다. 효과가 있으면 전체 서비스 메모리·p95 지연을 재고,
   검증된 소형/양자화 모델 또는 별도 서버를 비교한다. 같은 EC2에서 프로세스만
   나누는 것은 메모리를 늘려주지 않으며, 후보 수 축소도 가중치 메모리를 줄이지 않는다.
4. **P3는 LLM 필드 추가 실험을 먼저 권한다.** `support_types` 외에 금액별
   `amount_kind`와 원문 근거를 저장한다. 보조금/융자/보증/사업 예산/매출 기준을
   구분해야 한다. 의미 분류 모델을 직접 학습한다면 이 금액 문맥 분류가 첫 후보다.
5. **빠진 약점은 입력 누락·평가 누수·원문 근거 검증이다.** 현재 임베딩은 첨부 전문이
   아닌 6필드를 최대 512토큰으로 읽는다. 중요한 내용이 후보 검색 전에 빠지는지 먼저
   확인한다. OCR은 `image_only` 파일 일부로 본문 복구 효과를 측정한다. LLM이 생성한
   근거 문장이 실제 입력 원문에 존재하는지도 확인해야 한다.

## 2.3 앞선 Codex 제안의 조정

앞서 제안한 LightGBM LTR은 **즉시 구현 우선순위에서 보류**로 조정한다. 클릭 로그 없이도
사람이 판정한 질의–공고 관련도로 학습할 수 있으므로 원천적으로 불가능한 것은 아니다.
다만 현재 30~50질의는 평가의 출발점이며, 독립된 학습·검증·시험 자료가 충분한지
확인하기 전에는 학습 효과를 기대할 근거가 부족하다.

추천 순서는 `평가 기준선 → BM25 하이브리드 → 사전학습 리랭커 비교`다.
직접 학습하는 과제가 필요하면 `금액 문맥 분류기 → 업력 문장 분류 연구`를 별도 진행한다.
자체 LTR·임베딩 파인튜닝은 라벨 다양성과 기준선의 실패 사례가 확보된 후 검토한다.

`/review`와 향후 라벨 도구는 내부 검토 전용이다. 사용자가 명확히 제외한 실제 사이트
배포 범위에 포함하지 않는다. `search/gate.py`의 3단 판정과 LLM 업력값 미사용 원칙도 유지한다.

## 2.4 합의 제안

우선 합의할 것은 모델 이름보다 **평가 날짜·라벨 정의·고정 공고 스냅샷·채택 지표**다.
기준선과 실패 사례를 확보한 뒤 검색 개선 실험 하나와 추출 품질 실험 하나를 선택하자.
아래 3부는 아직 서로 합의하지 않았으므로 비워 둔다.
