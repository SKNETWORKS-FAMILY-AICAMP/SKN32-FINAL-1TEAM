# Codex 머신러닝 설계 제안

작성일: 2026-09-15 · 범위: `data-collection/`

이 문서는 Claude에게 전달하기 위한 설계안이다. 코드 구현·모델 학습·배포·DB 변경을
수행한 결과가 아니다. [ML_DIRECTION.md](ML_DIRECTION.md) 1부와 현재 코드를 검토했다.
데이터 건수·실측 속도는 [HANDOFF.md](HANDOFF.md)에 기록된 값이며 이번에 DB를 조회해
재측정한 것은 아니다. 모델 성능·필요 메모리·목표 달성 가능성은 실험 전 가설이다.

## 1. 목표와 유지할 원칙

목표는 두 가지다. 사용자에게 관련 있는 공고를 상위에 보여주고, 공고에서 추출한
지원 조건을 근거와 함께 정확하게 전달한다. 검색 순위와 신청 자격은 독립적으로 평가한다.

- 검색 후보는 반드시 Chroma를 거친다. MySQL 벡터의 NumPy 전수 검색을 서비스에 넣지 않는다.
- 자격 판정은 충족/미달/확인 필요를 유지한다. 모델 점수를 신청 자격이나 선정 확률로 표시하지 않는다.
- LLM 업력값은 운영 판정에 사용하지 않는다. 업력 문장 분류 실험도 이 제한을 변경하지 않는다.
- `/review`와 라벨 도구는 내부 작업용이다. 실제 사이트의 사용자 경로·배포 대상에서 제외한다.
- 학습·라벨링·모델 비교는 PC에서 실행한다. EC2 4GB는 추론 전체 부하를 측정한 후 모델을 추가한다.
- 문서에 나온 61%는 수동 정답셋으로 새로 측정한 일반화 오류율로 취급하지 않는다.
  규칙이 폐기한 사례에 실제 업력도 포함되므로, 보존/폐기 결과 모두 재검토가 필요하다.

## 2. 현재 구조에서 먼저 확인할 사실

| 현재 코드 | 설계에 미치는 영향 |
|---|---|
| `embed.py`: 제목·개요·지원대상·분류 6필드, 최대 512토큰 | 필요한 정보가 입력에 없거나 잘렸다면 리랭커 추가만으로 후보 누락을 해결할 수 없다 |
| `app.py`: Chroma 조회 후 마감 필터, 카드 선택 후 자격 확인 | 순수 검색 품질과 사용자가 보는 최종 결과 품질을 따로 측정해야 한다 |
| `gate.py`: 예산 소진·상시·모집 완료형은 접수기간 `None` | 문서의 접수기간 100%는 확정 판정 정확도 100%가 아니다 |
| `extract_conditions.py`: 원문 발췌·LLM 추출·규칙 검산 | 발췌 누락, 의미 오분류, 수치 오류를 서로 구분해야 한다 |
| `notice_conditions`: 금액·형태 등이 저장돼 있으나 화면 연결은 미완료 | 추출 성능과 화면에서 사용하는 범위를 혼동하지 않는다 |
| `eval/queries.jsonl`: 주석과 여러 줄 JSON이 있는 초안 | 실제 실행 전 한 줄당 JSON 객체인 JSONL로 정리하고 스키마 검증해야 한다 |

현재 자료를 자동 변경하지 않는다. 특히 Claude가 작업 중인 `eval/queries.jsonl`은
이번 문서 작성에서 수정하지 않았다.

## 3. 제안하는 검색 구조

### 3.1 운영 후보 흐름

```text
사용자 폼 입력
  → 버전이 고정된 build_query
  → BGE-M3 질의 벡터
  → Chroma 후보 검색 ───────────────────────┐
  → BM25 후보 검색 [비교 실험 후 선택] ─────┤
                                          ↓
                           후보 합집합 / RRF 순위 결합
                                          ↓
                    공고 스냅샷 또는 최신 상세 + gate 판정
                    확실한 미달 제외 / None은 확인 필요로 유지
                                          ↓
                     리랭커 [효과와 자원 검증 후 선택]
                                          ↓
                       동일 모집 공고 묶기 + 상위 3건
                                          ↓
                    관련성 결과와 항목별 자격 근거를 표시
```

화살표는 제안 설계다. 현재 화면은 카드 클릭 후 자격을 확인하며, 추천 전에 확실한
미달을 제외하는 단계는 팀과 합의 후 연결할 변경이다. 임의의 LLM 추출값으로 탈락시키지
않고, 검증된 근거와 명확한 규칙이 있는 조건만 적용한다.

BM25 경로를 추가해도 모든 검색 요청에서 Chroma를 호출하는 원칙을 유지한다.
BM25 단독은 오프라인 비교 기준선으로만 둔다. RRF는 점수 척도가 다른 두 검색 결과의
순위를 결합하는 비학습 방법이다. 초기에는 가중치 학습을 추가하지 않는다.

후보 수는 실험값이다. 먼저 Chroma 30~50건에서 비교하고, 필터 후 3건이 안 남으면
후보를 더 읽되 상한을 둔다. 적합한 후보가 부족하면 0~2건만 반환할 수 있다.
무관한 공고를 채워 3건을 맞추지 않는다. 단순 점수 차이·최고 점수만으로 무관 판정을
확정하지 않고 별도 검증 질의에서 보류 기준을 정한다.

크로스인코더는 질의와 후보 공고를 함께 읽어 순서를 재평가한다.
사전학습 모델 사용과 자체 지도학습은 구분해서 결과를 보고한다.
이 두 단계 검색 구조는 [Sentence Transformers 공식 설명](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)을 참고한다.

### 3.2 비교 실험

| 실험 | 후보 검색 | 순위 결정 | 확인할 질문 |
|---|---|---|---|
| E0 | 현재 Chroma | 현재 코사인 순위 | 기준 성능은 어느 정도인가? |
| E1 | Chroma + BM25 | RRF | 고유명사·기술어 누락이 줄어드는가? |
| E2 | E0와 동일 후보 | 사전학습 크로스인코더 | 후보가 같을 때 순위만 개선되는가? |
| E3 | E1과 동일 후보 | 같은 크로스인코더 | 후보 확대와 재정렬의 결합 효과가 있는가? |

실험마다 공고 입력·질의 입력·필터·후보 수를 기록한다. 리랭커의 효과를 측정할 때
첨부 전문 추가까지 동시에 바꾸지 않는다. 첨부 발췌를 추가하는 실험은 별도 E4로 둔다.

## 4. 평가 데이터 계약

### 4.1 파일과 버전

| 제안 파일 | 담을 내용 |
|---|---|
| `eval/queries.jsonl` | qid, scenario_group, category, kind, payload, as_of_date |
| `eval/qrels.jsonl` | qid, notice_id, topic_rel(0/1/2), judge, reason, label_version |
| `eval/eligibility_cases.jsonl` | qid, notice_id, 항목별 true/false/null, 근거, 기준 날짜 |
| `eval/pool_meta.json` | 공고 스냅샷 해시, 코드/모델 리비전, 입력 구성, 후보 방식·수·순서 섞기 seed |
| `eval/splits.json` | 시나리오 단위 개발/시험 분할 및 정한 시점 |
| `eval/runs/` | 실험별 검색 결과·설정·지표; 큰 산출물은 별도 보관 정책 |

질의는 폼 입력을 유지하고 예제 인물 정보는 합성 데이터로 만든다. `as_of_date`로
업력 계산과 마감 판정 날짜를 고정한다. 현재 날짜를 사용하는 `build_query()`와 gate에는
평가용 기준 날짜를 주입할 수 있게 하는 변경이 필요하다.

공고 수와 임베딩 지문만으로는 재현되지 않는다. 공고 본문·기간·조건의 당시 내용도
고정된 스냅샷으로 보관하고 해시를 남긴다. 임베딩·Chroma·BM25가 같은 공고 집합과
버전을 사용하는지도 확인한다. 원문 전체를 Git에 넣는 것은 별도 보관 정책으로 정하고,
작은 합성 질의·라벨·메타데이터를 우선 Git에서 관리한다.

### 4.2 라벨링 원칙

1. 첫 10질의로 판정 기준을 맞추고 이후 30~50질의로 확장한다. 숫자는 시작 규모이며 충분성을 보장하지 않는다.
2. Dense@20 ∪ BM25@10 전체를 중복 제거한다. 최대 30건이며 25건으로 임의 절단하지 않는다.
3. 후보 시스템명·순위·점수를 가리고 판정한다. 두 판정자의 불일치는 원문을 보고 조정한다.
4. 주제 관련성은 서비스·제품·지원 목적의 일치를 보고 판정한다. 마감·업력 적합성은 별도 정답이다.
5. `kind: negative`는 도메인 밖 질의의 표식이지 모든 공고가 무관하다는 자동 정답이 아니다.
   도메인 안이지만 현재 공고에 답이 없는 질의, 지나치게 모호한 질의도 별도로 포함한다.
6. 판단할 근거가 부족하면 미판정으로 남긴다. 미판정을 0으로 자동 변환하지 않는다.
7. 새 시스템이 반환한 미판정 상위 결과를 추가 판정하고, 동일 라벨 버전으로 모든 시스템을 다시 평가한다.
8. 같은 아이디어의 바꿔 쓴 질의는 같은 scenario_group에 둔다. 최종 시험 자료로 임계값·모델을 선택하지 않는다.

30~50질의에서는 소수의 예제로 임계값을 정밀하게 추정하기 어렵다. 정상/무관 5~8개씩
관찰한 결과는 예비 결과로 보고하고, 중요한 판단 유형을 늘린 뒤 확정한다.
학습 자료와 최종 평가 자료를 분리하는 이유는 [scikit-learn 평가 문서](https://scikit-learn.org/stable/modules/cross_validation.html)를 참고한다.

### 4.3 지표

| 평가 대상 | 주 지표와 주의점 |
|---|---|
| 주제 순위 | nDCG@3 주 지표, Precision@3 보조. nDCG@10은 더 넓은 순위 진단용 |
| 후보 검색 | 판정 풀 기준 Recall@30/50. 전체 공고의 진짜 Recall로 표현하지 않는다 |
| 무관 질의 대응 | 잘못 추천한 비율과 관련 질의를 잘못 보류한 비율. AUC는 보조값 |
| 자격 판정 | 확실한 미달을 통과시킨 건수, 맞는 후보를 잘못 제외한 건수, None 유지율 |
| 최종 화면 | 유효 결과 수 0~3, 주제 관련성, 자격 미달 노출, 동일 모집 중복 노출 |
| 운영 비용 | 질의 전체 p50/p95 지연, 동시 요청 시 피크 메모리, 오류·fallback 비율 |

Precision의 이진 기준은 예를 들어 `topic_rel >= 1`로 미리 고정하고, rel=2인 결과
비율도 따로 보고한다. Recall 분모는 풀에서 판정된 관련 공고 수다. 분모가 0인 질의는
Recall/nDCG 평균에서 구분하고 무응답 평가로 보고한다. Precision@3에서 3건 미만
반환 시 분모를 임의 축소하지 않는다. 보류 기능과 검색 순위 자체도 따로 평가한다.

미판정 비율 10% 하나만 통과하면 충분하다고 보지 않는다. 주 지표인 상위 3건은 가능한
전부 판정하고, 풀 밖 무작위 표본과 새 검색 방식의 후보를 확인해 풀의 편향을 점검한다.
질의 단위 지표 차이와 bootstrap 신뢰구간을 함께 보고한다. 개선이 불명확하면 기존
경로를 유지한다. 높은 정확도가 나와도 표본 수·출처 편중을 함께 공개한다.

## 5. data-collection에 직접 학습을 넣는 설계

### 5.1 첫 과제: 금액 문맥 분류

현재 단일 금액은 보조금, 융자, 보증, 총예산, 매출 기준을 혼동할 수 있다.
P3의 공고 전체 `support_types`는 도움이 되지만 복합 지원 공고의 개별 금액 의미까지
확정해주지는 않는다. 다음 둘을 구분한다.

- `support_types`: 공고 전체의 보조금/융자/보증/교육/공간 등 다중 유형.
- `amount_mentions`: 원문에서 찾은 각 금액과 그 의미·수혜 단위·기간·근거.

```text
추출된 첨부 본문 + 공고 개요
  → 금액이 등장하는 원문 구간 확보
  → LLM이 지원 유형·금액 후보·근거를 구조화
  → 원문에 근거가 실제 존재하는지 검증
  → 금액 의미 분류 [학습 모델은 검증 후 선택]
  → 숫자·단위·범위 검산
  → 채택 / 보류 + 값·근거·이유·버전 저장
```

권장 금액 클래스는 `기업당 보조금 / 기업당 융자한도 / 기업당 보증한도 / 사업 총예산 /
매출·자산 자격기준 / 자부담·비용 / 기타·판단불가`다. 같은 문장에 여러 금액이 있으면
대상 금액을 표시하고 각각 분류한다. 문장만 던져 어떤 금액을 분류했는지 모르게 하지 않는다.

예: “총예산 30억원, 기업당 최대 5천만원, 자부담 20%”는 값 하나로 합치지 않는다.
보조금 5천만원과 사업 예산 30억원을 구분하고 자부담 조건도 별도로 보존한다.
연간/총기간, 기업당/과제당, 최대/정액, 지급/융자/보증의 차이를 저장한다.

초기에는 LLM 스키마 확장 + 기존 검산을 기준선으로 삼는다. 직접 학습이 필요하면
사람이 확인한 금액 문맥 수백 건으로 `문자 n-gram TF-IDF + 로지스틱 회귀`를 실험한다.
각 클래스가 충분히 포함되는지 먼저 확인하고 희귀 클래스는 섣불리 성능을 주장하지 않는다.
예상 결과가 없는 문장·복합 지원·규칙이 폐기한 문장도 표본에 넣는다.

분할은 문장 무작위가 아니라 공고/동일 사업군 기준으로 한다. 같은 양식의 복사 문장이
학습과 시험 양쪽에 들어가지 않도록 점검한다. TF-IDF 어휘도 학습 분할에서만 만든다.
정답은 원문을 검토한 사람 라벨이다. 기존 LLM 출력과 규칙 판정은 약한 라벨 및 표본
선정 재료이며 시험 정답으로 그대로 사용하지 않는다.

채택 기준은 전체 정확도보다 기업당 지원금 채택 정밀도, 금액·단위 정확 일치,
근거 일치, 보류율과 복구한 유효 건수다. 임계값은 검증셋에서 정하고 보류 기능을 둔다.
분류기의 확률을 곧바로 정답 확률로 해석하지 않는다.

`AMOUNT_SANITY_MAX`는 현재 안전장치로 유지한다. 새 의미 분류기가 있다는 이유로
상한을 바로 없애지 않고, 제외된 큰 금액을 사람이 검토한 뒤 별도 실험으로 비교한다.

### 5.2 두 번째 과제: 업력 문장 분류는 연구용으로 제한

Claude P2의 의미 분류 방향은 좋지만 `{업력, 사람 나이, 근속, 개월}`은 축이 섞인다.
“3개월 이상 영업”도 업력이다. 다음 두 단계를 분리한다.

1. **의미 분류:** 기업 업력 / 사람 나이 / 근로자 근속 / 사업 수행기간 / 기타·불명확.
2. **조건 해석:** 대상 주체, 값, 년·개월 단위, 이상·초과·이하·미만, 기준일, 예외 조건.

“창업 3년 이내”가 기업 업력 문장이라는 판정만으로 상한 3년을 안전하게 사용할 수는
없다. 예외 조항·기준일·복수 조건까지 확인해야 한다. 원문에 여러 의미가 섞인 문장은
구간을 나누거나 보류한다.

따라서 문장 분류 모델은 잘못 폐기된 근거를 검토 대상으로 올리는 역할부터 시작한다.
`gate.py`의 운영 업력 판정은 기존 정형 데이터로 유지한다. 이 연구 결과로 업력 판정
가능 범위가 즉시 늘었다고 발표하지 않는다.

### 5.3 근거와 버전 계약

필드별로 다음 메타데이터를 보존하도록 제안한다. 실제 테이블 변경은 별도 작업이다.

```text
notice_id / attachment_id / 문서 내용 해시
대상 필드 / 추출값 / 원 단위 / 정규화값
근거 원문 / 원문 내 위치 / 주변 문맥
의미 클래스 / 검산 상태 / 보류·폐기 이유
추출 모델·프롬프트·스키마·발췌·검산 버전
사람 검토 여부 / 검토자 / 검토 시각
```

LLM이 반환한 quote에서 숫자를 찾는 것만으로 원문 근거가 확인되지는 않는다.
실제 추출 본문에 해당 구간이 존재하는지 먼저 대조한다. 공백 정규화로 대응시켰다면
변환 규칙을 남기고 원문으로 역추적 가능해야 한다. 근거 위치 확보와 의미 검증은 별개다.
스캔 문서는 추후 OCR 버전과 페이지 번호도 연결한다.

문서가 같아도 스키마·프롬프트·검산이 바뀌면 재평가 대상이다. 원시 LLM 응답을 보존하면
검산 규칙만 바꿀 때 유료 재호출 없이 재검산할 수 있다. 단 새 필드가 필요한 경우는
기존 응답으로 복구 가능한지 확인하고 재추출 범위를 정한다.

## 6. EC2 자원과 채택 순서

1. PC에서 고정 후보로 리랭커 효과부터 측정한다. 후보 수와 입력 길이를 기록한다.
2. EC2에서는 BGE-M3 + MySQL + Chroma + API 전체 메모리와 동시 요청 지연을 측정한다.
3. 효과가 있으면 소형 다국어 모델 또는 해당 모델에서 실제 지원되는 양자화 경로를 시험한다.
4. 품질 저하·메모리·p95 지연을 만족하지 못하면 리랭커를 생략하거나 별도 서버를 검토한다.

`bge-reranker-v2-m3`는 다국어 후보 중 하나이며 채택 확정 모델이 아니다.
모델의 점수를 0~1로 변환해도 보정된 확률이 되는 것은 아니다.
[BAAI 공식 모델 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)를 참고한다.

같은 EC2에 별도 프로세스로 띄우는 것은 자원 분리가 아니다. 후보 수를 줄이면 계산량은
줄지만 모델 가중치 메모리는 남는다. ONNX/int8도 자동 해결책으로 가정하지 않는다.
재정렬 서비스 장애 시 Chroma 또는 검증된 하이브리드 순위로 돌아가는 경로를 둔다.

## 7. 우선순위와 완료 산출물

| 순서 | 작업 | 완료 증거 |
|---|---|---|
| 1 | 질의·라벨 규칙 합의, 공고·날짜 고정 | 10질의 파일럿, 판정 불일치 정리, 버전 메타데이터 |
| 2 | 검색 평가셋 30~50질의로 확대 | E0 결과, 실패 유형, 미판정 현황 |
| 3 | E1 하이브리드와 E2 사전학습 리랭커 비교 | 동일 데이터에서 품질·지연·메모리 비교 |
| 4 | P3 지원 유형·금액 의미 추출 실험 | 사람 검토 표본, 기존 방식 대비 정밀도·보류율 |
| 5 | 직접 학습이 필요하면 금액 문맥 분류기 | 공고군 분리 평가, 오류 사례, 운영 적용 여부 |
| 6 | 업력 문장 분류·OCR 표본·중복 탐지 | 각 과제의 실제 복구 효과와 오탐 사례 |

OCR은 `image_only` 157개가 곧 157개의 새 공고임을 뜻하지 않는다. 공고별 다른 첨부에서
이미 본문을 확보했는지 확인하고, 미확보 공고를 중심으로 20~30개 파일럿을 제안한다.
OCR 뒤에는 텍스트 수뿐 아니라 조건 추출의 정확도와 추가 확보 공고 수를 측정한다.

중복 공고는 벡터로 후보를 찾고 사업명·기관·기간·차수·지역·원문을 비교한다.
확정 시 화면에서 묶고 출처는 보존한다. 데이터 삭제·병합을 먼저 하지 않는다.

## 8. LTR을 다시 검토할 조건과 팀 경계

사용자 로그가 없어도 사람 관련도 라벨로 LTR을 학습할 수 있다. 다만 평가셋을 그대로
학습에 모두 사용하면 개선을 증명할 자료가 사라진다. 시나리오 다양성이 있는 별도 학습
라벨이 쌓이고 E0~E3의 한계가 확인되면 LightGBM 등 작은 모델을 비교한다.
주제 라벨만 학습하는 모델에는 자격 적합성 개선까지 기대하지 않는다.

행동 로그를 쌓는다면 클릭뿐 아니라 노출된 공고·순위·모델 버전·질의 식별자·시각도
필요하다. 클릭은 위치 편향이 있으므로 자동 정답으로 쓰지 않는다. 신청 링크 클릭과
실제 신청 완료도 구분한다. 이는 웹 담당과 별도 인터페이스를 합의할 작업이다.

`data-collection` 담당 산출물은 평가 데이터·추출 품질·모델 산출물·읽기 계약이다.
실제 사이트의 입력 필드, 검색 API 통합, 로그 적재, 결과 표시 변경은 웹 담당과 조율한다.
현재 배치의 실패 상태 전달·색인 정합성 같은 문제도 기준선 측정 전에 점검한다.
오래된 색인이나 누락 데이터를 모델 성능 문제로 오인하지 않기 위해서다.

Claude에게 제안하는 첫 합의는 **P0 강화 → 검색 E1/E2 비교 → 금액 의미 추출 개선**이다.
모델 이름이나 3주 일정부터 고정하지 말고, 평가셋 완성도와 실측 자원에 따라 다음 단계를 정하자.
