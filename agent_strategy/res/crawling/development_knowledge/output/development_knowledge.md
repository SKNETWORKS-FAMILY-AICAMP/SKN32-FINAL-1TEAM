# 웹 개발 Agent 지식 TOP 40

각 분류 10개. 순위는 실무 활용도를 기준으로 한 편집 순서입니다.

## 개발 방법론 및 개발 프로세스

### 1. 워터폴

- 개념: 요구·설계·구현·검증을 순차 단계로 계획하는 방식
- 언제: 범위와 승인 단계가 명확한 프로젝트
- 적용: 요구사항과 단계별 산출물·검수 기준을 먼저 정하고 변경 절차를 둔다
- 장점: 일정과 승인 기준이 명료하다
- 주의: 변경이 잦으면 후기 수정 비용이 커진다
- 출처: https://www.atlassian.com/agile/project-management/waterfall-methodology

### 2. 애자일

- 개념: 작은 가치 단위를 자주 전달하고 피드백으로 계획을 조정하는 원칙
- 언제: 요구가 변하거나 사용자 검증이 필요한 제품
- 적용: 작은 기능을 우선순위화하고 작동하는 결과를 주기적으로 보여준다
- 장점: 변화에 빨리 대응한다
- 주의: 계획·문서가 불필요하다는 뜻은 아니다
- 출처: https://agilemanifesto.org/principles

### 3. 스크럼

- 개념: 제품 목표·스프린트·검토·회고를 사용하는 경험적 프레임워크
- 언제: 팀이 짧은 주기로 제품 가치를 전달할 때
- 적용: 제품 백로그를 정렬하고 스프린트 목표와 완료 정의를 합의한다
- 장점: 목표와 피드백 주기가 선명하다
- 주의: 이벤트만 흉내 내고 완료 가능한 증가분이 없으면 효과가 약하다
- 출처: https://scrumguides.org/scrum-guide.html

### 4. 칸반

- 개념: 작업 흐름을 시각화하고 진행 중 작업을 관리하는 풀 방식
- 언제: 지원·유지보수처럼 일이 계속 유입될 때
- 적용: 시작·진행·완료 흐름을 정의하고 병목·흐름 지표를 점검한다
- 장점: 과부하와 병목을 볼 수 있다
- 주의: 보드만 만들고 흐름 정책을 운영하지 않으면 개선되지 않는다
- 출처: https://kanbanguides.org/the-kanban-guide/2020.12/

### 5. 테스트 주도 개발 TDD

- 개념: 실패하는 테스트·최소 구현·리팩터링을 반복하는 개발 방식
- 언제: 규칙이 명확한 로직을 안전하게 만들 때
- 적용: 작은 동작의 실패 테스트를 작성하고 통과시킨 뒤 중복을 정리한다
- 장점: 빠른 회귀 피드백을 얻는다
- 주의: 구현 세부사항만 테스트하면 변경에 취약하다
- 출처: https://martinfowler.com/bliki/TestDrivenDevelopment.html

### 6. 행동 주도 개발 BDD

- 개념: 업무·개발·테스트 담당자가 구체적 사례로 기대 행동을 합의하는 방식
- 언제: 요구 해석 차이가 잦은 기능
- 적용: 사용자 예시를 발견·표현하고 중요한 시나리오를 자동화한다
- 장점: 공통 이해와 실행 가능한 명세를 만든다
- 주의: Given/When/Then 문법만 쓰는 것은 BDD가 아니다
- 출처: https://cucumber.io/docs/bdd/

### 7. 도메인 주도 설계 DDD

- 개념: 도메인 모델과 공통 언어로 복잡한 업무 규칙을 설계하는 접근
- 언제: 업무 규칙이 복잡하고 팀 간 의미가 다른 경우
- 적용: 도메인 전문가와 용어를 맞추고 경계별 모델·규칙을 분리한다
- 장점: 업무 의미를 코드에 반영한다
- 주의: 단순 CRUD에 모든 패턴을 적용하면 과설계가 된다
- 출처: https://www.domainlanguage.com/ddd/reference/

### 8. MVP

- 개념: 핵심 가설을 검증할 수 있는 최소한의 제품 버전
- 언제: 제품 가치와 고객 수요가 불확실할 때
- 적용: 검증할 가설·대상 사용자를 정하고 최소 기능을 출시해 학습한다
- 장점: 투자 전에 가정을 검증한다
- 주의: 최소 기능을 저품질과 혼동하지 않는다
- 출처: https://martinfowler.com/articles/lean-inception/

### 9. 프로토타이핑

- 개념: 구현 전 핵심 사용 흐름이나 기술 가정을 빠르게 시험하는 시제품 활동
- 언제: 사용성·기술 가능성이 불확실할 때
- 적용: 가설 하나를 정해 화면 또는 기술 시제품을 만들고 관찰 결과를 기록한다
- 장점: 큰 구현 전에 위험을 드러낸다
- 주의: 시제품을 검증 없이 운영 코드로 승격하지 않는다
- 출처: https://www.ibm.com/training/enterprise-design-thinking/framework

### 10. 반복 개발

- 개념: 짧은 개발 반복마다 실행 가능한 결과와 학습을 쌓는 방식
- 언제: 초기 요구를 모두 확정하기 어려울 때
- 적용: 기능을 세로로 작게 나누고 반복마다 통합·평가·재계획한다
- 장점: 초기에 오류와 요구 오해를 찾는다
- 주의: 반복 계획 없이 기능만 추가하면 범위가 흔들린다
- 출처: https://martinfowler.com/articles/newMethodology.html

## 소프트웨어 설계·아키텍처

### 1. SOLID

- 개념: 객체 설계에서 책임·확장·대체 가능성·인터페이스 분리·의존성 역전을 다루는 원칙
- 언제: 변경이 잦고 객체 간 결합이 높을 때
- 적용: 변경 이유별로 책임을 분리하고 핵심이 구현 세부사항에 의존하지 않게 한다
- 장점: 변경 영향을 줄인다
- 주의: 모든 클래스에 추상화를 추가하는 규칙으로 쓰지 않는다
- 출처: https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/architectural-principles

### 2. DRY

- 개념: 같은 지식이나 규칙이 여러 곳에 중복되지 않게 하는 원칙
- 언제: 동일 업무 규칙이 여러 곳에서 수정될 때
- 적용: 중복 규칙의 단일 소유 위치를 만들고 호출 측에서 재사용한다
- 장점: 수정 불일치를 줄인다
- 주의: 겉모양만 비슷한 코드를 성급히 합치지 않는다
- 출처: https://martinfowler.com/bliki/BeckDesignRules.html

### 3. 단순 설계 KISS

- 개념: 현재 요구를 만족하는 이해하기 쉬운 구조를 우선하는 원칙
- 언제: 새 기능의 구조를 선택할 때
- 적용: 테스트를 통과하는 가장 단순한 설계를 택하고 실제 변경 압력이 생길 때 확장한다
- 장점: 이해·유지 비용을 낮춘다
- 주의: 단순함을 필수 요구 누락의 핑계로 삼지 않는다
- 출처: https://martinfowler.com/bliki/BeckDesignRules.html

### 4. MVC

- 개념: 모델·뷰·컨트롤러의 책임을 분리하는 UI 구조
- 언제: 서버 렌더링 웹 앱이나 요청 처리 계층을 설계할 때
- 적용: 컨트롤러는 입력을 조정하고 모델은 규칙을, 뷰는 표시를 담당하게 한다
- 장점: 화면과 규칙의 결합을 줄인다
- 주의: 컨트롤러에 모든 업무 로직을 몰아넣지 않는다
- 출처: https://learn.microsoft.com/en-us/aspnet/core/mvc/overview

### 5. 클린 아키텍처

- 개념: 업무 핵심을 중심에 두고 인프라가 핵심에 의존하게 하는 구조
- 언제: 외부 DB·UI 교체나 복잡한 업무 규칙이 예상될 때
- 적용: 핵심 모델·인터페이스를 안쪽에 두고 DB·HTTP 구현을 바깥에 둔다
- 장점: 기술 교체와 핵심 테스트가 쉬워진다
- 주의: 작은 앱에 계층·프로젝트를 과도하게 늘리지 않는다
- 출처: https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures

### 6. 레이어드 아키텍처

- 개념: UI·업무·데이터 접근 등 책임을 계층으로 나누는 구조
- 언제: 전형적인 업무 웹 앱의 변경 경계를 정할 때
- 적용: 계층별 인터페이스와 호출 방향을 정하고 순환 의존을 피한다
- 장점: 책임과 변경 범위를 명확히 한다
- 주의: 단순 전달 계층만 늘면 복잡도만 증가한다
- 출처: https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier

### 7. REST 자원 설계

- 개념: HTTP의 자원·메서드·상태 코드를 일관되게 활용하는 API 설계
- 언제: 외부 또는 프런트엔드용 HTTP API를 만들 때
- 적용: 자원 URI를 정하고 GET·POST·PUT·DELETE와 상태 코드를 의미에 맞게 사용한다
- 장점: 클라이언트 계약을 이해하기 쉽다
- 주의: 모든 동작을 CRUD에 억지로 맞추지 않는다
- 출처: https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods

### 8. 데이터베이스 제약과 트랜잭션

- 개념: 스키마 제약과 원자적 작업으로 데이터 일관성을 지키는 설계
- 언제: 여러 테이블을 갱신하거나 중복·누락을 막을 때
- 적용: 기본키·외래키·유니크 제약을 두고 함께 성공해야 할 변경을 트랜잭션으로 묶는다
- 장점: 데이터 무결성을 높인다
- 주의: 긴 트랜잭션과 불필요한 잠금을 피한다
- 출처: https://www.postgresql.org/docs/current/tutorial-transactions.html

### 9. 디자인 패턴

- 개념: 반복되는 설계 문제에 검증된 구조적 해법을 적용하는 방식
- 언제: 객체 생성·상태·구성의 문제가 반복될 때
- 적용: 문제를 먼저 설명하고 적합한 패턴을 작은 범위에 적용한다
- 장점: 공통 설계 어휘를 제공한다
- 주의: 패턴 이름을 목표로 과설계하지 않는다
- 출처: https://refactoring.guru/design-patterns

### 10. 의존성 주입

- 개념: 필요한 구현을 내부 생성 대신 외부에서 제공받는 구성 방식
- 언제: 테스트 대역이나 구현 교체가 필요한 서비스
- 적용: 핵심 코드는 인터페이스에 의존하고 시작 지점에서 실제 구현을 연결한다
- 장점: 결합을 낮추고 테스트를 쉽게 한다
- 주의: 단순 객체까지 모두 주입하면 구성이 난해해진다
- 출처: https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/overview

## 개발 실무 및 품질 관리

### 1. Git 브랜치와 통합 전략

- 개념: 변경을 분리하고 공통 브랜치에 안전하게 합치는 작업 방식
- 언제: 여러 개발자가 같은 저장소에서 일할 때
- 적용: 작은 브랜치를 만들고 자주 동기화하며 검토·검사를 통과한 뒤 병합한다
- 장점: 협업 변경을 추적할 수 있다
- 주의: 오래 살아 있는 브랜치는 통합 충돌을 키운다
- 출처: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches

### 2. 코드 리뷰

- 개념: 병합 전 변경의 정확성·가독성·위험을 동료가 검토하는 절차
- 언제: 공유 코드나 운영 영향이 있는 변경
- 적용: 작은 PR에 의도·검증 결과를 적고 구체적인 리뷰 의견을 주고받는다
- 장점: 결함 발견과 지식 공유에 도움 된다
- 주의: 리뷰를 개인 평가나 단순 승인 절차로 만들지 않는다
- 출처: https://docs.github.com/en/pull-requests/reference/pull-request-reviews

### 3. 단위 테스트

- 개념: 작은 함수·모듈의 동작을 격리해 검증하는 테스트
- 언제: 업무 규칙과 경계 조건을 빠르게 확인할 때
- 적용: 입력·기대 출력을 명시하고 정상·오류·경계 사례를 자동화한다
- 장점: 빠른 회귀 피드백을 준다
- 주의: 내부 구현만 고정하는 테스트를 피한다
- 출처: https://docs.pytest.org/en/stable/getting-started.html

### 4. 통합 테스트

- 개념: 여러 구성 요소의 실제 연결과 계약을 검증하는 테스트
- 언제: DB·API·서비스 사이 오류가 걱정될 때
- 적용: 실제 또는 통제된 의존성을 연결해 주요 성공·실패 흐름을 실행한다
- 장점: 경계 연결의 오류를 찾는다
- 주의: 모든 사례를 느린 통합 테스트로만 검증하지 않는다
- 출처: https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests

### 5. E2E 테스트

- 개념: 사용자 관점에서 앱의 전체 흐름을 실행하는 테스트
- 언제: 로그인·결제 등 핵심 경로를 출시 전 확인할 때
- 적용: 브라우저로 시작부터 결과까지 실행하고 안정적인 사용자 선택자를 사용한다
- 장점: 시스템 전체의 깨진 흐름을 잡는다
- 주의: 모든 세부 경우를 E2E로 검증하면 느리고 불안정하다
- 출처: https://playwright.dev/docs/intro

### 6. CI

- 개념: 변경을 자주 통합하고 자동 빌드·검사를 실행하는 실무
- 언제: 팀 변경의 통합 결함을 일찍 찾을 때
- 적용: PR과 기본 브랜치에서 빌드·린트·테스트를 자동 실행한다
- 장점: 통합 문제를 일찍 발견한다
- 주의: CI가 느리거나 자주 실패하면 신뢰가 떨어진다
- 출처: https://docs.github.com/en/actions/get-started/continuous-integration

### 7. CD

- 개념: 검증된 변경을 자동 배포 파이프라인으로 전달하는 실무
- 언제: 반복 배포와 롤백을 안정화할 때
- 적용: 빌드·테스트 뒤 환경별 배포와 승인·비밀 관리·복구 경로를 설정한다
- 장점: 반복 작업과 배포 오류를 줄인다
- 주의: 자동화 전에 배포 실패 시 복구 방법을 정한다

### 8. 디버깅

- 적용: 오류를 재현하고 로그·브라우저 개발 도구·중단점으로 원인을 좁힌다

- 주의: 민감 정보를 로그에 남기지 않는다
