# 전체 파이프라인 및 문서 목차
전략·작성·검증1 Agent 워크플로우

> 이 문서는 개발·검증 중인 워크플로우 초안임. 작성 흐름은 큰 변경이 적지만 검증 과정에서 세부 동작과 설명이 조금씩 수정될 수 있으며, 전체 내용은 2026년 10월 12~16일에 확정할 예정임.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">문서 유형 선택 (documentType / kind)</h2>

UI에서 선택한 `documentType`을 `kind`로 전달하며, 이 값으로 입력 구조와 사업계획서 기준을 선택함. 파이프라인은 입력 JSON의 내용을 추측해 문서 유형을 정하지 않음.

| kind | 문서 유형 |
|---|---|
| `general` | 일반 사업계획서 |
| `pre_startup` | 예비창업패키지 |
| `early_startup` | 초기창업패키지 |

선택된 유형은 입력 정규화, 항목 매핑, 작성 규칙, 예산·일정 및 검증 기준 전반에 적용됨.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">파이프라인 진입점 (run_pipeline)</h2>

`run_pipeline(raw, kind, ...)`은 back에서 전달된 JSON과 선택된 문서 유형을 받는 파이프라인 진입점임. `raw`는 사용자·프로젝트 입력이고 `kind`는 `documentType` 값이며, 이를 실행 조정 모듈인 `runtime/pipeline.py`에 전달함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">오케스트레이터 구성 (pipeline.py)</h2>

`runtime/pipeline.py`는 전체 실행 순서와 데이터 전달을 조정하는 오케스트레이터임. 세부 함수의 처리는 각 전용 모듈에 위임하고, 실행 범위와 단계 간 연결을 관리함.

| 모듈 | 책임 |
|---|---|
| `runtime/pipeline.py` | 파이프라인 실행 순서, 범위 제어, 결과 저장 |
| `runtime/llm_runtime.py` | 모델 호출, 프롬프트 합성, 토큰 한도, JSON 계약, 사용량 기록 |
| `functions/python_functions.py` | F01, F14, F15, F17 등 Python 기반 처리 |
| `functions/gpt_functions.py` | F02~F13, F16, F18 등 LLM 기반 처리 |
| `app/testing/test_server.py` | UI 요청, 실행 범위, 작업 상태, 중단 요청, 결과 경로 관리 |
| `agent_validation_1/validation_1.py` | F19 검증 1과 점수·상태 판정 |
| `res/js/strategy_writing_agent.js` | 선택 항목·자동 회귀·이미지 전용 재작성, UI 이력 표시 |

계약과 모델 실행은 `llm_runtime.py`, 전략·작성 함수는 Python 및 GPT 함수 모듈, 검증은 validation 모듈이 담당하며 `pipeline.py`가 이들을 연결함.

<br><br><h3 style="color:#92400e;background:#fffbeb;border-left:4px solid #f59e0b;padding:8px 12px;border-radius:5px">오케스트레이터 공통 운영</h3>

`pipeline.py`가 조정하는 공통 실행·복구 정책은 다음과 같음. 단계별 처리 순서는 실행 순서 요약과 1~8단계 절에 설명하고, F19 fail 이후의 회귀 재작성 절차는 7단계에 따로 정리함.

**실행 제어와 재작성**

- **실행 범위 제어**: `/api/run`의 `executionScope`는 `full`과 `strategy_writing`을 구분함. 기존 결과 검증·조립, 선택 항목 재작성, 이미지 전용 재작성은 별도 요청 경로임. `/api/retry-latest`의 `mode`는 현재 실행 범위를 제한하지 않고 재작성 이력에 기록함.
- **부분 실행 데이터 재사용**: 재작성 경로는 기존 `canonical` 결과와 `strategyProvenance`를 재사용하며, F01~F15를 다시 호출하지 않음.
- **재작성 범위 결정**: 선택 항목과 직접 연관된 항목의 계산은 `impact_plan`이 담당함. F19 fail 후 자동·수동 실행 조건과 처리 순서는 **7. F19 fail 회귀 재작성·재검증**을 따름.

**조사 자료와 작성 제약**

- **선택적 산업 조사 갱신**: `refresh_user_industry_research`는 `SBRAIN_AUTO_RESEARCH=1`일 때만 현재 사용자의 산업 키워드로 KIET 크롤러를 실행함. 기본값에서는 갱신을 건너뜀.
- **조사 자료 검색**: `research_context.retrieve`는 기존 크롤링·지식 JSON을 대상으로 로컬 키워드 검색을 수행함. 실시간 웹 검색이나 임베딩 검색은 아니며, F01 자료와 시장·경쟁·개발 근거를 각 전략 함수에 전달함.
- **사실 상태 전달**: `_annotate_status`가 전략 사실을 `provided`, `proposed`, `needs_confirmation`으로 표시해 작성·검증 단계에 전달함.
- **유형별 제약 적용**: `_strategy_limits`로 `deadline`, `supportLimit`, `featureList`를 확인하고, 예비창업 예산은 `_pre_startup_budget_phases`를 통해 1·2단계로 나눠 관리함.

#### 실행 상태·부분 결과 보존

- **결과와 이력 추적**: 함수별 모델, 입력·출력 토큰, 총 토큰, 실행 시간, 호출 횟수와 자동·수동 재작성 이력을 실행 결과에 기록함.
- **실행 중 오류·중단**: 함수가 실패하면 그 전에 완료된 호출 trace와 작성 항목·이미지를 부분 결과로 저장함. 호출 trace는 함수가 반환된 뒤에 추가되므로 실패한 현재 호출의 결과는 완료 결과에 포함되지 않음. 취소 요청은 진행 중인 모델 호출이 끝난 뒤 다음 실행 경계에서 반영됨.
- **저장되는 파일**: 서버는 성공·오류·취소 결과를 실행별 폴더에 저장함. 부분 실행도 `result.json`, `validation.json`, `result.html`, `manifest.json`을 남기며, 생성된 SVG가 있으면 함께 저장함. 저장 자체가 실패하면 가능한 경우 `saveError`에 오류를 기록함.
- **복구 범위**: 이 동작은 완료된 결과를 다시 확인하고 별도 재검증·재작성 요청을 이어갈 수 있도록 보존하는 기능임. 마지막 함수부터 자동으로 이어 실행하는 체크포인트 재개 기능은 아님. 재작성 중 오류가 나면 재작성 함수가 반환하기 전의 변경분은 보장하지 않고 이전 저장 결과를 바탕으로 부분 결과를 저장함.
- **실행별 이력 관리**: 실행 ID와 시각을 포함한 새 폴더에 각 결과를 저장해 기존 실행 파일을 덮어쓰지 않음. 실행 범위별 결과와 검증·재작성 이력을 구분해 추적함.

<br><br><h3 style="color:#92400e;background:#fffbeb;border-left:4px solid #f59e0b;padding:8px 12px;border-radius:5px">실행 순서 요약 (목차 1~8단계)</h3>

아래 1~8단계는 `executionScope: "full"`의 처리 순서임. `strategy_writing`은 5.1 작성 결과를 3.4의 구조에 보존한 뒤 F19·F20을 생략하고 `validation.status=not_run`으로 기록함. 상세 설명은 각 번호의 제목에서 확인하며, 7단계 회귀 재작성은 6단계 검증에서 fail이 있을 때만 실행함.

1. **실행 계약·입력 준비**
   - **1.1 실행 계약 로드 (execution_contract.json)**: 함수별 입력·출력과 실행 설정을 준비함.
   - **1.2 입력 정규화 (normalize_back_input)**: back JSON을 `kind`별 canonical data로 변환함.
   - **1.3 실행 제약 확인 (_strategy_limits)**: 일정·예산 상한·필수 기능 조건을 확인함.

2. **조사 자료 준비: 사이트별 수집·검색 경로**
   - **2.1 기준 자료 구축·선택적 갱신**: 사이트별 기준 자료를 준비하고 설정에 따라 KIET 자료를 갱신함.
   - **2.2 파이프라인 실행 시 검색·전달**: 저장된 자료를 로컬 검색해 필요한 전략 함수에 전달함.

3. **F01~F15 공통 전략 실행**
    - **3.1 실행 흐름과 함수 목록**에 따라 전략 함수를 실행함.
    - **3.2 F01~F15 프롬프트 구성** 기준에 맞춰 함수별 지시와 입력을 전달함.
    - **3.3 F01~F15 결과 구조와 근거 보존**에서 `canonical`, 근거, 사실 상태를 함께 관리함.
    - **3.3.1 canonical 데이터 계보: 생성·참조·사용 경로**와 **3.3.2 항목별 sourceKeys 선별·작성·검증 전달**로 후속 작성 입력까지 연결함.
    - **3.4 F16~F18 작성·결과·근거 보존**은 같은 상위 목차 아래 묶은 관련 하위 절임. 실제 작성 실행은 4단계 항목 연결과 5단계 유형 규칙 적용 뒤 진행함.
      - **3.4.1 F16 프롬프트 지시 구성·F17 표·F18 이미지 작성**에서 함수별 실행 내용을 확인함.
      - **3.4.2 F16~F18 결과 구조와 생성 산출물 보존**을 기록함.
      - **3.4.3 작성 데이터 계보: sourceKeys 선별·작성·검증 전달**을 추적함.

4. **작성 항목 연결 (section_mapping.json + execution_contract.json)**: 항목·`sourceKeys`를 연결함.

5. **문서 유형별 작성 규칙 (writing_rules.json)**: 공통 및 유형별 규칙을 적용함.
   - **5.1 항목별 F16/F17/F18 작성 및 작성 단계 재시도**: 유형 규칙과 `section_spec`, `source_data`로 본문·표·이미지 명세를 생성함.
   - 함수별 프롬프트와 로컬 처리 경계는 **3.4.1 F16 프롬프트 지시 구성·F17 표·F18 이미지 작성** 설명을 참조함.
6. **F19 검증·결과 저장·상태 분기**
   - **6.1 저비용 구조·계약 검사 (F19-1 · Python)**와 **6.2 원본 사실·근거·상태값 대조 (F19-2 · Python)**를 먼저 수행함.
   - issues가 발견되면 `fail`로 기록하고 의미 검증 호출을 생략함.
   - 저비용 검사를 통과한 경우 다음 하위 절을 순서대로 진행함.
     - **6.3 규정·공고 자료와 유형별 기준 (F19-3 · LLM 호출)**에서 의미 검증을 수행함.
     - **6.4 의미 검증 결과 재분류·조정 (F19-4 · Python, 추가 LLM 호출 없음)**을 진행함.
     - **6.5 점수 계산과 공식 배점 구분 (F19-5 · Python)**을 적용함.
       - **6.5.1 rubric 평가 항목과 유형별 가중치**를 확인함.
       - **6.5.2 점수 계산 순서와 기본 감점**, **6.5.3 감점 간격을 둔 이유**를 설명함.
       - **6.5.4 공고 평가영역과 내부 점수의 관계**, **6.5.5 별도 제약 감점과 70점 척도 구분**을 정리함.
     - **6.6 최종 상태와 회귀 재작성 연결 (F19-6 · Python)**에서 결과를 판정함.
     - **6.7 판정 저장과 후속 경로 분기 (Python)**에서 검증·평가·시도 기록을 저장하고 다음 단계로 연결함.
   - 전체 대상이 `pass`/`warning`이면 8단계로 진행하고, `fail`이 있으면 F20 조립을 보류함.

7. **F19 fail 회귀 재작성·재검증**
    - 6단계 또는 재검증에서 `fail`이 남으면 F20을 보류함.
    - 전체 실행 완료 후 자동 회귀 설정을 따르거나 사용자가 fail 항목을 선택함.
    - 선택 항목과 `impact_plan` 연관 항목만 다시 작성하고 F19를 재실행함.
    - F01~F15 결과는 재사용함. 재검증 결과가 모두 `pass`/`warning`이면 8단계로 진행하고, fail 잔존 시 조립을 보류함.

8. **F20 조립 및 결과 저장**: 초기 실행 또는 재검증에서 전체 대상이 `pass` 또는 `warning`일 때 최종 문서 구조를 조립하고 저장함. `fail`이 남아 있으면 조립을 보류함.

단계별 상세 기준과 구현 설명은 아래에서 같은 번호의 제목을 확인함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">1.1 실행 계약 로드 (execution_contract.json)</h3>

`llm_runtime.py`는 파이프라인 실행에 필요한 [`execution_contract.json`](../runtime/execution_contract.json)을 읽음. 함수별 입력·출력 구조, 모델, 출력 토큰 한도와 `general`, `pre_startup`, `early_startup`별 항목 계약을 준비함.

**모델 설정과 실제 실행 구분**

- 표의 모델 ID는 `execution_contract.json`에 설정된 기본값임. 해당 함수의 `STRATEGY_MODEL_F01`~`STRATEGY_MODEL_F20` 환경변수가 있으면 그 값으로 override함.
- 실제 호출 모델은 실행 trace의 `model` 및 함수 호출정보에서 확인함. `modelLabel`은 계약에 적힌 표시용 별칭이며, 이름에 Web·RAG가 포함되어도 실시간 웹 검색을 의미하지 않음.

**함수별 호출 예외**

- **F01**: 로컬 `retrieve` 검색을 먼저 수행하고, 검색 결과가 있을 때만 모델에 해석을 요청함.
- **F17**: 계약에 모델 ID가 있어도 현재 구현은 Python 로컬 처리만 수행함.
- **F19**: 저비용 검사에서 `issues`가 발생하면 의미 검증 LLM 호출을 생략함.

아래는 `execution_contract.json` 함수 설정의 주요 필드를 발췌한 예임. `input`·`output` 설명 배열이 아니라 계약에 저장된 `inputs`·`output` 값을 그대로 표시함.

```json
{
  "name": "generate_section",
  "inputs": "section_spec, source_data, writing_rules",
  "output": "section_content",
  "maxOutputTokens": 4000
}
```

```json
{
  "name": "generate_table",
  "inputs": "columns, rows, rules",
  "output": "table",
  "maxOutputTokens": 0
}
```

```json
{
  "name": "generate_image_spec",
  "inputs": "item, architecture, flow_type",
  "output": "image_spec",
  "maxOutputTokens": 1600
}
```

표마다 필요한 열은 문서 유형과 항목에 따라 다르므로, F17 함수에 공통으로 고정하지 않고 각 항목의 `section_spec.rules.requiredColumns`에 지정함. 예를 들어 개발계획 표와 사업비 표는 필요한 열 구성이 서로 다름.

계약의 `output: "table"`은 결과 종류를 나타내는 이름임. 실제 F17은 Python에서 표 데이터 `tables`, 표 내용을 연결한 `generatedText`, 처리 상태인 `status` 등을 반환함.

F14·F15도 모델에게 계산과 행 구성을 전부 맡기지 않음. F14는 Python이 금액 합계를 계산하고, F15는 Python이 일정 행을 구성함. 모델은 이렇게 정리된 원본과 규칙을 받아 설명을 작성하고, 계산된 합계와 일정 행은 Python 결과에 보존함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">1.2 입력 정규화 (normalize_back_input)</h3>

사용자 입력은 마이페이지 정보와 프로젝트 관련 입력값으로 구성됨. back JSON과 선택된 `kind`를 기준으로 문서 유형별 입력 필드, 일정, 예산, 팀 구성, 사업계획서 항목을 전략 실행용 canonical data로 변환함.

```python
if kind == 'general':
    # 일반 사업계획서 입력 정규화
elif kind == 'pre_startup':
    # 예비창업패키지 입력 정규화
elif kind == 'early_startup':
    # 초기창업패키지 입력 정규화
```

정규화 단계에서는 입력값을 보존함. 지원금 상한, 자기부담금, 단계별 예산 합계, 협약 종료월 등 입력값 간의 정합성은 이후 F19에서 검증함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">1.3 실행 제약 확인 (_strategy_limits)</h3>

`_strategy_limits`는 파이프라인이 계산하는 값이 아니라 입력 JSON에서 읽어 이후 단계에 전달하는 제약값임. 실제 정규화 로직은 최상위 `_strategy_limits`, 호환 키 `strategyLimits`, `tableData` 안의 `_strategy_limits` 순으로 확인함.

초기창업 입력 JSON의 마지막 속성에는 실제로 다음 제약값이 들어 있음.

```json
"_strategy_limits": {
  "deadline": "2027-03",
  "supportLimit": 100000000,
  "featureList": [
    "수요예측 모델 고도화",
    "발주 자동화 기능",
    "POS 판매 데이터 연동",
    "유료 전환 및 매장 확장"
  ]
}
```

이는 [`example_early_startup.json`](../res/back_input/example_early_startup.json)에 저장된 블록임.

```python
table = raw.get("tableData") or {}
limits = (
  raw.get("_strategy_limits")
  or raw.get("strategyLimits")
  or table.get("_strategy_limits")
  or {}
)
plan["strategy_limits"] = limits
```

주요 필드는 다음과 같음.

- `deadline`: 협약기간 일정의 종료 기한. 예비창업 유형은 협약 이후 로드맵과 구분해 적용함.
- `supportLimit`: 정부지원사업비 상한. 예산 결과가 유형별 한도를 넘는지 검증할 때 사용함.
- `featureList`: 작성·검증에서 빠뜨리지 않아야 할 전략 기능 목록.

예비창업은 `implementationSchedule`만 협약기간 일정으로 보고 `deadline`을 적용함. `fullScaleSchedule`은 협약 이후 로드맵이므로 전체 일정 데이터에는 포함하되 협약 종료일 초과로 판정하지 않음. 예산은 항목의 단계별 금액을 `budget.phase_1`, `budget.phase_2`로 분리함.

```python
agreement = [
  {**row, "_schedule_scope": "agreement"}
  for row in (table.get("implementationSchedule") or [])
]
roadmap = [
  {**row, "_schedule_scope": "roadmap"}
  for row in (table.get("fullScaleSchedule") or [])
]
schedules = agreement + roadmap
dev_start, dev_end = _period_months(agreement)  # 협약기간 기준일은 agreement에서만 계산

if kind == "pre_startup":
  c["budget"] = _pre_startup_budget_phases(c["budget"], budgets)
```

`_pre_startup_budget_phases`는 각 예산 항목의 단계값을 기준으로 항목과 합계를 분리해 `phase_1`, `phase_2`에 채움.

파이프라인은 준비된 로컬 JSON 자료에서 아이템 설명과 기술 분야에 맞는 근거를 찾음.

- **F01 조사 결과**: `collect_web_data`가 같은 검색어로 자체 자료를 찾고, 결과가 있을 때만 모델에 해석을 요청함.
- **후속 분석용 근거**: F01과 별도로 시장·경쟁·개발 자료를 다시 검색해 각각 F03, F04, F02·F07에 전달함.

```python
web_data = collect_web_data(query, source_type="attached_crawling", target_fields=["market", "development", "design"])
market_evidence = retrieve(query, domains=("market",), limit=4)
competitor_evidence = retrieve(query + " 경쟁사 경쟁 비교", domains=("market",), limit=4)

```

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">3.2 F01~F15 프롬프트 구성</h3>

F01~F15의 프롬프트 본문은 함수별 별도 파일이 아니라 [`runtime/llm_runtime.py`](../runtime/llm_runtime.py)의 공통 지침과 `FIELDS[fid]` 지시를 조합해 실행 시 구성함. 입력 payload는 JSON으로 직렬화해 user 메시지에 전달함.

`execution_contract.json`은 함수별 모델·입출력·출력 토큰 한도를 정하는 호출 설정이며, 프롬프트 원문은 아님.

공통 지침은 JSON 객체 반환, 입력을 지시가 아닌 데이터로 취급, 제공된 원본 사실·근거 우선, 사실과 제안 구분, 개인정보 제한 등을 요구함. 여기에 함수별로 반환 필드와 판단 규칙을 덧붙임.

| 함수 | 함수별 프롬프트 지시 요약 |
|---|---|
| F01 | 제공된 검색 결과를 왜곡하지 않고 `summary`와 실제 `sourceRef`만 반환. 요약은 3문장 이내 |
| F02 | `coreFeatures`, `targetCustomer`, `deliverables`, `differentiation`을 구조화 |
| F03 | `marketNeed`, `marketTrend`, `developmentNeed`를 반환하고 근거 주장마다 `sourceRef` 인용 |
| F04 | 경쟁사별 제품·관계·근거 참조·신뢰도를 반환. 근거가 없으면 경쟁사를 만들지 않음 |
| F05 | 대표·팀원 역량과 요구 역량의 차이를 `gaps`로 구조화 |
| F06 | 목표·핵심기술·측정 환경이 포함된 KPI를 정의하고 미확정 목표값은 확정하지 않음 |
| F07 | 기술별 개발·확보 방법과 아키텍처를 구조화 |
| F08 | 단계와 산출물을 반환하고 입력된 기간을 유지 |
| F09 | 제품화·양산 단계를 `stage`, `features`, `plan`으로 구조화 |
| F10 | 시장 진입 전략을 `earlyAccess`, `matureStage`로 구분 |
| F11 | 고객·수익·채널을 구조화 |
| F12 | 경쟁·진입·비즈니스 모델·투자·사회적 가치를 통합 |
| F13 | 장비·채용·협력기관 계획을 반환하고 입력의 `no_hires`, `no_equipment`, `no_partners` 상태를 보존 |

| F15 | 제공된 일정만 설명하고 날짜를 변경하지 않음. 일정 행 구성은 Python에서 선행 |

F02~F13은 `gpt_functions.py`의 함수가 `request_json`으로 연결함. F01·F14·F15는 `python_functions.py`가 검색·계산·일정 행 구성 등 입력을 먼저 준비한 뒤 필요 시 같은 `request_json`을 호출함. F01 함수는 매번 로컬 검색을 실행하고, 검색 결과가 있을 때만 모델 해석 요청을 추가함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">3.3 F01~F15 결과 구조와 근거 보존</h3>

F01~F15 결과는 공통 구조인 `canonical`에 모임. 가능한 경우 `sourceRefs`, `evidence`, `originalFacts`, `status`를 함께 보존함. `_annotate_status`는 사실을 `provided`(확정 입력), `proposed`(제안값), `needs_confirmation`(확인 필요)으로 표시함.

실제 조사 원문 파일은 사용자 산업 키워드에 따라 달라질 수 있으며, `sourceRefs`와 `evidence`로 원문 경로·JSON 위치·발췌를 추적함.

이 단계는 별도 조사 기능이 아니라 F01~F15 결과를 canonical에 정리하고, 항목별 작성·검증으로 넘기는 데이터 연결 단계임. 아래 세 부분으로 나누어 설명함.

1. **생성·보존**: F01~F15가 canonical 키별 결과를 만들고, 결과에 출처·근거·사실 상태를 붙임.
2. **계보 추적**: canonical 표에서 각 키의 생성 함수, 참조 경로, 포함 데이터, 후속 사용처를 확인함. 표 자체가 근거 원문은 아님.
3. **항목별 전달·검증**: 항목의 `sourceKeys`로 필요한 canonical 값만 골라 F16/F17/F18에 전달하고, F19가 같은 근거와 생성 결과를 함께 검증함.

예를 들어 `web_data`는 조사 자료와 출처를, `item_spec`은 아이템 요구사항을, `development_plan`은 개발 목표·내용·산출물·일정 연결을 보관함.

```python
# F01~F15 결과를 모은 공통 데이터
canonical = {
  "web_data": {
    "market": {...}, "development": {...}, "design": {...},
    "sourceRefs": [...], "evidence": [...]
  },
  "item_spec": {...},
  "market_analysis": {...},
  "competitor_analysis": {...},
  "development_plan": {...}
}
```

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.3.1 canonical 데이터 계보: 생성·참조·사용 경로</h4>

아래 표는 앞 절의 자세한 출처 목록을 반복하지 않고, 실행 중 canonical 키가 어떤 입력을 받아 어디로 전달되는지 요약함. 실제 근거 원문은 각 결과의 `sourceRefs`·`evidence`가 가리킴.

| canonical 키 | 생성 | 주요 입력·근거 | 후속 사용처 |
|---|---|---|---|
| `web_data` | F01 | `query` 기반 로컬 검색 결과·출처 | sourceKeys에서 선택하는 F16 항목 (예비·초기 2.1.1·3.1.1) |
| `item_spec` | F02 | 아이템 입력·개발 근거 | F05·F06·F09~F11·F13·F16·F18 |
| `market_analysis` | F03 | `item_spec`·별도 검색한 `market_evidence` | F04·F10~F12·F16 |
| `competitor_analysis` | F04 | `item_spec`·`market_analysis`·별도 검색한 `competitor_evidence` | F12 |
| `development_plan` | F08 | `development_goal`·기간·단계(`phases`) | F09·F16·F17 |

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.3.2 항목별 sourceKeys 선별·작성·검증 전달</h4>

앞의 계보표에 나온 canonical 전체를 매 항목에 넘기지 않음. 매핑에 등록된 `sourceKeys`가 필요한 canonical 키만 선별하며, 해당 `source_data`를 F16/F17/F18 작성에 사용함. F19에는 그 항목의 생성 결과와 같은 `source_data`를 함께 전달해 본문·표·이미지와 근거의 일치 여부를 검증함.

```python
# 항목에 필요한 결과만 F16에 전달
spec = {"sectionId": "2.1.2", "sourceKeys": ["item_spec", "market_analysis"]}
sources = select_sources(canonical, spec["sourceKeys"])
content = generate_section(spec, source_data=sources)

# 같은 본문·근거를 F19에서 검증
validation = validate_section(spec, content, source_data=sources)
```

`select_sources(...)`, `generate_section(...)`, `validate_section(...)`은 데이터 전달 관계를 설명하기 위한 예시 함수명임. 실제 `sourceKeys`는 항목 매핑에서 관리하며, canonical 전체가 아니라 지정된 결과만 작성·검증 입력으로 구성함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">3.4 F16~F18 작성·결과·근거 보존</h2>

항목별 `section_spec`, 매핑된 `source_data`, 문서 유형별 작성 규칙을 바탕으로 작성함. 생성 출력과 입력 근거는 이 절의 하위 항목에서 보존하며, F19 이후 `validation`·`evaluation`·`attempts` 저장과 상태 분기는 **6. F19 검증·결과 저장·상태 분기**에서 설명함.

| 함수 | 역할 | 반환 및 후속 처리 |
|---|---|---|
| F16 `generate_section` | 본문 생성 | `generatedText`, 상태값, 근거 연결을 F19로 전달 |
| F17 `generate_table` | 표 생성 | `columns`, `rows`, 상태를 반환하고 F20 조립에 사용 |
| F18 `generate_image_spec` | USER_FLOW·SERVICE_ARCHITECTURE 이미지 명세 생성 | `image_spec`을 반환한 뒤 로컬 SVG 변환·저장. 파일 경로는 결과 JSON의 `images`에 기록 |

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">3.4.1 F16 프롬프트 지시 구성·F17 표·F18 이미지 작성</h3>

F16은 모든 항목에 같은 본문 지시만 보내지 않음. 런타임은 공통 JSON·사실성 지침과 문서 유형별 `writing_rules.json` 규칙을 적용한 뒤, 실행 계약의 해당 항목 `section_spec`을 입력으로 전달함.

`section_spec.title`이 항목별 작성 지시이고, `section_spec.rules`가 문장 수·줄 수·필수 개수 같은 추가 제약임. `sourceKeys`로 고른 `source_data`는 작성 근거로 함께 전달하며, 항목별 공고·양식 기준이 있으면 `sectionCriteria`도 추가함.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.4.1.1 F16 본문 생성</h4>

**입력**: 항목 계약, `sourceKeys`로 고른 `source_data`, 문서 유형별 작성 규칙을 준비함.

**생성**: 준비한 입력을 한 번의 F16 호출에 전달함.

```python
output = call(
  "F16",
  gpt.generate_section,
  section_spec=spec,
  source_data=source,
  writing_rules={
    "documentType": kind,
    "sectionCriteria": _writing_criteria(kind, sid),
    "tableGenerationEnabled": False,
    "validationFeedback": [],
    "previousText": None,
    "preserveProvenance": True,
    "statusPolicy": ["provided", "proposed", "needs_confirmation"],
  },
)
```

**검증 연결**: F16 결과의 `generatedText`와 근거 참조를 저장하고, 같은 `source_data`를 F19에 전달함. 빈 응답, 빈 객체, 제목만 있는 응답, 출력 한도에 걸린 잘린 응답은 성공으로 저장하지 않음.

F19 fail 이후 회귀 재작성에서는 기존 본문과 검증 issues, 재작성 지시를 `writing_rules`에 추가해 전달함. 최초 작성 호출에는 이전 본문이나 검증 피드백이 없음.

<br><br>

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.4.1.2 F17 표 생성</h4>

**입력 구성**: `columns`, `rows`, `rules`는 문서 유형별 원본 입력과 실행 계약에서 구성함. 원본 표가 없는 일부 항목은 canonical의 일정·예산 행을 보조 입력으로 사용함.

```python
table_args = table_arguments(raw, kind, spec, canonical)
output = call("F17", py.generate_table, **table_args)
```

**문자열 생성**: 현재 F17은 OpenAI를 호출하지 않음. `generate_table`이 입력 행을 복사해 `tables`에 보존하고, 열·셀 값을 ` | `로 연결해 `generatedText`를 만듦. `narrativeRequired`가 켜져 있으면 일정 또는 예산 행의 값을 정해진 문장 틀에 넣어 서술문을 덧붙임. 셀 문자열과 서술문 모두 Python 로컬 처리 결과임.

**결과 전달**: `tables: [{"columns": ..., "rows": ..., "rules": ...}]`와 `generatedText`를 반환함. F19가 결과를 검증하고, 통과 조건을 충족하면 F20 조립에 전달함. F19의 의미 검증에는 OpenAI 호출이 사용될 수 있음.

**구조 복구**: F19가 fail이면 전체 실행에서 F17을 최대 한 번 더 호출함. 재호출에도 이전 F19 issues를 전달하지 않으며, F17은 같은 입력을 처리하는 로컬 Python 함수라 결과를 새로 추론하지 않음. 따라서 원본 행 누락 같은 결정론적 오류는 재호출로 해결되지 않으며, 두 번째 시도도 fail이면 `tableFallbackUsed`, `fallbackReason`을 기록하고 문자열 설명으로 대체함. `strategy_writing` 범위에서는 F19를 실행하지 않으므로 한 번만 호출함.

F16·F17·F18 결과는 저장 전에 JSON 계약과 필수 필드를 확인함.

<br><br>

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.4.1.3 F18 이미지 명세 생성</h4>

**명세 생성**: 한 섹션에서 `USER_FLOW`와 `SERVICE_ARCHITECTURE` 명세를 각각 F18로 생성함.

```python
image_specs = []
for flow_type in ("USER_FLOW", "SERVICE_ARCHITECTURE"):
  image_specs.append(call(
    "F18",
    gpt.generate_image_spec,
    item=source["item_spec"],
    architecture={"design": source.get("architecture", {}), "validationFeedback": []},
    flow_type=flow_type,
  ))
images = [render_image(image_spec) for image_spec in image_specs]
```

**렌더링·저장**: 모델은 이미지 명세를 반환하고, SVG 변환과 파일 저장은 로컬 Python 렌더러가 수행함.

**이미지 전용 재작성**: `2.3.6` 또는 `3.3.6` 요청에서는 F18 이미지 명세와 SVG를 갱신함.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">3.4.1.4 F16~F18 작성 단계 내부 실패·재시도</h4>

이 절은 한 번의 작성 실행 안에서 함수가 처리하는 실패와 재시도만 설명함. F19 fail 이후 UI가 시작하는 회귀 재작성은 아래 **7. F19 fail 회귀 재작성·재검증** 절에서 설명함.

| 함수 | 작성 단계 내부 처리 |
|---|---|
| F16 본문 | 한 번 생성함. 빈 응답·빈 객체·제목만 있는 응답·잘린 응답은 성공으로 저장하지 않음. 작성 단계 내부 재시도는 없음. |
| F17 표 | 검증이 실행되는 경로에서는 F19 fail이면 같은 입력으로 최대 한 번 더 호출함. 로컬 결정론적 변환이므로 결과를 새로 추론하지 않으며, 이전 F19 issue도 전달하지 않음. 두 번째 시도도 fail이면 fallback 설명문을 만들고 `tableFallbackUsed`, `fallbackReason`을 기록하며 `tables`는 비움. `strategy_writing`처럼 F19를 실행하지 않는 범위에서는 한 번 호출함. |
| F18 이미지 | `USER_FLOW`, `SERVICE_ARCHITECTURE`를 각각 한 번 생성하고 로컬에서 SVG로 렌더링함. 한 작성 단계 안에서의 추가 재시도는 없음. |

F17의 fallback은 표 구조를 설명문으로 보존하는 내부 복구이며, F19 fail을 통과로 바꾸지는 않음. F19 이후 선택·연관 항목의 재작성은 별도 통합 회귀 경로임.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">3.4.2 F16~F18 결과 구조와 생성 산출물 보존</h3>

F16~F18의 생성 출력과 선택된 근거를 항목별로 보존하고, `full` 실행에서는 6단계 F19 검증에 같은 `source_data`를 전달함. F19의 `validation`, `evaluation`, `attempts`는 검증 종료 후 6.7에서 같은 항목 결과에 추가함. `strategy_writing`은 F19 검증 없이 작성 결과만 저장하고 `validation.status`를 `not_run`으로 표시함.



| 함수 | 항목 결과에 저장하는 내용 | 근거 추적 |
|---|---|---|
| F16 본문 | `generatedText`, `facts`, `status`, `issues`, `needsUserConfirmation`, `sourceRefs`와 모델 호출 정보 | 선택된 `sourceKeys`, 반환된 `facts`·`sourceRefs`, F19 검증 입력인 `validationSource`를 항목 결과에 저장 |
| F17 표 | 원본 기반 `tables`의 `columns`, `rows`, `rules`와 로컬 생성한 `generatedText` | 표 입력 행과 `sourceKeys`, F19의 `validationSource`를 항목 결과에 저장. 출처는 섹션 단위로 추적하며 개별 셀마다 별도 sourceRef를 붙이지는 않음 |
| F18 이미지 | `imageSpecs`의 USER_FLOW·SERVICE_ARCHITECTURE 명세와 렌더링된 `images` 경로 | 선택된 `sourceKeys`와 F19의 `validationSource`를 항목 결과에 저장하고, 명세와 SVG 파일 경로를 연결 |

항목 결과에는 공통으로 `sectionId`, `sourceKeys`, `functionOutput`, `validationSource`를 보존함. `validation`, `evaluation`, `attempts`는 F19가 실행된 뒤 같은 항목 결과에 추가됨.

```text
section result
  ├─ sectionId / sourceKeys
  ├─ generatedText / tables / images
  ├─ functionOutput (F16 facts·sourceRefs, F18 imageSpecs 등)
  ├─ validationSource (작성에 사용한 source_data, F19 입력)
  └─ validation / evaluation / attempts (6.7에서 F19 이후 추가)
```

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">3.4.3 작성 데이터 계보: sourceKeys 선별·작성·검증 전달</h3>

`sourceKeys`가 작성에 사용할 근거를 고르고, 생성 결과와 사용한 근거를 각각 저장함. F19는 저장된 결과와 같은 근거를 받아 검증함.

```text
sourceKeys로 근거 선택
  → F16/F17/F18 결과 생성
  → 결과(functionOutput)와 근거(validationSource) 저장
  → 같은 근거(validationSource)로 F19 검증
```

F17 표는 back 원본 표를 우선 사용하고, F18은 이미지 명세와 렌더링된 SVG를 함께 보존함.


<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">4. 작성 항목 연결 (section_mapping.json + execution_contract.json)</h2>

두 파일의 역할은 다름. [`section_mapping.json`](../res/back_input/section_mapping.json)은 문서 유형별 섹션 제목, back 입력 `inputPaths`, back 결과 `writeTarget`을 정의함.

[`execution_contract.json`](../runtime/execution_contract.json)은 같은 `sectionId`에 실제 사용할 `functionId`(F16/F17/F18), `sourceKeys`, 규칙, `enabled` 여부를 정의함.

`writeTarget`은 F16/F17/F18 호출을 켜고 끄는 스위치가 아니며, 실행 여부는 계약의 `functionId`와 `enabled`로 결정함. `section_mapping.json` 자체에는 `functionId`·`sourceKeys`·재작성 연관 목록이 없음.

```json
// section_mapping.json: back 입력과 쓰기 대상
"2.1.2": {
  "title": "개요 요약",
  "inputPaths": ["tableData.itemSummary"],
  "writeTarget": "generatedText"
}
```

```json
// execution_contract.json: 실행 함수와 canonical 입력
{
  "sectionId": "2.1.2",
  "functionId": "F16",
  "sourceKeys": ["item_spec", "market_analysis", "development_plan"],
  "enabled": true
}
```

`impact_plan()`은 계약의 `sourceKeys`에서 최상위 canonical root를 비교해 하나라도 공유하는 섹션을 재작성 연관 항목으로 계산함. 아래 표는 section mapping의 sectionId/제목과 실행 계약의 함수/sourceKeys를 합쳐 유형별 관계를 요약한 것임. 한 섹션이 여러 sourceKey를 가지면 해당 그룹들의 합집합이 연관 항목이며, 이는 재작성 시 다시 검토할 섹션을 뜻함.

유형별 총 섹션 수와 F16/F17/F18별 개수는 현재 `execution_contract.json`에서 `enabled: true`인 항목을 집계한 값임. 같은 유형의 `section_mapping.json` 섹션 수와도 일치함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">5. 문서 유형별 작성 규칙 (writing_rules.json)</h2>

[`writing_rules.json`](../res/prompts/writing_rules.json)의 공통 규칙을 먼저 적용하고, `documentTypes`에서 `kind`에 맞는 규칙을 추가 적용함. 요청된 항목만 작성하고 근거 없는 사실은 확인 필요로 표시하며, 실적·계획·제안을 구분함.

| 규칙 범위 | 적용 기준 |
|---|---|
| 공통 | 요청 항목만 작성, 근거 없는 사실 확인 필요 표시, 실적·계획·제안 구분, 공문서형 문체와 개인정보 제한 |
| `general` | 불릿 중심, 정량 지표·측정 환경 제시, 시장·기술·사업화 구분 |
| `pre_startup` | MVP·고객검증·실증 중심, 미확정 금액·기간·인원 표시, 해당 유형 이미지 항목 적용 |
| `early_startup` | 실행 증거와 확장 계획 구분, 사업비·성능·일정 구체화, 해당 유형 이미지 항목 적용 |

이 규칙은 작성 오류를 줄이기 위한 내부 운영 기준이며 공고 원문을 그대로 옮긴 내용은 아님.

유형별 Markdown 템플릿([`general.md`](../res/prompts/templates/general.md), [`pre_startup.md`](../res/prompts/templates/pre_startup.md), [`early_startup.md`](../res/prompts/templates/early_startup.md))은 개발 검토용 상세 문서이며 런타임이 직접 읽지는 않음.

변경 제안은 템플릿에 기록해 검토·합의한 뒤 `writing_rules.json`에 반영함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">5.1 항목별 F16/F17/F18 작성 및 작성 단계 재시도</h3>

`pipeline.py`는 선택된 문서 유형의 실행 계약에서 활성화된 항목을 순회함. 각 `section_spec.sourceKeys`로 `canonical`의 필요한 값만 골라 `source_data`를 만들고, 원본 사실·전략 근거·공고 기준을 함께 보존함. 여기에 공통·유형별 `writing_rules.json`과 항목별 `_writing_criteria`를 적용한 뒤 `functionId`에 따라 F16 본문, F17 표, F18 이미지 명세 생성을 분기함. 항목별 title·rules·sourceKeys 구성은 **3.4.1**, 입력과 결과의 보존 구조는 **3.4.2·3.4.3**에 설명함.

| 함수 | 실행 입력과 처리 | 작성 단계 재시도 |
|---|---|---|
| F16 `generate_section` | `section_spec`, 선별된 `source_data`, 문서 유형·항목 기준·검증 피드백을 담은 `writing_rules`를 모델에 전달 | 한 번의 작성 pass에서 1회 호출. 실패 응답을 이 단계에서 자동 재호출하지 않음 |
| F17 `generate_table` | 원본 `tableData`를 우선 사용하고, 해당 일부 항목에만 canonical 일정·예산 행을 보조 입력으로 사용. Python이 `columns`, `rows`, `rules`로 표와 `generatedText`를 구성 | `full` 실행에서 첫 결과가 F19 `fail`이면 최대 1회 더 로컬 생성. 재시도 후 실패하면 `tableFallbackUsed`와 `fallbackReason`을 저장하고 문자열 설명으로 대체함. `strategy_writing`에서는 F19가 실행되지 않으므로 추가 시도하지 않음 |
| F18 `generate_image_spec` | `item`, `architecture`, `flow_type`를 모델에 전달해 `USER_FLOW`와 `SERVICE_ARCHITECTURE` 명세를 각각 생성하고, SVG 변환·저장은 로컬 렌더러가 수행 | 한 작성 pass에서 명세별 1회 호출. F19 fail 이후 다시 작성하는 회귀 재시도는 7단계에서 처리함 |

`full` 실행은 작성 결과를 정규화한 뒤 같은 `source_data`와 함께 즉시 F19에 전달함. 작성 및 F19 결과는 항목별 `attempts`에 기록하고, 회귀 재작성의 자동·수동 선택과 최대 반복 횟수는 작성 단계 내부 재시도와 별개로 7단계에서 처리함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">6. F19 검증·결과 저장·상태 분기</h2>

`full` 실행에서 F19는 먼저 Python으로 본문 구조, 원본 사실·근거, 일정·예산 같은 제약을 확인함. 순서는 다음과 같음.

```text
Python 기본 검사
  ├─ 문제 발견 → issues 기록, fail 처리, 의미 검증은 생략
  └─ 통과 → 규정·공고 기준을 포함한 의미 검증
               → 결과 조정 및 점수 계산
               → pass / warning / fail 저장
```

실행 범위에 따라 검증 대상은 달라짐.

- **`full`**: 방금 생성한 항목을 작성 직후 검증함.
- **`strategy_writing`**: F19를 건너뛰고 `validation.status`를 `not_run`으로 저장함.
- **기존 결과 검증 요청**: 선택한 항목 또는 요청한 범위의 저장 결과만 다시 검증함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.1 저비용 구조·계약 검사 (F19-1 · Python)</h3>

`agent_validation_1/validation_1.py`는 LLM에 의미 검증을 요청하기 전에 작성 결과가 기본 형식과 원본 제약을 지키는지 Python으로 빠르게 확인함.

- **본문**: `generatedText`가 있고, 항목별 `exactItems`·`minItems`·`maxLines`·`maxSentences`·`requiredFields`·`stages` 조건을 지키는지 확인함.
- **표·이미지**: 필요한 표와 필수 컬럼, 이미지 노드 수(3~6개)와 이미지 유형 명세를 확인함.
- **원본 제약**: 해당 항목의 기능 목록, 마감일, 정부지원사업비 상한을 확인함.

위반을 `issues`로 남기고 `fail`로 처리하는 흐름을 간단히 나타내면 다음과 같음.

```python
if not text.strip():
    issues.append("필수 generatedText 없음")
if missing_columns:
    issues.append("필수 표 컬럼 누락")
if deadline_exceeded:
    issues.append("마감일 초과")
if issues:
    return {"status": "fail", "semanticCalled": False, ...}
```

**현재 검사 범위의 제한**: 표가 존재하는지와 필수 컬럼이 있는지는 검사하지만, 표에 행이 하나 이상 있는지 또는 `requiredRows`를 충족하는지는 Python에서 검사하지 않음. `validation_rubric.json`에는 `requiredRows` 기준이 있어 문서 기준과 실제 코드 사이에 차이가 있음.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.2 원본 사실·근거·상태값 대조 (F19-2 · Python)</h3>

**F19가 대조하는 입력**

- `originalFacts`: 정규화된 back 입력의 원본 사실
- `strategyProvenance`: F01~F15 결과와 그 상위 근거
- `source_data`: 항목의 `sourceKeys`로 골라 작성 단계에 전달한 자료. `evidence`와 규정 근거도 포함하며, 의미 검증에도 전달함.

F16 결과에 `facts`와 `sourceRefs`가 있으면 원본 사실·상위 근거와 대조함. F17 표와 F18 이미지 명세도 결과와 함께 저장된 같은 항목의 `validationSource`를 연결해 검증함.

**상태값별 처리**

| 상태 | 검증에서의 의미 |
|---|---|
| `provided` | back 입력 등 원본에서 받은 확정값. 원본과 다르면 `fail` |
| `confirmed` | 확인된 확정값. 원본과 다르면 `fail` |
| `proposed` | 사업계획을 위해 새로 제안한 값. 완료 사실로 쓰지 않고 계획·목표·제안임을 표시하면 `warning` |
| `needs_confirmation` | 사용자 확인이 필요한 값. `warning`과 `needsUserConfirmation` 대상으로 기록 |

제안값에는 이를 뒷받침하는 사용자 원본 근거가 없을 수 있음. F19는 본문에서 계획·목표·제안·확인 필요로 표현했는지 확인함. 이런 표시 없이 확정 사실로 단정하면 오류로 처리함.

`sourceRefs`가 입력 근거나 적용 규정 출처에 연결되지 않으면 내용과 상태에 따라 출처 오류 또는 확인 경고를 기록함. 같은 원인의 메시지는 중복 제거함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.3 규정·공고 자료와 유형별 기준 (F19-3 · LLM 호출)</h3>

저비용 검사를 통과한 항목은 다음 기준으로 의미 검증함.

**검증 프롬프트에 포함되는 내용**

- 공통 검토 기준: persona, checklist, style guide, 유형별 템플릿, `validation_rubric.json`
- 자료 발췌: 문서 유형에 맞는 `validation_sources.json`과 규정 자료
- 현재 항목: `section_spec`, 생성 본문·근거·fact·이미지 정보, `source_data`, 항목별 기준

**참고 자료를 사용하는 방식**

| 자료 | 검증에서의 역할 |
|---|---|
| 공고·관리기준 원문 | 자격, 협약, 사업비 등 명시 조건 위반 확인 |
| 신청 양식 | 필수 항목과 표 구조 확인 |
| FAQ·과거 자료 | 기준 해석을 돕는 참고. 현재 확정 사실의 직접 근거로 사용하지 않음 |

항목별 기준과 관련 발췌는 `criteria_registry.json` 설정에 따라 선택함.

**문서 유형에 따른 검증 차이**

- **예비·초기창업**: 연결된 해당 연도 공고와 관리기준을 기준으로 지원 자격, 협약기간, 정부지원사업비 상한·집행 비목·합계, 개발·PoC·매출·사업화 단계, 필수 표·항목을 확인함.
- **일반 사업계획서**: rubric에 정부 규정 원문이 연결되어 있지 않으므로 back 입력과 실행 계약을 기준으로 구조·사실·근거 연결을 확인함. 예비·초기창업의 자격·사업비 규정은 적용하지 않음.

**공통 제약 확인**

- `_strategy_limits.deadline`은 협약기간 일정에 적용하며, 협약 이후 로드맵과 구분함.
- `supportLimit`은 정부지원사업비 상한임.
- `featureList`는 해당 개발 항목에 기능이 보존됐는지 확인함. 기능명은 괄호·구분자·공백·등록된 동의어 차이를 정규화해 비교함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.4 의미 검증 결과 재분류·조정 (F19-4 · Python, 추가 LLM 호출 없음)</h3>

저비용 검사를 통과해 의미 검증 결과가 나온 뒤에는 판정을 다음 순서로 정리함.

1. **경고와 실패 구분**: 계획·제안·확인 필요, 출처 보완, 시험조건 미확정, 표현 구체화는 상황에 따라 `warning`으로 분류함. 필수 구조나 확정 사실·마감일·예산 상한 위반은 `fail`로 남김. `semantic_review.py`가 문구를 규칙으로 분류하며, 추가 LLM은 호출하지 않음.

   `HARD_MARKERS`는 필수 누락·원본 불일치처럼 실패로 남길 문구를 찾는 키워드 목록이고, `ADVISORY_MARKERS`는 근거 보완·제안처럼 경고로 볼 문구를 찾는 목록임.

   ```python
   if any(marker in text for marker in HARD_MARKERS):
       target = hard
   elif any(marker in text for marker in ADVISORY_MARKERS):
       target = warnings
   else:
       target = hard
   ```

2. **실제 결과 구조와 대조**: `_reconcile_validation()`이 모델 판정과 저장된 표·이미지를 비교함. 표의 필수 열이나 두 이미지 명세가 이미 있는데 누락으로 지적한 경우, 그리고 F17 일정·예산 표에 모든 `featureList`를 반복하지 않았다는 지적은 오류 목록에서 제거함.

   ```python
   if spec.get('functionId') == 'F17':
       issues = [i for i in issues if 'featureList 누락' not in i]
   ```

3. **협약 일정 확인**: 초기창업 `3.5.2` 표의 종료월이 원본 협약 일정의 마지막 달을 넘으면 `fail`로 추가함. 협약 이후 로드맵은 협약기간 일정과 따로 구분함.

   ```python
   if source_end and generated_end and generated_end > source_end:
       validation.setdefault('issues', []).append(
           f'개발계획 표 종료월 {generated_end}이 원본 협약 일정 종료월 {source_end} 이후임')
       validation['status'] = 'fail'
   ```

위 코드는 각 처리의 핵심 부분만 발췌한 것임. 실제 코드는 표·이미지 누락 문구, 검증 상태와 원본 일정 행을 더 확인함.

이 조정이 끝난 결과를 최종 `pass`·`warning`·`fail` 판정과 다음 처리 단계에 사용함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.5 점수 계산과 공식 배점 구분 (F19-5 · Python)</h3>

`scoring.py`는 [evaluation_rubric.json](../../agent_validation_1/res/prompts/evaluation_rubric.json)을 읽어 항목별 점수를 계산함. 이 파일은 모델 프롬프트가 아니라 **점수 계산 기준표**임.

기준표에는 점수 범위(0~100), 평가 항목과 유형별 가중치, 기본 감점, 공식 배점 참고 정보가 들어 있음. 다만 `fail` 40점은 `scoring.py`에 고정값으로 적용되고, `issue`·`warning`·사용자 확인 필요 감점은 rubric의 `penalties` 값을 읽어 적용함. rubric의 `fail: 40`은 코드의 고정값과 같은 숫자로 선언되어 있음.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">6.5.1 rubric 평가 항목과 유형별 가중치</h4>

| 평가 항목 | 보는 내용 | 일반 | 예비·초기 |
|---|---|---:|---:|
| 구조 (`structure`) | 필수 본문·항목 수·표 열·이미지 구조 | 25% | 20% |
| 작성 요건 (`requirement`) | 항목 목적과 공고 기준 충족 | 25% | 30% |
| 근거 (`provenance`) | 출처·원본 사실·상태값 추적 가능성 | 20% | 20% |
| 일관성 (`coherence`) | 전략·원본·연관 항목 간 내용 일치 | 20% | 15% |
| 명확성 (`clarity`) | 사실·제안 구분과 문장 가독성 | 10% | 15% |

가중치는 공식 배점이나 심사 통계에서 가져온 값이 아니라, 문서 유형별 평가 초점을 반영한 내부 배분임.

- **일반 유형**은 특정 공고의 평가 기준이 고정되어 있지 않아 구조와 작성 요건을 각각 25%로 균형 있게 두고, 전략·원본 간 일관성은 20%로 반영함.
- **예비·초기 유형**은 공고 평가영역과 필수 작성 기준을 맞추는 일을 우선해 작성 요건을 30%로 높임. 근거 추적은 사실 신뢰성에 중요하므로 모든 유형에서 20%로 유지함.
- **구조·일관성·명확성**은 유형별 우선순위에 따라 나머지 비중을 배분함. 필수 구조 위반은 점수 비중과 별도로 F19에서 `fail` 처리될 수 있어 구조 점수만으로 심각도를 표현하지 않음.

따라서 이 비율은 설계 의도를 설명하는 내부 정책이며, 실제 심사 점수에 맞춰 최적화된 수치는 아님.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">6.5.2 점수 계산 순서와 기본 감점</h4>

점수 계산은 다음 순서로 진행함.

1. 각 평가 구성요소를 100점에서 시작함.
2. F19 판정과 항목별 감점을 해당 구성요소에서 차감함. 기본 감점은 `fail` 40점, `issue` 12점, `warning` 3점, 사용자 확인 필요 2점임.
3. 구성요소 점수에 문서 유형별 가중치를 적용해 합산함.
4. 최종 `score`, 구성요소별 `components`, 감점 사유와 값인 `deductions`를 결과에 저장함.

기본 감점이 어느 항목에서 차감되고 전체 점수에 어느 정도 영향을 주는지는 다음과 같음.

| 판정 | 차감 대상 | 전체 점수에 미치는 대략적 영향 | 해석 |
|---|---|---:|---|
| `fail` 40점 | `structure`; 최종 점수는 최대 59점 | 가중치 기준 약 8~10점 차감 후 59점 상한 적용 | 필수 위반이 높은 점수로 통과처럼 보이지 않게 함 |
| `issue` 12점 | `requirement` 또는 `provenance` | 약 2.4~3.6점 | 필수요건·근거 결함을 보완 경고보다 크게 반영 |
| `warning` 3점 | `provenance` 또는 `clarity` | 약 0.3~0.6점 | 개선 신호를 남기되 제안·표현 보완의 영향은 작게 제한 |
| 사용자 확인 필요 2점 | `clarity` | 약 0.2~0.3점 | 사실 오류와 구분해 가볍게 반영하고 사용자 결정 과제를 표시 |

감점은 구성요소 점수에 적용한 뒤 유형별 가중치로 합산함. 동일 문구는 중복 차감하지 않으며, 감점 후 구성요소 점수는 0점 아래로 내려가지 않음.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">6.5.3 감점 간격을 둔 이유</h4>

- **`fail` 40점**: F20 조립을 막는 판정이므로 큰 감점을 주고, 별도 59점 상한으로 다른 구성요소의 높은 점수가 실패를 가리지 않게 함.
- **`issue` 12점**: 필수요건·근거의 실질적 결함을 가벼운 보완 의견보다 뚜렷하게 반영하도록 `warning` 3점의 네 배로 설정함.
- **`warning` 3점**: 결과 저장은 가능하지만 보완이 필요한 상태이므로 점수에 작은 개선 신호를 남김.
- **사용자 확인 필요 2점**: 사용자 판단이 필요한 상황 자체를 확정 사실 오류처럼 취급하지 않도록 가장 낮은 감점으로 둠.

40·12·3·2는 위 심각도 순서를 표현하기 위해 정한 내부 정책값임. 실제 심사 표본으로 검증하거나 통계적으로 최적화한 숫자는 아님.

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">6.5.4 공고 평가영역과 내부 점수의 관계</h4>

**먼저 볼 점수의 의미**<br>

F19의 `evaluation.score`와 `estimatedPoints`는 이 시스템의 내부 품질 점수임. 평가위원의 실제 점수나 선정 가능성을 예측하는 공식 점수가 아님. 2026년 공고가 평가영역을 공개하더라도 사업계획서 항목별 세부 배점은 제공하지 않아, 현재 가중치와 감점값을 공식 배점에서 산출할 수 없음.

**공고에서 확인되는 공식 평가 기준**<br>

2026년 모집공고에서 확인되는 평가영역과 공개되지 않은 점수 정보는 다음과 같음.

| 유형 | 공고에서 명시한 기준 | 공고에 제시되지 않은 점수 정보 |
|---|---|---|
| 예비창업패키지 | 문제인식·실현가능성·성장전략·팀(기업) 구성. 중기부 제2026-207호(2026-03-24) | 평가영역별·사업계획서 항목별 점수 배분 |
| 초기창업패키지 일반형 | 문제인식·실현가능성·성장전략·팀(기업) 구성. 중기부 제2026-38호(2026-01-23) | 평가영역별·사업계획서 항목별 점수 배분 |
| 일반 사업계획서 | 이 실행 유형에 연결된 특정 정부 공고 기준 없음 | 적용할 공고별 공식 배점 기준 |

원문: [예비창업패키지 2차 수정 공고(중소벤처기업부)](https://www.mss.go.kr/site/smba/ex/bbs/View.do?bcIdx=1066579&cbIdx=310), [초기창업패키지 일반형 공고(중소벤처기업부)](https://www.mss.go.kr/site/smba/ex/bbs/View.do?bcIdx=1065015&cbIdx=310&parentSeq=1065015)

공고의 평가영역은 예비·초기 유형의 검토 초점을 정하는 참고 기준으로 사용함. 다만 평가영역별·사업계획서 항목별 점수가 공개되지 않아 내부 가중치와 감점값의 직접적인 수치 근거로 삼을 수 없음. 일반 사업계획서는 연결된 특정 정부 공고가 없어 내부 계약을 기준으로 평가함.

**실제 심사 결과에 맞춰 보정하려면**<br>

감점값을 통계적으로 보정하려면 동일한 사업계획서 표본과 평가위원의 항목별 점수처럼 서로 대응되는 기준 데이터가 필요함. 현재 `result.json`에는 이 시스템의 점수만 저장되므로 실제 심사 점수와의 보정에는 사용할 수 없음. 따라서 현 가중치·감점값은 오류의 상대적 심각도를 구분하기 위한 내부 정책이며, 실제 심사 점수를 예측하도록 검증된 수치는 아님.

자동 채점 연구의 가중치나 계수를 현재 rubric에 그대로 옮길 수도 없음. ETS 연구는 사람 평가 점수와 연계된 자료에서 평가 특징의 가중치를 조정하는 보정 방법을 다루며, 현재 감점값의 직접 근거가 아니라 향후 실제 사업계획서·전문가 평가 자료로 점검할 필요성을 뒷받침함 ([ETS Research Report RR-17-04](https://www.ets.org/research/policy_research_reports/publications/report/2017/jxhq.html)).

<br><br><h4 style="color:#334155;background:#f8fafc;border-left:3px solid #94a3b8;padding:6px 10px;border-radius:4px">6.5.5 별도 제약 감점과 70점 척도 구분</h4>

**일정·지원금 제약 감점**<br>

- 개발 일정이 `_strategy_limits.deadline`을 넘으면 `requirement`에서 40점을 차감함.
- 정부지원사업비가 `supportLimit`을 넘으면 `requirement`에서 50점을 차감함.

두 감점은 사업계획의 실행 가능성과 예산 준수에 직접 영향을 주므로 `requirement`에서 별도로 차감함.

- **일정 초과 40점**: 협약기간 안에 계획을 이행하기 어려운 중대한 요건 위반으로 반영함.
- **지원금 상한 초과 50점**: 신청 가능한 사업비 한도를 벗어나므로 일정 초과보다 더 큰 감점을 둠.

두 수치는 공식 배점이나 실제 심사자료에서 산출된 값이 아니라 내부 심각도 정책값임.

같은 위반이 검증 `fail` 또는 `issue`에도 기록되면 감점이 누적될 수 있음. 이 경우 `deductions`에서 사유별 차감 내역을 확인해야 하며, 중복 적용은 같은 결함의 점수 영향을 키울 수 있음.

**공식 배점과 내부 점수**<br>

`officialExpectedScoring`은 공고 평가영역과 필수조건을 참고 기준으로 제공하지만, 공식 항목별 배점표는 아님.

따라서 `officialPoints`는 `null`로 저장함. 계산된 값은 `estimatedPoints`의 **내부 예상 배점**으로 표시하고, `isOfficial`은 `false`로 기록함.

신뢰도는 예비·초기 유형 `medium`, 일반 유형 `low`임. 이 구분도 공식 점수의 신뢰도가 아니라 참고할 공고 기준의 유무를 나타냄.

`documentLayerScore`는 F19 내부 품질 점수를 70점 만점으로 환산한 값임. `fail`의 59점 상한도 내부 상태 표현 규칙이며, 정부기관의 공식 심사 점수나 합격선을 재현하지 않음.

**서로 다른 70점 척도**<br>

| 값 | 의미 | 적용 위치 |
|---|---|---|
| `documentLayerScore`의 70점 만점 | F19의 내부 품질 점수(0~100)를 70점 척도로 환산한 값 | `scoring.py` 결과에 기록 |
| 오케스트레이션 문서층 70점 + 산출물층 30점 | 문서층과 프로토타입·산출물층을 합산하는 별도 평가 체계의 배점 상한 | `agent-orchestration` 설정과 점수 보고서에서 계산 |

현재 `agent-orchestration`은 `agent_validation_1`의 rubric이나 `evaluationSummary`를 코드에서 직접 불러오지 않으며, 점수 계산 경로도 별도로 관리함. 따라서 두 곳의 70점은 서로 독립된 값임.

두 점수 체계를 연결할 때는 `internalQualityScore`(0~100)를 문서층 상한 70에 맞춰 환산하거나, 이미 환산된 `documentLayerScore`(0~70)를 사용해야 함. 두 값을 연달아 환산하지 않도록 입력 계약을 정해야 함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.6 최종 상태와 회귀 재작성 연결 (F19-6 · Python)</h3>

| 상태 | 판정 기준 | 다음 처리 |
|---|---|---|
| `pass` | 필수 구조와 원본·근거 대조를 통과하고, 확정 사실·규정상 차단 조건의 위반이 없음 | 결과 저장. 모든 대상이 `pass` 또는 `warning`이면 F20 조립 가능 |
| `warning` | 제안값, 사용자 확인 필요, 근거 보완, 시험조건 미확정 등 개선할 내용이 남음 | 결과를 저장하고 자동 회귀 재작성 대상에서는 제외함. warning만으로 F20 조립을 막지 않음 |
| `fail` | 필수 본문·표·이미지 구조 누락, 확정값과 원본 불일치, 마감일·지원금 상한 위반, 적용 항목의 필수 기능 누락, 근거 없는 값을 확정 사실로 표현 | F20 초기 조립을 보류함. UI 통합 회귀 재작성 대상으로 전달하고, 재작성 후 F19를 다시 실행함 |

자동 회귀는 전체 실행이 끝난 뒤 `fail` 항목만 대상으로 시작하며 `warning`은 자동 재작성하지 않음. 재검증 결과 모든 대상이 `pass` 또는 `warning`이면 F20이 최종 조립을 수행하고, `fail`이 하나라도 남으면 조립을 보류함.

<br><br><h3 style="color:#1e40af;background:#f8fafc;border-left:4px solid #60a5fa;padding:8px 12px;border-radius:5px">6.7 판정 저장과 후속 경로 분기 (Python)</h3>

F19 종료 후 `validation`, `evaluation`, `attempts`를 항목별 결과 객체에 저장함. 전체 대상이 `pass` 또는 `warning`이면 8단계 F20 조립으로 진행함. `fail`이 하나라도 있으면 F20을 보류하고 7단계 회귀 재작성 경로로 전달함. 이 절은 판정 결과를 저장하고 다음 경로를 고르는 단계이며, 재작성 절차 자체는 7단계에서 설명함. 재검증에서도 같은 판정·보존 흐름을 반복함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">7. F19 fail 회귀 재작성·재검증</h2>

통합 회귀 재작성은 전체 파이프라인을 처음부터 다시 실행하지 않고, F19 `fail` 이후 UI가 시작하는 별도 복구 경로임. `run_pipeline`은 전체 실행 중 F19 결과를 저장하고 fail 여부를 반환하며, 자동 재시도는 전체 실행이 끝난 뒤 UI 컨트롤러가 시작함. 결과를 다시 불러오거나 새로고침하는 것만으로는 자동 실행되지 않음.

입력 근거의 보존은 재작성 API 경로에 따라 차이가 있음. 진행 중 화면의 완료 작업을 대상으로 하는 `/api/retry`는 작업 메모리에 보관한 실제 입력 JSON을 전달함. 반면 자동 회귀와 최신 결과 기반 `/api/retry-latest`는 현재 구현에서 실행 당시 입력을 저장 결과로부터 복원하지 않고, 유형별 예시 JSON을 다시 읽어 `retry_sections`에 전달함. 따라서 사용자 정의 입력으로 만든 결과를 재작성할 때 원본 fact 및 F17 표 입력이 예시 JSON 기준으로 구성될 수 있어, 현재는 원본과 근거 보존이 보장되지 않는 구현상 제한임.

1. 자동 모드는 `fail` 항목만 재작성하며 `warning`은 자동 대상에서 제외함. 항목별 최대 재시도 횟수는 UI 설정을 따르고 기본값은 1회임. 자동 모드가 꺼져 있으면 사용자가 회귀 카드에서 실패 항목 하나 또는 실패 항목 전체를 선택함.
2. `impact_plan(kind, sectionId)`가 실행 계약의 `sourceKeys`에서 최상위 canonical root를 비교해 선택 항목과 연관 항목을 계산함.
3. `retry_sections`가 이전 실행 trace에서 F01~F15의 `canonical` 결과와 저장된 조사 근거를 복원함. F01~F15 전략 함수는 다시 호출하지 않음.
4. 선택 항목과 연관 항목의 `functionId`에 따라 F16 본문, F17 표, F18 이미지 명세를 다시 생성하고 각 결과를 F19로 재검증함. 한 번의 재작성 요청 안에서 F16/F18은 한 번, F17은 최대 두 번 시도함.
5. 재검증된 모든 대상이 `pass` 또는 `warning`이면 F20 조립을 수행함. `fail`이 남으면 조립을 보류하고, 선택 항목·지시문·영향 범위·검증 결과·자동/수동 모드를 `retryHistory`에 기록함.

기존 결과 전체 검증과 Fail-only 검증은 작성 회귀와 별개임. 이 경로는 본문·표·이미지를 다시 생성하지 않고 F19만 실행하며, 대상 전체에 `fail`이 없을 때 F20 조립을 진행함. 이미지 전용 재작성은 별도의 요청 경로에서 F18 명세와 SVG만 갱신함.

<br><br><br><h2 style="color:#1d4ed8;background:#eff6ff;border-left:5px solid #2563eb;padding:10px 14px;border-radius:6px">8. F20 조립 및 결과 저장</h2>

F20은 검증 대상 항목의 F19 결과가 모두 `pass` 또는 `warning`인 경우에만 항목별 본문·표·이미지를 `document` 데이터 구조로 조립함. `warning`은 보완사항으로 결과에 보존하지만 조립을 막지 않음. 하나라도 `fail`이 남아 있으면 F20 조립을 실행하지 않고 검증 상태와 실패 항목을 결과에 남김.

현재 F20은 `sections`, `tables`, `images`를 묶은 결과 객체를 반환함. HWP·DOCX 파일을 생성하거나 페이지 수·문서 레이아웃을 검증하지 않으며, 반환값의 `pageCountVerified`는 `false`임.

실행 결과는 `agent_strategy/res/back_output/runs/<실행폴더>/result.json`에 저장함. 각 항목은 최상위 `results` 배열 안에 들어가며, 같은 항목 객체에 F19 `validation`과 내부 평가기 `evaluation`을 함께 기록함. 예시는 다음 구조의 일부임.

```json
{
  "results": [
    {
      "sectionId": "3.4.1",
      "validation": {
        "status": "pass",
        "issues": [],
        "warnings": [],
        "needsUserConfirmation": [],
        "agent": "검증 1"
      },
      "evaluation": {
        "score": 95.7,
        "components": {},
        "deductions": [],
        "basis": [],
        "officialPoints": null,
        "estimatedPoints": {
          "score": 95.7,
          "isOfficial": false,
          "label": "내부 예상 배점"
        }
      }
    }
  ],
  "evaluationSummary": {}
}
```

`result.json`에는 생성 결과, 검증·규정 근거, 평가 점수, 모델·토큰 사용량, 실행 시간, 재작성 이력도 저장함. 토큰 사용량은 모델 응답의 `usage`를 호출별 trace와 전체 `usage` 합계에 보존함. 입력 크기는 `inputChars`와 `contextMetrics`의 문자 수로 비교함. 현재 프로세스 RAM 사용량이나 최대 메모리(RSS/peak memory)는 측정·기록하지 않음. 별도의 `validation.json`에는 항목별 상태·issues·warnings·`attempts`를 요약함. `retryHistory`에는 재작성 요청별 모드, 선택 항목, 요청사항, 영향 범위, 결과 상태와 시각을 기록함. 생성 재시도 횟수와 각 시도의 검증 결과는 항목별 `attempts`에 저장하며, `retryHistory`에 시도 횟수를 별도 필드로 기록하지는 않음.

<br><br><br><h2 style="color:#0f766e;background:#f0fdfa;border-left:5px solid #14b8a6;padding:10px 14px;border-radius:6px">부록 A. API 연동 명세 (백엔드·협업자 공유용)</h2>

이 절은 UI↔로컬 테스트 서버, 서버↔OpenAI, 자료 수집기의 API 주소를 구분해 기록함. 로컬 API 기본 주소는 `http://127.0.0.1:8765`이며 서버 실행 시 `--port`로 변경할 수 있음. 문서 유형별 차이는 endpoint가 아니라 `documentType` 및 요청 payload임.

<br><br><h3 style="color:#0f766e;background:#f0fdfa;border-left:4px solid #14b8a6;padding:8px 12px;border-radius:5px">A.1 UI ↔ 로컬 테스트 서버</h3>

| Method | URL | 용도·주요 요청/응답 |
|---|---|---|
| GET | `/api/status` | OpenAI 키 설정 여부와 `models.list()` 연결 확인 결과, 함수별 모델 설정 반환 |
| GET | `/api/examples` | `general`, `pre_startup`, `early_startup` 예시 입력 JSON 반환 |

`/api/run`은 요청 본문에 `input` 객체가 있어야 함. 서버는 `tableData`가 비어 있지 않거나 `2_지금_입력받는값.POST_projects_body.description`이 있으면 입력을 유효한 것으로 보고, 둘 다 없으면 선택된 유형의 예시 back JSON으로 대체 실행함. 빈 객체는 예시 입력으로 대체되므로, 성공 응답만으로 사용자가 입력한 데이터가 실행됐다고 판단할 수 없음.

<br><br><h3 style="color:#0f766e;background:#f0fdfa;border-left:4px solid #14b8a6;padding:8px 12px;border-radius:5px">A.2 UI 버튼과 실행 요청 대응</h3>

| 현재 탭 작성만 재실행 (F16~F18) | `/api/latest-results` 조회 후 각 작성 항목별 `POST /api/retry-latest`, `mode: "writing_only"` | **버튼 이름·완료 안내와 실제 서버 범위가 일치하지 않음.** 서버는 `mode`를 이력에만 기록하고 `retry_sections`를 호출하므로 선택·연관 항목을 재작성한 뒤 F19 검증과 조건부 F20 조립까지 수행함. UI는 각 F16~F18 항목을 순회 호출하므로 여러 회귀 작업이 연속 실행될 수 있음. 기존 결과가 `strategy_writing` 범위여서 나머지 항목의 validation이 `not_run`이면 F20이 이를 거부할 수 있으므로, 먼저 기존 결과 전체 검증·조립을 완료해야 함 |
| 현재 탭 전체 재실행 (F01~F18·F19 검증·F20 조립) | `POST /api/run`, `executionScope: "full"` | F19는 항목별 작성 직후 실행. fail이 있으면 최초 F20은 보류하고, 자동 회귀 설정에 따라 완료 후 재시도할 수 있음 |
| 실행 중단 | `POST /api/cancel`, `{ "jobId": "..." }` | 실행 중인 작업을 중단 요청하고 완료된 결과를 부분 결과로 저장 |
| 현재 탭 기존 결과 검증·조립만 (F19·F20) | `POST /api/validate-all-latest`, `{ "documentType": "..." }` | 기존 작성 결과를 다시 생성하지 않고 F19 검증. 구조 검사에 문제가 없으면 의미 검증을 수행할 수 있고, Fail이 없을 때 F20 조립 |
| 현재 탭 기존 결과 검증·조립만 (Fail 항목만 검증) | 같은 endpoint에 `skipPassed: true` | Pass·Warning을 건너뛰고 Fail·미검증 항목을 F19 검증. 구조 검사 통과 시 의미 검증을 수행할 수 있으며 Fail이 없을 때 F20 조립 |
| 재작성 함수 목록·연관 항목 보기 | 초기 목록은 `/api/section-mapping`, 선택 항목 영향 범위는 `GET /api/impact?documentType={kind}&sectionId={id}` | 전략 함수 전체 재실행이 아니라 선택한 작성 항목의 F16/F17/F18 종류와 `impact_plan`의 영향 항목을 보여줌 |
| 선택 항목 검증만 실행 | `POST /api/validate-latest`, `{ "documentType": "...", "sectionId": "..." }` | 선택 항목과 연관 항목만 기존 결과로 F19 검증. 구조 검사 통과 시 의미 검증을 수행할 수 있으며, 재작성과 F20 조립은 하지 않음. 전체 상태는 결과 전체에 fail이 남아 있는지로 계산하므로, 다른 항목이 not_run이어도 fail이 없으면 `validation1_passed`로 표시될 수 있음 |

| 평가 요약·항목별 점수 보기 | `/api/latest-results` 응답의 `evaluationSummary`와 각 `results[].evaluation`을 화면에 표시 | 내부 품질 점수·문서층 점수·내부 예상 배점 및 감점 사유. 공식 배점은 제공하지 않음(`officialPoints: null`) |

| 점수 개선 제안 | 현재 화면의 `evaluationSummary`, 항목별 `deductions`·`warnings`로 UI가 실패 또는 최저 점수 항목을 골라 제안 문구 구성 | 제안 수를 정하는 설정·API는 없고 화면상 현재 대상 하나를 제시함. 수락하면 요청 지시문을 만들고 선택 항목 재작성 API를 실행 |
| 개선 제안 수락 이력 | 브라우저 `localStorage` (`sbrain-evaluation-suggestions-{documentType}`) | 유형별 최근 50건을 브라우저에 저장. 서버 `result.json`이나 API의 `retryHistory`에는 제안 수락 이력 자체가 저장되지 않음 |
| 자동·수동 회귀 재작성 이력 | 성공적으로 반환된 재작성 결과에 서버가 `result.json`의 `retryHistory`를 누적 | 모드, 선택 항목, 지시문, 영향 범위, 상태·시각을 실행 결과에 보존. 예외·취소로 재작성 함수가 반환하지 못하면 새 이력 이벤트가 남지 않을 수 있음. 자동 재시도 최대 횟수 설정은 UI `localStorage`에 보관하며 기본 1회, 1~3회 선택 가능 |

선택·전체 검증 API는 F19 Python 진입점에서 저비용 구조·원본 검사를 먼저 수행하고, 이 단계에서 issues가 생기면 의미 검증 호출을 생략함. 저비용 검사 통과 시 의미 검증 LLM을 호출할 수 있음. 다만 기존 pass/fail 결과의 contentHash와 policyVersion이 현재 값과 일치하면 서버가 검증 결과를 재사용할 수 있으며, Fail-only 모드는 기존 Pass·Warning을 건너뜀. 따라서 검증 요청마다 모델 호출이 반드시 발생하지는 않음.

| 서비스 | Method | 전체 URL | 호출 위치·용도 |
|---|---|---|---|
| OpenAI 연결 확인 | GET | `https://api.openai.com/v1/models` | `/api/status`가 Python SDK `OpenAI().models.list()`로 키·접속 상태 확인 |
| OpenAI 함수 실행 | POST | `https://api.openai.com/v1/chat/completions` | `llm_runtime.request_json`이 JSON 응답 형식으로 모델 호출. F01~F16(단 F17 제외), F18, F19가 사용하며 F01은 검색 결과가 있을 때만 호출 |
| KIET 검색 | GET | `https://www.kiet.re.kr/searchAll` | 시장 크롤러가 연구·동향 검색 결과 조회 |
| KIET 상세 요약 | POST | `https://www.kiet.re.kr/getSearchEtt` | 시장 크롤러가 검색 결과의 SummaryPop 본문 요청 |

OpenAI의 함수별 URL이 각각 다른 것은 아님. LLM을 사용하는 함수는 같은 Chat Completions endpoint를 사용하고, 모델 ID는 `execution_contract.json`의 함수 설정 및 `STRATEGY_MODEL_{FID}` 환경변수 override로 결정함.

F17 표 생성과 F20 문서 조립은 현재 Python 로컬 처리라 OpenAI endpoint를 호출하지 않음. KIET 외 MSS 공고/PDF와 Figma 페이지는 자료 출처이며 별도 API endpoint로 호출하지 않음.

<br><br><br><h2 style="color:#0f766e;background:#f0fdfa;border-left:5px solid #14b8a6;padding:10px 14px;border-radius:6px">부록 B. 구현 실패 사례·개선 계획·성과 측정</h2>

이 부록은 구현·테스트 중 확인된 대표 실패와 적용한 개선을 기록하고, 저장된 실행 결과를 바탕으로 task 및 사업계획서 항목별 품질·성능을 측정하기 위한 계획을 정리함. 확인되지 않은 과거 수치나 실패 원인은 임의로 채우지 않으며, 실제 실행 기록과 회귀 테스트 결과로 갱신함.

<br><br><h3 style="color:#0f766e;background:#f0fdfa;border-left:4px solid #14b8a6;padding:8px 12px;border-radius:5px">B.1 확인된 실패 사례와 적용한 개선</h3>

| 실패·오탐 유형 | 적용한 개선 | 현재 확인 방법 |
|---|---|---|
| F16 응답이 비거나 JSON이 잘리거나 유효한 `generatedText`를 반환하지 않음 | 빈 응답·잘린 응답을 성공으로 저장하지 않고 오류와 부분 결과를 보존함 | F16 실행 결과 계약 검사와 오류 경로 회귀 테스트 |

| 실행·재작성 도중 오류나 취소가 발생해 완료 결과 확인이 어려움 | 실행별 폴더에 부분 결과·trace·검증 요약을 보존하고 기존 결과를 덮어쓰지 않음 | `result.json`, `validation.json`, `result.html`, `manifest.json` 및 생성 SVG 확인 |

위 항목은 README의 오류 처리·변경 이력과 현재 코드에 기재된 구현 사항을 요약한 것임. 각 개선의 실제 효과를 주장하려면 재현 입력, 변경 전후 결과, 테스트 또는 측정값을 함께 기록해야 함.

<br><br><h3 style="color:#0f766e;background:#f0fdfa;border-left:4px solid #14b8a6;padding:8px 12px;border-radius:5px">B.2 개선 계획과 검증 방법</h3>

1. **실패 사례 고정**: 재현 가능한 입력과 오류 조건을 익명화해 테스트 fixture로 보존하고, 기대 상태·오류 분류·보존되어야 할 결과를 명시함.
2. **개선 전 기준선 확보**: 기존 실행 폴더와 회귀 테스트에서 확인 가능한 값만 집계함. 과거 결과에 없는 값은 추정하지 않고 `unavailable`로 표시함.
3. **계측 공백 보완**: 함수 호출이 실패한 경우에도 `functionId`, `sectionId`, 시작·종료 시각, 오류 분류를 trace에 남기고, OpenAI 요청 시도와 기본·대체 모델 결과를 구분해 기록함. 항목별 경과시간도 항목 결과에 보존함.
4. **기록 저장·집계**: 실행 폴더에 task·항목별 측정 요약을 저장하고, 정기 집계는 실행 ID를 기준으로 기존 결과를 읽어 별도 보고서로 생성함. 같은 `runId`를 중복 집계하지 않음.
5. **개선 효과 검증**: 동일한 회귀 fixture에서 변경 전후 실패율·최종 검증 상태·처리시간을 비교하고, 테스트 통과 여부와 측정 기간·표본 수를 보고서에 함께 적음. 실제 OpenAI 비용이 드는 실행은 로컬 mock 회귀 테스트와 구분함.

계획의 완료 상태와 기준선·개선 후 측정치는 실행 기록이 확보된 뒤 갱신함. 성공률이 올랐다는 결론은 동일 조건의 비교 데이터가 있을 때만 기록함.

<br><br><h3 style="color:#0f766e;background:#f0fdfa;border-left:4px solid #14b8a6;padding:8px 12px;border-radius:5px">B.3 task·항목별 성과 측정 기록</h3>

현재 `result.json`에는 **반환에 성공한 함수 호출**의 `functionId`, `durationMs`, 모델, 토큰 사용량이 `trace`에 저장되고, 항목별 최종 검증 상태와 시도 내역이 `results[].validation`·`results[].attempts`에 저장됨. 하지만 예외가 난 함수 호출은 trace에 추가되기 전에 빠져나가므로 함수별 전체 시도 수와 성공률을 완전하게 계산할 수 없음. trace 호출에는 `sectionId`가 없어 항목별 함수 시간도 정확히 묶을 수 없으며, OpenAI API의 실패 시도 수·오류율 역시 현재 결과만으로는 계산할 수 없음. 저장된 모든 실행 결과에서 이 지표를 소급 산출할 수 있다고 보지 않음.

계측 보완 후에는 다음 지표를 실행별 측정 기록으로 저장하고, 여러 실행을 합친 성공률은 문서 유형·task·항목별로 집계함.

| 측정 단위 | 기록값·산출 기준 | 해석 |
|---|---|---|
| task/function (`F01`~`F20`) | `functionId`, `sectionId`(작성 항목 호출이면), 시도 수, 성공·실패 수, `durationMs`, 모델, 입력·출력 토큰, 오류 분류 | task 성공률은 성공 반환 호출 ÷ 전체 시작 호출. F17·F20 등 Python 로컬 처리도 task 시간·오류를 기록하되 API 지표에서는 제외 |
| 사업계획서 항목 (`sectionId`) | 생성 함수, 첫 시도 결과, 최종 `validation.status`, 전체 시도 수, 재작성 횟수, 항목 경과시간 | 최종 수용률은 최종 검증이 완료된 항목 중 `pass` 또는 `warning`인 비율. 최초 시도 통과율과 재작성 후 최종 수용률을 따로 표시 |
| OpenAI API 요청 | 모델 요청 시도 수, 성공·실패, 기본/대체 모델, 지연시간, 오류 유형 | API 오류율은 실패한 요청 시도 ÷ 전체 요청 시도. 기본 모델 실패 후 대체 모델이 성공한 경우 기본 모델 실패와 최종 task 성공을 각각 기록 |
| 실행·문서 유형 | `runId`, 기간, `documentType`, `executionScope`, 결과 상태, 표본 수 | 기간별·유형별 집계의 범위를 밝히고 실행 ID 중복 계산을 방지 |

보고서에는 비율만 제시하지 않고 분자·분모, 표본 수, 측정 기간, 미분류·누락 수를 함께 기록함. `warning`은 파이프라인상 저장 가능한 상태이므로 최종 수용률에 포함하되 `pass`와 분리해 건수·비율도 표시함. 취소·중단으로 검증이 끝나지 않은 항목은 성공/실패 분모에 섞지 않고 별도 상태로 집계함.

측정 기록은 실행별 `measurement.json`(task·항목 상세)으로 보존하고, 누적 집계는 실행 폴더의 원본 결과를 덮어쓰지 않는 별도 보고서로 저장하는 것을 목표로 함. 이 파일과 실패 호출 계측은 **현재 구현되어 있지 않으며**, B.2 계획에 따라 추가한 뒤 실제 측정값을 기입해야 함.
