# 검증 1 공통 체크리스트

- 필수 본문·항목 수·표 컬럼·이미지 nodes가 계약을 충족하는가
- provided·confirmed 값이 원본과 일치하는가
- proposed·needs_confirmation 값이 계획·제안 문장으로 표시되었는가
- 마감일 이후 일정이나 지원금 상한 초과가 없는가
- featureList 기능이 핵심 토큰 기준으로 보존되었는가
- 근거·출처·시험조건 부족은 warning으로 기록했는가

## 공고·관리기준 검증
- `validation_sources.json`의 현재 문서 유형 자료가 실제로 로드되었는가
- 공고 원문 조건은 파일 경로 또는 JSON 경로를 `sourceRefs`에 남겼는가
- 지원 대상·협약기간·지원금 상한·집행 가능 비목을 유형별로 대조했는가
- 원문에 없는 조건을 공고의 필수 조건처럼 단정하지 않았는가
- 예비창업은 문제 가설·MVP·실증을, 초기창업은 개발·PoC·매출·사업화를 구분했는가

## 근거와 상태 검증
- 확정 문장에는 `provided` 또는 `confirmed` 상태와 추적 가능한 근거가 있는가
- 계획·목표·추정 문장에는 `proposed` 상태가 있는가
- 사용자 확인이 필요한 값은 `needsUserConfirmation`에 중복 없이 기록했는가
- 표현 차이는 정규화하고 근거 부족은 `warning`으로 남겼는가

## 판정 기록
- `issues`는 재작성 또는 계약 수정이 필요한 오류만 기록한다.
- `warnings`는 제안값·근거 보완·시험 조건 미확정 사항을 기록한다.
- 메시지에는 가능하면 항목 위치, 원인, 필요한 조치를 포함한다.

## 자료 품질과 충돌 처리
- 등록된 규정 원문이 없거나 읽히지 않으면 공고 조건을 추정하지 않고 `needsUserConfirmation`으로 남겼는가
- 여러 원문에서 기간·금액·비목이 다르면 최신 문서와 현재 공고를 우선하고 충돌을 경고했는가
- 원문 발행연도와 현재 공고 유형이 맞지 않으면 과거 자료를 현재 조건으로 확정하지 않았는가
- 원문 발췌에 없는 내용을 원문 근거처럼 인용하지 않았는가
- `sourceRefs`가 실제 등록된 파일·JSON 경로를 가리키며 생성 본문과 근거를 혼동하지 않았는가
- 공고·관리기준을 사용했다면 해당 내부 파일 경로를 F19 `sourceRefs`에 포함했는가
- 규정 자료의 연도·사업 유형이 현재 검증 대상과 다르면 조건을 확정하지 않고 경고했는가
