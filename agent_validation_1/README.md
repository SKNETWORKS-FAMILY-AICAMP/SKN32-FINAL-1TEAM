# Validation 1

`validation_1.py`가 F19를 수행한다. 필수 텍스트·항목 개수·줄 수·필수 필드·표 컬럼(표가 요청된 경우)·이미지 노드·원본 facts·출처 ID·원 단위 금액을 Python으로 검사한다. 구조 오류가 없을 때만 GPT-5.6 Terra로 원본 충실성·근거 관련성·논리·항목 요구조건을 검증한다.

실패 항목은 결과를 보존한 뒤 UI의 통합 회귀 재작성 정책에서 F16/F18 재작성과 재검증을 수행한다. 여전히 실패하면 초안과 오류를 보존하되 F20 최종 조립을 실행하지 않는다. 표 생성 제외 항목은 검증 대상에서도 제외한다. 분량·페이지 수는 실제 문서 렌더링 전 확정하지 않는다.

## 실행 위치와 연결 구조

검증 1의 판정 코드는 이 폴더의 `validation_1.py`에 별도 Agent 영역으로 관리한다. 전략·작성 Agent 코드에 검증 규칙을 복사해 넣지 않는다.

현재 개발·테스트 단계에서는 `agent_strategy/runtime/pipeline.py`가 F16/F17/F18 작성 결과를 만든 뒤 `agent_validation_1.validation_1.validate_section()`을 호출하는 방식으로 연결되어 있다. UI 요청과 실행 상태 관리는 `agent_strategy/app/testing/test_server.py`가 담당한다.

```text
agent_strategy/app/testing/test_server.py
        ↓
agent_strategy/runtime/pipeline.py
        ├─ 전략·작성 결과 생성
        └─ agent_validation_1.validation_1 호출
                ↓
        검증 1 결과(validation/issues/warnings)
```

따라서 현재 검증 1은 독립된 코드 영역을 유지하면서 전략·작성 테스트 파이프라인에 연결되어 실행된다. 추후 전체 `agent-orchestration` Supervisor가 연결되면 동일한 검증 1 인터페이스를 통해 조율 Agent의 실행 흐름에 편입한다.

검증 결과는 항목별 `results[].validation`, 전체 `validation1`, 별도 `validation_results` 배열에 기록하며, 실행 폴더에는 `validation.json`을 별도로 저장한다.

전략·작성 Agent와의 입력·출력 계약과 회귀 재작성 흐름은 [`agent_strategy/res/reference/agent_validation_integration.md`](../agent_strategy/res/reference/agent_validation_integration.md)에 정의한다. 검증 1은 이 계약에 따라 `section_spec`, `content`, `source_data`를 받고 `status`, `issues`, `warnings`, `needsUserConfirmation`, `contentHash`, `policyVersion`을 반환한다.

예비·초기창업패키지의 관리기준과 질의응답 원문은 `res/prompts/reference/validation_sources.json`에 경로를 등록한다. F19 프롬프트는 문서 유형에 맞는 원문 JSON을 제한된 길이로 읽어 공고의 지원 대상·협약기간·사업비·성과 기준을 참고한다. 원문 전체를 결과에 복사하지 않고 출처 경로와 필요한 발췌만 전달한다.

## 평가 점수 서비스

`scoring.py`는 검증 1의 판정과 분리된 결정론적 평가기다. `res/prompts/evaluation_rubric.json`의 유형별 가중치와 내부 규정 근거 경로를 사용해 각 항목에 0~100점을 계산한다. 구조·작성 목적·근거 추적·내용 일관성·표현 명확성을 평가하며, `issues`, `warnings`, `needsUserConfirmation`의 원인과 감점 내역을 함께 반환한다.

점수는 임베딩 유사도나 임의의 정부 평가점수가 아니다. 규정에 없는 기준을 만들어내지 않고, 검증 결과와 관찰 가능한 계약만 계산한다. 공식 배점표가 공개되지 않는 상황을 전제로 `estimatedPoints`를 작성 전략용 예상값으로 제공한다. 공식 배점과 혼동하지 않도록 별도 필드와 안내문을 유지한다.

## 판정·평가 기준의 분리

- `validation_1.py`는 필수 구조, 원본과 다른 확정 사실, 마감일·지원금 한도, 필수 기능·표·이미지 누락을 `fail`로 판정한다.
- 계획·제안·확인 필요 문구, 시험 조건 미확정, 직접 근거가 약한 출처는 `warning` 또는 `needsUserConfirmation`으로 분류한다.
- `semantic_review.py`는 의미 검증 결과를 재검토할 때 표현 차이만으로 실패시키지 않고, 구조 검증 결과와 충돌할 때만 재판정을 요청한다.
- 기능명·기술명·단계명·날짜·금액은 정규화하여 괄호, 구분자, 공백, 표기 형식 차이로 인한 오탐을 줄인다.
- 성능지표·서비스 개요에는 `featureList` 전체 반복 검사를 적용하지 않고, 실제 기능·개발방법·개발계획 항목에만 기능 불변식을 적용한다.

## 공고 유형별 기준과 한도

일반 사업계획서는 사용자 입력과 실행 계약을 중심으로 평가한다. 예비·초기창업패키지는 `res/reference/regulations`의 원문 JSON을 `validation_sources.json`으로 연결해 지원 대상, 협약 기간, 사업비 집행, 성과·실증 기준을 참고한다. 규정 원문에 없는 조건을 임의로 만들지 않으며, 자료가 없으면 확인 필요 경고로 남긴다.

전략·작성 Agent가 back JSON에 넣은 `_strategy_limits.deadline`, `_strategy_limits.supportLimit`, `_strategy_limits.featureList`는 검증 1이 동일하게 받아 일정 초과, 지원금 합계 초과, 확정 기능 목록 변경을 판정한다. 날짜·금액 표기는 월·숫자로 정규화하고, 제안값은 계획 수립을 위한 값으로 표시된 경우 실패가 아닌 경고로 처리한다.

## 결과 저장과 회귀 흐름

각 실행 항목에는 `validation`, `evaluation`, `contentHash`, `policyVersion`이 저장된다. 실행 폴더의 `validation.json`에는 검증 결과만 별도로 보존하고, `result.json`에는 전체 결과와 `evaluationSummary`를 함께 저장한다. 동일 본문과 동일 정책 버전이면 기존 판정을 재사용해 불필요한 LLM 호출을 줄인다.

검증 실패 회귀 재작성은 실패 항목과 검증 사유를 전략·작성 Agent에 전달하고, 동일 Canonical Data를 사용하는 연관 항목만 재생성한 뒤 F19를 다시 호출한다. 자동 회귀는 항목별 최대 횟수에 도달하면 중지하며, 각 시도와 중지 사유를 history에 기록한다. API·크레딧·토큰 오류가 발생해도 이미 완료된 항목과 trace를 `error_partial` 결과로 보존한다.

## 현재 검증 범위와 한계

회귀 테스트 19개와 Python 문법 검사를 통과했다. 점수는 정부기관 공식 배점이 아니라 내부 계약·규정 근거 기반 품질 지표이며, 공식 배점표가 공개되지 않아도 공고 평가영역과 필수 기준을 이용해 `estimatedPoints`를 산출한다. 규정 자료가 갱신되면 원문 JSON, `validation_sources.json`, rubric 정책 버전을 함께 갱신한다.

## 초기창업 전용 기준 보완

초기창업 템플릿에 개발계획·단계별 사업비·전체 일정·USERFLOW/서비스 구조도 검증 조건을 추가했다. 2025년 초기창업패키지 세부관리기준은 `validation_sources.json`으로 연결되어 있으며, `_strategy_limits`의 deadline·supportLimit·featureList와 함께 사용한다. 제안 KPI·시험조건·수량·단가 미확정은 warning으로 남기고, 확정 사실 불일치·한도 초과·마감일 초과·필수 계약 누락만 fail로 판정한다.

### 초기창업 매핑 기반 검증 보완

초기창업 항목별 매핑이 단순 표시용 경로에 그치지 않도록 3.3.6 이미지 유형·nodes 범위, 3.5.2 개발계획 표 컬럼·서술문 최소 분량, 3.5.3·3.5.4 단계 선택·미구분 중복 금지, 3.6.2 개발·성장전략 일정 병합과 마감일 검증 메타데이터를 연결했다. 검증 1은 이 메타데이터와 원본 JSON을 함께 참고해 초기창업 누락을 판정한다.

### 초기창업 규정 자료 확장

초기창업 검증 자료에 2026년 초기창업패키지 일반형 모집공고문과 사업계획서 양식 JSON을 추가로 보관하고 `validation_sources.json`에 연결했다. 세부관리기준은 집행·협약·성과 기준에, 모집공고는 지원 대상·기간·지원 규모에, 양식 JSON은 필수 섹션·표 구조 확인에 사용한다. 세 자료가 서로 다른 연도나 목적을 갖는 경우 원문 경로와 문서 유형을 결과에 남기고, 충돌하는 조건은 임의로 합치지 않고 확인 필요로 분류한다.


### 초기창업 표 계약 재점검

초기창업 3.5.2·3.5.3·3.5.4·3.6.2의 매핑 대상을 실제 표 생성 계약과 일치시켰다. 검증 1은 해당 항목에서 필수 컬럼·행을 `tables` 구조로 확인하며, 본문에 JSON 배열만 있는 경우 표 계약 누락으로 판정한다.

### 45. 초기창업 F18·표·featureList 판정 보완

초기창업 F18 검증은 USERFLOW와 SERVICE_ARCHITECTURE 두 이미지 명세를 모두 대상으로 하며, 각 명세의 `nodes`와 `flowType`을 확인한다. 작성 단계에서 두 이미지가 저장되도록 전략 파이프라인이 보장하고, 한 이미지의 검증 상태 때문에 다른 이미지가 누락되지 않도록 한다.

단계가 미지정인 사업비는 1·2단계 표에 중복 배분하지 않는다. `unassignedOriginalRows`가 보존된 빈 단계 표는 원본 입력 부족에 따른 확인 필요 warning으로 분류하며, 임의 금액을 생성하지 않는다. 3.6.2는 개발·검증·출시 일정과 성장전략 일정을 합친 결과를 검증한다.

`featureList`는 개별 일정표의 모든 기능 반복을 요구하지 않는다. 실제 기능·핵심기술·개발방법 항목에서만 핵심 토큰 일치 여부를 확인하며, 일정·예산 표의 기능 미반복은 그 자체로 fail 처리하지 않는다.
### 초기창업 사업비 검증 항목 정정 (2026-10-02)

초기창업패키지는 단일 사업비 집행계획 표를 사용하므로 검증 1은 초기창업 `3.5.3`의 원본 행·산출근거·지원금 합계·상한을 확인한다. 예비창업 전용 1·2단계 항목인 `3.5.4`는 초기창업 계약과 검증 대상에서 제거했다. 단계 미지정 원본을 별도 단계에 임의 배분하지 않는다.
## 초기창업 검증 보완 이력

- 초기창업 원문 양식에 맞춰 단일 사업비 표 `3.5.3`만 검증하고, 예비창업 전용 `3.5.4`는 초기창업 검증 대상에서 제외했다.
- `3.5.3`은 원본 사업비 행, 산출근거, 정부지원사업비 합계와 `_strategy_limits.supportLimit`을 확인한다.
- `3.5.2`와 `3.6.2`는 일정표의 필수 컬럼·행·기간을 확인하며 `featureList` 전체 반복 여부를 실패 조건으로 사용하지 않는다.
- `3.3.6`은 USER_FLOW와 SERVICE_ARCHITECTURE 두 이미지 명세와 각 명세의 3~6개 nodes를 확인한다.
- F19 LLM 응답이 실제 저장 구조와 불일치할 때 구조 검증 결과를 우선한다. 실제 표가 저장됐으면 표 누락 진단을 제거하고, 두 이미지 명세가 저장됐으면 이미지 구조 누락 진단을 제거한다.
- 제안값·확인 필요·시험조건 미확정은 warning으로 남기며, 필수 구조·마감일 초과·예산 상한 초과만 fail로 유지한다.

초기창업 계약에 `3.5.4`가 다시 들어오는 것을 방지하는 회귀 테스트를 포함해 총 18개 테스트가 통과했다.
### 검증 정책 버전 및 구조 재검토 보완 (2026-10-02)

- 검증 결과 재사용 조건은 `contentHash`와 `policyVersion`의 일치 여부로 관리한다. 판정 규칙을 수정하면 `validation_rubric.json` 버전을 올려 기존 결과를 반드시 재검증한다.
- 실제 표의 필수 컬럼·행이 존재하는데 F19가 `필수 표 없음`, `content.tables 없음`, `표 형식 텍스트만`으로 판정하는 경우 구조 검증을 기준으로 오탐을 제거한다.
- 실제 `imageSpecs`에 USER_FLOW·SERVICE_ARCHITECTURE가 모두 존재하면 서비스 구조도 누락을 실패로 처리하지 않는다.
- 이 보정은 전체 실행뿐 아니라 기존 결과 검증·조립 API와 선택 항목 검증에도 적용된다.
- 현재 정책 버전은 `2026-10-02.12`이다. 제안값·근거 보완·시험조건 미확정은 warning으로 남기고, 실제 구조·한도·마감일 위반만 fail로 유지한다.
### 예비창업 제안 금액 판정 보완 (2026-10-02)

예비창업 `2.1.4`에서 사업비 상한 조정을 위해 본문에 제안한 금액이 원본 확정 금액이 아니라 `facts.status: proposed`로 기록된 경우를 구분한다. `budget` 또는 지원금 관련 제안 fact와 연결된 금액은 원본에 없더라도 fail이 아닌 warning으로 분류한다. 확정 fact와 불일치하는 금액은 기존처럼 fail로 유지한다. 정책 버전은 `2026-10-02.13`으로 갱신했다.
### 회귀 재작성 이력

검증 실패 회귀 재작성은 수동·자동·이미지 전용 모드를 구분해 `retryHistory`에 누적한다. 자동 회귀는 항목별 최대 횟수 설정을 넘으면 중지하며, 각 시도와 결과 상태를 전략/작성 Agent 결과 JSON에 남긴다.
전체 실행은 항목을 한 번만 생성한다. `warning`은 합격 상태로 저장하고 추가 생성 호출을 하지 않는다. `fail` 항목의 재작성은 UI 통합 회귀 재작성 정책에서만 수행한다.
### 검증 상태별 재작성 기준 보완 (2026-10-02)

검증 결과는 `pass`, `warning`, `fail` 세 상태로 관리한다. `warning`은 합격으로 저장하고, `fail`만 UI의 통합 회귀 재작성 정책 대상으로 삼는다.

예비창업 본문에서 `facts.status`가 `proposed` 또는 `needs_confirmation`인 지원금·예산 금액은 확정 사실 불일치가 아니라 사업계획 제안값으로 warning 처리한다. 확정 fact와 원본 금액이 다르면 기존처럼 fail로 판정한다.
### T-C3 지시문과 검증 회귀 연동 (2026-10-06)

검증 1은 Orchestrator가 전달한 `instruction`과 `rework_input`의 타입을 변경하지 않는다. 재작성·재수행 지시문에는 작업 틀·작업 안내·참조 자료가 포함될 수 있으며, 검증 실패 원문은 지시문 끝의 정해진 블록으로 전달된다. 검증 1은 이 원문을 근거로 판정하되 작업 틀의 고정 규칙을 우선한다.
전략/작성 Agent와 검증 1을 호출하는 개발자는 [`agent_strategy/res/reference/agent_api_contract.md`](../agent_strategy/res/reference/agent_api_contract.md)의 공통 함수·결과·재작성 계약을 따른다.


### 공식 기준과 내부 점수의 구분

`res/reference/regulations`의 공고·관리기준은 지원 자격, 협약기간, 사업비 비율·집행 기준, 성과·최종평가 판정 기준을 규정 적합성 점검에 사용한다. 다만 현재 제공된 원문에는 사업계획서 작성 항목별 공식 배점표가 완결된 형태로 포함되어 있지 않으므로 `scoring.py`의 점수는 공식 배점이 아닌 내부 품질 평가 점수로 산출한다.

각 평가 결과에는 `officialExpected.status=criteria_only`, `officialExpected.isOfficial=false`, 적용된 규정 경로(`basis`)와 반영 기준(`criteriaApplied`)을 함께 기록한다. 향후 기관의 공식 배점표가 공개되지 않는다는 전제에서 현재는 공고 평가영역과 필수 기준으로 `estimatedPoints`를 산출한다. 공식 배점표가 향후 제공되더라도 현재 예상값과 별도 필드로 관리한다.

### 규정 원문에서 확인된 공식 기준의 범위

규정 파일을 재검토한 결과, 초기창업패키지 2026년 모집공고에는 문제인식·실현가능성·성장전략·팀(기업) 구성이라는 평가영역과 평가 단계별 60점 미만 선정 제외 기준이 명시되어 있다. 이 기준은 `officialExpected.explicitCriteria.early_startup`에 원문 경로와 함께 기록한다. 영역별 배점 비율은 공고에 없으므로 임의로 분배하지 않는다.

예비창업패키지 자료는 요건검토·서류평가·인큐베이팅·발표평가·최종선정 절차와 사업비 심의·관리 기준을 제공하지만, 항목별 배점과 합격선은 별도 평가계획으로 정하도록 되어 있다. 따라서 `pre_startup`은 정량 배점 없이 절차·자격·사업비 기준만 적용한다. 일반 사업계획서는 공식 규정 원문이 없으므로 내부 계약만 사용한다.

이 구분으로 공식 원문에 있는 60점 제외 기준은 누락하지 않으면서도, 제공되지 않은 영역별 점수를 추정해 공식 배점처럼 표시하지 않는다.

`officialExpected.sourceEvidence`에는 각 `basis` 파일에서 평가 기준 키워드 주변을 추출한 짧은 원문 발췌가 저장된다. 따라서 결과 JSON에서 파일 경로만 확인하는 것이 아니라 해당 기준을 뒷받침하는 원문 문장도 함께 확인할 수 있다. 원문 전체를 결과에 복사하지 않고 파일별·키워드별 발췌와 읽기 가능 여부만 기록한다.

현재 규정 자료의 남은 한계도 결과에 명시한다. 예비창업 2026년 모집공고 원문은 `test/docextract/results/예비창업패키지/.../2026 예비창업패키지 예비창업자 모집 수정 공고(2차)(2026-207호).pdf.json`으로 연결해 지원 대상·절차·작성 기준에 사용한다. 아직 제공되지 않은 것은 선정평가 세부 배점표뿐이며, 이는 `officialExpected.explicitCriteria.pre_startup.missingOfficialSources`에 기록한다.

초기창업의 공고상 60점 미만 기준은 전체 서류·발표 평가 단계에 적용되는 기준이다. 화면에 표시되는 항목별 내부 점수에 60점을 직접 합격선으로 적용하지 않도록 `officialExpected.explicitCriteria.early_startup.applicationScope=stage_level_metadata_only`로 범위를 구분한다. 예비창업은 절차·자격 기준만, 일반은 내부 계약만 적용한다.


### 내부 예상 배점

공식 배점표가 없는 유형도 작성 전략에 참고할 수 있도록 항목별 `estimatedPoints`를 별도로 저장한다. 이 값은 현재 내부 품질 점수와 동일한 산출 결과를 공고 평가영역·필수 조건 관점의 예상값으로 표시한 것이며, `isOfficial=false`와 신뢰도(`low`·`medium`)를 함께 기록한다. `officialPoints`와 절대 혼합하지 않는다.

## 최근 평가 기준 보완 이력

### 2026년 공고 원문 연결

예비창업 2026년 모집 수정 공고와 초기창업 2026년 최종 모집 공고문을 `test/docextract/results`의 추출 JSON으로 연결했다. 검증 1은 기존 관리기준뿐 아니라 최신 공고의 지원 대상, 신청 자격, 평가 절차, 협약기간, 지원 규모, 사업계획서 작성 요구사항을 함께 참조한다.

### 규정 근거의 결과 저장

항목별 평가 결과의 `officialExpected`에는 다음 정보가 저장된다.

- `basis`: 적용한 규정·공고 파일 경로
- `criteriaApplied`: 평가에 반영한 규정 기준
- `sourceEvidence`: 기준 키워드 주변의 실제 원문 발췌
- `officialPoints`: 공식 배점표가 없으면 `null`
- `explicitCriteria`: 유형별 평가 절차, 명시된 기준, 적용 범위

원문 전체를 결과에 복사하지 않고 파일별 관련 문장만 발췌해 근거 추적성과 결과 크기를 함께 관리한다.

### 공식 점수와 내부 예상값 분리

공식 배점표가 없는 상태에서 정부기관 점수를 임의로 만들지 않도록 점수 영역을 분리했다.

- `officialPoints`: 기관의 공식 배점표가 있을 때만 사용
- `internalQualityScore`: 구조·작성 목적·근거·일관성·명확성을 계산한 내부 점수
- `estimatedPoints`: 공고 평가영역과 필수 조건을 내부 rubric에 반영한 작성 전략용 예상값

`estimatedPoints`는 `isOfficial=false`와 `confidence`를 함께 저장한다. 예비·초기창업은 공고의 평가영역이 있어 `medium`, 일반 사업계획서는 공식 기준이 없어 `low`로 기록한다. UI에는 이를 “내부 품질 점수”와 “내부 예상 배점”으로 구분해 표시하며, 정부기관 공식 점수라는 표현을 사용하지 않는다.

초기창업 공고의 평가 단계별 60점 미만 제외 기준은 전체 평가 단계의 메타데이터로만 기록한다. 항목별 내부 점수에 60점을 직접 합격선으로 적용하지 않는다. 예비창업은 2026년 세부 배점표가 제공되지 않았으므로 절차·자격·사업비 기준만 반영한다.




평가 구조 회귀 테스트를 추가해 `officialPoints`가 `null`로 유지되고 `estimatedPoints`가 `isOfficial=false`로 분리되는지, 공고 원문 `sourceEvidence`가 결과에 포함되는지 자동 확인한다. 현재 관련 테스트를 포함해 총 19개가 통과했다.

### 공고 원문 보관 위치 통일

예비창업 2026년 모집 수정 공고와 초기창업 2026년 최종 모집 공고문은 원본 `test/docextract/results`를 직접 참조하지 않고 다음 검증 Agent 내부 경로에 복사해 보관한다.

- `res/reference/regulations/2026_early_pre_startup_general_announcement.json`
- `res/reference/regulations/2026_early_startup_general_announcement_final.json`

`validation_sources.json`과 `evaluation_rubric.json`도 이 내부 경로를 사용하므로 검증 Agent를 별도 브랜치로 분리해도 공고 근거가 누락되지 않는다.

### 항목별 규정 레지스트리와 선택 주입 (2026-10-06)

`res/reference/regulations/criteria_registry.json`은 사업 유형과 사업계획서 항목을 규정 근거에 연결하는 단일 레지스트리입니다. 각 항목에는 `criteria`, `weights`, `sourceRefs`, `sourceMappings`(파일 경로·검색어·사용 목적)가 저장됩니다. 검증 1은 전체 규정 원문을 매 호출에 넣지 않고 현재 `documentType`·`sectionId`에 해당하는 기준만 F19 입력의 `criteria`와 `_sectionCriteria`로 전달합니다. 결과에는 적용된 기준과 출처 매핑을 남겨 재현할 수 있습니다.

레지스트리 또는 특정 매핑이 없을 때는 기존 공통 검증 계약으로 안전하게 돌아가며, 검증을 중단하거나 사실을 임의로 만들지 않습니다. 새 공고·관리기준은 `res/reference/regulations`에 원문 JSON을 추가하고 레지스트리의 `sourceMappings`에 항목별 키워드와 적용 목적을 등록한 뒤 테스트합니다.

`scoring.py`도 동일한 `criteria_registry.json`을 우선 사용하며, 기존 `section_scoring_criteria.json`은 하위 호환용 fallback으로만 읽습니다. 따라서 새 항목 기준은 레지스트리에만 추가하면 검증과 점수 산정에 함께 반영됩니다.

### 기획서 v1.10 2층 검증 정합성

검증 1은 기획서의 문서층(T-V1)에 해당하며, 사업계획서 항목 계약·원본 근거·공고 규정·일정·예산 상한을 구조 검사와 의미 검증으로 판정합니다. 산출물층 30점과 프로토타입 기능 대조는 검증 1의 책임이 아니며 `agent-orchestration`의 T-V2가 담당합니다. 따라서 검증 1의 내부 점수와 기획서의 문서층 70점 환산값을 결과에서 구분하고, 공식 심사 점수로 표시하지 않습니다.

### 항목별 규정 레지스트리

- `criteria_registry.json`에 일반·예비창업·초기창업 항목별 기준을 저장한다.

- 실패 항목은 `issues`, 개선 권고는 `warnings`, 입력 보완 대상은 `needsUserConfirmation`으로 분리한다.
- 실패 항목은 F20 조립 전에 차단하고 회귀 재작성 이력과 정책 버전을 보존한다.
- 규정 매핑 196건의 경로 존재 여부를 점검했으며 누락 경로는 0건이다.

### 규정 근거 기록 방식

규정 파일은 본문에 근거 문장을 임의로 삽입하는 방식이 아니라, 작성·검증 결과의 provenance로 기록한다. F19는 항목별 `criteria_registry.json` 기준을 읽고 `criteriaApplied`, `sourceMappings`, `sourceRefs`를 검증 결과의 `criteria`에 저장한다. 따라서 결과 JSON에서 어떤 규정 파일의 어떤 키워드·주제를 적용했는지 확인할 수 있으며, 사업계획서 본문은 자연스러운 제출 문체를 유지한다. 필요한 경우 UI나 보고서에서 해당 매핑과 발췌를 근거로 표시한다.

### 규정 근거 문자열 첨부

항목별 검증 결과의 `criteria.evidence`에 규정 파일 경로뿐 아니라 locator 키워드 주변의 짧은 근거 문자열을 함께 저장한다. 같은 evidence를 F19 의미 검증 프롬프트에도 전달하되 파일 전체를 넣지 않고 파일별 최대 2개 발췌로 제한한다. 원문을 읽지 못한 경우 `readError` 또는 `available:false`로 기록하며 검증을 중단하지 않는다.

### 규정 파일 장애 방어

레지스트리·rubric·규정 JSON이 일시적으로 없거나 형식 오류인 경우 모듈 import 단계에서 중단하지 않고 빈 기준으로 fallback한다. 해당 항목은 기존 구조 검증을 계속 수행하며, 근거를 읽지 못한 상태는 `available:false`·`readError` 또는 검증 경고로 기록한다. locator 키워드가 목록이 아닌 잘못된 형식이어도 단일 키워드로 안전하게 정규화한다.

점수산정 기준의 원천은 `criteria_registry.json`이다. 항목별 `sourceMappings`의 파일 경로와 locator 키워드는 UI의 작성 지침으로도 제공되며, F19 결과의 `criteria.evidence`에는 실제 키워드 주변 근거 문자열이 저장된다.

## 2026-10-06 규정 자료 역할 분리 및 항목별 근거 검증 보완

### 규정 자료의 증거 수준

공고·양식·질의응답·세부관리기준을 같은 수준의 사실 근거로 사용하지 않도록 `sourceRole`, `authorityLevel`, `directFactAllowed`를 도입했다. 공고는 공식 조건, 양식은 구조, 최신 관리기준은 협약·사업비·수행 조건, FAQ는 해석 보조, 과거 관리기준은 참고용으로 구분한다.

### 항목별 evidence 처리

항목별 `sourceMappings`와 `locatorKeywords`를 기준으로 원문을 검색하고 `matchedKeywords`, `relevance`, `useFor`, `rationale`, `excerpts`를 생성한다. `high`·`medium` 근거만 의미 검증 프롬프트에 전달하며 `low` 근거는 결과 JSON 추적용으로만 보존한다.

근거 연결 사유는 다음 형식으로 기록한다.

> `<파일 경로> 파일에서 <일치 키워드>로 언급되어 있어 <항목 목적>에 맞춰 작성·검증함`

일치 키워드가 없으면 직접 근거로 사용하지 않았다고 기록한다.

### F19 판정 정책

F19는 공식 조건과 양식 구조의 위반을 fail로 판단하고, FAQ·과거 자료와의 차이 또는 제안값의 구체화 부족은 warning·needsUserConfirmation으로 분류한다. 확정 사실과 제안값은 `provided`, `proposed`, `needs_confirmation` 상태로 구분한다.

검증 결과에는 `evidenceRoles`, `sourcePolicy`, `sourceRefs`, `evidence`, `matchedKeywords`, `relevance`, `rationale`를 저장한다. 이를 통해 어떤 파일의 어떤 문장을 어떤 목적으로 적용했는지 재현할 수 있다.

### 항목별 보완 사례

초기창업 인력 항목은 사업비·창업프로그램 자료가 섞이지 않도록 사업계획서 양식과 인력 관련 공고만 연결했다. 예비창업의 일반현황·아이템명·산출물·장비·협력기관 항목도 공통 검색어를 제거하고 전용 키워드로 변경했다. 문제인식·실현가능성·일정 항목은 공고와 양식 중심으로 제한했다.

### 실행 범위

F16 작성 프롬프트 변경은 선택 재작성 또는 전체 재실행이 필요하다. 기존 본문을 유지하면서 역할·근거 메타데이터만 갱신할 때는 기존 결과 검증·조립만 실행한다. 작성 호출과 검증 호출을 혼동하지 않도록 README의 실행 범위를 구분한다.

## v1.11 연동 및 판정 정책

`agent_validation_1`은 기능정의서의 T-V1 사업계획서 검증에 해당하며, 전략·작성 Agent의 F16 본문, F17 표, F18 이미지 명세를 검증한다. 프로토타입 코드 점검과 계획서 대조는 T-V2 범위다.

검증 실패 항목은 자동 회귀 재작성 기본 1회 정책의 대상이 된다. warning만 발생한 항목은 자동 재작성하지 않으며, 추가 보완은 검증 사유를 사용자 개선 제안 문자열로 제공하고 사용자가 수락할 때 실행한다.

현재 검증 점수는 내부 품질 점수이며, 기획서의 문서층 70점·산출물층 30점 및 공식·예상 배점과는 별도 필드로 분리할 예정이다.
