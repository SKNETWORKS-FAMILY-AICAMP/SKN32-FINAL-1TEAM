## 1. 연결 방식 — 직접 import 대신 HTTP API

공고팀 설명서는 Orchestrator가 공고팀 파이썬 함수를 직접 불러 쓰는 방식을 전제로 했다. 사용자와 협의해 **공고 서버의 HTTP API를 부르는 방식**으로 정했다.

| 이유 | 내용 |
|---|---|
| 무게 | 직접 import하면 웹 서버와 Orchestrator 워커(단계를 실행하는 프로세스)마다 공고팀 패키지(torch · chromadb 등)를 설치하고 약 2GB를 함께 올려야 한다(시작 약 20초, 매일 재시작). 공고 서버는 이미 웹 서버와 따로 떠 있다 |
| 규칙이 한 곳에 | 추천 순위, 자격 판정(신청자 유형 해석 · 업력 계산 · 확인 필요), 수집 상태 판단이 공고팀 한 곳에 있게 된다. 우리가 규칙을 복사하지 않으므로 추천과 판정이 서로 다른 결론을 내지 않는다 |

이에 따라 우리는 다음을 하지 않는다.

- 공고팀 코드(`search` · `shared` 등)를 import하거나 복사하지 않는다.
- 공유 DB의 공고 표(`notices` · `notice_conditions` 등)를 읽지 않는다. 공고 정보는 API로만 받는다.
- 웹 서버는 공고 서버를 부르지 않는다. **공고 서버를 부르는 곳은 Orchestrator 워커뿐**이다.

| 우리 단계 | 부르는 API | 부르는 때 |
|---|---|---|
| 공고 매칭(T-C2) | ① 수집 상태 → ② 공고 추천 | 첫 조회(사전 정보 입력 직후) 1회, 사용자가 '추가 조회'를 누르면 1회 더(`offset` 10) |
| 자격 확인(G-01) | ① 공고 상세 → ② 자격 판정 | 사용자가 후보 공고 하나를 고를 때마다. 같은 공고를 다시 골라도 매번 새로 묻는다 |

## 2. 네 API 약속

### 2.1 공통

**주소와 요청**
- 공고 서버 주소(예: `http://example.invalid:8000`)는 우리 워커 설정에 둔다. 주소 뒤에 아래 경로를 붙여 부른다.
- 요청 본문이 있으면 `Content-Type: application/json; charset=utf-8`, 응답은 `Accept: application/json`으로 받는다.
- 다른 주소로 보내는 응답(3xx)은 따라가지 않고 오류로 본다. 주소는 정확한 값을 알려 달라.
- 지금 우리 요청에는 인증 정보가 없다(5절 질문).

**응답 형식**
- 성공(2xx) 응답의 본문은 JSON(UTF-8)이어야 한다.
- 각 API 표에서 "**있어야 함**"인 키는 값이 `null`이어도 **키 자체는 늘 있어야 한다**. 키가 없으면 형식 오류로 본다.
- 키가 없어도 되는 것은 아래뿐이다. 없으면 표에 적은 값으로 받는다.

| API | 없어도 되는 키 |
|---|---|
| 공고 추천 결과(`results[]` 한 건) | `content_version` · `bonus_score` · `bonus_items` · `apply_period_type` |
| 공고 상세 | `bonus_info` · `apply_period_type` |

- 표에 없는 키가 더 있어도 괜찮다. 쓰지 않고 넘어간다.
- 수는 유한한 값만 받는다. `NaN` · `Infinity`, 실수로 나타낼 수 없을 만큼 큰 수(예: `1e400`)는 형식 오류다.
- 정수 칸(순위 · 건수 · 개월 · 원)은 소수점 없는 정수로 준다(`3.0`이 아니라 `3`). 참 · 거짓 칸은 JSON `true` · `false`로 준다(`0` · `1`이 아니라).
- 형식 오류인 응답은 쓰지 않는다. 아래 재시도 규칙대로 다시 부르고, 그래도 안 되면 사용자에게 "잠시 문제가 있었습니다. 다시 시도해주세요." 안내를 낸다.

**공고 없음 (공고 상세 · 자격 판정만)**
- 요청한 공고가 데이터에 없으면 **HTTP 404**에 본문 **`{"code": "NOTICE_NOT_FOUND"}`**를 준다.
- 본문 **최상위**에 `"code": "NOTICE_NOT_FOUND"`가 있어야 한다. 다른 키가 함께 있어도 되지만, `{"detail": {"code": "NOTICE_NOT_FOUND"}}`처럼 한 겹 안에 들어 있으면 공고 없음으로 보지 않는다.
- **본문 코드가 없는 404는 일반 오류로 본다.** API 경로가 아직 없을 때도 404가 나기 때문이다. 404를 모두 공고 없음으로 보면 경로가 없는 동안 모든 공고가 "공고 없음"으로 잘못 안내된다.
- 공고 없음은 다시 부르지 않는다. 사용자에게 "선택하신 공고를 더 이상 확인할 수 없습니다. 다른 공고를 선택해주세요."를 보여 주고 고르기 전 화면으로 돌아간다. 그 공고는 후보 목록에 남고 다시 고를 수 있다(4절).
- 수집 상태 · 공고 추천 API의 404는 늘 일반 오류다.

**우리 쪽 호출 규칙** — 공고 서버의 부하와 응답 설계에 참고해 달라.

| 항목 | 값 |
|---|---|
| 제한 시간 | 시도 한 번에 30초 |
| 다시 부르기 | 시간 초과 · 연결 실패 · HTTP 오류 코드 · 형식 오류면 같은 요청을 2초 간격으로 다시 보낸다. 처음 1번 + 다시 5번, **같은 요청이 최대 6번** 갈 수 있다. 네 API 모두 같은 요청을 여러 번 받아도 같은 결과를 주어야 한다 |
| 동시 호출 | 워커 프로세스 안에서 공고 서버 호출을 한 번에 하나씩 보낸다. 공고팀이 동시 호출 안전성을 확인하기 전까지 운영 워커는 1대로 둔다(5절) |
| 기록 | 우리 호출 기록에는 목적(수집 상태 · 공고 매칭 · 공고 상세 · 자격 판정), 시도별 결과, 오류 종류 · 상태 코드만 남긴다. 주소 · 요청 본문 · 응답 본문은 기록하지 않는다 |

### 2.2 공고 추천 — `POST /api/match` (있음, 결과 키 추가 요청)

**보내는 값** — 순위에 쓰이는 칸만 보낸다(공고팀 설명서 4.2). 공고팀 `MatchRequest` 중 아래 키만 채운다.

| 키 | 값 |
|---|---|
| `applicant_type` | `"예비창업자"` · `"개인사업자"` · `"법인"` |
| `idea` | `"{아이템 이름}. {한 줄 요약}. 목표 고객: {목표 고객}. 핵심 기능: {핵심 기능을 ', '로}. 키워드: {키워드를 ', '로}"` (공고팀 설명서 5절 그대로) |
| `founded_at` | 설립일 `"YYYY-MM-DD"`, 없으면 `""` |
| `region` | 시 · 도를 공고팀 16개 값으로 바꾼 것(⑨, 6절). 바꿀 수 없으면 `""` |
| `district` | 시 · 군 · 구(사용자 자유 입력 그대로, 공백이 있을 수 있다). 없거나 `region`이 `""`이면 `""` |
| `gender` | `"남성"` · `"여성"` (웹 입력값 그대로) |
| `certifications` | 인증 목록(문자열 목록), 없으면 `[]` |
| `first_startup` | 지금은 늘 `null`(웹 입력에 없음) |
| `main_industry` | 업종 **이름**(웹 입력값 그대로, ⑫) |
| `hiring_plan` | 채용 계획이 비어 있지 않고 `"없음"`이 아니면 `true`, 아니면 `false` |
| `partners` | 협력 기관을 `"; "`로 나눈 목록. 비었거나 `"없음"`이면 `[]` |
| `team` | 팀원 경력마다 `{"career": 값}`. 값은 사용자가 쓴 그대로라 이름 · 역할이 들어 있을 수 있다 |
| `revenue` | 수익모델 항목마다 `{"item": 서비스 · 상품명, "price": 단가(원)를 문자열로}` |
| `top` | `10` |
| `offset` | 첫 조회 `0`, 추가 조회 `10` |

- **보내지 않는 것:** 대표자 이름, 생년월일, 사업자등록번호, 자기부담금, 희망 사업 규모, 보유 시설, 그 밖의 입력. 가산점 계산에 어떤 칸이 꼭 필요하다고 답해 주면 그 칸만 더한다(3.2).
- 요청 본문에는 신청자 정보가 들어 있다. 그래서 우리 보안 문서에 공고 서버를 신청자 정보를 받는 곳으로 적는다(5절 질문).

**받는 값** — 최상위

| 키 | 있어야 함 | 값 |
|---|---|---|
| `results` | 있어야 함 | 추천 결과 목록. **요청한 `top`보다 많으면 형식 오류** |
| `filtered_count` | 있어야 함 | 정형 필터 통과 건수(정수) |
| `fallback_used` | 있어야 함 | 대체 경로를 썼는지(`true` · `false`) |
| `fallback_mode` | 있어야 함 | `"BM25단독"` · `"임베딩단독"` · `"마감임박순"` 또는 `null`. **이 밖의 값은 형식 오류**다. 공고 서버가 다른 표기를 쓰면 알려 달라 |

**받는 값** — `results[]` 한 건

| 키 | 있어야 함 | 값 | 우리가 쓰는 곳 |
|---|---|---|---|
| `notice_id` | 있어야 함 | 공고 ID(빈 문자열 안 됨) | 공고를 가리키는 값. 공고 상세 · 자격 판정 경로에 그대로 쓴다 |
| `title` | 있어야 함 | 문자열 | 카드 제목 |
| `organizer` | 있어야 함 | 문자열 또는 `null` | 카드 기관. 비었으면 `-` |
| `source` | 있어야 함 | 출처(빈 문자열 안 됨) | 출처 고지 문구. `kstartup` → "K-Startup", `bizinfo` → "기업마당", 그 밖에는 값 그대로 |
| `apply_end` | 있어야 함 | `"YYYY-MM-DD"`, `""` 또는 `null` | 마감일. `""` · `null`은 마감일 없음 |
| `apply_period_type` | 없어도 됨 | `fixed` · `budget_exhaustion` · `rolling` · `until_filled` | 모집 형태 표기(①). 그 밖의 값 · 없음은 "모름" |
| `url` | 있어야 함 | 문자열 | 원문 공고 링크 |
| `rank` | 있어야 함 | 정수 1~20 | **화면 순위로 그대로 쓴다.** 결과 목록 순서도 받은 그대로 둔다 |
| `display_type` | 있어야 함 | 문자열(`card` · `list`) | 카드 · 목록 표시 |
| `fit_score` | 있어야 함 | 0~1의 수 또는 `null` | 적합도. `null`이면 0으로 표시 |
| `band` | 있어야 함 | `"매우 적합"` · `"적합"` · `"참고"` 또는 `null`. 이 밖의 값은 형식 오류 | 추천 이유 문장(⑤) |
| `region` | 있어야 함 | 문자열 또는 `null` | 추천 이유 — `"전국"`이면 "전국 대상 공고입니다" |
| `region_match` | 있어야 함 | `true` · `false` · `null` | 추천 이유 — 희망 지역과 맞는지 |
| `content_version` | 없어도 됨 | 문자열 또는 `null` (**요청**, 3.1) | 추가 조회 때 "내용 바뀜" 판단 |
| `bonus_score` | 없어도 됨 | 유한한 수 또는 `null` (**요청**, 3.2) | 카드 가산점 합계 |
| `bonus_items` | 없어도 됨 | 목록 또는 `null`. 항목마다 `{"name": 문자열, "points": 유한한 수}` (**요청**, 3.2) | 가산점 항목별 근거. 없거나 `null`이면 빈 목록 |

- 다시 정렬하지 않는다. 적합도나 가산점으로 순서를 바꾸지 않고, 공고팀이 준 `rank`와 목록 순서를 그대로 보여 준다(사용자 결정).
- 추천 결과에는 지원 금액이 없으므로 카드의 지원 금액은 비워 둔다(②).
- 대체 경로(`fallback_used`가 `true`)면 화면에 "추천 정확도가 낮아질 수 있습니다."를 띄우고, `fallback_mode`가 `"마감임박순"`이면 끝에 " 마감 임박순으로 보여드립니다."를 붙인다(기준 문서 시트 6 E-C2-EMBED). 마감 임박순 결과는 `fit_score`가 `null`이라 카드 적합도가 0이 되고, 우리 쪽 웹 화면은 적합도가 0인 카드의 적합도를 숨기기로 했다. 그래서 정상 결과의 `fit_score`가 정확히 0이 되는 일이 없는지 확인을 부탁한다(9절 질문 11).
- 우리 쪽 대체 검색은 없다. 공고 서버가 안에서 대체 경로를 쓰고 결과로 알려 주는 것으로 받는다. 공고 서버 호출 자체가 실패하면 첫 조회는 "잠시 문제" 안내로 끝나고, 추가 조회는 안내 후 추가 조회 기회를 사용자에게 돌려준다.

예시 (가짜 값):

```json
{
  "results": [
    {"notice_id": "<공고 ID>", "title": "<공고 제목>", "organizer": "<기관>", "source": "kstartup",
     "apply_end": "2026-11-30", "apply_period_type": "fixed", "url": "<원문 링크>", "rank": 1,
     "display_type": "card", "fit_score": 0.82, "band": "매우 적합", "region": "전국", "region_match": null,
     "content_version": "<내용 버전>", "bonus_score": 2.0,
     "bonus_items": [{"name": "<가점 항목>", "points": 1.0}, {"name": "<가점 항목>", "points": 1.0}]}

```

### 2.3 수집 상태 — `GET /api/collection_status` (새로 요청)

| 키 | 있어야 함 | 값 |
|---|---|---|
| `status` | 있어야 함 | `"정상"` · `"지연"` · `"실패"`. 이 밖의 값은 형식 오류 |

- 공고 추천 전에 먼저 부른다. `"정상"`이 아니면 **공고 추천을 부르지 않는다**(기준 문서 시트 2 T-C2 L열 ②). 첫 조회면 사용자에게 "공고 정보를 갱신하는 중입니다. 갱신 후 다시 확인해주세요."(E-C2-STALE)를 보여 주고, 추가 조회면 같은 안내 후 추가 조회 기회를 돌려준다.
- 기준 문서는 "수집 실패 또는 최종 수집 시각이 24시간 초과"면 매칭하지 않는다고 정한다. 이 두 경우가 `"정상"`이 아닌 값으로 오게 해 달라. `"지연"`과 `"실패"`를 어떻게 나누는지 알려 달라.

### 2.4 공고 상세 — `GET /api/notices/{notice_id}` (새로 요청)

- 경로의 `{notice_id}`는 추천 결과의 `notice_id`를 **퍼센트 인코딩**해서 넣는다. ID에 `:`가 있기 때문이다(예: `a:1` → `a%3A1`). `/` 등 다른 특수 문자도 같은 방식으로 인코딩한다. 공고 서버는 인코딩을 풀어 원래 ID로 찾아야 한다.
- 공고가 없으면 404 + `{"code": "NOTICE_NOT_FOUND"}`(2.1).

| 키 | 있어야 함 | 값 | 우리가 쓰는 곳 (선택 공고) |
|---|---|---|---|
| `notice_id` | 있어야 함 | **요청한 공고 ID와 같아야 한다**. 다르면 형식 오류 | 공고 ID |
| `title` | 있어야 함 | 문자열 | 제목 |
| `organizer` · `supervising_org` · `executing_org` | 셋 다 있어야 함 | 문자열 또는 `null` | 기관 — 이 순서로 비어 있지 않은 첫 값, 모두 비었으면 `-` |
| `source` · `url` · `apply_url` | 셋 다 있어야 함 | 값은 쓰지 않는다 | (약속한 키라 있는지만 본다) |
| `category` | 있어야 함 | 문자열 또는 `null` | 지원 분야 — 분류 문자열 그대로(④) |
| `apply_start` · `apply_end` | 둘 다 있어야 함 | `"YYYY-MM-DD"`, `""` 또는 `null` | 접수 시작 · 마감일. `""` · `null`은 없음 |
| `apply_period_type` | 없어도 됨 | 2.2와 같은 값 | 모집 형태 표기(①) |
| `recruitment_status` | 있어야 함 | `open` · `closed` · `unknown` | 모집 상태 — `open` → 모집중, `closed` → 마감, 그 밖 → 모집중(⑥) |
| `support_amount_max_won` | 있어야 함 | 0 이상의 정수(원) 또는 `null` | 지원 금액 상한(②) |
| `support_amount_text` | 있어야 함 | 공고 원문의 금액 표기(예: `"1억원"`) 또는 `null` | 계획서 본문 · 보호 토큰(금액)의 원본(②) |
| `bonus_info` | 없어도 됨 | 공고의 가점 · 우대 조건 원문 또는 `null` (**요청**, 3.2) | 기준 문서 `Announcement.bonusInfo`(가산점 정보) |
| `eligibility` | 있어야 함 | 아래 객체 | 자격 조건 — 선택 공고에 담아 둔다(판정은 2.5의 API가 한다) |
| `eligibility.applicant_types` | 있어야 함 | 허용 지원대상 유형 목록(문자열) | |
| `eligibility.business_age_max_months` | 있어야 함 | 업력 상한(0 이상의 정수, 개월) 또는 `null`(제한 없음) | 년으로 바꿔 둔다(개월 / 12) |
| `eligibility.parsed` | 있어야 함 | 조건을 읽었는지(`true` · `false`) | |

- 요약 벡터(`summary_embedding`)는 넣지 않아도 된다(⑪).

### 2.5 자격 판정 — `POST /api/notices/{notice_id}/eligibility` (새로 요청)

경로는 2.4와 같은 방식으로 인코딩한다. 공고가 없으면 404 + `{"code": "NOTICE_NOT_FOUND"}`(2.1).

**보내는 값**

```json
{"applicant_type": "개인사업자", "founded_at": "2024-03-02", "today": "2026-10-03"}
```

| 키 | 값 |
|---|---|
| `applicant_type` | `"예비창업자"` · `"개인사업자"` · `"법인"` |
| `founded_at` | 설립일 `"YYYY-MM-DD"`, 없으면 `""` |
| `today` | 판정 기준일 `"YYYY-MM-DD"`. 업력은 이 날짜로 계산한다 |

- 사업자(개인사업자 · 법인)인데 설립일이 없으면 이 API를 부르지 않고 우리 쪽에서 "필수 입력 없음"(E-G1-MISSING)으로 처리한다. 사전 정보 입력이 설립일을 필수로 받아 정상 흐름에서는 생기지 않는다.

**받는 값**

| 키 | 있어야 함 | 값 |
|---|---|---|
| `passed` | 있어야 함 | 통과 여부(`true` · `false`) |
| `failed_conditions` | 있어야 함 | 불통과한 조건 이름 목록. 불통과면 하나 이상 넣어 달라 — 사용자 안내 "이 공고는 {사유}로 신청이 어렵습니다."의 사유로 쓴다 |
| `unknown_conditions` | 있어야 함 | 읽지 못해 통과로 본 조건 이름 목록(확인 필요) |
| `business_age_months` | 있어야 함 | 업력(0 이상의 정수, 개월) 또는 `null`. 사업자면 우리가 개월 / 12를 소수 한 자리로 반올림(사사오입)해 업력(년)으로 둔다. 예비창업자면 쓰지 않는다 |

- **조건 이름은 `"지원대상 유형"`과 `"업력"` 두 가지뿐이다.** `failed_conditions` · `unknown_conditions`에 다른 이름이 오면 형식 오류로 본다. 조건을 더 두려면 먼저 알려 달라(우리 쪽 화면 안내와 기준 문서 개정이 함께 필요하다).

**판정 규칙** (공고팀 설명서 5절 `g01()`의 원칙, 사용자가 정함)

| 규칙 | 내용 |
|---|---|
| 불통과 | 확실히 안 되는 경우만 불통과다 |
| 확인 필요 | 조건을 읽지 못했으면 통과로 보고, 그 조건 이름을 `unknown_conditions`에 넣는다. 우리는 진행을 막지 않고 자격 확인 화면에 "이 공고는 자격요건 자동 확인이 어렵습니다. 공고문을 직접 확인해주세요."를 띄운다 |
| 판정하지 않는 것 | 접수기간과 모집 상태는 판정하지 않는다. 추천이 이미 걸렀고, 마감 여부는 우리가 공고 상세의 마감일 · 모집 상태로 따로 안내한다 |
| 업력 | `today` 기준으로 계산한다 |
| 추천과 같은 규칙 | 자격 규칙(신청자 유형 · 업력)은 **추천(2.2)이 순위를 매기기 전에 거르는 정형 필터와 같게** 해 달라. 신청자 유형을 공고 본문으로 판정하는 규칙도 같게 해 달라. 정형 필터 가운데 접수기간 · 모집 상태만 뺀다 |

- 추천과 같은 규칙을 요청하는 이유: 추천에 나온 공고를 사용자가 골랐는데 판정에서 까닭 없이 불통과가 나면 사용자가 혼란스럽다. 두 결론이 한 곳의 규칙에서 나오게 하려는 것이다.
- 불통과가 나온 공고는 그 실행 건에서 다시 고를 수 없게 막는다(추가 조회에서 그 공고의 내용이 바뀌면 다시 고를 수 있다). 그래서 "확실히 안 되는 경우만 불통과"가 지켜져야 한다.

**기존 화면용 `POST /api/eligibility`와 다른 점** — 기존 API는 그대로 두고 새 경로로 만들어 달라.

| 항목 | 기존 `/api/eligibility` | 새 API |
|---|---|---|
| 공고 지정 | (본문) | 경로의 `{notice_id}` |
| 기준일 | 받지 않는다(서버 날짜) | `today`를 받아 업력을 계산한다 |
| 접수기간 · 모집 상태 | 판정한다 | 판정하지 않는다 |
| 결과 | 기존 키 | `passed` · `failed_conditions` · `unknown_conditions`(조건 이름 목록) · `business_age_months` |
| 공고 없음 | 기존 응답 모양 | 404 + 본문 `{"code": "NOTICE_NOT_FOUND"}` |

## 3. 공고 추천 결과에 더해 달라는 것

### 3.1 내용 버전 — `content_version` (사용자 결정)

| 항목 | 내용 |
|---|---|
| 뜻 | **공고 내용이 바뀔 때만 바뀌는 문자열.** 우리는 두 값이 같은지만 비교한다. 만드는 방식(내용 해시 등)은 공고팀이 정한다 |
| 넣을 내용 | 카드에 없는 것까지 포함한 공고 내용: 본문, 지원대상, 제외 조건, 업력 조건, 가점 조건, 접수기간, 지원 금액 등. **어떤 칸으로 만드는지 정해서 알려 달라** |
| 넣으면 안 되는 것 | 매일 수집할 때마다 바뀌는 값(가져온 시각, 행 수정 시각 등). 이런 값이 들어가면 내용이 그대로인 공고도 매일 "내용 바뀜"이 된다 |
| 쓰는 곳 | 추가 조회의 "내용 바뀜" 판단뿐이다. 화면에 값을 보여 주지 않는다 |

- 쓰는 방식: 추가 조회 결과에 첫 조회 공고가 다시 나오면, 그 공고를 추가 후보에서 빼고 첫 조회 카드를 새 내용으로 바꾼다. 아래 둘 중 하나면 그 카드에 "내용 바뀜"을 붙인다.
  1. 카드의 공고 정보(제목 · 기관 · 마감일 · 모집 형태 · 지원 금액 · 링크)가 달라졌다.
  2. 두 카드에 `content_version`이 모두 있고 서로 다르다. 카드에 없는 본문 · 지원대상 · 업력 조건의 변화를 잡기 위한 것이다.
- 적합도 · 추천 이유 · 가산점만 달라진 것은 "내용 바뀜"이 아니다.
- "내용 바뀜"이 붙은 공고가 자격 불통과로 막혀 있었으면 막힘을 푼다. 내용 버전이 오기 전에는 1번(카드 정보 비교)으로만 동작한다.

### 3.2 가산점 (사용자 결정, 새 기능)

화면 3(공고 후보)에 신청자별 가산점이 필요하다. 지금 공고 서버에 이 기능이 없다는 것을 알고 있다. 우리 쪽 연결 코드와 자리는 만들어 두었고, 값이 오기 전에는 비어 있다.

| 키 (추천 결과 한 건) | 값 |
|---|---|
| `bonus_score` | 이 신청자가 그 공고에서 받을 수 있는 가산점 합계(수). 공고의 가점 조건과 보낸 신청자 정보로 계산한다. 만점 기준은 공고마다 달라도 된다 |
| `bonus_items` | 항목별 근거 목록 `[{"name": "<가점 항목>", "points": 1.0}, ...]`. **합계(`bonus_score`)와 맞아야 한다** |

| 경우 | `bonus_score` | `bonus_items` |
|---|---|---|
| 해당하는 가점이 없음 | `0` | `[]` |
| 계산하지 못함 | `null` | `[]` |

- **`0`과 `null`을 구분해 달라.** 화면은 `0`을 "해당 가점 없음", `null`을 "가산점 정보 없음"으로 다르게 보여 준다.

| 키 (공고 상세) | 값 |
|---|---|
| `bonus_info` | 공고의 가점 · 우대 조건 원문(또는 `null`). 기준 문서 `Announcement.bonusInfo`(가산점 정보)에 넣는다 |

**순위 반영 (요청)**
- 가산점을 적합도와 함께 **순위(`rank`)에도 반영**해 달라. 지금 공고팀 순위는 검색 점수(적합도의 바탕) 순에 규칙으로 뒤로 미는 단계를 더한 것이고, 가산점은 없는 것으로 알고 있다.
- 적합도와 가산점을 어떻게 섞을지는 공고팀이 정하고 **알려 달라.** 화면 문구("아이템과 맞는 정도와 가산점을 함께 보고 골랐어요" 등)를 그에 맞춘다.
- 우리는 어느 경우든 공고팀이 준 `rank`를 그대로 쓰고 다시 정렬하지 않는다. 웹도 다시 정렬하지 않는다.

**필요한 신청자 입력 (질문)**
- 가산점 계산에 필요한 신청자 입력이 무엇인지 알려 달라. 예를 들어 청년 가점에 생년월일이 필요하다면 그렇게 답해 달라.
- 지금은 생년월일을 보내지 않는다. 답을 받은 뒤 **필요한 칸만** 공고 추천 요청에 더한다(사용자 결정). 필요 없는 개인정보는 보내지 않는다.

## 4. 질문 — 공고 없음이 생기는 경우 (사용자 요청)

- **어떤 경우에 공고가 데이터에서 빠져 "공고 없음"이 되는지** 알려 달라(예: 원천에서 내려감, 수집 범위 변경, 데이터 정리 등).
- **빠진 공고가 다시 생길 수 있는지** 알려 달라.
- 지금 우리는 공고 없음이 나온 공고를 막지 않는다. 후보 목록에 남기고, 사용자가 다시 고르면 그때 다시 묻는다. 공고 서버가 잠깐 없다고 답했을 수 있고, 다시 생긴 공고의 내용이 그대로면 막힘을 풀 방법이 없기 때문이다. 답을 받으면 이 처리를 다시 정한다.

| 인증 | 인증이 필요하면 방식을 알려 달라. 지금 우리 요청에는 인증 정보가 없고 내부망만 전제한다. 인증이 생기면 우리 쪽 연결 코드도 고친다 |
| 요청 본문 기록 | 공고 추천 요청에는 신청자 정보가 들어 있다(2.2). 공고 서버가 요청 본문을 로그 등에 남기는지 알려 달라 |
| 시험 서버 | 지금의 시험 공고 서버(공개 주소, 인증 없음)에는 **가짜 신청 정보로만** 연결한다 |

## 6. 공고팀 설명서 합의 요청 ①~⑫에 대한 답

| 번호 | 주제 | 답 |
|---|---|---|
| ① | 마감일 | 마감일은 날짜 또는 비어 있음(`null`)으로 받는다. 마감일이 없는 공고(예산 소진 · 상시 · 선착순)는 비워 두고 **모집 형태** 표기를 함께 둔다: `fixed` → "기간 있음", `budget_exhaustion` → "예산 소진 시까지", `rolling` → "상시·수시", `until_filled` → "선착순·모집 완료 시까지", 그 밖 · 없음 → "모름". 가짜 날짜(예: 9999-12-31)는 쓰지 않는다 |
| ② | 지원 금액 | 비울 수 있게 했다. 공고 상세 API에 `support_amount_max_won`(원)과 `support_amount_text`(원문 표기)를 요청한다(2.4). 추천 결과에는 금액이 없어 카드 금액은 비워 둔다. 0을 "정보 없음"으로 쓰지 않는다 |
| ③ | 신청서 양식 · 평가 항목 | 지금은 신청자 유형(예비창업자 · 개인사업자 · 법인)마다 미리 정해 둔 양식 · 평가 항목 · 채점 기준표 중에서 작업 분해(T-C3)가 고른다(값 잠정, 2026-10-04). 공고 상세로 만든 선택 공고의 양식 칸은 쓰지 않는다. 공고별 양식 · 평가 항목을 받게 되면 신청자 유형별 값과 무엇이 우선인지는 그때 정한다. 공고팀이 이 부분을 고도화하고 있다면 알려 달라 |
| ④ | 지원 분야 | 공고 상세의 `category`(분류 문자열)를 그대로 받는다. 기준 문서의 두 값(창업(06) · 기술개발(02))으로 바꾸지 않는다 |
| ⑤ | 추천 이유 | 우리가 재료(`band` · `region` · `region_match` · `fallback_mode`)로 정해진 문장을 만든다(잠정, AI를 부르지 않음). 아래 표 |
| ⑥ | 모집 상태 | `open` → 모집중, `closed` → 마감, 모르면(`unknown` 등) 모집중으로 둔다. 그래서 모집 상태를 모르는 공고에는 마감 안내가 붙지 않는다 |
| ⑦ | 확인 필요 | 자격 판정 API가 `unknown_conditions`로 준다(2.5). 우리는 자격 결과의 확장 필드(`unknownConditions`)로 받아 자격 확인 화면에 "공고문 직접 확인" 안내를 띄운다. 진행은 막지 않는다 |
| ⑧ | 수집 지연 시 매칭 중단 | 기준 문서대로 한다. 수집 상태 API가 `"정상"`이 아니면 공고 추천을 부르지 않는다(2.3) |
| ⑨ | 지역 | 웹은 시 · 도를 드롭다운 17개 값으로, 시 · 군 · 구를 자유 입력으로 저장한다. 시 · 도는 아래 표로 공고팀 16개 값으로 바꿔 `region`에 보낸다(광주광역시 · 전라남도 → `전남광주`). 표에 없는 값(예: 옛 자료)은 `""`로 보내며 그 건은 지역 순위 조정만 꺼진다(공고팀 설명서 4.2). 시 · 군 · 구는 바꾸지 않고 `district`에 그대로 보낸다 |
| ⑩ | G-01 입력 | 공고 조건을 우리가 넘기지 않는다. 고른 공고 ID로 자격 판정 API를 부른다(2.5) |
| ⑪ | 요약 벡터 | 쓰지 않는다. 공고 상세에 넣지 않아도 된다 |
| ⑫ | 업종 · 채용 계획 · 기준일 | 업종은 웹 입력값이 업종 **이름**이라 `main_industry`에 이름 그대로 보낸다. 채용 계획은 규칙으로 바꾼다(비어 있지 않고 "없음"이 아니면 `true`). 기준일은 자격 판정 API에 `today`로 넘긴다. 공고 추천 API가 공고 서버의 오늘 날짜를 쓰는 것은 받아들인다 |

**⑤ 추천 이유 문장** (잠정) — 앞 문장과 뒷말을 `" · "`로 잇는다.

| 조건 | 앞 문장 |
|---|---|
| `band`가 `"매우 적합"` | 아이템 설명과 공고 내용이 매우 비슷합니다 |
| `band`가 `"적합"` | 아이템 설명과 공고 내용이 비슷합니다 |
| `band`가 `"참고"` | 아이템 설명과 관련이 있는 공고입니다 |
| `band`가 `null`이고 `fallback_mode`가 `"마감임박순"` | 마감이 가까운 신청 가능 공고입니다 |
| `band`가 `null`인 그 밖의 경우 | 아이템 설명과 관련이 있는 공고입니다 |

| 조건 | 뒷말 |
|---|---|
| 공고 `region`이 `"전국"` | 전국 대상 공고입니다 |

| `region_match`가 `false` | 다른 지역 대상 공고일 수 있습니다 |
| 그 밖 | 붙이지 않는다 |

## 8. 실제 연결을 켜기 전에 함께 확인할 것

연결을 켜는 것(워커 설정에 공고 서버 주소를 넣는 것)은 우리 쪽에서 한다. 아래가 모두 맞은 뒤에 켠다.

1. 공고팀이 네 API(수집 상태 · 공고 추천 · 공고 상세 · 자격 판정)를 이 문서의 약속대로 제공하고 확인을 마쳤다.
   - 있어야 하는 키가 모두 있고(값은 `null`이어도 됨), 값이 2절의 범위 안이다.
   - 공고 없음은 404 + 본문 최상위 `{"code": "NOTICE_NOT_FOUND"}`이고, 경로가 없을 때의 404와 구분된다.
   - 자격 판정의 조건 이름은 `"지원대상 유형"` · `"업력"`뿐이다.
2. 시험 공고 서버에 가짜 신청 정보로 연결해, 우리 쪽에서 네 API 응답이 형식 오류 없이 받아지는지 함께 본다.
3. 운영 공고 서버가 AWS 내부망에 있고 외부 접근이 막혀 있다.
4. 동시 호출 안전성을 확인하기 전이면 운영 워커는 1대다.
5. 인증이 필요하면 방식이 정해졌고 우리 쪽 연결 코드에 반영했다.
