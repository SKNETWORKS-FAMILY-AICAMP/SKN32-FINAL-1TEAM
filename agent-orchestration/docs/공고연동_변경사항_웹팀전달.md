## 0. 먼저 알아 둘 것

- **지금 웹의 화면 3 · 4는 Orchestrator에 연결되지 않은 임시 구현이다.** 공고 표(`notices`)를 직접 조회하고, 자격 판정은 더미이며, 가산점은 무작위 값이다. 이 문서의 동작은 웹이 화면 3 · 4를 Orchestrator 함수(`screen(project_id, 3)` · `screen(project_id, 4)` · `more_candidates_for_project` · `select_announcement_for_project`)로 바꾼 뒤에 보인다(대응 문서 2.1절).
- 웹은 공고 서버를 부르지 않는다. 공고 서버를 부르는 곳은 Orchestrator 워커뿐이다. 웹은 지금처럼 명령을 부르고 `wait_project`로 기다린 뒤 결과를 읽는다.
- 공고 서버 연결은 워커 설정으로 켠다. 꺼져 있으면 워커는 가짜 공고와 가짜 판정을 쓴다(새 판정 규칙 그대로, 업력 상한 없음). 그래서 공유 DB 워커로 시험할 때도 아래 동작이 같다.

## 1. 화면 3 — 공고 후보

### 1.1 결과 필드 (`screen(project_id, 3)`, `CandidatesScreen`)

| 필드 | 내용 | 바뀜 |
|---|---|---|
| `candidates` | 첫 조회 카드 목록. 추가 조회에서 다시 나온 공고는 새 내용으로 바뀌어 있다(2절) | 내용 갱신 |
| `moreCandidates` | 추가 조회 카드 목록. **첫 조회와 겹친 공고는 없다** | 겹침 제거 |
| `moreAvailable` | 추가 조회를 할 수 있는지(1회, 합계 20건 미만). 추가 조회가 실패하면 다시 참이 된다 | |
| `collectionStatus` · `filteredCount` · `fallbackUsed` · `fallbackMode` | 수집 상태 · 필터 통과 건수 · 대체 경로 | 실패한 추가 조회는 반영하지 않는다 |
| `blockedAnnouncementIds` | **새로.** 막힌 공고 ID 목록(1.7) | 새 필드 |
| `screen` · `projectId` · `runId` · `step` · `progress` · `notices` | 공통 | |

- `outputs(project_id)`의 `candidates` · `moreCandidates`도 화면 3과 같은 목록이다(명세 5.2절).
- 화면 3은 공고선택 · 사용자대기와 계획서작성 · 사용자대기(자격 통과 뒤 작성 시작 전)에서 열린다(지금과 같음).

### 1.2 카드 필드 (`AnnouncementCard`)

| 필드 | 값 | 바뀜 |
|---|---|---|
| `announcementId` | 공고 ID. 공고 서버 연결을 켠 워커에서는 공고 표 `notices.notice_id`와 같은 값이다(공고팀 추천이 그 표를 읽는다). 연결을 끈 워커(가짜 공고)의 ID(`A01` 등)는 `notices`에 없으니, 제목 등은 공고 표에서 찾지 말고 카드나 `selectedAnnouncement`에서 읽는다 | 확인 끝남 |
| `title` · `agency` | 제목 · 기관(기관을 모르면 `-`) | |
| `applyEnd` | 마감일 또는 **`null`**(마감일 없는 공고 — 예산 소진 · 상시 · 선착순) | `null` 가능 |
| `applyPeriodType` | **새로.** 모집 형태 표기: `기간 있음` · `예산 소진 시까지` · `상시·수시` · `선착순·모집 완료 시까지` · `모름`. `applyEnd`가 `null`이면 이 표기를 보여 준다 | 확장 |

| `fitScore` | 적합도 0~1. 마감 임박순 카드는 0이고, 이 0은 점수가 아니다(1.6) | |
| `rank` | 공고팀 순위(1~20). 이 순서로 보여 준다(1.3) | |
| `displayType` | `card` · `list` | |
| `matchReason` | 추천 이유 한 줄. 정해진 틀로 만든 문장이다(잠정) | |

| `contentVersion` | **새로.** 공고 서버의 내용 버전. Orchestrator가 비교에만 쓴다. **웹은 쓰지 않는다** | 확장 |

- 카드에는 자격 결과를 싣지 않는다. 화면 3이 보여 주는 자격 정보는 막힌 공고 목록(1.7)뿐이다.

### 1.3 순서 — 공고팀 순위 그대로

- 카드는 `rank` 순서(목록 순서와 같다)대로 보여 준다. **웹은 다시 정렬하지 않는다.** 지금 웹의 가산점 높은 순 정렬(`_candidates_response`, 무작위 값 기준)은 없앤다. 첫 조회 · 다시 찾은 공고 묶음 나누기(`batch` 1 · 2)는 그대로 둘 수 있다.
- 공고팀 순위는 검색 점수에 지역 등 규칙으로 뒤로 미는 단계가 더해진 것이다. 가산점도 순위에 반영해 달라고 공고팀에 요청했다. 그래서 순서대로 적합도나 가산점이 줄지 않을 수 있다. 순위가 한 값의 순서라고 가정하지 않는다.
- "가산점이 높은 순서로 골랐어요" 문구는 공고팀 순위 기준에 맞게 바꾼다. 예: "아이템과 맞는 정도와 가산점을 함께 보고 골랐어요" — 공고팀이 가산점 반영을 확인한 뒤.

### 1.4 가산점 — `bonusScore` · `bonusItems`

| `bonusScore` | 뜻 | 화면 |
|---|---|---|
| 수 (예: `2.0`) | 이 신청자가 그 공고에서 받을 수 있는 가산점 합계 | 그대로 보여 준다 |
| `0` | 해당하는 가점이 없다 | "해당 가점 없음" 등 |
| `null` | 계산하지 못했다 | "가산점 정보 없음"으로 보이거나 숨긴다 |

- **`0`과 `null`은 뜻이 다르다.** 공고팀이 가산점 기능을 만들기 전에는 모든 카드가 `null`이다.
- `bonusItems`는 항목별 근거(`name` · `points`)이고 합계와 맞는다. 오른쪽 "매칭 근거"(`MatchScoreReason`)에 정량 근거로 보여 줄 수 있다.
- 만점 기준은 공고마다 다르다.

### 1.5 출처 고지 — 카드의 `sourceNotice`

- 웹 고정 문구(K-Startup) 대신 카드의 `sourceNotice`를 쓴다. 기업마당 공고는 "본 AI 요약 정보는 기업마당 공고 내용을 바탕으로 생성되었습니다."다.

### 1.6 마감 임박순 대체 경로 — 적합도 숨기기

- 공고 서버가 검색 오류로 마감 임박순 대체 경로를 쓰면 그 조회의 카드는 `fitScore`가 0이다. 이 0은 실제 점수가 아니다(공고 서버가 적합도를 주지 않았다).
- **웹은 카드마다 `fitScore`가 0이면 그 카드의 적합도를 숨긴다.** 화면 3의 `fallbackMode`로 판단하지 않는다. 화면 3에는 첫 조회와 추가 조회의 카드가 함께 있는데 `fallbackMode`는 하나뿐이라, 추가 조회만 마감 임박순이면 첫 조회 카드의 실제 적합도까지 숨기게 된다(반대도 생긴다). 정상 결과의 적합도는 0이 되지 않는다.
- 이때 안내 E-C2-EMBED 문구 끝에 " 마감 임박순으로 보여드립니다."가 붙는다(7절). 공고 서버 연결을 켠 워커에서는 카드의 추천 이유도 "마감이 가까운 신청 가능 공고입니다"로 시작한다.

### 1.7 막힌 공고 — `blockedAnnouncementIds`

자격 확인에서 불통과가 나온 공고는 그 실행 건에서 다시 고를 수 없다. 이 목록은 Orchestrator가 관리하고 웹은 표시만 한다.

| 때 | 목록 |
|---|---|
| 자격 확인 결과가 불통과(E-G1-REJECT) | 들어간다 |
| 추가 조회에서 그 공고 카드가 `contentChanged = true`가 됨 | 빠진다(막힘이 풀린다) |
| 공고 없음(X-C2-GONE) · 오류(X-C2-FAIL) · 설립일 없음(E-G1-MISSING) | 들어가지 않는다 |

- **웹의 지금 막힘(브라우저 메모리의 `checkedFailedTitles`, 제목 비교)을 이 목록으로 바꾸고 공고 ID로 비교한다.** 제목이 같은 다른 공고가 함께 막히던 문제가 없어진다.
- 새로고침 · 프로젝트 다시 열기에도 그대로다. 웹이 따로 기억하거나 비울 필요가 없다. 새 프로젝트(새 실행 건)는 빈 목록에서 시작한다.
- 막힌 공고를 고르는 명령은 `ANNOUNCEMENT_BLOCKED`로 거절된다(3.2). 버튼을 막아 두면 이 오류를 볼 일이 없다.
- 풀린 공고를 다시 골라 또 불통과면 다시 막힌다. 추가 조회는 한 번뿐이라 그 뒤로는 풀리지 않는다.
- "추천 공고 모두 자격에 맞지 않음" 배너는 이 목록으로 계산할 수 있다(후보 ID가 모두 이 목록에 있을 때).
- 풀림은 "내용이 바뀌었으니 다시 확인할 수 있다"는 뜻일 뿐, 통과할 수 있다는 뜻이 아니다.

## 2. 화면 3 — 공고 추가 조회 (`more_candidates_for_project`)

### 2.1 받는 때와 한도

- 받는 때와 한도(1회, 합계 20건)는 지금과 같다. 성공하든 실패하든 끝나면 **공고선택 · 사용자대기**로 돌아간다(자격 통과 뒤 계획서작성 · 사용자대기에서 눌렀어도 같다).

### 2.2 성공 — 겹침 빼기 · 첫 조회 카드 갱신 · 내용 바뀜

- 추가 조회 결과 가운데 첫 조회와 공고 ID가 같은 것은 `moreCandidates`에서 뺀다. 그만큼 추가 후보가 줄어도 된다.
- 첫 조회(`candidates`)의 그 카드는 추가 조회에서 받은 새 내용으로 바뀐다. 자리 · `rank` · `displayType`은 그대로이고, 제목 · 기관 · 마감일 · 모집 형태 · 지원 금액 · 적합도 · 가산점 · 추천 이유 · 출처 고지 · 링크가 새 값이다.
- **`contentChanged`는 공고 내용이 바뀌었을 때만 참이다.** 아래 둘 중 하나다.
  1. 공고 정보(제목 · 기관 · 마감일 · 모집 형태 · 지원 금액 · 링크)가 달라졌다.
  2. 공고팀 내용 버전이 달라졌다(카드에 없는 본문 · 지원대상 · 업력 조건 변화 포함).
- 이런 경우는 `false`다.
  - 적합도 · 추천 이유만 달라짐(값은 새로 바뀌어 있다)
  - 가산점만 달라짐(값은 새로 바뀌어 있다)
  - 공고 없음 · 불통과였던 공고가 내용 그대로 다시 나옴
- **웹은 `contentChanged`가 참인 카드를 강조해 다시 보게 한다.** 문구는 "내용이 바뀌었어요, 다시 확인해 보세요" 정도로 한다.
  - `contentChanged`는 자격 통과 · 불통과를 뜻하지 않는다. 화면 3은 자격 결과를 암시하지 않으며, 자격은 공고를 골라야 새로 판정된다. "이제 신청 가능" 같은 표현은 쓰지 않는다.
  - 내용이 바뀌면 통과 → 불통과, 불통과 → 통과 모두 생길 수 있고, 날짜만 지나도(업력 상한) 통과가 불통과로 바뀔 수 있기 때문이다.
- 다시 나오지 않은 첫 조회 공고는 내용이 바뀌었어도 알 수 없다(그대로 둔다). 그래도 고르면 새로 판정한다.
- **추가 조회가 성공했는데 새 후보가 0건일 수 있다**(겹친 공고를 빼서). 이때도 추가 조회 기회는 쓴 것이고, 첫 조회 카드는 갱신돼 "내용 바뀜"이 붙을 수 있다. "더 보여드릴 공고가 없어요"와 함께 갱신된 첫 조회 목록을 보여 준다.

### 2.3 실패 — 안내 후 기회 반환

| 경우 | 안내 (`notices`) |
|---|---|
| 추가 조회가 어떤 오류로든 끝남(공고 서버 응답 없음 · 형식 오류 · 코드 오류 등) | X-C2-FAIL "잠시 문제가 있었습니다. 다시 시도해주세요." |
| 수집 상태가 정상이 아니어서 매칭하지 않음 | E-C2-STALE "공고 정보를 갱신하는 중입니다. 갱신 후 다시 확인해주세요." |

- 실행을 실패시키지 않고 공고선택 · 사용자대기로 돌아간다.
- **추가 조회 기회를 돌려준다** — `moreAvailable`이 다시 참이다(대응 문서의 `rematch_used`는 거짓).
- 화면 3의 나머지 값(`candidates` · `moreCandidates` · `collectionStatus` · `filteredCount` · `fallbackUsed` · `fallbackMode` · `blockedAnnouncementIds`)은 **추가 조회 전 그대로**다. 실패한 추가 조회의 카드는 보이지 않고, 고를 수 없고, 20건 한도에 세지 않는다.

## 3. 공고 선택 (`select_announcement_for_project`)

### 3.1 명령은 고른 ID만 남긴다

- 명령은 고른 공고 ID와 고르기 전 대기 지점(공고선택 또는 계획서작성)만 남기고 자격 확인(G-01)을 대기열에 넣는다. **선택 공고를 만들지 않고 `RunView.announcement_id`도 바꾸지 않는다.**
- 워커의 G-01이 공고 서버에서 공고 상세와 자격 판정을 함께 받아 선택 공고 · 자격 결과 · 업력을 한 번에 저장한다. 그때 `RunView.announcement_id`와 `outputs.selectedAnnouncement`가 바뀐다.
- 웹은 지금처럼 `wait_project`로 기다린 뒤 결과를 읽는다. 명령 직후에 `view_project`의 `announcement_id`나 `outputs.selectedAnnouncement`를 읽으면 아직 이전 값이다.

### 3.2 거절 — 실행 건은 바뀌지 않는다

| 순서 | 확인 | 오류 |
|---|---|---|
| ① | 받는 상태(공고선택 · 사용자대기, 계획서작성 · 사용자대기) | `INVALID_STATE`(작성 시작 뒤), `BUSY`(점유 겹침 — 잠시 뒤 다시) |
| ② | 후보(첫 조회 · 유효한 추가 조회)에 있는 공고인가 | `INVALID_ANNOUNCEMENT` |
| ③ | 막힌 공고가 아닌가(1.7) | **`ANNOUNCEMENT_BLOCKED`** (새로) |

- `ANNOUNCEMENT_BLOCKED`는 명령 오류 코드라 문구가 없다. 웹은 지금 문구 "신청 자격에 맞지 않는 공고예요. 다른 공고를 선택해 주세요."를 쓸 수 있다.

### 3.3 자격 확인이 끝난 뒤

| G-01 결과 | 다음 상태 | 안내 | `announcement_id` · 선택 공고 · 화면 4 |
|---|---|---|---|
| 통과(확인 필요 포함) | 계획서작성 · 사용자대기 | 확인 필요가 있으면 화면 4에만 E-G1-UNPARSED(4절) | 고른 공고로 바뀜 |
| 불통과 | 공고선택 · 사용자대기 | E-G1-REJECT. 그 공고는 막힌다(1.7) | 고른 공고로 바뀜(화면 4에 불통과 결과) |
| 설립일 없음 | 공고선택 · 사용자대기 | E-G1-MISSING(정상 흐름에서는 생기지 않음). 막지 않는다 | 고른 공고로 바뀜 |
| **실패 — 공고 없음** | **고르기 전 대기 지점** | **X-C2-GONE** "선택하신 공고를 더 이상 확인할 수 없습니다. 다른 공고를 선택해주세요." | **고르기 전 그대로** |
| **실패 — 그 밖의 오류** | **고르기 전 대기 지점** | **X-C2-FAIL** "잠시 문제가 있었습니다. 다시 시도해주세요." | **고르기 전 그대로** |

- 실패는 실행을 실패시키지 않는다. "고르기 전 대기 지점"은 공고선택 · 사용자대기(화면 3)에서 골랐으면 화면 3, 계획서작성 · 사용자대기(자격 통과 뒤, 화면 5)에서 골랐으면 화면 5다. 화면 5로 돌아가면 이미 통과한 이전 공고로 '작성 시작'을 할 수 있다.
- 실패하면 화면 4는 **이전 공고의 결과 그대로**다. 이전 결과가 없으면 화면 4는 `SCREEN_NOT_READY`다.
- 웹이 이번 선택의 실패를 아는 법: `wait_project` 뒤 `notices` 끝에 선택 뒤 시각(`at`)의 X-C2-GONE 또는 X-C2-FAIL이 새로 붙어 있다. `notices`는 실행 건의 안내를 계속 쌓는 목록이라, 새로 붙은 것만 보여 준다.
- 공고 없음 · 불통과 · 오류였던 공고도 작성 시작 전이면 다시 고를 수 있다(불통과는 막힌 동안 빼고). 고를 때마다 공고 서버에 새로 묻는다. 공고 없음이었던 공고가 다시 생겼으면 정상으로 진행한다.
- 공고 없음이 나온 공고도 후보 목록에 그대로 남고 따로 표시하지 않는다.

## 4. 화면 4 — 자격 확인 (`screen(project_id, 4)`, `GateScreen`)

| 필드 | 내용 | 바뀜 |
|---|---|---|
| `announcementId` | 자격 확인한 공고 ID | |
| `gateResult.passed` | 통과 여부 | |
| `gateResult.failedConditions` | 불통과한 조건 이름(`지원대상 유형` · `업력`) | |
| `gateResult.missingInputs` | 누락 입력(`foundedAt`) — 정상 흐름에서는 비어 있다 | |
| `gateResult.undecidable` | **늘 `false`.** 판정 불가로 막는 경우는 없어졌다 | 쓰지 않음 |
| `gateResult.unknownConditions` | **새로.** 확인이 필요한 조건 이름(`지원대상 유형` · `업력`) — 공고 서버가 읽지 못해 통과로 본 조건 | 확장 |
| `businessAgeYears` | 업력(년, 소수 한 자리). 예비창업자 · 업력을 모르면 `null` | |
| `canStartWriting` | 작성 시작을 할 수 있는지(통과) | |
| `notices` | 공통 안내 + `unknownConditions`가 있으면 **E-G1-UNPARSED** | 화면 4에만 |

- `unknownConditions`가 있으면 화면 4 `notices`에 E-G1-UNPARSED "이 공고는 자격요건 자동 확인이 어렵습니다. 공고문을 직접 확인해주세요."가 하나 붙는다.
  - **진행을 막지 않는다.** 통과이므로 `canStartWriting`이 참이고 작성 시작을 할 수 있다.
  - 실행 건 안내 목록에는 쌓지 않는다. 그래서 `view_project`의 `notices`에는 나오지 않고, 화면 4를 열 때마다 지금 자격 결과로 다시 만든다.
- 화면 4는 확인 필요 조건 이름을 보여 줘야 한다(예: "업력 — 공고문을 직접 확인해 주세요").
- 지금 웹의 더미 자격 판정은 없앤다. 대응 문서 2.1절 `POST …/generate` 행의 `eligibility` 응답은 위 `gateResult`로 채운다.

## 5. 선택 공고 (`outputs.selectedAnnouncement`, `Announcement`)

| 필드 | 바뀜 |
|---|---|
| `applyStart` · `applyEnd` | 날짜 또는 `null` |
| `supportAmountMax` · `supportAmountText` | 지원 금액(원) · 원문 금액 표기 또는 `null` |
| `applyPeriodType` | **새로.** 모집 형태 표기(1.2와 같은 값) |
| `status` | `모집중` · `마감`. 공고 서버가 모집 상태를 모르면 `모집중`이다 — 기업마당 공고처럼 실제로는 모를 수 있다 |
| `supportField` | 공고 서버의 분류 문자열 그대로 |
| `bonusInfo` | 공고의 가점 · 우대 조건 원문 또는 `null`(공고팀에 요청) |
| `summaryEmbedding` | **늘 빈 목록**이다. 응답이 더 이상 크지 않다 |
| `formSpec` · `evaluationItems` | 기본 양식(잠정). 작성 · 검수 Agent 연동 때 정한다 |

- 선택 공고는 워커의 G-01이 성공했을 때만 바뀐다(3.1). 자격 확인이 실패하면 이전 선택 공고 그대로다.

## 6. 진행 상태 — 마감 안내 (`view_project`, `/status`의 `notice_closed`)

진행 상태(`RunView.notices`)에 E-RUN-CLOSED "선택하신 공고의 접수가 마감되었습니다. 계속 진행할지 선택해주세요."가 붙는 조건이 바뀌었다. 진행 중 · 대기 중인 실행 건(실행 · 재개대기 · 사용자대기)에 선택 공고가 있을 때 아래 둘 중 하나면 붙는다.

1. `applyEnd`가 있고 오늘보다 앞이다. `applyEnd`가 `null`이면 이 조건은 보지 않는다.
2. `status`가 `마감`이다(G-01이 공고 상세를 받을 때의 모집 상태).

- **지금 웹의 마감 확인(`_is_notice_closed` — 공고 표를 읽어 모집 상태가 `open`이 아니거나 마감일이 지나면 마감)은 이 안내로 바꾼다.** 대응 문서의 `/status` 행 그대로 `notice_closed` ← `notices`에 E-RUN-CLOSED가 있는지.
- **모집 상태 모름(`unknown`)은 이제 마감이 아니다.** 웹은 모름을 마감으로 보았지만, 바뀐 뒤에는 마감 안내가 붙지 않는다.
- 공고를 고른 뒤에 공고 서버에서 바뀐 모집 상태는 반영되지 않는다. 그래서 마감일이 없는 공고(예산 소진 · 상시 · 선착순)가 고른 뒤에 모집을 끝내면 안내가 없다.
- 마감 안내는 알리기만 하고 진행을 막지 않는다(지금과 같다).
