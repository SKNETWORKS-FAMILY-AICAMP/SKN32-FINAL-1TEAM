## 1. 무엇이 바뀌었나 (①)

- **진행 상태의 원본은 Orchestrator다.** 웹은 함수로 읽는다. Orchestrator는 웹 `projects`의 **어떤 컬럼에도 쓰지 않는다**(진행 컬럼 5개 `status` · `stage` · `progress_percent` · `notice_id` · `failure_reason` 포함). 2026-09-30 교체 목록의 "D. projects 요약 5개를 Orchestrator가 쓴다"는 없어졌다.
- **결과는 기준 문서 모양으로 돌려준다.** 웹 응답(`schemas.py`) 모양으로 바꾸는 일은 웹 백엔드가 한다. Orchestrator 쪽에 웹 응답용 변환 모듈은 두지 않는다. 대응표가 3절이다.
- 웹 테이블 중 **알림 · 관리자 실패 알림 · 검수 회수 문단**은 웹에 두고, 워커는 행을 만들기만 한다(INSERT).
- **설정**(`verification_policies`)과 **사전 정보 입력**은 지금처럼 웹 테이블에 두고 Orchestrator가 읽는다.

| 일 | 웹 (백엔드 · 프론트) | Orchestrator (웹 프로세스 안 함수 + 워커) |
|---|---|---|
| 로그인 · 동의 · 마이페이지 프로필 | 한다 (지금 그대로) | `request_start`가 `profile_count`로 프로필만 다시 확인 |
| 사전 정보 입력 저장 | 한다 (`projects` 입력 컬럼 · `project_plan_inputs` 등) | 저장된 값을 읽어 변환 · 확인 |
| 동시 실행 확인 | 저장 전 `active_work`로 확인, 409 응답 | 판단 기준 · 최종 확인(`request_start`가 계정 잠금 안에서) |
| 주인 확인 | **모든 함수를 부르기 전에** 한다 (관리자 함수는 관리자 확인) | `request_start`만 다시 확인 |
| 단계 진행 · 재개 · 재작성 · 전후 비교 · 되돌리기 | 하지 않는다 | 워커가 한다 |
| 진행 상태 · 결과 저장 | 하지 않는다 (`orch_` 테이블은 쓰지 않음) | `orch_` 테이블에 한 트랜잭션으로 저장 |
| 진행 상태 · 결과 보여 주기 | 함수 결과를 웹 응답 모양으로 바꿔 보여 준다 | 기준 문서 모양으로 돌려준다 |
| 알림 (`notifications`) | 목록 · 읽음 표시(`read_at`) | 단계 저장과 같은 트랜잭션에서 INSERT |
| 관리자 실패 알림 (`generation_failure_alerts`) | 목록 · 확인 처리(`acknowledged_at`) | 실행이 실패로 바뀔 때 INSERT |
| 검수 회수 문단 (`proofread_logs`) | '검수 회수 문단' 탭 목록 · 라벨링 | 학습 동의 계정의 반려된 표현 검수 시도를 INSERT (웹 스키마 변경 전제, 4절) |
| 설정 (`verification_policies`) | 관리자 화면에서 저장 | 실행을 시작할 때 읽어 끝까지 고정 |
| 프로젝트 · 계정 삭제 | 행을 지우기 전에 `abort_project` · `delete_project_data`를 부른다 | 진행 중 실행 건 중단 · 산출물 내용 삭제 |

## 2. 엔드포인트별 대응 (②)

- "부를 함수"는 `build_web`으로 조립한 `orch`의 함수다(명세 2.2절). 모든 행에서 그 앞에 지금의 주인 확인(`_get_owned_project` 등)을 한다.
- "응답 필드 채우는 법"의 값별 대응은 3절 표를 따른다. 함수 오류는 `CommandError.code`(명세 10.2절)로 가른다.
- HTTP 상태 코드는 웹이 정한다. 아래 "지금 응답" 언급은 같은 뜻의 지금 웹 응답을 가리킨다.

## 4. 필수 웹 스키마 변경 (④)

### 4.1 `proofread_logs` — 워커가 쓰는 테이블로 바뀜

이전 교체 목록에서 C 분류(정리 대상)였던 `proofread_logs`는 **정리 대상에서 빠지고, 워커가 행을 INSERT한다**. 지금 구조는 `business_plans` 기준(`plan_id NOT NULL`)이라 아래처럼 바꿔야 한다.

| 변경 | 내용 |
|---|---|
| `project_id` 추가 | `projects(project_id)` 참조. 워커가 채운다. 삭제 때 처리(외래 키 동작)는 8절 확인 사항 |
| `model_version` 추가 | 그 시도를 만든 검수 모델 이름(관리자 '검수 회수 문단' 탭의 모델 표시용 — 지금은 정리 대상인 `verdicts`에서 가져온다) |
| `plan_id` · `section_id` 참조 | `business_plans` · `plan_sections` 참조를 없애거나 NULL 허용으로 바꾼다(`plan_id NOT NULL` 해제) |

워커가 채우는 컬럼: `project_id` · `original_text` · `corrected_text` · `reason` · `attempt_no` · `passed`(FALSE) · `violation_type` · `violation_note` · `recovery_status`('pending') · `model_version`. 나머지(`log_id` · `score` · `recovery_label` · `created_at` 등)는 웹 기본값이다. 그래서 위 컬럼 밖의 NOT NULL 컬럼에는 기본값이 있어야 한다.

참고 — Orchestrator 테스트 DB에서 바뀐 모양을 만들 때 쓴 문장(MySQL 8, 테스트 전용):

```sql
-- plan_id · section_id 외래 키를 먼저 지운 뒤
ALTER TABLE proofread_logs
  MODIFY plan_id BIGINT UNSIGNED NULL,
  ADD COLUMN project_id BIGINT UNSIGNED NOT NULL AFTER log_id,
  ADD COLUMN model_version VARCHAR(50) NULL,
  ADD KEY ix_proofread_logs_project (project_id),
  ADD CONSTRAINT fk_proofread_logs_project FOREIGN KEY (project_id)
    REFERENCES projects(project_id) ON DELETE CASCADE;   -- 삭제 동작은 8절에서 정한다
```

- **바뀌기 전에는** 워커가 이 테이블 쓰기만 건너뛴다(실행 건마다 추적 사건 '검수회수기록생략' 한 번, 실행 · 검수는 정상). 바뀐 뒤 생기는 반려 시도부터 쌓이고 지난 시도를 나중에 채우지는 않는다. 맞지 않는 구조는 기억하지 않아 다음 저장부터 쓴다.
- 이 행에는 문장 내용이 들어간다. 학습 데이터 편입에 동의한 계정(`users.ai_training_agreed`가 저장 순간 참)의 **반려된 시도**만 쓴다(기획서 6-6). 반려 = 보호 토큰 검사를 통과하지 못한 시도.

### 4.2 `projects` 진행 컬럼 — 정리 대상

Orchestrator가 쓰지 않으므로 아래는 아무도 쓰지 않는 컬럼이 된다. 읽기를 함수로 바꾼 뒤 정리한다.

| 컬럼 | 대체 |
|---|---|
| `status` · `stage` · `progress_percent` · `notice_id` · `failure_reason` (2026-09-30판 D 분류) | `view_project` · `project_views`(3.1 · 3.2), 실패 사유는 `admin_runs.failureReason`(관리자만) |
| `resume_count` · `retry_count` · `next_retry_at` · `resume_started_at` · `last_error_kind` · `worker_claimed_at` | `RunView`(`resume_count` · `retry_count` · `next_resume_at` · `last_error_kind`), 점유는 `orch_runs` |
| `is_regenerating` · `regenerate_fail_streak` | 없는 기능("처음부터 다시 생성") |

- 이 컬럼들에 걸린 외래 키 · 인덱스(`notice_id` → `notices` 외래 키, `ix_projects_notice` · `ix_projects_status` · `ix_projects_stage_claim`)도 컬럼과 함께 정리한다.
- `fit_score` · `reason`은 이전 교체 목록 3.1의 확인 사항 그대로다(선택 공고 카드의 `fitScore` · `matchReason`으로 대체 가능, 3.6).

### 4.3 더미 결과 테이블 — 정리 대상

`business_plans` · `plan_sections` · `plan_canonical_data` · `plan_score_reasons` · `artifacts` · `artifact_score_reasons` · `verdicts` · `match_candidates` · `match_score_reasons` · `eligibility_checks` · `format_findings` · `agent_executions` · `verification_score_history`, 그리고 "처음부터 다시 생성" 컬럼 `verification_policies.regenerate_cap` · `generation_failure_alerts.regenerate_exhausted`.

- `proofread_logs`는 이 목록에서 빠진다(4.1).
- `project_budget_items` · `project_schedule_items` · `project_partners`는 이전 교체 목록 3.5의 확인 사항 그대로다.

### 4.4 유지해야 하는 컬럼

| 테이블 | 워커가 쓰는 컬럼 (구조가 맞지 않으면 그 테이블 쓰기가 실패한다) |
|---|---|
| `notifications` | `notification_id` · `project_id` · `kind` · `failure_scope` · `target_step` · `channel` · `created_at` · `read_at` |
| `generation_failure_alerts` | `alert_id` · `project_id` · `stage` · `resume_count` · `last_error_kind` · `failure_reason` · `created_at` |
| `verification_policies` (읽기) | `policy_id` · `doc_weight` · `code_weight` · `plan_weight` · `pass_threshold` · `rerun_cap` · `rework_cap` · `deviation_cap` · `token_retry_cap` |
| `projects` · `companies` · `users` (읽기, 학습 동의) | `projects.project_id` · `company_id`, `companies.company_id` · `user_id`, `users.user_id` · `ai_training_agreed` |

- `generation_failure_alerts.regenerate_exhausted`는 워커가 채우지 않는다. 지우기 전까지는 지금처럼 기본값(FALSE)이 있어야 한다.

### 4.5 참고 — 공유 DB의 Orchestrator 테이블

`orch_runs`에 `collect_until DATETIME(6) NULL` 컬럼이 늘었다(재작성 요청을 모으는 시간이 끝나는 시각 — 그 전에는 워커가 가져가지 않는다). 공유 DB 적용은 Orchestrator 담당이 한다. 웹은 `orch_` 테이블을 쓰지 않으므로 할 일이 없다.

## 6. 웹 백엔드 동작 규칙 (⑥)

1. **모든 함수 호출 전 주인 확인.** 관리자 함수는 관리자 확인. Orchestrator는 `request_start` 말고는 주인을 확인하지 않는다.
2. **사전 정보 저장 전 `active_work`로 동시 실행 확인**(기존 409 응답 유지). 최종 확인은 `request_start`가 한다.
3. **프로젝트 행을 지우거나 숨기는 모든 경로**(휴지통 · 완전 삭제 · 계정 삭제)에서 먼저 `abort_project`를 부른다. 완전 삭제 · 계정 삭제 · 실행 건 없는 휴지통 실제 삭제는 `delete_project_data`(`BUSY`면 잠시 뒤 다시). 빠뜨리면 진행 중 실행 건이 주인 없이 남아 그 계정이 새 작업을 시작하지 못한다.
4. **'매칭됨' 판단을 `projects.notice_id` 대신 우리 함수 결과로.** 휴지통 실제 삭제 · 보관 구분, 목록, 관리자 보관 가능 여부는 실행 건 유무(`view_project(project_id).run`), 선택 공고는 `RunView.announcement_id`, 공고 마감은 `RunView.notices`의 E-RUN-CLOSED.
5. **사용자용 응답에서 실패 사유 제외.** `failure_reason`(관리자용 `"<Task>: <재개상한초과 · 영구오류> — <오류 요약>"`)은 관리자 화면(`admin_runs`, `generation_failure_alerts`)에만 보인다. 사용자에게는 E-RUN-FAIL 문구만.
6. **사전 단계 다시 시도.** 공고 후보 조회 때 마지막 시작 요청이 다시 시도할 수 있는 실패(E-C1-TIMEOUT · X-C2-FAIL · E-C2-STALE)면 웹 백엔드가 `request_start`를 다시 부른다. E-C2-NOMATCH는 다시 넣지 않는다(입력 확인 안내).
7. **동기 대기는 `wait_project`.** 공고 후보 · 공고 다시 찾기 · 자격 확인처럼 한 번 요청하고 기다리는 곳만. 제한 시간을 넘기면 오류 없이 그때 상태가 오므로 진행 중으로 답한다. 계획서 작성 · 프로토타입 제작 · 재작성 · 검수는 기다리지 않는다.
8. **이미 시작된 명령의 거절은 상태로 돌려준다.** `plan/start` · `prototype/start`처럼 프론트가 여러 번 부르는 곳에서 `INVALID_STATE`면 `view_project`로 지금 상태를 돌려준다. `BUSY`는 잠시 뒤 다시.
9. **사전 단계 실행 함수를 부르지 않는다.** 웹 조립에서 `run_start_request`는 `WEB_NOT_ALLOWED`다(시작 요청은 바뀌지 않는다).
10. **더미 파이프라인 코드 삭제 대상:** `app/agents.py`, 생성 시뮬레이션(`_simulate_generation`) · 클레임(`_try_claim_and_run`) · 복구 루프(`_recover_orphaned_generations_once` · `_generation_recovery_loop` · `start_generation_recovery_loop`), `seed_dummy_pipeline` 호출, `retry_task`의 더미 처리, `pipeline_stages.py`의 더미 전용 상수(클레임 · 재개 백오프 · `STAGE_TO_AGENT_TASK` · `classify_error_kind` 등. 화면 표시에 계속 쓰는 `STAGE_*` · `STAGE_TO_SCREEN` · 묶음 이름 · 알림 상수는 웹 판단으로 남겨도 된다).

## 7. `/admin/policy` (⑦)

- `verification_policies`는 지금처럼 **웹이 저장**하고, Orchestrator가 **실행을 시작할 때 읽어** 실행 건에 고정한다(바꾼 값은 그 뒤에 시작하는 실행부터 적용). 첫 행(`policy_id` 최솟값)을 읽는다.

| `verification_policies` | Orchestrator 설정 |
|---|---|
| `doc_weight` | 문서층 배점 |
| `code_weight` + `plan_weight` | 산출물층 배점 |
| `pass_threshold` | 기준 점수(Threshold) |
| `rerun_cap` | 재수행 횟수 |
| `rework_cap` | 재작성 횟수 — 묶음마다 |
| `token_retry_cap` | 검수 재수행 횟수 |
| `deviation_cap` | 확장 필드에 담아만 둔다(검증-1 연동 전, 잠정) |
| `regenerate_cap` | **없는 기능 — 정리한다**(화면 · 입력 · 컬럼) |

- 화면에 없는 설정(재시도 횟수 · 간격 · 제한 시간 · 재개 간격 · 재개 횟수 · 재개 총 대기 상한 · Agent별 모델 등)은 Orchestrator **코드 기본값**이다.
- 관리자 화면에서 바꾸고 싶어지면: 웹이 `verification_policies`에 칸을 더하고 관리자 화면에 입력을 두면, Orchestrator 쪽에서 그 칸을 읽도록 고친다(`store_sql/settings_source.py`의 읽기 목록과 `store_sql/web_tables.py`의 `WEB_COLUMNS`). 칸 이름 · 단위는 그때 함께 정한다.
