# verification_agent — 검증-2 (T-V2)

[구현 Agent](../engineering_agent/README.md)가 만든 프로토타입과 인포그래픽을 받아 **산출물층 30점**을 매기는 Agent입니다. "계획서에 쓴 기능이 프로토타입에 정말 있는가"를 대조하는 것이 핵심입니다.

- 담당: 정재희 · 이슈 `SB-125`
- 서버 · DB · 화면이 없는 파이썬 함수입니다. 조율(Orchestrator)이 부르고, LLM 호출은 조율이 넘겨 주는 `tools`로만 합니다.
- 위치: `agent-orchestration/sbrain/agents/partner_bv/verification_agent/` — 맨 아래 "이 폴더의 위치" 참고.
- 합격 · 불합격은 판정하지 않습니다. 점수를 돌려주면 조율이 문서층 70점과 합쳐 합격선(80점)과 비교합니다.

## 30점의 구성

```
산출물층 30점 = 코드 점검 15점 (규칙만) + 계획서 대조 15점 (규칙 → LLM 요소 판정 → 코드 계산)
```

```
Prototype + Infographic + 기능 목록 + 사업계획서
 → 통과 필수 조건 ─ 하나라도 어기면 30점 전체 0, 이하 생략
 → 코드 점검 8항목 (규칙만) → 15점 환산
 → 계획서 대조
     1단계 규칙: 기능마다 최소 조건을 넘는지
     2단계 LLM: 넘긴 기능만, 계획서 정의를 요소로 나눠 요소별 있음 / 없음
     점수 계산은 코드
```

### 통과 필수 조건

점수가 아니라 채점 자격입니다. 하나라도 어기면 코드 점검 8칸이 모두 0, 계획서 대조도 0입니다.

| 코드 | 조건 |
|---|---|
| `entry` | 진입 파일(HTML은 `index.html`, 원페이지는 `onepage.svg`)이 있고 형식이 맞다. 원페이지는 인포그래픽과 프로토타입이 같은 파일이다 |
| `secret` | 원문에 API 키 · 토큰 · 비밀번호 값이 없다 (끼워 넣은 글꼴 · 그림, `your_api_key` 같은 자리 표시는 제외) |
| `sandbox` | HTML에 스크립트를 멈추는 저장소 API(`localStorage` · `sessionStorage` · `document.cookie` · `indexedDB`)가 없다 |

### 코드 점검 15점 — LLM 없이 규칙만

카테고리마다 8항목입니다. 같은 입력이면 늘 같은 점수가 나옵니다.

| No | HTML 실행 파일 (KWCAG 2.2 근거) | 배점 | 원페이지 SVG (지면 파싱 근거) | 배점 |
|:-:|---|:-:|---|:-:|
| 1 | 동작 연결 — 조작 요소에 이벤트가 직접 붙어 있다 | 3 | 대체 텍스트 — `title` · `desc` | 2 |
| 2 | 대체 텍스트 — `img` alt, `svg` title · aria-label (인포그래픽도 함께) | 2 | 핵심 정보 6항목이 실재한다 | 3 |
| 3 | 입력칸 label | 2 | 명도 대비 4.5:1 | 2 |
| 4 | 명도 대비 4.5:1 | 2 | 정보 계층 (글자 크기 3단 이상) | 2 |
| 5 | 제목 계층 (`h1` 하나, 단계 건너뛰기 없음) | 1 | 잘림 없음 | 2 |
| 6 | 1440px 폭을 넘는 고정 폭 없음 | 2 | 지면 밖 넘침 없음 | 2 |
| 7 | 스크립트 동작 오류 없음 (없는 id · 무시되는 API · 외부 의존) | 2 | 텍스트 실재성 (그림 면적 35% 이하) | 1 |
| 8 | 임시 문구 없음 (lorem ipsum · TODO 등) | 1 | 최소 글자 크기 12px | 1 |

- 3점 항목만 부분 점수가 있습니다(100% 3점 · 80% 2점 · 50% 1점).
- 대상이 없는 항목(예: 입력칸 0개)은 만점이 아니라 "해당 없음"으로 빼고, 남은 배점으로 15점을 다시 환산합니다. 단, HTML 동작 연결(조작 요소 0개)과 명도 대비(색 짝 0개)는 0점입니다.
- "동작 연결"은 이벤트 위임이나 `querySelectorAll` 반복문으로 한꺼번에 다는 방식을 인정하지 않습니다. 요소마다 직접 붙어 있어야 계획서 대조에서도 그 기능이 동작한다고 볼 수 있기 때문입니다.

### 계획서 대조 15점

```
점수 = 15 × 인정 몫 합계 ÷ 대조 대상 수
```

1. **규칙 단계**: 기능이 최소 조건을 넘지 못하면 몫 0이고 LLM에 묻지 않습니다.
   - HTML: 기능 이름이 화면 글자에 있고, 그 이름이 붙은 조작 요소에 이벤트가 직접 붙어 있다.
   - 원페이지: 지면의 기능 설명이 비어 있지 않고, 계획서에 없는 숫자가 없고, 설명 낱말 절반 이상이 계획서 원문에서 확인된다.
2. **요소 판정 (LLM)**: 계획서에서 기능 이름이 들어간 줄을 LLM이 요소(최대 5개)로 나눕니다. 예를 들어 "사진과 증상을 올린다"는 사진 / 증상, 이렇게 둘로 나눕니다. 그다음 요소마다 "산출물에 있는가"를 세 번 물어 다수결로 정합니다. 기능의 몫은 `있는 요소 ÷ 전체 요소`입니다.
3. **원페이지 핵심 칸**: 문제 정의 · 해결 방안 · 수익모델 단가 · 추진 일정 4칸이 계획서와 어긋나지 않는지 대조 대상에 더합니다. 지면에 계획서에 없는 숫자를 지어내면 종류당 1점, 최대 3점을 뺍니다.

- LLM은 판정(있음 / 없음, 충족 / 부분 / 미충족)과 이유만 냅니다. 점수는 코드가 계산합니다.
- **구현 쪽 신고는 근거로 쓰지 않습니다.** 구현 Agent가 낸 `implemented_features`, 산출물 안의 "구현 완료" 같은 문장, 지면에 기능 이름이 적혀 있다는 사실은 인정 근거가 아닙니다. 근거는 계획서 원문과 실제 코드뿐입니다.
- 뽑은 요소 목록은 출력(`featureElements`)으로 내보내고, 같은 실행 건의 다음 채점이 이어 받아 다시 씁니다. 같은 산출물을 다시 채점해도 기준이 흔들리지 않게 하기 위해서입니다.
- LLM 호출이 실패하면 예외를 내지 않고 규칙 결과로 점수를 냅니다. 다만 결제 · 한도 소진으로 끝난 실패는 대체하지 않고 올려서 조율이 재개를 기다리게 합니다.

## 출력에 담기는 것

| 칸 | 내용 |
|---|---|
| `code_check` | 8칸 결과(항목마다 얻은 점수 · 근거), 깨진 통과 필수 조건 `gate_failures`, 결함이 있는 산출물 `defect_sources`(T-B1 / T-B2 중 어디를 다시 만들지) |
| `feature_match` | 대조 점수, 빠진 기능 `missing_features`, 일부 요소만 있는 기능 `partial_features`, 기능별 이유 `findings` |
| `artifact_score.total` | 코드 점검 + 계획서 대조 (0 ~ 30) |
| `diagnostics` | 관리자용 기록 (점수 · 흐름에는 쓰지 않음) |

조율은 `gate_failures` · `defect_sources` · `missing_features` · `partial_features`로 재작성 대상과 사유를 만들고, 웹은 이것을 "미달 항목"으로 보여 줍니다.

## 파일 구성

| 파일 | 하는 일 |
|---|---|
| `tasks.py` | 진입 함수 `run_tv2`, 채점 본체 `score_artifact` |
| `score.py` | 통과 필수 조건 → 8항목 → 15점 환산 |
| `rules/gates.py` | 통과 필수 조건, 비밀값 모양, sandbox API |
| `rules/r4.py` · `rules/r4_onepage.py` | HTML 8항목 · 원페이지 8항목 |
| `rules/items.py` | 항목 한 칸의 모양, 구간 점수, 15점 환산 |
| `rules/wiring.py` | 이벤트가 요소에 직접 붙었는지 (코드 점검 1번과 계획서 대조가 함께 씀) |
| `rules/html_parser.py` · `rules/color.py` | 표준 라이브러리 HTML 파싱, 색 해석 · 대비 계산 |
| `feature_match.py` | 계획서 대조의 규칙 단계와 점수 계산. LLM 판정 함수를 인자로 받음 |
| `llm_judge.py` | 요소 추출 · 저장, 요소별 판정, 원페이지 핵심 칸 판정, 다수결 |

`rules/`와 `score.py`는 LLM을 부르지 않는 순수 함수입니다.

## 모델

계획서 대조의 판정 모델은 `gpt-6-luna`입니다. 2026-10-15에 산출물 6개를 채점 모델만 바꿔 각 3회씩 다시 채점해 비교했습니다.

| 채점 모델 | 최상위 Astra 판정과의 차이 (15점 중) | 1회 비용 |
|---|---|---|
| `gpt-6-luna` (선택) | 0.26점 — 6개 모델 중 가장 가까움 | 약 14원 |
| `gpt-6-astra` (기준) | — | 약 1,300원 |
| `gpt-6.1-sol` · `gpt-5-mini` · `gpt-5` · `gpt-5.6-terra` | 0.56 ~ 1.34점 | 약 78 ~ 445원 |

같은 Luna가 만들고 채점하는 것에 대한 편향도 따로 확인했습니다. HTML 20개를 Luna와 6.1-sol로 함께 채점했을 때 두 모델의 점수 차는 Luna가 만든 것에서 +0.25점, 다른 모델이 만든 것에서 +1.39점이었습니다. 자기 산출물을 더 후하게 채점하는 경향은 없었습니다. 구조적으로도 30점 중 15점은 규칙만 쓰고, 나머지 15점도 LLM은 요소 판정만 합니다.

## 이 폴더의 위치

이 폴더가 서비스가 실제로 돌리는 코드입니다. 원래 저장소 루트의 `verification_agent/`(담당자 원본)를 조율이 이곳으로 옮겨 붙여 썼고, 2026-10-16에 루트 원본을 지우고 이곳 하나로 합쳤습니다. 앞으로 수정은 이 폴더를 직접 고칩니다.

원본과 달라진 곳은 연결부뿐이고 [`VENDORED.md`](../VENDORED.md)에 모두 적혀 있습니다. 산출물은 경로 대신 파일 참조로 받아 `tools.files`로 읽고, 요소 목록은 로컬 파일(`.cache/`) 대신 실행 건의 산출물로 이어 받습니다. 바로 위 폴더의 `resources.py`(자료 파일을 불러올 때 한 번 읽어 둔 상수)와 `tasks.py`(Task 등록)는 조율의 연결 코드입니다. 지우기 전 원본은 커밋 `155195b`에 남아 있습니다.
